# 了解 OceanSeek

## 场景速览

* **AI 应用与 Agent 数据管理**

  OceanSeek 提供的核心能力：

  * **数据隔离**：租户级、Database 级、Namespace 级、表级、行列级，多级隔离机制
  * **逻辑表**：百万/千万级 Agent 数据隔离
  * **数据冷热分层**：99% 沉睡实例低成本保留

* **Agent 评测**

  OceanSeek 提供的核心能力：

  * **Fork Table/Database**：数据沙箱，类 Git 数据分支管理，Copy-on-Write 毫秒级 Fork，共享基础数据、隔离增量变更

* **多模态数据处理** 

  OceanSeek 提供的核心能力：

  * **多模表（敬请期待）**：文章/图片/音频/视频作为 LOB 入表，按规模选择行内/行外/库外引用三种存储方式
  * **文件处理**：Model in DB，解析、切片、Embedding、索引构造均可在库内进行

* **RAG/语义搜索/记忆召回**

  OceanSeek 提供的核心能力：

  * **混合搜索**：向量+全文+标量，非结构化+半结构化+结构化，1 条 SQL 完成混合搜索
  * **融合排序**：库内 RRF、MINMAX_NORMALIZER、WEIGHT_SUM 多种融合排序算法可选，高性能精准召回
  * **RAG Pipeline in DB**：文件入库，答案出库，SQL 接口提供完整 RAG 流程

* **MySQL + ES + 向量库整合**

  OceanSeek 提供的核心能力：

  * **一个引擎**：无需多组件双写、无需 CDC 同步、无需跨系统查询，保证数据一致性
  * **一份数据多种查询**：在一份数据上提供标量、JSON、全文、向量混合搜索

* **实时数仓**

  OceanSeek 提供的核心能力：

  * **流批一体**：高频实时写入、大数据量批量导入均可，无需复杂的 lambda 架构
  * **物化视图**：增量/全量刷新，准实时/实时查询。实时数据加工、灵活数仓分层
  * **行列混存**：行存、列存、行列混存灵活定义，1 份数据高效支撑多类查询
  * **向量化引擎**：按批处理数据，相比非向量化性能提升 1 个数量级
  * **MPP**：原生 MPP 计算引擎，节点-分区-任务多层并行执行策略，弹性扩展
  * **存算分离**：计算、存储、日志服务资源按需单独扩展，冷数据低成本存储
  * **单副本**：支持数据单副本降本，基于独立日志服务和对象存储的全量数据存储，仍然保证 RPO=0

* **数据加工**

  OceanSeek 提供的核心能力：

  * **资源隔离**：租户-资源组两级资源隔离策略，数据加工与交互式分析互不干扰
  * **引擎集成**：兼容 Arrow Flight SQL 协议，原生集成 Spark、Daft、Ray 引擎，PB 级批处理和特征工程在 Lakebase 内闭环

* **数据湖融合**

  OceanSeek 提供的核心能力：

  * **Iceberg/Paimon（敬请期待）/Hive 融合**：湖上查询分析加速，库内数据入湖
  * **Parquet/ORC/CSV 适配**：本地缓存/分层裁剪/谓词下推/统计信息/Bloom Filter 过滤等优化，高效计算
  * **Unified Catalog 统一管理**：通过 catalog sync 将库内表信息同步至 HMS，元数据统一管理和共享

* **海量 KV/HBase 替换/历史库/归档库**

  OceanSeek 提供的核心能力：

  * **低成本存储**：海量数据位于对象存储，支撑 KV/SQL/分析。支持单副本，仍保证 RPO=0
  * **冷热分层**：热数据本地缓存、全量数据共享存储，减少归档迁移

## OceanSeek 简介

过去十余年，OceanBase 支撑过支付宝核心交易的毫秒级响应，登顶过 TPC-C 7.07 亿 tpmC、TPC-H 1526 万 QphH 的全球榜单，实现了 RTO<8s 的极致高可用，也让 4000+ 客户的核心系统稳定上线。这些成就的背后，是 OceanBase 始终致力于解决的一个问题：如何让人类更好地管理结构化数据。

但现在，AI Agent 开始接管企业的真实工作，非结构化数据成为企业的主要资产，现有的数据管理方式正面临以下困境：

* **非结构化数据开发不足**：非结构化数据占组织数据的 70%-90%，缺少统一的管理和分析工具。
* **数据与 AI 割裂**：数据团队的工作台与 AI 工程师的训练/部署平台互不相通，协作困难。
* **数据时效性差**：传统湖仓以批处理为主，难以支持流式数据的秒级响应与动态查询。
* **技术栈碎片化**：在线交易、海量数据存储、数据实时分析、向量搜索、全文检索，多套系统，多份运维。
* **数据一致性难保证**：一份数据在多个系统间流转，难以保证跨系统查询的数据一致性。

AI 时代的业务转型与当下数据管理的困境正在重塑对数据库的要求：

* **湖库一体**：融合数据湖的开放格式、海量存储与数据库的事务、一致性、实时能力，结构化、半结构化与非结构化数据可在统一体系中存储、分析与搜索。
* **多模表**：从关系表走向多模表，让文本、图片、音频、视频等数据进入数据库表语义，在同一套事务、权限、版本与生命周期机制下被管理、搜索和计算。
* **混合搜索**：将标量过滤、向量与全文纳入统一查询链路，在数据库内完成多路召回、相关性排序与一致性维护，让 AI 应用能从多模态数据中找到准确、实时、可信的上下文。
* **Agent 友好**：围绕 Agent 的长期记忆、会话上下文、业务状态、行动记录和试错过程提供原生能力，支撑 AI 应用从验证走向规模化运行。
* **开放生态**：支持基于 S3 协议的对象存储、Iceberg/Paimon 开放表格式与统一 Catalog，对接 Spark、Ray 等开放计算引擎，减少数据复制、格式转换与系统锁定。

**OceanSeek 正是为这些诉求而生的新一代多模一体、冷热分层的存算分离数据库。它是在 OceanSeek 经过大规模生产验证的分布式底座上，为 AI 数据场景量身定制的数据库；它不只是 OceanBase 数据库能力的升级，更是 AI 时代数据管理的产品革新。**

## 产品架构

![OceanSeek 产品架构图](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/database-ai/1.product%20architecture.png)

* **统一应用接口**：

  * 统一查询语言：一套 SQL 语法即可访问所有多模数据类型，无需为向量、全文等多模搜索分别学习查询语言。
  * 原生 Python SDK：提供简单易用的 Python SDK，降低 Agent 访问的复杂度，便于 AI 生态框架集成。

* **支持混合负载的多模计算层**：

  * 向量化执行引擎：逐列批量处理，提升大数据量分析性能。
  * 并行执行引擎：多节点多核并行，支撑大规模扫描与聚合。
  * 混合负载自适应执行与查询优化器：同一集群内 TP、AP、AI 共存，自动调度资源，自适应选择计划。
  * 语义搜索：支持基于向量的最近邻搜索。
  * 混合搜索：结构化过滤 + 向量 + 全文的多路召回与融合排序。
  * AI 函数：SQL 中直接调用模型推理。

* **多模数据类型**：

  * 原生支持多种数据模型，无需外挂不同数据库：关系表、宽表、向量、JSON 文档、文本、空间、数组/映射，同一张表里可以同时存在结构化列、JSON 列、向量列、文本列，查询时可跨类型。

* **多模索引层**：

  * 原生支持多种索引类型，无需外挂不同数据库：二级索引（关系表）、向量索引（向量）、JSON 索引（JSON 文档）、多值索引（数组/多值列）、全文索引（文本）、GIS 索引（空间）、搜索索引（多列倒排），每种数据类型都有匹配的索引加速路径。

* **基于存算分离架构具有事务语义的行列混合存储层**：

  * 本地缓存：计算节点本地 SSD 缓存热数据保证性能。
  * 独立日志服务：基于 Paxos 的分布式事务日志服务，负责事务日志（clog）的持久化与复制，保证事务语义。
  * 对象存储：最终持久化层，所有数据的落地归宿，成本低、容量近乎无限。
  * 行列混合：同一份存储同时支持行存和列存，不需要像传统方案那样在行库和列库之间同步数据。

## 核心能力

### Agent Database：隔离、记忆、试错，三大行为全部原生化

当 AI 让创建 App 的成本接近于零，真正的挑战变成了长期运行：

* 千万 App/Agent 实例，99% 沉睡但被唤醒时必须秒级响应。
* Agent 不能每次从零开始，要记住用户、上下文、业务事实和历史判断。
* Agent 会自动改表、写数据、换方案，失败路径不能污染生产数据。

![Agent Database 架构图](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/database-ai/introcn2.png)

**OceanSeek 让 Agent 的隔离、记忆、试错三个核心行为都成为数据库原生能力。**

* **隔离**：支持租户、Database、Namespace、表、行/列五层隔离，满足不同场景的隔离需求，支撑千万级应用实例。
* **记忆**：支持在一条 SQL 完成 Agent 记忆召回，无需跨系统，数据一致性由数据库事务保证。
* **试错**：同一份基线数据，毫秒级生成多个相互隔离的实验数据库，实验结束即可丢弃或合并。

更多信息，请参考 [核心特性](300.key-feature.md) 中关于 Agent 场景原生能力的介绍。

### 多模态数据库：让非结构化数据从成本中心变成可计算资产

企业数据中约 90% 是非结构化的（图片、视频、文档、音频），这些数据长期以“只存不算”的方式躺在对象存储或文件系统中，占用成本，却无法被业务系统直接理解和使用。

AI 时代，大模型第一次让非结构化数据变得“可理解”：图片可以被看懂，音频可以被转写，文档可以被摘要。但生产系统面临的真正难题是：原始文件、模型理解结果、业务元数据三者仍然分散在不同系统中，统一治理、高效搜索和结果回流缺乏一体化方案。

![多模态数据库架构图](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/database-ai/introcn3.png)

**OceanSeek 把 LOB 文件、AI 模型、推理结果和业务字段纳入同一套数据库语义**：

* **LOB 统一治理**：文档、图片、音视频按大小自动存储到 InRow/OutRow/对象存储，库内统一事务处理和权限管理。
* **Model in DB**：大模型作为数据库的一等公民，可被定义、管理和引用。基于 AI 算子，实现多模态文件的解析、摘要、Embedding 等，并支持创建各类索引支撑高效查询。
* **混合搜索**：标量、向量、全文在一条 SQL 中被查询，多路召回，自动融合排序。

非结构化数据从此不再只是被保存，而是可以被 SQL 查询、被混合搜索、被业务系统直接消费，让结构化数据库升级为多模态数据库。

更多信息，请参考 [核心特性](300.key-feature.md) 中关于多模一体化的介绍。

### 存算分离：单副本的成本，多副本的可靠

AI 时代的数据有两个显著特征：规模巨大且冷热不均。存算一体架构带来了持续高效的响应性能，但也引入了不可忽略的资源成本。每增长一份数据就要同步扩容计算节点和本地 SSD，冷数据也占用昂贵的本地盘和三副本/两副本空间。

**OceanSeek 使用存算分离 + 冷热分层 + 日志与计算解耦的架构，平衡资源成本、可靠性与性能。**

* **三层解耦**：计算、日志、存储各自独立部署、独立扩展，资源互不干扰。
* **无状态计算节点**：不持久化全量数据，弹性扩缩容无需迁移数据，支持单副本部署降低成本。
* **独立日志服务**：LogService 基于 Paxos 三副本部署，事务日志在多数派副本确认后才返回成功，保证 RPO=0。
* **对象存储底座**：全量数据最终持久化在低成本对象存储，容量近乎无限，多个计算节点共享同一份数据。
* **冷热自动分层**：热数据缓存在本地 SSD 保证性能，冷数据保留在对象存储，系统自动识别访问热度并迁移。

更多信息，请参考 [核心特性](300.key-feature.md) 中关于存算分离架构的介绍。

### RAG Pipeline in DB：文档入库，答案出库

企业知识库、智能客服、文档问答等 RAG 应用，传统链路通常需要多个系统协作：文档存储、文本解析、Embedding 服务、向量数据库、全文检索、重排序模型、大模型推理。数据在多个系统间搬运，带来同步延迟、一致性维护、运维复杂等问题。

**OceanSeek 把完整 RAG 链路收敛到数据库内，让“文档入库，答案出库”在一个系统内完成。**

![RAG Pipeline in DB 架构图](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/oceanseek/oceanseek-architecture.png)

从图中可以看到，RAG Pipeline in DB 分为两条主线：

* **文档入库**：知识库文档 → 文档解析 → 文档分割 → 文本向量化 → 构建全文索引 + 向量索引
* **用户查询**：用户问题 → 混合搜索 → 加权融合 → 结果重排序 → 模型推理 → 返回答案

文档入库与用户查询全链路都在数据库内完成：

* **AI 函数**：文档解析（AI_Parse_Document）、文档分割（AI_Split_Document）、文本向量化（AI_Embed）、结果重排序（AI_Rerank）、模型推理（AI_Complete）等，均可在 SQL 中直接调用。
* **库内双索引**：同一批文本块在库内构建全文索引（关键词检索、BM25 排序）与向量索引（语义相似度检索），无需同步到外部 ES 或向量库。
* **混合搜索**：1 条 SQL 同时发起向量搜索、关键词搜索与标量过滤，通过 RRF、WEIGHT_SUM、MINMAX_NORMALIZER 等算法融合排序。
* **AI 算子可扩展**：AI 算子可以是 Embedding、Rerank、文档解析、文本分类等模型，也支持通过 Python UDF 定义新的 AI 算子。

更多信息，请参考 [核心特性](300.key-feature.md) 中关于 RAG 的介绍。

## FAQ

**Q：与 OceanBase 数据库是什么关系？**

同源内核、不同定位：OceanBase 数据库主要面向对响应时延的稳定性要求极高的 TP/HTAP 场景；OceanSeek 主要面向 AI 与湖仓分析场景。

**Q：容灾能力如何？**

日志服务三副本强同步；1F 部署 RPO=0、RTO 分钟级，2F 部署 RPO=0、RTO<8 秒。

**Q：支持哪些渠道使用？**

私有化部署与 OB Cloud 云服务均可（目前 OceanSeek 暂未在 OB Cloud 上线，具体可售区域、规格和上线时间可以关注 [OB Cloud 产品动态](https://www.oceanbase.com/docs/common-oceanbase-cloud-1000000005032716) 或咨询 OceanBase 销售人员）。支持 x86、ARM 及主流国产操作系统。

**Q：有哪些兼容模式？**

支持 **MySQL 模式** 和 **KV 模式**。其中 KV 模式包含 OBKV-Table 和 OBKV-HBase。

**Q：周边配套和 OceanBase 数据库的异同？**

仍然配套 ODP 和 MySQL 生态驱动，配套 OCP、ODC、OMS、导数工具、DataPilot 等原有工具链。新增了 DataStudio 平台的支持。

**Q：计算节点扩展是否灵活？**

OceanSeek 采用存算分离架构，数据持久化在对象存储上，本地磁盘仅作缓存。计算节点可以灵活按需扩缩。

**Q：本地缓存建议设置多大？**

数据冷热分层，建议按照 max（内存\*3，热数据\*2）来设置。
