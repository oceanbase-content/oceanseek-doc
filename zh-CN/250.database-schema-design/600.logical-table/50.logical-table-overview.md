# 逻辑表概述

本文档为逻辑表能力（Logical Table）的总概述文档，介绍其解决什么问题、基本概念，以及两类落地场景的差异。

逻辑表（Logical Table）是 OceanBase AI 数据库提供的一种数据组织方式。多个需要相互隔离的数据空间可以共用同一套底层物理表，通过 Namespace 区分彼此，而不必为每个空间单独建表。

## 背景

在常规用法中，业务上的一张表通常对应数据库中的一张物理表。当需要大量独立数据空间时（例如按用户、Agent、会话或应用划分），若仍为每个空间创建独立物理表，容易带来以下问题：

| **问题** | **说明** |
| --- | --- |
| 元数据负担加重 | 物理表数量随隔离空间增长，元数据管理成本上升，影响相关运维与查询开销。 |
| DDL 变更频繁 | 动态表结构或大量小应用场景下，频繁建表、改表会增加变更风险与运维复杂度。 |
| 存储难以复用 | 各隔离空间本可共用同一套物理存储与索引配置，却被拆到不同物理表中。 |

逻辑表的做法是：数据仍落在共享的物理表上，空间之间的隔离由 Namespace 完成，从而减少物理表数量与 DDL 压力。

## 对象模型

使用逻辑表时，对象层级如下。不同场景在 Namespace 之下存放的业务数据形态不同，上层隔离关系一致：

```shell
Client
  └── Collection
        └── Namespace
              └── 业务数据
```

| **对象** | **说明** |
| --- | --- |
| Client | SDK 连接入口，用于连接数据库并管理 Collection。 |
| Collection | 顶层容器，对应一组共享的物理表及相关配置（如分区、索引等）。一个 Collection 下可以包含大量 Namespace。 |
| Namespace | **数据隔离的基本单元**。不同 Namespace 的数据互不可见，读写在所属 Namespace 内完成。闪应用场景中，Namespace 对应 App。 |
| 业务数据 | Namespace 内实际存放的内容。Agent 混合搜索场景中是一条条固定结构的搜索记录；闪应用场景中为虚拟表及其行数据。 |

相关 SDK 需要开启 Namespace 模式后才能使用逻辑表（例如设置 `use_namespace=True`）。具体参数与调用方式见各场景文档。

## 落地场景

逻辑表是底层能力。当前文档按接口与数据模型分为以下两类场景。二者的隔离方式相同，但数据模型与 SDK 相互独立，不可混用。

| **对比项** | **Agent 混合搜索场景** | **闪应用场景** |
| --- | --- | --- |
| 适用场景 | Agent 记忆、知识库及多用户空间搜索 | 动态表结构、多应用虚拟表的 SQL 读写 |
| SDK | pyseekdb | json-table-sdk |
| 开发者如何读写 | 调用 SDK 的写入 / 查询接口；不必建表 | 先 `CREATE TABLE` 定义列，再 `INSERT` / `SELECT` 等 SQL |
| 一个 Namespace 里存什么 | 多条搜索记录。例如某 Agent 的若干条对话记忆，每条都有 id、文本、向量、元数据 | 用户自定义的多张表和行。例如一个小应用里可有 `orders`、`users` 等多张表（库内按 JSON 存放，用户侧仍按普通表使用） |
| 核心能力 | 向量搜索、全文搜索、混合搜索 | 虚拟表的创建与变更、SQL 读写、基于 JSON 的结构化查询、使用搜索索引进行查询加速 |

字段含义、索引、限制与操作示例等细节，见各场景文档。
