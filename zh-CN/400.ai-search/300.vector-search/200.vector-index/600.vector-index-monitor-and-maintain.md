# 索引监控与维护

本文档介绍了如何监控和维护 OceanBase AI 数据库中的向量索引。

## 监控

本节介绍如何通过系统视图查看向量索引的状态，以及如何使用 Profile 分析单次向量搜索各阶段的耗时和执行情况。

### 单次向量搜索性能监控

当向量搜索 SQL 执行耗时较高或偶尔出现延迟明显升高时，可以通过 `DBMS_XPROFILE.DISPLAY_PROFILE()` 查看本次向量搜索各阶段的执行情况，定位主要开销。该功能覆盖当前支持的所有稠密和稀疏向量索引。

#### 执行向量搜索 SQL 并查看 Profile

以下示例省略了建表步骤。假设示例表 `test_table` 已包含 `id` 列、四维向量列 `vector_col`，以及使用余弦距离的向量索引 `idx_vector`。实际应用中请根据实际表结构、索引和向量维度调整查询。

1. 使用 `MONITOR` Hint 执行待分析的向量搜索 SQL。

    ```sql
    -- VECTOR_INDEX Hint 用于指定向量索引
    SELECT /*+ MONITOR VECTOR_INDEX(test_table idx_vector) */ id
    FROM test_table
    WHERE id >= 3
    ORDER BY COSINE_DISTANCE(vector_col, '[0.1, 0.2, 0.3, 0.4]') APPROXIMATE
    LIMIT 5;
    ```

2. 在同一会话中紧接着查看该查询的 Profile：

    ```sql
    SELECT DBMS_XPROFILE.DISPLAY_PROFILE();
    ```

    如需查看指定查询，可显式传入其 `trace_id`：

    ```sql
    SELECT DBMS_XPROFILE.DISPLAY_PROFILE('<trace_id>');
    ```

返回结果在实际执行向量搜索的 SQL 物理算子下展示 `Vector Search` 子树。以下为结构示意，数值仅用于说明，并非上述 SQL 的实测结果：

```shell
0.PHY_TABLE_SCAN
  ...
  Vector Search
    Partition
      tablet id:200017
      Vector Iter
        try path:1
        current path:2
        switch reason:1
        pre filter rows scanned:10000
        pre filter time:49.879ms
        vec index search time:9.199ms
        iter filter loop cnt:2
        iter filter row:98
        iter filter matched row count:10
        iter filter time:317.727ms
        output row count:10
        total search time:376.949ms
        Vector Index HNSW Scan
          filter mode:0
          vsag query segment cnt:1
          vsag query time:5.081ms
```

#### 定位主要耗时阶段

可按以下顺序分析定位主要耗时阶段：

1. **查看总体耗时和执行实例。** 从 SQL 物理算子的统计信息进入 `Vector Search`，查看各 `Partition` 的 `tablet id` 和 `total search time`。如果本次向量搜索涉及多个数据分片（Tablet），可根据 tablet id 对比各执行实例的耗时，判断开销是否集中在某个数据分片。  
2. **区分过滤与索引搜索开销。** 比较前过滤耗时（`pre filter time`）、候选过滤耗时（`iter filter time`）和获取候选结果耗时（`vec index search time`）。若候选行数多、过滤后匹配行数少且迭代轮次较多，说明为获得足够结果进行了多轮候选扩展。  
3. **检查过滤路径是否发生切换。** `try path` 和 `current path` 分别表示初始路径和最终路径，非零 `switch reason` 说明发生了实际生效的切换。上述示意中，`switch reason:1` 表示前过滤超时，最终使用迭代过滤；候选过滤耗时较高，可进一步检查过滤条件的匹配情况。  
4. **进入算法节点查看具体开销。** HNSW、SINDI 系列可关注索引搜索、增量数据搜索和查询所需索引数据的补齐耗时；IVF 系列可关注候选扫描、距离计算以及缓存构建或缓存不可用时的回退耗时。例如，`complete data total time` 较高表示索引数据补齐开销较大，IVF 的缓存构建耗时较高则表示当前查询承担了缓存构建工作。  
5. **检查是否发生查询重试。** 若同一 Tablet 出现多个实例，可检查失败实例中的路径切换原因（`vec retry reason`）。最终成功实例不展示该字段，不能只查看最后一个实例来判断重试原因。

完整的输出字段和数字取值说明，请参见 [DISPLAY_PROFILE](../../../700.reference/600.pl-reference/1000.pl-system-package-mysql/20750.dbms-xprofile-mysql/200.display-profile-of-mysql-mode.md)。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <ul>
    <li>不同阶段的耗时可能存在包含关系，不能直接相加。并行执行时，各执行实例的累计耗时也可能大于本次向量搜索实际经过的时间。</li>
    <li>字段未展示通常表示对应阶段未执行或不适用，不代表该字段的值为 0。</li>
    <li>Profile 仅展示指定 Trace 对应的一次执行，不能反映同一 SQL 多次执行的平均耗时或历史趋势。</li>
    <li>Profile 可以帮助定位耗时较高的执行阶段，但不能直接确定 CPU、I/O、内存或锁等待等资源层面的原因。定位耗时阶段后，还需结合执行计划、ASH、资源监控和日志进一步排查。</li>
  </ul>
</main>

## 基础维护

增量数据过多的情况下，搜索性能会下降。为减小增量数据表的数据量，OceanBase AI 数据库引入了 `DBMS_VECTOR` 对向量索引进行维护。

### 在线修改索引参数（仅 HNSW 系列）

HNSW 系列索引支持通过 [DBMS_VECTOR.ALTER_INDEX_PARAMS](#相关文档) 在线修改索引的目标参数。构建参数变化时触发异步分区级重建；仅修改查询类参数时不触发重建。修改后，可查询 [(G)V$OB_HNSW_INDEX_SEGMENT_INFO](#监控) 的 `SEGMENT_PARAMS` 列，查看各数据段实际使用的参数。

### 全量刷新（重建）

#### 手动全表重建

如果建立索引后更新或删除数据较多，建议使用 `[REBUILD_INDEX](../../../700.reference/600.pl-reference/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md)` 过程进行全量刷新。说明和示例请参见 REBUILD_INDEX。

全量刷新每 24 小时会检查一次，如果新增数据超过原有数据的 20%，则自动执行全量刷新。全量刷新会在后台异步执行，首先创建新的索引，然后替换旧索引。在重建过程中，旧索引保持可用状态，但整体过程相对较慢。

我们还提供了 `vector_index_memory_saving_mode` 配置项来控制索引重建的内存占用。开启此模式可以降低分区表向量索引重建（rebuild）过程中的内存消耗。通常，向量索引重建需要消耗相当于索引两倍的内存。开启省内存模式后，系统会在分区表单个分区构建完成后，通过暂时删除该分区的内存索引来释放内存，从而有效降低重建操作所需的总内存。语法和示例请参见[vector_index_memory_saving_mode](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8240.vector_index_memory_saving_mode.md)。

注意事项如下：

* 执行 [离线 DDL](../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md) 操作（例如 `ALTER TABLE` 修改表结构或主键）时，将导致索引表的重建。由于重建索引无法指定并行度，系统会默认使用单线程，因此在数据量较大时，重建过程会比较缓慢，从而影响整个 离线 DDL 的执行效率。
* 重建索引时如果需要修改索引参数，必须在参数列表中同时指定 `type` 和 `distance`，且 `type` 和 `distance` 必须和原索引类型一致，例如原来索引类型是 `hnsw`，距离算法是 `l2`，则重建时必须同时指定 `type=hnsw` 和 `distance=l2`。
* 重建索引时支持：
    * 修改 `m`，`ef_search`，`ef_construction` 值。
    * 通过 `duplicate_group` 启用或关闭 HNSW 系列索引的完全相同向量分组。具体见[切换相同向量分组模式](#切换相同向量分组模式)。
    * 在线重建 `ef_search` 参数。
    * `hnsw` 与 `hnsw_sq` 索引类型互相转换重建。
    * `ivf_flat` 与 `ivf_flat`，`ivf_pq` 与 `ivf_pq` 的索引类型互相转换重建。
    * 支持重建时设置并行度。示例见 REBUILD_INDEX。

* 重建索引时不支持：
    * 修改 `type` 和 `distance` 类型。
    * `hnsw` 与 `ivf` 的索引类型互相转换重建。
    * `hnsw` 与 `hnsw_bq` 的索引类型互相转换重建。
    * `ivf_flat`，`ivf_pq` 之间的交叉重建。

#### 切换相同向量分组模式

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>本功能从 V4.6.3 Hotfix1 版本开始支持。</p>
</main>

对于已有的 HNSW 系列索引，可以通过 `DBMS_VECTOR.REBUILD_INDEX` 的 `IDX_PARAMETERS` 参数启用或关闭完全相同向量分组功能，以调整重复向量较多场景下的召回率优化设置。启用后可提升重复向量较多场景下的召回率，但会增加记录分组关系的内存开销。当前仅支持完全相同的向量，暂不支持按相似度阈值合并不同向量。

* 指定 `duplicate_group=TRUE`：通过全量重建，将索引转换为启用分组的格式。
* 指定 `duplicate_group=FALSE`：通过全量重建，将索引转换为不启用分组的格式。
* 不指定 `duplicate_group`：沿用当前生效索引的设置，不改变分组模式。

切换模式需要全量重建索引，并非仅修改一个参数值。重建期间原索引继续提供服务，新索引构建成功后再切换；如果重建失败，仍使用原索引。

完整参数说明请参见 [REBUILD_INDEX](#相关文档)。

#### 自动分区重建（推荐）

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p><ul><li>如需启用或恢复自动分区重建任务，请先手动全表重建所有向量索引，否则可能无法自动执行分区重建任务。</li><li>此功能支持 HNSW 系列索引，语义索引，内存稀疏索引，不支持 IVF 系列索引。</li></ul></p>
</main>

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>语义索引在自动分区重建时，会同时处理增量数据与快照任务，确保索引数据的一致性与完整性。</p>
</main>

会触发自动分区重建任务的场景有两种：

* 执行向量索引搜索语句时。
* 定时检查，可手动配置执行周期。

1. 配置执行周期

    在 `oceanbase` 数据库下，通过配置项 [vector_index_optimize_duty_time](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8250.vector_index_optimize_duty_time.md) 配置执行周期。示例如下：

    ```sql
    ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
    ```
    如上配置完成后，分区重建任务只会在 23:00:00~24:00:00 时间段执行，其他时间段里不会发起。详细参数说明参见相应配置项文档。

2. 查看任务进展/历史任务

    可通过 [CDB/DBA_OB_VECTOR_INDEX_TASKS](#相关文档) 或 [CDB/DBA_OB_VECTOR_INDEX_TASK_HISTORY](#相关文档) 视图查看任务进展和历史任务。

    <main id="notice" type='notice'>
      <h4>注意</h4>
      <p>上述视图涵盖分区重建、Segment 转储与合并、IVF 聚类中心加载与清理、语义索引刷新、内存同步等向量索引后台任务，可通过视图中的 <code>TASK_TYPE</code> 字段区分任务类型。</p>
    </main>

    通过 `STATUS` 字段判断任务当前状态：

    * `PREPARE`：任务等待执行。
    * `RUNNING`：任务正在执行中。
    * `PENDING`：任务暂停执行。
    * `FINISHED`：任务已完成。
    * `STANDBY`：手动触发的任务等待节点认领并执行。
    * `QUEUE`：任务在优先级队列中排队等待执行。
    * `CANCEL`：任务已被取消。
    * `EXCHANGE`：新旧索引交换中（此状态为自动分区重建任务的特有状态）。
    * `CLEAN`：资源清理中（此状态为自动分区重建任务的特有状态）。

    执行结束的任务，即状态为 `FINISHED` 的任务，无论是否执行成功都会被转存到历史表。详细使用示例请参见相应视图文档。

3. 取消任务

    如需取消任务，可通过 [DBA_OB_VECTOR_INDEX_TASKS](#相关文档) 或 [CDB_OB_VECTOR_INDEX_TASKS](#相关文档) 视图获取 trace_id 后，执行以下命令：

    ```sql
    --示例，trace_id 需要根据实际情况填写
    ALTER SYSTEM CANCEL TASK "Y61480BA2D976-00063084E80435E2-0-1";
    ```

## 专项维护

### 手动强制转储/合并（备选）

增量段（Segment）的转储与合并流程通常由数据库系统后台模块在满足特定条件时自动触发。OceanBase AI 数据库支持以下手动触发方式：

* 表级触发：通过 `DBMS_VECTOR` 系统包中的 `FLUSH_INDEX` 和 `COMPACT_INDEX` 过程，在表/索引粒度上强制触发转储和合并任务。语法和示例请参见 [FLUSH_INDEX](../../../700.reference/600.pl-reference/1000.pl-system-package-mysql/17850.dbms-vector-mysql/600.flush-index-mysql.md) 和 [COMPACT_INDEX](../../../700.reference/600.pl-reference/1000.pl-system-package-mysql/17850.dbms-vector-mysql/700.compact-index-mysql.md)。
* Tablet 级触发：通过 `DBMS_VECTOR` 系统包中的 `TRIGGER_ASYNC_TASK` 存储过程，通过指定任务类型与 `tablet_id` 手动创建向量索引后台任务，支持增量 Segment 冻结、合并及 Follower 内存加载等类型。语法和示例请参见 [TRIGGER_ASYNC_TASK](../../../700.reference/600.pl-reference/1000.pl-system-package-mysql/17850.dbms-vector-mysql/800.trigger-async-task-mysql.md)。

触发后，可以查询 `DBA_OB_VECTOR_INDEX_TASKS`，其中 `TASK_TYPE='INCREMENTAL_INDEX_FREEZE'` 为触发的转储任务，`TASK_TYPE='INCREMENTAL_INDEX_MERGE'` 为触发的合并任务。如果当前增量数据量较小，任务可能很快完成，此时可以查看历史任务视图 `DBA_OB_VECTOR_INDEX_TASK_HISTORY`。如果数据量较大，合并过程可能耗时较长，可通过 [GV$SESSION_LONGOPS](../../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/4800.gv-session_longops-of-mysql-mode.md) 视图实时查看执行进度。查询示例和详细说明请参见相应视图文档。

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>查看 Segment 合并任务进度的功能从 V4.6.2.1 版本开始支持。</p>
</main>

Segment 是向量索引中用于组织分区内存数据的基本单元，负责管理增量数据的存储与合并。详细概念介绍和阈值控制方法请参见[向量索引内存管理](#相关文档)。

### 后台任务优先级调度

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>本功能从 V4.6.2.1 版本开始支持。</p>
</main>

向量后台任务共用一个线程池，系统按 6 级优先级（P0–P5）调度：影响前台服务的任务优先，轻量资源清理次之，重操作中等优先级，后台重任务最低。默认优先级与水位阈值如下：

| **优先级** | **任务类型** | **默认水位阈值** |
| --- | --- | --- |
| P0 | 手动触发的任务 | 100% |
| P1 | IVF 聚类中心 cache 加载、内存数据同步 | 90% |
| P2 | IVF cache 清理、增量 Segment 冻结 | 70% |
| P3 | Embedding 计算、增量 Segment 合并 | 50% |
| P4 | 分区级索引重建 | 35% |
| P5 | 保留 | 20% |

水位阈值表示：当前正在运行的任务数占线程池总线程数的百分比。只有当运行中任务的水位低于该阈值时，该优先级及更低优先级的任务才会被调度。这样可保证高优先级任务始终有可用线程，低优先级任务不会占满全部线程。

若某类任务在特定租户或时段需要更激进或更保守的执行策略，可通过配置项 [vector_task_thread_limit_percent](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8255.vector_task_thread_limit_percent.md) 按任务类型覆盖默认调度水位。例如，在业务高峰期降低 Segment 转储、合并任务的调度比例以减轻资源争用：

```sql
ALTER SYSTEM SET vector_task_thread_limit_percent = 'INCREMENTAL_INDEX_FREEZE:30,INCREMENTAL_INDEX_MERGE:30';
```

详细取值格式与任务类型说明请参见相应配置项文档。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>将某任务类型的水位设为 <code>0</code> 时，仍受最小槽位保证保护，该类型任务可能仍会被调度。</p>
</main>

### 通过 cgroup 管控后台任务资源（可选）

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>本功能从 V4.6.2.1 版本开始支持。</p>
</main>

向量后台任务已接入函数（Function）级资源隔离，可按任务类型限制 CPU、IO 占用，对应资源请求类型如下：

| **资源请求类型** | **对应任务** |
| --- | --- |
| VECTOR_HIGH | 内存数据加载、IVF 缓存加载/清理 |
| VECTOR_MID | 增量 Segment 冻结与合并 |
| VECTOR_LOW | 分区级索引重建 |

具体配置步骤请参见 [后台任务的资源隔离配置案例](../../../600.manage/200.tenant-management/600.common-tenant-operations/300.resource-isolation/900.background-resource-isolation-of-mysql-or-oracle-mode.md) 和 [资源隔离概述](../../../600.manage/200.tenant-management/600.common-tenant-operations/300.resource-isolation/100.resource-isolation-overview.md)。

### 查看内存限流信息

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>本功能从 V4.6.2.1 版本开始支持。</p>
</main>

对于分区级索引重建、增量 Segment 合并等内存消耗较大的任务，调度器在触发执行前会检查租户向量内存是否充足。若当前内存不足，则暂缓调度该任务，将其保留在队列中，待其他任务释放内存后再执行，任务不会被丢弃。

任务完成后，内存限流相关信息会记录在历史任务视图 [DBA_OB_VECTOR_INDEX_TASK_HISTORY](#相关文档)（或 `CDB_OB_VECTOR_INDEX_TASK_HISTORY`）的 `TASK_INFO` 字段中，格式为 JSON，包含 `mem_limit_info` 段。

### 小租户自适应线程池机制

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>本功能从 V4.6.2.1 版本开始支持。</p>
</main>

为避免小规格租户因后台线程数过多而浪费资源，系统会根据租户 CPU 规格自适应计算向量后台任务线程池的最大线程数。本节说明其机制与计算公式。具体计算公式如下：

```shell
max_threads = clamp(floor(cpu × 0.5), 2, 64)
```

计算参数含义如下：

| **参数** | **含义** |
| --- | --- |
| cpu | 租户分配的 CPU 核数 |
| cpu × 0.5 | 按 CPU 数量的一半来估算线程数 |
| floor(...) | 向下取整，得到整数 |
| clamp(..., 2, 64) | 把结果限制在 2 到 64 之间 |

常见租户规格对应的最大线程数如下：

| **租户 CPU** | **最大线程数** |
| --- | --- |
| 1~5 | 2 |
| 6~7 | 3 |
| 8~9 | 4 |
| 10~11 | 5 |
| 12~13 | 6 |
| 16~17 | 8 |
| 32~33 | 16 |
| 64~65 | 32 |
| 128+ | 64 |

当租户 CPU 配额发生变更（如在线扩缩容）时，线程池规模会自动刷新，确保线程数与当前 CPU 规格匹配，无需手动干预。即使线程池较小，系统也会通过最小槽位保证机制，确保各优先级任务都能获得基本的调度机会。
