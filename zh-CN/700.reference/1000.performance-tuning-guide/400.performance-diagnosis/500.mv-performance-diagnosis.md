# 诊断实践：使用 TRACE_ID 诊断物化视图刷新性能问题

本文介绍如何在 OceanSeek 中，当物化视图刷新耗时较长时，可以结合 `TRACE_ID` 关联 SQL Audit、ASH、刷新历史和运行状态视图，分析刷新过程中的 CPU、IO、等待事件以及高耗时 SQL。

## 前提条件

在执行本文操作前，请确认以下条件：

* 权限设置：登录租户的用户需要拥有 `CREATE TABLE`、`INSERT`、`SELECT` 等权限。有关权限设置的更多信息，请查看 [直接授予权限](../../../600.manage/500.security-and-permissions/300.access-control/200.user-and-permission/200.permission-of-mysql-mode/200.authority-of-mysql-mode.md)。
* 已明确待排查的物化视图名称，或已知对应刷新任务的大致时间范围。

## 使用限制

|             **视图**          | **说明** |
|-------------------------------|----------|
| GV$OB_SQL_AUDIT               | 该视图为环形缓冲区，保留时间有限。较早的刷新记录可能已被覆盖。|
| GV$OB_ACTIVE_SESSION_HISTORY  | 适用于近期或正在运行任务的分析，保留时间较短。|
| DBA_WR_ACTIVE_SESSION_HISTORY | 适用于历史分析，保留时间通常长于 ASH。|

## 操作概述

推荐按以下顺序进行排查：

1. 获取目标物化视图刷新的 `TRACE_ID`。
2. 基于 `TRACE_ID` 聚合分析 SQL Audit 中的 CPU 和 IO 指标。
3. 查看刷新期间资源消耗较高的 SQL。
4. 定位具体刷新阶段。
5. 对长时间运行的刷新，使用 ASH 或 WR 分析等待事件。
6. 如果刷新任务仍在执行，可查看实时运行状态。
7. 如需评估整体资源占用，可查看物化视图刷新的聚合 IO 统计。

## 准备示例

本文以下 SQL 以物化视图 `mv_order_daily` 为例。实际执行时，请根据环境替换文中的物化视图名、`TRACE_ID`、`refresh_id` 和 `mview_id`。

### 步骤一：创建基表

创建一张分区订单明细表，按天分区。表中包含 `order_date DATE` 列：

```shell

    order_id    BIGINT NOT NULL,
    user_id     BIGINT NOT NULL,
    product_id  BIGINT NOT NULL,
    amount      DECIMAL(10,2) NOT NULL,
    order_date  DATE NOT NULL,
    order_time  DATETIME NOT NULL,
    channel     VARCHAR(32) DEFAULT 'web',
    PRIMARY KEY (order_id, order_time)
    )
    PARTITION BY RANGE(TO_DAYS(order_time)) (
        PARTITION p202601 VALUES LESS THAN(TO_DAYS('2026-02-01')),
        PARTITION p202602 VALUES LESS THAN(TO_DAYS('2026-03-01')),
        PARTITION p202603 VALUES LESS THAN(TO_DAYS('2026-04-01'))
        );
```

创建一张按天、渠道、商品维度汇总的增量（`FAST`）刷新物化视图：

```shell
obclient> CREATE MATERIALIZED VIEW mv_order_daily (PRIMARY KEY(order_date, channel, product_id))

        order_date,

        product_id,

        COUNT(amount) AS count_amount,
        SUM(amount) AS total_amount
    FROM   order_detail
    GROUP BY order_date, channel, product_id;
```

## 诊断操作步骤

### 步骤一：获取物化视图刷新的 TRACE_ID

每次物化视图刷新执行时，OceanSeek 会为该次刷新分配唯一的 `TRACE_ID`。刷新期间执行的内部 SQL 会携带相同的 `TRACE_ID`。

#### 方式一：根据物化视图名称获取最近一次刷新的 TRACE_ID

如果需要查看某个物化视图最近一次刷新的资源消耗，执行以下 SQL：

```shell
obclient> SELECT TRACE_ID, START_TIME, END_TIME, MVIEW_NAME
    FROM oceanbase.DBA_MVREF_RUN_STATS
    WHERE MVIEW_NAME = 'mv_order_daily';
```

**返回结果说明：**

* `TRACE_ID`：表示刷新任务 Trace 标识。
* `START_TIME`：刷新运行的开始时间。
* `END_TIME`：刷新运行的结束时间。
* `MVIEW_NAME`：表示物化视图名称。

请记录查询结果中的 `TRACE_ID`，用于后续步骤。后续示例步骤中即使用 `YXX-AB12CD34EF56-0001` 作为 `TRACE_ID`。

#### 方式二：根据刷新历史获取 TRACE_ID

如果需要排查某次历史刷新，可执行以下 SQL：

```shell
obclient> SELECT
        refresh_id,
        trace_id,
        mviews,
        start_time,
        end_time,
        elapsed_time,
        parallelism
    FROM oceanbase.DBA_MVREF_RUN_STATS
    ORDER BY start_time DESC
    LIMIT 20;
```

**返回结果说明：**

* `refresh_id`：刷新任务 ID。
* `trace_id`：该次刷新的 `TRACE_ID`。
* `mviews`：涉及的物化视图。
* `start_time`、`end_time`：刷新开始和结束时间。
* `elapsed_time`：刷新耗时。
* `parallelism`：刷新并行度。

如果需要继续关联刷新步骤信息，请同时记录 `refresh_id`。如后续需要关联具体物化视图，也需要获取对应的 `mview_id`。

### 步骤二：聚合分析该次刷新的 CPU 和 IO 消耗

获取 `TRACE_ID` 后，可以通过 `GV$OB_SQL_AUDIT` 聚合该次刷新期间所有 SQL 的资源消耗。

```shell
obclient> SELECT
        TRACE_ID,
        COUNT(*) AS stmt_count,
        SUM(ELAPSED_TIME) AS total_elapsed_us,
        SUM(EXECUTE_TIME) AS total_execute_us,
        SUM(USER_IO_WAIT_TIME) AS total_io_wait_us,
        SUM(APPLICATION_WAIT_TIME) AS total_app_wait_us,
        SUM(CONCURRENCY_WAIT_TIME) AS total_concurrency_wait_us,
        SUM(SCHEDULE_TIME) AS total_schedule_us,
        SUM(DISK_READS) AS total_disk_reads,
        SUM(DATA_BLOCK_READ_CNT) AS total_data_block_reads,
        SUM(DATA_BLOCK_CACHE_HIT) AS total_data_block_cache_hit,
        SUM(INDEX_BLOCK_READ_CNT) AS total_index_block_reads,
        SUM(INDEX_BLOCK_CACHE_HIT) AS total_index_block_cache_hit,
        SUM(MEMSTORE_READ_ROW_COUNT) AS total_memstore_rows,
        SUM(SSSTORE_READ_ROW_COUNT) AS total_ssstore_rows,
        SUM(AFFECTED_ROWS) AS total_affected_rows,
        SUM(RETURN_ROWS) AS total_return_rows,
        SUM(REQUEST_MEMORY_USED) AS total_memory_used,
        SUM(RPC_COUNT) AS total_rpc_count
    FROM oceanbase.GV$OB_SQL_AUDIT
    WHERE TRACE_ID = 'YXX-AB12CD34EF56-0001'
    GROUP BY TRACE_ID;
```

**参数说明：**

将 `WHERE` 中 `<trace_id>` 替换为步骤一中获取的实际值。

**返回结果说明：**

|         **字段**       |       **说明**       | **建议关注点** |
|------------------------|----------------------|----------------|
| stmt_count             | SQL 条数              | 并行刷新场景下可能较大。|
| total_elapsed_us       | 总耗时（微秒）         | 可作为总体耗时参考。|
| total_execute_us       | 执行时间汇总           | 可作为 CPU 消耗的参考指标。|
| total_io_wait_us       | 用户 IO 等待时间汇总   | 数值较高时通常表示 IO 等待较多。|
| total_disk_reads       | 物理磁盘读次数         | 反映物理读压力。|
| total_data_block_reads | 数据块读取次数         | 可结合缓存命中情况分析。|
| total_memstore_rows    | 从 MemTable 读取的行数 | 可用于分析热数据读取情况。|
| total_ssstore_rows     | 从 SSTable 读取的行数  | 可用于分析基线数据扫描量。|
| total_rpc_count        | RPC 调用次数           | 可作为分布式开销的参考。|
| total_memory_used      | 请求内存使用量          | 适用于观察大内存消耗场景。|

**使用建议：**

* 如果 `total_io_wait_us` 在总体耗时中占比较高，通常表示主要耗时集中在 IO 等待。
* 如果 `total_execute_us` 占比较高，通常表示主要耗时集中在计算执行阶段。
* 如果 `total_disk_reads` 和 `total_data_block_reads` 较高，通常表示刷新过程中扫描或读取较多。

**示例输出：**

```shell
+----------------------+------------+----------------+----------------+----------------+------------------+
| TRACE_ID             | stmt_count | total_elapsed  | total_execute  | total_io_wait  | total_disk_reads |
+----------------------+------------+----------------+----------------+----------------+------------------+
| YXX-AB12CD34EF56-0001|         12 |     325000000  |     180000000  |     120000000  |           15420  |
+----------------------+------------+----------------+----------------+----------------+------------------+
```

在实际排查中，优先关注 `ELAPSED_TIME` 排名靠前的 SQL，并且需要结合 `USER_IO_WAIT_TIME`、`DISK_READS`、`TABLE_SCAN` 字段判断该 SQL 的资源开销。初步判断该次刷新同时存在计算和 IO 开销。

**注意事项：**

如果该查询未返回结果，可能是对应 SQL Audit 记录已被覆盖。此时建议参考步骤五中的 WR 分析方法，或结合步骤四中的刷新步骤明细进行分析。

### 步骤三：定位资源消耗较高的 SQL

如果需要进一步定位刷新过程中具体哪条 SQL 消耗了较多资源，可执行以下 SQL：

```shell
obclient> SELECT
        SQL_ID,
        QUERY_SQL,
        ELAPSED_TIME,
        EXECUTE_TIME,
        USER_IO_WAIT_TIME,
        DISK_READS,
        DATA_BLOCK_READ_CNT,
        AFFECTED_ROWS,
        RETURN_ROWS,
        REQUEST_MEMORY_USED,
        PLAN_TYPE,
        TABLE_SCAN
    FROM oceanbase.GV$OB_SQL_AUDIT
    WHERE TRACE_ID = 'YXX-AB12CD34EF56-0001'
    ORDER BY ELAPSED_TIME DESC;
```

**返回结果说明：**

* `SQL_ID`：SQL 标识。
* `QUERY_SQL`：SQL 文本。
* `ELAPSED_TIME`：SQL 耗时。
* `EXECUTE_TIME`：执行时间。
* `USER_IO_WAIT_TIME`：IO 等待时间。
* `DISK_READS`：物理读次数。
* `DATA_BLOCK_READ_CNT`：块读取次数。
* `REQUEST_MEMORY_USED`：内存使用量。
* `PLAN_TYPE`：执行计划类型。
* `TABLE_SCAN`：是否包含表扫描。

**使用建议：**

* 优先关注 `ELAPSED_TIME` 排名靠前的 SQL。
* 可通过 `QUERY_SQL` 判断对应 SQL 属于刷新过程中的哪个阶段，例如 `INSERT`、`MERGE` 或 `SELECT`。
* 当 `TABLE_SCAN = 1` 时，可重点关注是否存在大范围扫描。
* 当 `DISK_READS` 和 `DATA_BLOCK_READ_CNT` 均较高时，可进一步分析物理读和缓存命中情况。

**示例输出：**

```shell
+-------------+------------------------------------------+--------------+--------------+----------------+------------+--------------------+------------+
| SQL_ID      | QUERY_SQL                                | ELAPSED_TIME | EXECUTE_TIME | USER_IO_WAIT   | DISK_READS | DATA_BLOCK_READ_CNT| TABLE_SCAN |
+-------------+------------------------------------------+--------------+--------------+----------------+------------+--------------------+------------+
| C2F8A1B20   | INSERT /*+ monitor */ INTO mv_order_daily|   210000000  |   120000000  |      80000000  |      10240 |              15360 |          1 |
| 7D3E9A1C50  | SELECT /*+ monitor */ COUNT(*) ...       |    85000000  |    45000000  |      35000000  |       4096 |               6144 |          1 |
| A1B2C3D4E0  | MERGE INTO mv_order_daily USING ...      |    30000000  |    15000000  |      5000000   |       1084 |               2048 |          0 |
+-------------+------------------------------------------+--------------+--------------+----------------+------------+--------------------+------------+
```

从示例输出可以看出：排名第一的 `INSERT` 语句耗时 210s，占总耗时的 65%，且 `TABLE_SCAN = 1`、`DISK_READS = 10240`，说明该 `INSERT` 操作存在大范围扫描，是本次刷新的资源消耗瓶颈。后续可通过步骤四关联刷新步骤明细，确认该 SQL 对应的刷新步骤序号。

### 步骤四：结合刷新步骤明细定位具体阶段

如果需要查看刷新过程中的步骤序号、完整 SQL 文本和执行时间，可将刷新步骤明细表与 SQL Audit 结果进行关联分析。

```shell
obclient> SELECT
        S.step,
        S.sqlid,
        S.execution_time,
        S.stmt,
        A.ELAPSED_TIME,
        A.EXECUTE_TIME,
        A.USER_IO_WAIT_TIME,
        A.DISK_READS,
        A.DATA_BLOCK_READ_CNT
    FROM oceanbase.DBA_MVREF_STMT_STATS S
        LEFT JOIN oceanbase.GV$OB_SQL_AUDIT A
        ON S.sqlid = A.SQL_ID
    WHERE S.refresh_id = 1025
    AND S.mview_id = 1100611139
    ORDER BY S.step;
```

**参数说明：**

* `<refresh_id>`：刷新任务 ID（示例值 1025），可从步骤一方式二获取。
* `<mview_id>`：物化视图内部 ID（示例值 1100611139），可通过 `SELECT mview_id FROM oceanbase.DBA_MVREF_RUN_STATS` 获取。

**返回结果说明：**

* `step`：刷新步骤序号。
* `sqlid`：步骤对应的 SQL ID。
* `execution_time`：该步骤执行时间。
* `stmt`：完整 SQL 文本。
* `ELAPSED_TIME`、`USER_IO_WAIT_TIME` 等字段：对应 SQL Audit 中的资源统计。

**使用建议：**

* 按 `step` 排序可还原刷新执行顺序。
* `stmt` 通常比 SQL Audit 中的 `QUERY_SQL` 更完整，适合确认具体执行逻辑。
* 如果关联后的 `Audit` 字段为空，通常表示对应 SQL Audit 记录已被覆盖。

### 步骤五：分析长时间运行刷新的等待事件

对于运行时间较长的刷新任务，建议结合 ASH 或 WR 分析等待事件分布。

#### 方式一：使用 ASH 分析近期或正在运行的刷新

```shell
obclient> SELECT
        SQL_ID,
        EVENT,
        WAIT_CLASS,
        COUNT(*) AS sample_count,
        SUM(CASE WHEN WAIT_CLASS IS NULL OR WAIT_CLASS = '' THEN 1 ELSE 0 END) AS on_cpu_samples,
        SUM(CASE WHEN WAIT_CLASS = 'USER_IO' OR WAIT_CLASS = 'User I/O' THEN 1 ELSE 0 END) AS io_wait_samples
    FROM oceanbase.GV$OB_ACTIVE_SESSION_HISTORY
    WHERE TRACE_ID = 'YXX-AB12CD34EF56-0001'
    GROUP BY SQL_ID, EVENT, WAIT_CLASS
    ORDER BY sample_count DESC;
```

**返回结果说明：**

* `sample_count`：采样次数。
* `on_cpu_samples`：可作为 CPU 活跃时间的参考。
* `io_wait_samples`：可作为 IO 等待时间的参考。
* `EVENT、WAIT_CLASS`：等待事件和等待类别。

**使用建议：**

* 每个采样点通常代表约 1 秒的活跃时间。
* 可根据 `sample_count` 判断主要等待事件。
* 可结合 `SQL_ID` 判断不同刷新步骤的等待特征。

#### 方式二：使用 WR 分析历史刷新

如果目标刷新已超出 ASH 保留时间，可执行以下 SQL：

```shell
obclient> SELECT
        SQL_ID,
        EVENT_ID,
        TIME_WAITED,
        COUNT(*) AS sample_count
    FROM oceanbase.DBA_WR_ACTIVE_SESSION_HISTORY
    WHERE TRACE_ID = 'YXX-AB12CD34EF56-0001'
    GROUP BY SQL_ID, EVENT_ID, TIME_WAITED
    ORDER BY sample_count DESC;
```

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>WR 适用于历史分析，但结果粒度取决于 WR 采样和保留策略。</p>
</main>

### 步骤六：查看当前正在运行的刷新任务

如果刷新任务尚未结束，可查看其运行状态和当前会话信息。

#### 1. 查看正在运行的刷新任务

```shell
obclient> SELECT
        SVR_IP,
        SVR_PORT,
        TABLE_NAME,
        JOB_TYPE,
        SESSION_ID,
        PARALLEL,
        JOB_START_TIME
    FROM oceanbase.DBA_MVIEW_RUNNING_JOBS;
```

**返回结果说明：**

* `TABLE_NAME`：物化视图名称。
* `SESSION_ID`：刷新任务对应会话 ID。
* `PARALLEL`：并行度。
* `JOB_START_TIME`：开始时间。

#### 2. 查看刷新会话的当前等待事件

```shell
obclient> SELECT *
    FROM oceanbase.GV$OB_PROCESSLIST
    WHERE ID = 3221225472;
```

**参数说明：**

请将 `<session_id>` 替换为上一步查询得到的会话 ID（示例值 `3221225472`）。

**返回结果说明：**

* `EVENT`：当前等待事件。
* `STATE`：当前状态。
* `WAIT_TIME_MICRO`：已等待时间。
* `TIME_REMAINING_MICRO`：预计剩余等待时间。

#### 3. 查看正在运行刷新的资源消耗

如果已获取当前刷新的 `TRACE_ID`，可复用步骤二中的 SQL Audit 聚合查询，查看截至当前时刻的资源消耗情况。

```shell
        MODE,
        MIN_IOPS,
        MAX_IOPS,
        REAL_IOPS,
        NORM_IOPS,
        MAX_NET_BANDWIDTH_DISPLAY,
        REAL_NET_BANDWIDTH_DISPLAY
    FROM oceanbase.GV$OB_GROUP_IO_STAT
    WHERE GROUP_NAME LIKE '%MVIEW%';
```

#### 3. 查看资源管理统计项

```shell
obclient> SELECT
        CON_ID,
        GROUP_ID,
        NAME,
        VALUE,
        VALUE_TYPE
    FROM oceanbase.GV$OB_RES_MGR_SYSSTAT
    WHERE GROUP_ID = 1001;
```

**参数说明：**

请将 `<group_id>` 替换为实际的物化视图相关资源组 ID（示例值 1001）。

### 步骤八：查看刷新历史与变更规模

刷新历史信息和基表变更规模可以为资源分析提供上下文，例如解释某次刷新为什么耗时更长或 IO 消耗更高。

#### 1. 查看单次刷新耗时和行数变化

```shell
obclient> SELECT
        MV_OWNER,
        MV_NAME,
        REFRESH_ID,
        REFRESH_METHOD,
        START_TIME,
        END_TIME,
        ELAPSED_TIME,
        LOG_PURGE_TIME,
        INITIAL_NUM_ROWS,
        FINAL_NUM_ROWS
    FROM oceanbase.DBA_MVREF_STATS
    ORDER BY END_TIME DESC
    LIMIT 20;
```

**返回结果说明：**

* `ELAPSED_TIME`：刷新耗时。
* `INITIAL_NUM_ROWS`：刷新前行数。
* `FINAL_NUM_ROWS`：刷新后行数。

**注意事项：**

`LOG_PURGE_TIME` 已废弃。在较新版本中，该列可能始终为 `NULL`。

#### 2. 按刷新运行汇总查看历史记录

```shell
obclient> SELECT
        RUN_OWNER,
        REFRESH_ID,
        NUM_MVS,
        MVIEWS,
        BASE_TABLES,
        METHOD,
        PARALLELISM,
        START_TIME,
        END_TIME,
        ELAPSED_TIME
    FROM oceanbase.DBA_MVREF_RUN_STATS
    ORDER BY START_TIME DESC
    LIMIT 20;
```

**返回结果说明：**

* `NUM_MVS`：涉及的物化视图数量。
* `MVIEWS`：涉及的物化视图。
* `BASE_TABLES`：涉及的基表。
* `METHOD`：刷新方式。
* `PARALLELISM`：并行度。

#### 3. 查看基表变更行数

```shell
obclient> SELECT
        TBL_OWNER,
        TBL_NAME,
        MV_OWNER,
        MV_NAME,
        NUM_ROWS_INS,
        NUM_ROWS_UPD,
        NUM_ROWS_DEL,
        NUM_ROWS
    FROM oceanbase.DBA_MVREF_CHANGE_STATS
    WHERE REFRESH_ID = 1025;
```

**参数说明：**

请将 `<refresh_id>` 替换为目标刷新任务 ID（示例值 1025）。

**返回结果说明：**

* `NUM_ROWS_INS`：插入行数。
* `NUM_ROWS_UPD`：更新行数。
* `NUM_ROWS_DEL`：删除行数。
* `NUM_ROWS`：总变更行数。

**使用建议：**

当 `NUM_ROWS` 明显增大时，通常表示该次刷新需要处理的数据量增加，这可能导致刷新耗时和 IO 消耗上升。

## 注意事项

* `GV$OB_ACTIVE_SESSION_HISTORY` 适用于近期或正在运行的任务；`DBA_WR_ACTIVE_SESSION_HISTORY` 更适合历史分析。
* 如果刷新任务启用了并行执行，SQL Audit 中可能记录多个并行子任务，`stmt_count` 可能显著高于实际刷新步骤数。
* 正在运行的刷新任务，其 `TRACE_ID` 可以结合刷新运行统计信息或相关日志获取。
* 不同兼容模式或版本下，视图名称、字段名称和返回结果可能存在差异，请以实际环境为准。
