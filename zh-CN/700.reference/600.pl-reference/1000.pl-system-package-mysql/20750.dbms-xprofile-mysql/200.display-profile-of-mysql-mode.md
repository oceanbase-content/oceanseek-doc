# DISPLAY_PROFILE

`DISPLAY_PROFILE` 用于展示 SQL 执行计划的性能分析数据，可查看指定 `trace_id` 对应的执行的算子级诊断信息。

## 语法

```sql
DBMS_XPROFILE.DISPLAY_PROFILE(
    trace_id    varchar2 default null,
    tenant_id   integer default 0,
    format      varchar2 default 'AGGREGATED',
    level       integer default 1,
    svr_ip      varchar2 default null,
    svr_port    integer default 0,
    op_id       integer default null
    )
```

## 参数说明

| **参数**  | **说明** |
|-----------|----------|
| trace_id  | 可选项，指定 trace id。展示指定 `trace_id` 下的 profile，省略、填 `null` 或者填 "" 时，默认选择当前 Session 上的 last trace id。|
| tenant_id | 可选项，指定租户 ID。省略或者填 0 时，默认选择当前当前租户 ID。除了系统租户外，用户租户指定了其他租户 ID 将会返回空结果。|
| format    | 可选项，指定展示形式。取值如下：<ul><li>`AGGREGATED`：默认值，表示展示聚合后的 profile。</li><li>`ORIGINAL`：表示输出聚合前的线程级 profile。</li></ul>|
| level     | 可选项，指定输出等级。每个指标都有各自的等级，高于 level 的指标将不会展示出来。取值如下：<ul><li>0：表示核心指标，一定会输出，比如吐行、dbtime 之类的信息。</li><li>1：默认值，表示标准指标，常用的一些指标可以设置为该等级。</li><li>2：表示排查指标，用于定位 BUG 或者进一步分析时用的指标，不常用，输出信息太多。</li></ul>|
| svr_ip    | 可选项，筛选只显示某个 IP 上的 profile。默认值为 `null`，表示全输出。|
| svr_port  | 可选项，筛选只显示某个 port 上的 profile。默认值为 0，表示全输出。|
| op_id     | 可选项，筛选只展示计划中编号为 ID 的算子的 profile。默认值为 `null`，表示全输出。|

## 返回结果说明

函数返回 Profile 文本，统计范围为指定 `trace_id` 对应的一次查询，不包含同一 SQL 多次执行的平均耗时或历史趋势。

### 向量搜索

执行带有 `MONITOR` Hint 的向量搜索 SQL 后，返回结果会在实际执行向量搜索的 SQL 物理算子下展示 `Vector Search` 子树。该信息用于分析过滤、索引搜索和数据加载等阶段的开销，不改变查询结果、执行计划或 Explain 输出。操作步骤请参见 [索引监控与维护](../../../../400.ai-search/300.vector-search/200.vector-index/600.vector-index-monitor-and-maintain.md)中的“单次向量搜索性能分析”。

#### 展示层级

```shell
SQL 物理算子
  Vector Search
    Partition
      tablet id:200017
      Vector Iter
        通用向量搜索指标
        Vector Index HNSW Scan / Vector Index SINDI Scan / Vector Index IVF Scan
          对应算法的指标
```

* `Vector Search`：向量搜索性能分析信息的根节点。
* `Partition`：单个分区（或叫数据分片，Tablet）的执行实例，`tablet id` 标识对应的数据表 Tablet。同一个 Tablet 可能因并行执行、重新扫描或查询重试出现多个实例，不等于表的物理分区数量。
* `Vector Iter`：展示过滤路径、过滤过程、索引搜索耗时和输出行数。
* 算法节点：HNSW、HNSW_SQ、HNSW_BQ 展示为 `Vector Index HNSW Scan`；SINDI、SINDI_SQ 展示为 `Vector Index SINDI Scan`；IVF、IVF_PQ 展示为 `Vector Index IVF Scan`。

上述节点仅用于展示性能分析信息，不是新增的 Explain 算子。

#### 通用指标

| 字段 | 含义 |
| --- | --- |
| `try path` | 本执行实例最初选择的向量执行路径；后续路径切换不会覆盖该值。 |
| `current path` | 本执行实例最终生效的向量执行路径。 |
| `switch reason` | 本执行实例最后一次真实生效的运行时路径切换原因。 |
| `pre filter rows scanned` | 前过滤阶段实际消费的累计行数。 |
| `pre filter time` | 实际消费前过滤结果的累计耗时。 |
| `iter filter row` | 候选过滤阶段实际执行标量判断的候选行数累计值。 |
| `iter filter matched row count` | 实际通过候选标量过滤的行数累计值。 |
| `iter filter loop cnt` | 实际进入候选过滤阶段的次数；单次后过滤记为 1，多轮迭代按轮次累计。 |
| `iter filter time` | 候选过滤及相关迭代处理的累计耗时。 |
| `vec index search time` | 从向量索引中获取候选结果的累计耗时，不包括标量过滤以及根据候选结果读取原表数据的耗时。 |
| `total search time` | `Vector Iter` 从开始执行到输出向量搜索结果的端到端累计耗时，包括搜索准备、过滤、向量索引搜索和结果处理等阶段。 |
| `output row count` | `Vector Iter` 实际输出的累计行数。多分区查询中，每个分区可以分别输出自身的 TopK 候选。 |

`try path` 和 `current path` 分别表示初始路径和最终路径，取值含义如下：

| 取值 | 含义 |
| --- | --- |
| 0 | 尚未确定路径；向量搜索未开始时，通常不展示路径字段。 |
| 1 | 前过滤：先根据标量条件筛选数据，再在符合条件的数据范围内执行向量搜索。 |
| 2 | 迭代过滤：先通过向量搜索获取一批候选数据，再根据标量条件进行筛选；如果筛选后的结果数量不足，则继续获取更多候选数据。 |
| 3 | 集合过滤：先获得符合标量条件的主键或向量 ID 集合，再将向量搜索范围限定在该集合内。 |
| 4 | 后过滤：先完成一次向量搜索，再按标量条件筛选本次搜索得到的候选数据。 |
| 5 | 无标量过滤，直接执行向量索引搜索。 |

`switch reason` 表示最后一次实际生效的运行时路径切换原因，取值含义如下：

| 取值 | 含义 |
| --- | --- |
| 0 | 没有记录到实际生效的路径切换。 |
| 1 | 前过滤的执行时间达到系统的路径切换阈值。 |
| 2 | 前过滤匹配的数据占比较高，继续使用前过滤的收益较低，因此系统切换执行路径。 |
| 3 | 系统评估 IVF 系列索引的前过滤成本达到路径切换阈值。 |
| 4 | 迭代过滤后保留的候选数据占比较低，达到系统的路径切换阈值。 |
| 5 | IVF 系列索引在迭代过滤过程中需要执行的向量距离计算量达到系统限制。 |
| 6 | HNSW 系列索引在按数据块分配并行扫描任务的场景下，被强制切换到前过滤。 |
| 255 | 已发生切换，但未归入已有原因。 |

判断是否发生运行时路径切换，应以非零 `switch reason` 为主要依据，不能仅比较初始路径和最终路径。由外层 SQL 算子执行的过滤条件，不会重复计入向量搜索内部指标。

#### 注意事项

* Profile 按实际执行路径展示字段。字段未展示通常表示对应阶段未执行或不适用，不代表该字段的值为 0。新旧版本混合部署时，旧版本节点也可能不展示新增字段。
* 时间、行数和次数在当前 `Partition` 执行实例内累计，多轮候选扩展累计到同一节点。重新扫描或查询重试可能产生新的执行实例。
* 同一个 Tablet 的多个执行实例分别展示，不会按 `tablet id` 合并。
* `total search time` 是端到端耗时，其他时间字段可能存在包含关系，不能直接将全部阶段耗时相加。
* 并行执行时，时间按线程累计，多个执行实例的累计耗时可能超过查询实际经过的时间。
* 本次向量搜索涉及多个数据分片时，各执行实例可能分别输出自身的 TopK 候选，因此 `output row count` 不一定等于 SQL 最终返回的行数。
* `candidate distance cal time` 可能包含在 `candidate scan time` 中，两者不能直接相加。

#### HNSW 和 SINDI 指标

以下字段由 HNSW 系列索引和 SINDI 系列索引共用，分别展示在 `Vector Index HNSW Scan` 和 `Vector Index SINDI Scan` 节点中。

| 字段 | 含义 |
| --- | --- |
| `filter mode`<main id="notice" type='explain'><h4>说明</h4><p><code>filter mode</code> 仅在 <code>Vector Index HNSW Scan</code> 节点展示。</p></main> | HNSW 系列索引实际采用的搜索模式：<li>`0` 表示 图搜索（`GRAPH_SEARCH`）</li><li>`1` 表示暴力距离计算（`BRUTE_FORCE`）</li> |
| `vsag query time` | 向量搜索引擎从索引中查找相似向量的累计耗时，不包括整理和返回候选结果的时间。 |
| `vsag query segment cnt` | 向量搜索实际访问的数据段（Segment）数量。同一执行实例包含多轮搜索时，各轮访问的数据段数量会累加，同一个数据段可能被重复计数，这里是累计数值。 | 
| `active rows cnt` | 本次向量搜索处理的增量向量数量。这些向量位于活跃数据段（Active Segment）中，尚未合并到持久化索引数据段。 |
| `active scan time` | Active Segment 向量搜索的累计耗时，不包括整理和返回候选结果的时间。 |
| `delta_buffer scan time` | 从 `delta_buffer` 表读取尚未合并到持久化索引中的增量数据所用的累计时间，不包括读取后的数据处理和向量数据补齐耗时。 |
| `index_id scan time` | 从 `index_id` 表读取索引 ID 和数据可见性信息的累计耗时，不包括读取后的内存状态更新耗时。 |
| `complete data total time` | 补齐查询所需索引数据的累计总耗时，包括增量向量、索引可见性信息和索引快照的处理时间。未发生数据补齐时不展示该字段。 |
| `complete delta_buffer time` | 将本次向量搜索所需的增量向量加载到内存增量 Segment，并使其可参与搜索的累计耗时。 |
| `complete index_id time` | 补齐本次向量搜索所需的索引 ID 及其可见性信息的累计耗时。可见性信息用于判断索引项是否可以参与本次搜索结果。 |
| `complete index_snapshot_data time` | 读取、校验并按需加载持久化索引快照的累计耗时。 |

算法节点还可能展示以下扫描和快照加载指标：

| 字段 | 含义 |
| --- | --- |
| `vec hnsw delta buf scan rows` | 实际读取并处理的 `delta_buffer` 有效行数。 |
| `vec hnsw index id scan rows` | 实际读取并处理的 `index_id` 有效行数。 |
| `vec hnsw snapshot scan rows` | 实际读取并处理的 `index_snapshot_data` 有效行数。 |
| `vec hnsw deserialize snap time` | 反序列化持久化索引快照的累计耗时。反序列化指的是将持久化索引快照还原为内存中可用的数据结构。 |

SINDI 节点也可能展示名称以 `vec hnsw` 开头的共用字段，不表示实际执行了 HNSW 搜索。HNSW_BQ 的外层精排耗时不在该算法节点重复展示。SINDI 对候选数据执行一次后过滤时，`iter filter loop cnt` 计为 1，但这不表示 SINDI 支持在结果不足时继续获取更多候选数据并重复过滤。

#### IVF 指标

以下字段由 IVF 系列索引共用。IVF 系列索引的 Profile 仅展示本次向量搜索实际执行阶段的指标，具体展示哪些指标，取决于索引类型和缓存是否可用。

| 字段 | 含义 |
| --- | --- |
| `search nlist time` | 定位初始聚类中心，以及迭代过滤时扩展更多中心的累计耗时。 |
| `candidate rows scanned` | 本次向量搜索实际扫描的候选向量数据行数，多轮扫描的行数会累加。 |
| `candidate scan time` | 从倒排桶（IVF 索引中同一聚类中心对应的向量集合）读取和处理候选向量的累计耗时。 |
| `candidate distance cal time` | 计算候选向量与搜索向量之间距离的累计耗时。 |

缓存相关指标如下：

| 字段 | 含义 |
| --- | --- |
| `centroid cache fallback scan time` | 聚类中心缓存（`IVF_CENTROID_CACHE`）不可用时，扫描聚类中心表的累计耗时。 |
| `centroid cache build time` | 当前执行实例在向量搜索过程中同步构建 `IVF_CENTROID_CACHE` 的累计耗时。 |
| `pq centroid cache fallback scan time` | `IVF_PQ_CENTROID_CACHE` 不可用时，查询回退访问 PQ 聚类中心数据的累计耗时。 |
| `pq centroid cache build time` | 当前执行实例在向量搜索过程中同步构建 `IVF_PQ_CENTROID_CACHE` 的累计耗时。 |
| `pq precompute cache fallback calc time` | `IVF_PQ_PRECOMPUTE_TABLE_CACHE` 不可用时，使用普通 PQ 距离计算路径的累计耗时；该字段不是扫表时间。 |
| `pq precompute cache build time` | 当前查询同步构建 PQ 聚类中心缓存（`IVF_PQ_PRECOMPUTE_TABLE_CACHE`）的累计耗时。 |
| `map centroid cache fallback scan time` | 当前实例在 `IVF_MAP_CENTROID_CACHE` 不可用时，扫描整张聚类中心表的累计耗时。 |

`candidate rows scanned` 受数据分布、聚类中心选择和候选扩展轮次影响，多次执行的数值可能不同。Map Centroid Cache 不在查询线程中同步构建，因此没有对应的构建耗时字段。当前不展示缓存命中数或命中率；缓存可用且未发生同步构建或回退时，不展示相应字段。

#### 查询重试信息

向量搜索 SQL 返回 `OB_SCHEMA_EAGAIN(-5627)` 并触发 SQL 重试时，失败执行实例会在直接触发重试的节点展示 `vec retry reason`。该字段可能位于 `Vector Iter` 或对应的算法节点，最终成功的执行实例不展示该字段。

| 取值 | 含义 |
| --- | --- |
| 1 | 向量索引状态的更新时间晚于查询快照，需要重新获取索引状态并执行查询。 |
| 2 | 其他查询已完成索引内存数据重新加载，需要重新获取状态并执行查询。 |
| 3 | 当前查询已刷新索引内存数据，需要重新执行查询。 |
| 4 | 索引可见性信息的版本晚于查询或上下文版本，当前快照无法继续使用该信息。 |
| 5 | 操作期间索引可见性信息已被替换，需要重新获取。 |
| 6 | 索引快照记录对当前查询不可见，异步索引状态尚未满足查询条件。 |

未发生重试时不展示该字段，不会输出为 `0`；`255` 是保留值，当前不输出。

### 混合搜索并行执行

开启混合搜索并行后，返回结果中可能出现下列信息：

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>自适应并行度（Auto DOP）相关信息从 V4.6.2.1 版本开始支持。</p>
</main>

| **输出信息** | **说明** |
| --- | --- |
| `auto dop cpu pressure pct` | 自适应并行度（Auto DOP）决策时使用的租户 CPU 压力；首次完整采样窗口前可能不存在 |
| `auto dop load cap` | CPU 负载档位给出的查询目标并行度上限 |
| `auto dop target` | 物理切分前的查询目标并行度 |
| `auto dop actual` | 物理切分后最终得到的查询切片（Slice）数量 |
| `parallel task count` | 本次 Fusion 生成的全部工作单元（WorkUnit）数量 |

## 示例

* sys 租户中查看其他租户的 profile。

    ```shell
    obclient> SELECT DBMS_XPROFILE.DISPLAY_PROFILE('Y7A8B64586C10-00063BAC30589818-0-0', tenant_id);
    ```

    <main id="notice" type='notice'>
    <h4>注意</h4>
    <p>只有 sys 租户才能查其他租户的 profile, 必须要指定 <code>tenant_id</code>。</p>
    </main>

* 用户租户查询自己的 profile。

    ```shell
    obclient> SELECT DBMS_XPROFILE.DISPLAY_PROFILE('Y7A8B64586C10-00063BAC30589818-0-0');
    ```
