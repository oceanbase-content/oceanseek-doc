# OBKV-Table Java 开发指南

本文介绍了 OBKV-Table 开发过程中的注意事项和最佳实践。在选择 OBKV-Table 开发之前，您需要先了解业务的实际应用场景，以及 [OBKV-Table 的产品定位](../100.introduction-to-obkv-table/100.implementation-of-obkv-table.md)。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>OBKV-Table 仅支持 Java 客户端。</p>
</main>

## 使用建议

### 批（Batch）

如果 Batch 中数据没有逻辑关系，Batch 尽量不要跨分区，OBKV-Table 客户端提供了分区接口，在使用 Batch 的时候，可以先基于分区接口计算分区 ID，然后每个分区单独攒批提交。好处是单机事务，性能损耗非常小，而且业务重试逻辑也比较简单。

### 索引

索引使用建议如下：

* 非必要不使用全局索引，主表数据写入/更新/删除场景，全局索引的维护，会有比较大的分布式事务开销。
* 虽然局部索引的维护开销比全局索引小，局部索引的数量要控制，索引数量也会成倍增加索引维护的开销。

## 分区规划

如下以 Key 分区举例。

### 分区键设计

在 OBKV-Table 中，分区键设计的第一个目标是通过分区键的设计，保证业务场景的请求不会跨分区。分区键的选择有如下规律：

* 分区键一般是主键或者主键前缀。

    * 分区键是主键的场景：如订单场景，建表时设置 orderid 为主键，又由于查询只有基于 orderid 进行精确点查这个类型，那么orderid 也可以直接作为分区键，便于快速点查到某个 orderid 下的所有或部分信息。
    * 分区键是主键前缀的场景：如订单场景，建表时设置主键为 userid 以及 orderid 的复合主键，查询操作可能会基于 userid 做前缀扫描，以获取该用户的全部以及部分订单，那么可以基于 userid 作为分区键。
* 业务场景做查询的时候，一定会带上分区键的字段。

### 分区数的设计考虑

#### 为什么要关注分区数

* 分区数的调整需要调整数据模式（即表的 Schema 或 DDL），需要重新做数据分布，调整代价较大。
* 分区数不宜过小：由于数据库的均衡算法会保证两个节点之间分区数的差异不超过 1，那么假设 3 个节点，7 个分区，三个节点上的分区数即 <3,2,2>，即节点间分区的不均衡度为 (3-2)/3 = 33%。在假定没有数据倾斜的条件下，分区数几乎正比于数据的存储量以及访问量，分区的不均衡度也会体现在各个节点资源使用上的不均衡。因此，分区数不宜过小。
* 分区数也不宜过大：可以将分区看做 mini 数据库，也就是一个数据库中有多个 mini 数据库。每个 mini 数据库独立管理自己的存储空间和数据访问。在这种结构下，首先 miniDB 多会导致存储空间不能极致共享，其次 Scan 算子可能会跨多个数据库，有一定的性能损失，业务上的 Batch 操作也难以直接下压给存储做极致的性能优化。因此，分区数不宜过大。

#### 分区数对性能的影响

一般情况下，分区数的大小对性能的影响不大。但如果是合并/迁移/备份等基于分区为粒度的任务，则会有影响。分区数过小分区过大，会导致单个任务的执行时间长，也会对空间资源的要求会更高。

#### 分区数如何选择

* 基于容量考虑，我们建议单分区单副本的数据量尽量不超过 100GB。在选取分区数的时候，尽量选择 23/59/97/193/389/997 等素数。比如三副本，24T 的存储空间占用，单分区单副本 8T，预估需要至少 80 个分区，基于上述推荐值，选择 97 个分区。
* 分区数的变更需要调整 DDL，有一定的开销。在设计分区数的时候，需提前做好分区规划，尽量避免频繁的分区数变更。假设当前的存储空间是 24T，但是未来一年，预期存储空间会扩大到 50T，那么在初始设计的时候，可以基于 50T 为基准，最好选择 193 的分区数。
* 分区数不宜过大，不建议超过 997。

#### 如何判断分区间的数据倾斜

Key 分区目前使用 MurmurHash 逻辑，会基于分区键把数据 Hash 后，投递到对应的分区。除非有极端情况，比如数据 1 亿条，1kw 的数据都是一个分区键，这种情况会造成比较严重的数据倾斜。如果数据 1 亿条，有部分分区键下有几千条数据，这种场景一般不会造成倾斜，因为在大样本下，经过 Hash 后算分区键，有比较大的随机性。从全局看，各个分区的数据最终会比较接近。
