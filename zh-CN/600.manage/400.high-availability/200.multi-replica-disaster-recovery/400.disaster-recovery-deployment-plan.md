# 容灾部署方案

## 概述

OceanBase AI 数据库采用存算分离架构，通过高可用日志服务提供数据的持久性，保证数据不丢失（RPO=0），通过多副本计算节点保障数据的高可用。本文介绍存算分离架构下支持的容灾部署方案，用户可根据机房条件以及对性能与可用性的要求进行灵活选择。

## 部署方案

用户可通过灵活调整集群各个 Zone 的机房分布，以及副本在这些 Zone 上的分布，调整集群的部署模式，达到不同的容灾级别。

OceanBase AI 数据库数据库支持的容灾等级如下所示。

| 部署模式 | 副本数 | RTO | RPO | 容灾场景 | 容灾能力 |
| --- | --- | --- | --- | --- | --- |

所有部署方案均依赖基于 Paxos 一致性协议的多副本高可用日志服务（LogService），其工作机制如下：

* 写入链路：计算节点 Leader 通过 Paxos 协议将日志直接写入日志服务的多副本，完成持久化。
* 读取链路：计算节点 Follower 从最近的日志服务副本读取日志，并在本地回放出热点数据。
* 容错能力：在少数派副本不可用时（日志服务三副本集群允许一个副本不可用），计算节点的读写不受影响，持续正常提供服务。

## 单机房部署

### 计算节点单副本

部署拓扑：计算节点单副本 + 日志服务三副本，均部署于同一机房内。

容灾机制：当计算节点不可用时，通过一台全新的计算节点从对象存储恢复数据与元数据，并从日志服务恢复增量数据，拉起完整的服务能力。

| 指标 | 值 |
| --- | --- |
| RPO | 0（不丢数据） |
| RTO | 分钟级 |
| 容灾粒度 | 机器级 |

适用场景：对恢复时间要求相对宽松，追求部署简洁、资源节约以及性能更优的业务场景。

### 计算节点两副本

部署拓扑：计算节点（OBServer）两副本 + 日志服务三副本，均部署于同一机房内。

容灾机制：当 Leader 所在 Server 宕机时，系统自动执行容灾切换，将 Follower 提升为 Leader 继续提供服务，全程无需人工介入。

| 指标 | 值 |
| --- | --- |
| RPO | 0（不丢数据） |
| RTO | < 8s |
| 容灾粒度 | 机器级 |

适用场景：对恢复时间要求较高，需要在秒级内完成故障切换以及追求性能更优的业务场景。

## 同城三机房部署

### 计算节点单副本

部署拓扑：计算节点单副本 + 日志服务三副本，日志服务的三个副本跨机房部署。

容灾机制：当任意一个机房不可用时，日志服务仍有多数派副本可用，保障日志的持久性与完整性。计算节点可从对象存储与日志服务恢复完整服务能力。

| 指标 | 值 |
| --- | --- |
| RPO | 0（不丢数据） |
| RTO | 分钟级 |
| 容灾粒度 | 机房级 |

适用场景：具备多机房条件，需要抵御机房级故障，但对恢复时间要求相对宽松的场景。

### 计算节点两副本

部署拓扑：计算节点两副本跨机房部署 + 日志服务三副本跨机房部署。

容灾机制：当任意机房不可用时，日志服务仍有多数派副本可用。当计算节点 Leader 所在机房不可用时，系统自动执行容灾切换，将其他机房的副本提升为 Leader，继续提供服务。

| 指标 | 值 |
| --- | --- |
| RPO | 0（不丢数据） |
| RTO | < 8s |
| 容灾粒度 | 机房级 |

适用场景：对可用性与恢复时间均有极高要求的核心生产环境，推荐作为核心业务的首选方案。

## 说明

* 计算节点及日志服务（LogService）当前只支持同城部署。
* 计算节点支持单副本和两副本部署；日志服务要求三副本部署，至少需要 3 个节点。
* 计算节点和日志服务节点可以部署在同一台机器上，也可独立部署在不同的机器上。
