# OceanBase AI 数据库 V4.6.2

## V4.6.2.2

### 版本信息

* 发布时间：2026 年 9 月 23 日
* 版本号：V4.6.2.2
* RPM 版本号：
    * oceanbase.ai-4.6.2.2-100000052026092215
    * oblogservice-1.3.3-42026092110
    * oceanbase-cdc-4.6.2.2-62026092216

### 版本概览

OceanBase AI 数据库 V4.6.2.2 是稳定性增强版本。核心亮点是支持带 LOB 类型数据的 OBCDC 同步，并发布了首个配套 OceanBase AI 数据库的 OBCDC 版本，可将库内数据经 OBCDC 同步至下游，打通数据向下游流转的链路。本版本同时针对迁移、FORK TABLE、GC、混合搜索等能力修复了多项问题，并新增两项 FORK TABLE 能力与无向量索引精确 KNN：

* 支持 fork 带搜索索引（`search_index`）的表，`search_index` 随表保留，源表与目标表独立维护。
* 支持 `FORK ... WITH READ LOCK`：fork 期间源表可读不可写，SQL 返回后即可恢复写入。
* 支持无向量索引精确 KNN：在包含向量列的堆表（HEAP）上，无需创建 HNSW/IVF 系列向量索引，即可通过 `HYBRID_SEARCH` 子句完成精确最近邻搜索。

### 关键特性说明

#### LOB 类型支持 OBCDC

此前版本 OBCDC 无法同步含 LOB 列的数据变更，库内多模大对象数据（如文档内容、元数据、多媒体信息等）难以流向下游。本版本起，OBCDC 支持同步包含 LOB 列的表变更，保证同步数据完整一致。具体功能说明如下：

* `FULL` 模式下可正确同步未修改的 LOB 列，保证下游数据完整。
* 暂不支持追加流式写入的 LOB 数据；遇到该类写入时 OBCDC 会主动报错，避免产生不一致数据。建议将使用追加流式写入 LOB 的表配置到 `tb_black_list` 中排除。

适用于将 OceanBase AI 数据库中的多模、半结构化数据经 OBCDC 实时同步至下游数仓、搜索引擎或订阅系统。

#### FORK TABLE 功能增强

FORK TABLE 增强两项能力，便于在保留搜索能力的同时保证 fork 结果正确：

* 支持 fork 带搜索索引（`search_index`）的表：`search_index` 及其索引辅助表随 fork 完整保留，源表与目标表解耦、独立维护；fork 返回后目标表索引即可使用，并支持混合搜索。
* 支持 `FORK ... WITH READ LOCK` 子句：fork 期间源表可读不可写（未提交的写事务需等待，新写入请求被阻塞）；SQL 返回后源表即可恢复写入。异常失败时读锁仍会正常释放，保证 fork 结果正确。

两种语法可在同一源表上并发使用、互不干扰。

#### 支持无向量索引精确 KNN

此前混合搜索中的 `knn` 查询强依赖 HNSW/IVF 系列向量索引，无索引时无法使用向量搜索。本版本支持在堆表上不创建任何向量索引，直接通过 `HYBRID_SEARCH` 完成精确最近邻搜索。具体功能说明如下：

* 支持 `cosine` / `l2` / `ip` 距离算法，以及标量与全文过滤、RRF / 加权融合等搜索方式。
* 语法与有索引时一致，系统自动选择访问路径。

适用于强过滤后的小集合搜索（如按 `user_id` 过滤后的千行级数据）、小表免索引维护、要求精确结果，以及全文 + 向量融合等场景，可省去索引构建与维护开销，同时保证结果精确。

### 升级说明

* 不支持 OceanBase AI 数据库 V4.6.0.1 版本升级到 OceanBase AI 数据库 V4.6.2 版本。
* 支持从 OceanBase AI 数据库 V4.6.2 / OceanBase AI 数据库 V4.6.2.1 升级到 OceanBase AI 数据库 V4.6.2.2。

## V4.6.2.1

### 版本信息

* 发布时间：2026 年 9 月 10 日
* 版本号：V4.6.2.1
* RPM 版本号：
    * oceanbase.ai-4.6.2.1-100000092026090921
    * oblogservice-1.3.2-92026090716

### 版本概览

OceanBase AI 数据库 V4.6.2.1 面向 AI 搜索、模型接入与湖仓读写做了能力增强，便于您直接在库内完成更多 AI 与数据分析工作。具体能力如下：

* AI 引擎：
    * AI 搜索：全文支持多语言分析；语义索引覆盖图片与大规模文本后建；混合搜索可更精细地控制召回松紧；向量搜索在大规模召回和节点迁移后更稳定。
    * 模型接入：用厂商配置一步接入主流模型，并通过网关做多端点路由与熔断，降低限流和单点故障的影响。
* 计算引擎：面向 DataFrame 生态提供高速批量写入；`JSON_EXTRACT` 等路径查询无需改 SQL 即可更快。
* 存储引擎：异步索引减轻写入压力；同一 Namespace 可建多张逻辑表并做关联查询；LOB 支持追加写入，容量提升至 4 TB。

同时支持用 SQL 查询 Paimon 数据湖表，日志服务可按需增减可用区，单副本部署也可在可用区故障后恢复服务。

### 关键特性说明

#### AI 引擎

* 全文索引支持多语言文本分析器（Analyzer）

    对英语、泰语、越南语、印尼语、马来语等文本做更合适的分词与分析。内置 `standard`、`english`、`thai`、`vietnamese`、`indonesian`、`malay` 等 Analyzer，其中 `standard` 适合多语言混排。也可用 JSON 自定义分析管道。具体请参见[全文搜索](../400.ai-search/500.full-text-search.md)。

* 混合搜索 `minimum_should_match` 更灵活

    用于控制至少命中多少个可选条件才算匹配。除整数外，还支持负数、百分比和组合写法（如 `"75%"`、`"3<90%"`、`"2<-25% 9<-3"`），在 `match`、`multi_match`、`query_string`、`bool`（`should`）中生效，便于在召回更全和结果更准之间调参。具体请参见 [HYBRID_SEARCH](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/8100.select-of-mysql-mode/500.hybrid-search-of-mysql-mode.md)。

* 后建语义索引支持批量嵌入

    大表后建语义索引时，默认通过 HTTP 逐条调用模型，耗时长、费用高。可将 `ai_service_tier` 设为 `BATCH`，走厂商 Batch 接口批量完成嵌入。该能力仅适用于已有表的全量后建，不支持建表时创建。具体请参见[语义搜索](../400.ai-search/400.semantic-search.md)与 [AI 模型交互（Batch File）](../700.reference/480.ai-function/250.ai-model-batch-file.md)。

* 语义索引支持图片 URL

    支持在 `VARCHAR` 列存放图片 URL，创建索引时指定 `content_type=image`，由多模态嵌入模型自动向量化。查询时仍传入原始 URL 或文本即可，支持以图搜图、以文搜图，适用于商品图搜索、内容审核、多模态 RAG 等场景。具体请参见[语义搜索](../400.ai-search/400.semantic-search.md)。

* AI 函数更易接入，并支持图片

    用厂商配置（Provider）、模型参数（Model Profile）和网关（Gateway）分别管理连接凭证、调用参数与多端点路由；内置主流厂商默认配置，一般只需填写 API Key 即可调用。同时支持图片多模态：用 `AI_PROMPT` 混排图片与文本，`AI_COMPLETE` 做图像理解，`AI_EMBED` 生成图片向量。具体请参见 [AI 模型注册](../700.reference/480.ai-function/200.ai-function-register-model.md)。

* 向量索引后台任务更可控、更好排查

    索引重建、增量 Segment 合并等后台任务统一调度，调配优先级与并发度，减少抢占租户资源。可通过系统视图查看任务类型、状态和进度，也可用 `DBMS_VECTOR.TRIGGER_ASYNC_TASK` 手动触发，降低巡检与排障成本。具体请参见[向量索引维护](../400.ai-search/300.vector-search/200.vector-index/600.vector-index-monitor-and-maintain.md)。

* 向量索引迁移后立即可查

    节点迁移或复制完成后，HNSW 向量索引无需再临时加载即可提供查询，避免迁移后出现明显的查询延迟抖动。

* 向量 Search Iterator（大规模相似召回）

    HNSW 近似搜索单次最多返回 16384 条相似结果。需要更大规模召回时，可用 Search Iterator 分批翻页继续取数，突破单次 TopK 上限。具体请参见 [HNSW 系列索引](../400.ai-search/300.vector-search/200.vector-index/300.dense-vector-index/200.hnsw-index.md)。

* 模型容错与模型熔断

    AI 函数、语义索引访问外部模型时，常会遇到某个 API Key 限流、某个模型实例短暂故障或网络超时。可将多个端点（不同 Key、厂商或模型实例）放到一个网关下，按权重在健康端点间分流；某个端点连续失败时自动熔断并切到其他可用端点，降低单点故障对业务的影响。具体请参见 [AI 模型注册](../700.reference/480.ai-function/200.ai-function-register-model.md)。

* 搜索索引支持嵌套查询（Nested Query）

    JSON 对象数组默认按路径扁平化后，同一对象内字段的关联会丢失，混搜时可能误命中。创建搜索索引时用 `NESTED_PATHS` 声明嵌套路径，即可要求多个条件命中同一个数组元素。具体请参见[搜索索引](../400.ai-search/300.vector-search/210.search-index.md)。

#### 计算引擎

* JSON 路径查询更快

    `JSON_EXTRACT` 等路径查询是 JSON 最常用的操作。本版本优化了 JSON 读取路径，绝大多数 JSON 函数无需改 SQL 即可受益。内部测试中，`JSON_EXTRACT` 等高频函数的响应时间平均降低 1/3～2/3。

* Arrow Flight SQL 高速写入

    从 Spark Connector、Python DataFrame 等客户端批量写入时，逐行 SQL 往往无法匹配其吞吐能力。本版本支持通过 Apache Arrow Flight SQL 协议以列式批量推送数据，写入仍使用现有 SQL 事务、索引维护与约束检查。支持 append、upsert、update 和 direct load，覆盖 `VECTOR`、`ARRAY` 等类型，适用于大规模导入与高速流式写入。

#### 存储引擎

* 异步索引（实验特性）

    同步索引写入即可见、查询强一致，但写入时要同步维护索引，开销较大。本版本支持在建 全文/搜索索引 时加 `ASYNC` 关键字：表照常写入，索引由后台周期性构建，通常秒级可见；查询为最终一致，可与同步索引一起做混合搜索。可通过视图观察刷新任务，并用 `DBMS_ASYNC_INDEX.FORCEMERGE` 手动触发合并。写入吞吐优先、可接受短暂可见延迟时选用异步索引；一致性优先时仍用同步索引。具体请参见[全文搜索](../400.ai-search/500.full-text-search.md)与[搜索索引](../400.ai-search/300.vector-search/210.search-index.md)。

* 单 Namespace 支持多逻辑表

    多张业务表可以共用底层物理表，避免为每个应用单独建大量物理表。此前一个会话只能访问一张逻辑表；本版本允许同一 Namespace 下创建多张逻辑表，并支持同 Namespace 内的 JOIN 与普通 DML，配合 json-table-sdk 的 Collection / App 隔离，适用于闪应用等多表关联场景。当前暂不支持跨 Namespace 的 JOIN。

* 宏块缓存接入 KVCache

    共享存储下，数据以宏块存放在对象存储，查询性能依赖本地缓存。本版本将宏块内存缓存统一纳入 KVCache 管理，并增加异步落盘：热点宏块会后台写入本地磁盘缓存。读取顺序为内存缓存 → 本地磁盘缓存 → 共享存储；缓存未命中或写入失败会回源，不影响数据正确性。用法不变，可减少重复访问对象存储，读取更快。

* LOB 支持旁路导入和 Offline DDL

    含大对象（LOB）的表可以使用旁路导入和 Offline DDL 重建，批量导入与表重建不必再绕开大对象列。当前支持全量旁路导入和增量基线，不支持增量旁路导入。新旧数据生命周期、提交与发布保持原子一致。具体请参见[LOB 类型](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/500.large-object-of-mysql-mode/400.lob-type-of-mysql-mode.md)。

* LOB 支持追加写

    `LONGTEXT` / `LONGBLOB` 不再受 512 MB 上限限制，容量提升至 4 TB − 1，同时大幅降低写入时的内存占用（如 11GB LOB 以 8MB 分片追加，任一请求内存仅约 16MB）。可用 `LOB_WRITEAPPEND(lob, amount, buffer)` 在单行 `UPDATE` 中分批追加，不必整段重写；写入后可用 `SUBSTR()` 流式读取，事务内支持回滚与连续追加。适用于超大文本、多模态对象的流式写入场景。具体请参见[LOB 类型](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/500.large-object-of-mysql-mode/400.lob-type-of-mysql-mode.md)和 [LOB_WRITEAPPEND 函数](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/500.large-object-of-mysql-mode/450.lob-writeappend-of-mysql-mode.md) 。

* 动态分区支持字符串时间列

    时间以字符串存储时，也可作为 `LIST COLUMNS` 分区键使用动态分区。分区值格式由 `TIME_UNIT` 自动推导，策略与 `RANGE COLUMNS` 一致。具体请参见[创建动态分区表](../700.reference/300.database-object-management/300.manage-partitions-of-mysql-mode/260.dynamic-partition-of-mysql-mode/200.create-a-dynamic-partition-table-of-mysql-mode.md)。

#### 日志服务

* 日志服务支持动态加减可用区

    容灾要求、部署环境或日志写入性能发生变化时，可为日志服务增加或删除可用区，灵活选择单机房或多机房部署，无需重建日志服务即可实现拓扑弹性调整。

#### 数据湖

* 支持查询 Paimon 表

    可用 SQL 直接查询 Apache Paimon 格式的数据湖表，接入 HMS Catalog，支持 Parquet / ORC，并自动做谓词下推、分区裁剪等优化，支持并行读取和线程池管理，用于数据湖查询加速。具体请参见[通过插件读取 Paimon 表](../300.data-pipeline/200.data-delivery/300.data-lake/200.data-lake-integration/250.data-lake-paimon.md)。

#### 容灾

* 单副本跨可用区容灾

    单副本部署下，整个可用区故障后，可在备用可用区恢复全部租户服务。恢复过程从共享存储拉起，无需搬运业务数据，适合在控制成本的同时保留跨可用区恢复能力。具体请参见[单副本场景容灾操作](../600.manage/400.high-availability/200.multi-replica-disaster-recovery/300.database-high-availability.md)。

* 支持从 OceanBase AI 数据库 V4.6.2 升级到 V4.6.2.1。

## V4.6.2

### 版本信息

* 发布时间：2026 年 8 月 10 日
* 版本号：V4.6.2
* RPM 版本号：
    * oceanbase.ai-4.6.2.0-100000162026080717
    * oblogservice-1.3.1-112026080715

### 版本概览

OceanBase AI 数据库是新一代多模一体的冷热分层的存算分离数据库。它是在 OceanBase 经过大规模生产验证的分布式底座上，为 AI 数据场景量身定制的能力。OceanBase AI 数据库基于 OceanBase V4.6.0 版本继续演进，仅支持存算分离部署形态，仅支持 MySQL 兼容模式。本版本支持在线升级至后续发布版本。主要能力如下：

* 面向 Agent 评测场景，支持 Fork table/database（实验特性）。
* 支持 Catalog Sync：将 internal catalog 的建表、建库等 DDL 主动同步到外部 HMS，便于数据平台做数据融合读取。
* 混合搜索能力：支持 Rerank 精排、分区内并行执行。

### 关键特性说明

#### LOB 能力增强

本版本增强 LOB 能力，更好支持多模场景，并便于后续版本兼容升级。需注意：带 LOB 的表不支持 CDC、旁路导入以及 Offline DDL。具体请参见[LOB 类型](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/500.large-object-of-mysql-mode/400.lob-type-of-mysql-mode.md)。

#### Fork table/database（实验特性）

新增 Fork table/database 功能，可快速对用户表或数据库做快照，并创建该对象的派生副本。副本最初共享底层数据，后续读写相互隔离。该功能适用于 Agent 评测场景：可基于生产数据集快速 Fork 出评测数据集，实现数据隔离与评测可复现，避免多个评测任务相互干扰。具体请参见[Fork 概述](../380.data-branching/100.data-branching-overview.md)。

#### 逻辑表能力增强（实验特性）

* 监控运维与限流

    支持按 Namespace 维度做监控与资源管控。监控方面，可查看行数、存储占用等统计信息，以及后台采集任务信息；资源管控方面，支持对 QPS、TPS、数据带宽做限流，还可设置行数上限、容量上限和并发线程槽位。运维可通过 `DBMS_LOGIC_TABLE.SET_NAMESPACE_RESOURCE_LIMIT` 下发配置。

* JSON Search 性能优化

    优化逻辑表 JSON Search 在编译与执行阶段的处理路径，提升查询性能。

* 逻辑表预热

    查询访问会刷新对应 Namespace 的热度；系统可将热 Namespace 的数据拉取到本地缓存，并淘汰冷 Namespace 的本地缓存以释放空间。

当前版本逻辑表能力具体请参见[Agent 混合搜索场景](../250.database-schema-design/600.logical-table/100.agent-hybrid-search-scene/100.overview.md)。

#### Catalog Sync

OceanBase 支持接入外部 HMS / Iceberg Catalog 做元数据读取，OceanBase AI 数据库在此之上进一步提供 Catalog Sync：将 internal catalog 的建表、建库等 DDL 主动同步到外部 HMS，使 OceanBase AI 数据库写入的表可被 Spark 等第三方引擎发现并查询。典型用法是：在 OceanBase AI 数据库侧创建相关 database 和 table 后，将元数据同步到 Hive Metastore，便于数据平台统一读取 Hive Metastore 上的 OceanBase AI 数据库表与 HMS 上的 Iceberg 表，形成数据融合读取方案。当前支持 internal 到外部 HMS 的单向同步，通过配置项 `catalog_sync_target` 控制是否同步目标 Catalog，且仅对开启后新发生的 DDL 生效。具体请参见[Catalog 数据同步](../300.data-pipeline/300.data-sharing/100.auto-synchronize-catalog-data.md)。

#### Catalog 外表采样

支持对 Catalog 外表（如 Hive、Iceberg 等数据源的外部表）执行统计信息采样。可通过 `DBMS_STATS.GATHER_CATALOG_TABLE_STATS` 采集外表统计信息，优化器可据此生成更优执行计划，提升跨源联邦查询性能。具体请参见[统计信息](../450.query-acceleration/200.query-statistics.md)。

#### 中等规模并行优化

优化中等规模并行（DOP 约 2000–6000）场景下的并行执行效率，AP 查询吞吐提升约 15%～30%。

#### 表达式增强

新增和修复多项内置函数，包括：

* 新增表达式：`NCHR`、`NEW_TIME`、`INSTR`、`ROUND`、`randCanonical`、`parseDateTime`
* 新增聚合函数：`avgWeighted`、`string_agg`
* 优化表达式性能：`json_extract`、`json_seek`、`json_length`、`json_type`、`ifnull`、`space`、`extract`、`date_format`

#### SQL 执行优化

多项算子和执行路径优化：

* HashDistinct 可根据数据量动态选择 Hash 或 Sort 去重策略。
* Partition Sort 利用分区有序性减少排序代价。
* 补充 Window Function、CASE WHEN 等算子的向量化路径。
* 聚合下推增强，覆盖更多可下推到存储层执行的场景。
* 列裁剪增强，可精确裁剪复杂视图嵌套场景下未使用的列。
* 优化算子内存控制与落盘，降低内存突增风险。

#### ARM AP 性能优化

增强 ARM 平台向量化与内存访问优化。ARM 平台 AP 核心算子性能提升约 20%～40%，整体 TPC-H 性能接近 x86 水平。

#### 混合搜索支持 rerank 精排

混合搜索在粗排阶段支持将多路召回结果通过 RRF、MinMax 归一化或加权融合进行合并。OceanBase AI 数据库在混合搜索语法中提供 `rerank` 参数，可在粗排融合之后进入精排阶段：调用外部 AI Rerank 模型，对靠前候选文档做语义级二次排序，进一步提升 Top 结果相关性。具体请参见[混合搜索](../400.ai-search/550.hybrid-search.md)。

#### 混合搜索分区内并行执行

混合搜索默认串行执行；数据量大时，单条查询可能较慢。本版本支持分区内并行，用于降低查询响应时间（RT），包含两种方式：

* 多路并行： 同一查询语句中的多条召回路径（多条 `knn` 路 + 全文 `query` 路）由不同工作线程并行执行，整体 RT 接近耗时最长的那条路径。
* 路径内并行：单条 `query` 查询路径内并行，包含全文、标量、JSON 类型过滤等召回路径，按数据范围切分后由多个工作线程并行扫描不同区间，进一步降低单路 RT。

两种方式可同时使用。该能力默认关闭，需设置租户级配置项 `_enable_hybrid_search_parallel_execution = true` 开启；开启后 CPU/内存占用可能上升，建议在资源充足的环境中评估后再启用。具体请参见[混合搜索](../400.ai-search/550.hybrid-search.md)。

#### 混合搜索语法扩展

本版本拓展了混合搜索 SQL 语法，以满足自定义结果集大小、模糊匹配、桶聚合、字段折叠与自定义排序等需求：

* 结果集大小（`num_candidates`）：控制 KNN 候选集规模（影响召回与时延；最终 TopK 仍由 `k` 等决定）。
* 通配符过滤（`wildcard`）：当前版本仅支持基于 JSON 路径与普通字符串列进行过滤。
* 聚合（`aggs.terms` / `aggs.cardinality`）：支持 terms 分组统计和 cardinality 基数估算。
* 折叠（`collapse`）：按指定字段对搜索结果去重，每组仅返回最佳匹配文档。
* 自定义排序（`sort`）：支持按任意表字段排序，并提供 NULL 值位置控制。
* 算分权重（`boost`）：标量过滤条件可在查询中参与算分，并通过兼容 ES 的 `boost` 参数指定分数权重。
* `term` / `terms`：新增对数组字段的查询。

具体请参见[混合搜索](../400.ai-search/550.hybrid-search.md)。
