# Hybrid search

This topic describes the hybrid search SQL interface of OceanBase AI Database. You can use this interface to combine full-text search, vector search, and filter conditions in a single `SELECT` statement by using the `HYBRID_SEARCH` keyword. OceanBase AI Database returns the search results sorted by relevance.

Hybrid search combines vector-based semantic search with keyword search based on full-text indexes, providing more accurate and comprehensive search results through comprehensive ranking. Vector search excels at semantic approximate matching but is weaker at matching exact keywords, numbers, and proper nouns, whereas full-text search can effectively compensate for this deficiency. Therefore, hybrid search has become one of the key features of OceanBase AI Database and is widely used in various products.

## Features and limitations

The features are as follows:

* Full-text indexing, starting from V4.6.2.1, supports text analyzers (Analyzers) in addition to regular tokenizers.
* Scalar filtering, JSON/ARRAY filtering can be executed even without indexes, but it is recommended to create the corresponding indexes for better performance.

The limitations are as follows:

* The current version supports only HNSW series vector index types.
* Only row-based tables are supported.
* Generated columns are not supported.
* When using asynchronous full-text or asynchronous search indexes, the syntax for hybrid search queries remains unchanged. However, index data is refreshed incrementally in the background. Queries guarantee eventual consistency but do not guarantee strong consistency or real-time visibility.
* `HYBRID_SEARCH` can only be used on **heap tables**.
* Vector search requires a vector index to have been created on the target vector column. Multi-way vector search currently only supports dense vector columns.
* Full-text search requires a full-text index to have been created on the target text column. If the full-text column has a composite index, hybrid search is not supported.

This section only lists the feature limitations. They should be understood in conjunction with the syntax limitations provided in the related document `HYBRID_SEARCH` at the end of this topic.

## Syntax

```sql
SELECT select_list
FROM HYBRID_SEARCH(TABLE table_name, dsl_string);
```

The parameters are described as follows:

* `table_name`: The name of the target table. Only heap tables (`ORGANIZATION = HEAP`) are supported. Partitioned and non-partitioned tables are supported.
* `dsl_string`: A JSON string used to describe query semantics such as full-text, vector search, filtering, and sorting fusion.

For complete syntax, parameters, and limitations, see the related document `HYBRID_SEARCH` at the end of this topic.

## Quick start examples

This section provides six simple core examples covering common scenarios of hybrid search, including vector search, full-text search, vector search + full-text search (RRF fusion), multi-vector search, filter condition merging, and score threshold filtering.

### Vector search

This example searches for the three records in the `doc_table` table that are most similar to the vector `[1,2,3]` and returns the `c1` column.

```sql
SELECT c1 FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "knn": {
      "field": "vector",
      "k": 3,
      "query_vector": "[1,2,3]"
    }
  }'
);
```

The expected result is as follows:

:::collapse
```sql
+------+
| c1   |
+------+
|    1 |
|    5 |
|    2 |
+------+
3 rows in set
```
:::

### Full-text and vector RRF hybrid search

This example simultaneously performs a full-text search (matching the keyword `"oceanbase mysql"`) and a vector search (searching for the five records most similar to the vector `[1,2,3]`), then merges the two results using the RRF fusion algorithm. By default, it returns the ten documents most relevant to the query, with a total of six matching records.

```sql
SELECT * FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "query": {
      "match": {"content": "oceanbase mysql"}
    },
    "knn": {
      "field": "vector",
      "k": 5,
      "query_vector": "[1,2,3]"
    },
    "rank": {
      "rrf": {
        "rank_constant": 60,
        "rank_window_size": 10
      }
    }
  }'
);
```

The expected result is as follows:

### Filter condition merging

This example searches for the six records in the `content` column of the `doc_table` table that contain `oceanbase mysql`. The filter condition is that `c1` is greater than or equal to 3 and less than or equal to 5, and the `c1` column is returned.

```sql
SELECT c1 FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "query": {
      "bool": {
        "must": [{"match": {"content": "oceanbase mysql"}}],
        "filter": [{"range": {"c1": {"gte": 3}}}]
      }
    },
    "knn": {
      "field": "vector",
      "k": 10,
      "query_vector": "[1,2,3]",
      "filter": [
        {"range": {"c1": {"lte": 5}}}
      ]
    }
  }'
);
```

The expected result is as follows:
:::collapse
```sql
+------+
| c1   |
+------+
|    1 |
|    3 |
|    6 |
|    5 |
|    2 |
|    4 |
+------+
6 rows in set
```
:::

### Hard filtering and scalar scoring

Scalar conditions can be used only for hard filtering or can participate in relevance scoring (contributing to `__score`). Scalar filter conditions (`term`, `range`, `terms`, `wildcard`, JSON/array expressions) support `boost` and can be placed anywhere in the query; whether they contribute to the score depends on their position. The position rules and syntax for each expression are described in the "Detailed description of boost parameters" section of the `HYBRID_SEARCH` documentation at the end of this topic.

The following example compares the behavior of the same `range` condition in `must` and `filter`:

```sql
-- must: Participate in scoring
SELECT c1, __score FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "query": {
      "bool": {
        "must": [
          {"range": {"c1": {"gt": 1, "boost": 2.1}}}
        ],
        "boost": 2.0
      }
    }
  }'
);

-- filter: not involved in scoring
SELECT c1, __score FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "query": {
      "bool": {
        "filter": [
          {"range": {"c1": {"gt": 1, "boost": 2.1}}}
        ]
      }
    }
  }'
);
```

In the former, `__score` includes a scalar contribution; in the latter, it is used only for filtering, and `__score` is `0` or has no scoring contribution.

## Extended examples

This section provides some more complex extended examples covering advanced scenarios of hybrid search, including filtering of complex data types (such as JSON and ARRAY), specifying the number of vector candidates with `num_candidates`, wildcard filtering, weighted blending of vector and full-text search, WRRF blending, normalization, hybrid search score queries, reranking, aggregation (`aggs`), counting (`count(*)`), sorting (`sort`), and result folding (`collapse`).

### Scalar + JSON/array filtering

These examples require the use of search indexes. In hybrid search scenarios, full-text tokenization and keyword search are handled by full-text indexes, while search indexes are used for structured, semi-structured, or simple scalar conditions on internal paths within complex types. The two apply to different column types, can coexist in the same table, and work together with vector indexes to improve query performance.

Furthermore, in analytical wide-table scenarios, search indexes can also leverage the optimizer's multi-index join query (Index Merge) capability. They automatically identify and combine available full-text and scalar indexes to select the optimal scan path, further enhancing query performance. For more information about search indexes, including usage, syntax, and complete examples, see [Search index](300.vector-search/210.search-index.md).

#### term/terms query array columns

Currently, only single-level array columns are supported. For complete syntax support and limitations, see the "Scalar query structure" section in the `HYBRID_SEARCH` documentation at the end of this topic.

1. Query array columns with `term`

    ```sql
    SELECT id, tags_array1 FROM HYBRID_SEARCH(
      TABLE doc_json_array,
      '{
        "query": {
          "bool": {
            "filter": [{"term": {"tags_array1": "ios"}}]
    ```

### Nested query example

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Nested queries are supported starting from V4.6.2.1.</p>
</main>

When a JSON object array needs to be filtered based on associations with the same array element, first declare `NESTED_PATHS` in the search index, then use nested queries within `dsl_string`. For example, to find all comments where `author=alice` and `rating>=5`:

```sql
CREATE SEARCH INDEX idx_nested ON movie_rating (
  j1 WITH (NESTED_PATHS = ('$.comments'))
);

SELECT k, j1 FROM HYBRID_SEARCH(
  TABLE movie_rating,
  '{
    "query": {
      "nested": {
        "path": "j1.comments",
        "query": {
          "bool": {
            "must": [
              {"term": {"j1.comments.author": "alice"}},
              {"range": {"j1.comments.rating": {"gte": 5}}}
            ]
          }
        }
      }
    }
  }'
);
```

For complete descriptions and examples of multi-level nesting, `must_not` parent/subdomain negation, table creation, and test data, see the nested query section in the `HYBRID_SEARCH` documentation at the end of this topic. For how to declare `NESTED_PATHS`, see the related documentation on search indexes at the end of this topic.

### Vector candidate set size (num_candidates)

`num_candidates` specifies the scale of the candidate set during vector search. It is mapped to `ef_search` at the execution layer, facilitating migration from other search systems. The value range is integers from `[k, 10000]`. When set together with `search_options.ef_search`, `num_candidates` takes precedence; sub-items such as `refine_k` and `filter_mode` in `search_options` can still take effect. For priority and complete descriptions and examples, including values, see the related sections in the `HYBRID_SEARCH` syntax documentation at the end of this topic.

### Wildcard filtering

`wildcard` is used for fuzzy matching on scalar columns, with semantics equivalent to SQL `LIKE ... ESCAPE '\\'`: `*` matches any multiple characters, and `?` matches any single character. `wildcard` can participate in scoring in `bool.must` / `bool.should`, or be used for hard filtering in `bool.filter` or `knn.filter`. Regular indexes on `VARCHAR` columns can speed up the process via index scan paths; prefix indexes, full-text indexes, and JSON-related indexes do not support this.

For more descriptions and examples, see the fuzzy match example section in the `HYBRID_SEARCH` syntax documentation at the end of this topic.

### Rerank fine ranking

Hybrid search first retrieves results using `query` or `knn`, then performs coarse ranking via `rank` (or the default fusion method if not specified). `rerank` then calls the AI Rerank model on the coarse-ranked candidate set to perform fine ranking, rearranging the results based on semantic relevance and returning `size` results.

Before use, you must register a vendor configuration and specify the Rerank model in the `provider/model` format. The following example uses the built-in vendor `aliyun-dashscope` (replace `access_key` with your actual API key):

```sql
CALL DBMS_AI_SERVICE.REGISTER_PROVIDER('aliyun-dashscope', '{
```

## Optimize performance through intra-partition parallelism

Hybrid search uses single-threaded serial execution by default, which may lead to high response time (RT) for individual queries in scenarios with large data volumes and sufficient CPU resources. To address this issue, the intra-partition parallel execution feature is introduced, which can reduce RT using a parallel execution strategy within a single partition. This feature is disabled by default and must be manually enabled.

The specific strategies for parallel execution are described as follows:

| **Parallel strategy** | **Note** |
| --------- | ------ |
| Multiplexing | Multiple recall paths (multiple `knn` paths + full-text `query` paths) are executed in parallel by different worker threads, and the overall response time approaches that of the longest path. Both vector paths and full-text paths are supported. |
| Parallelism within the `query` path | Parallelism within a single `query` path, including recall paths for full-text, scalar, and JSON type filtering. After splitting by data range, it is processed by multiple workers.
Threads perform parallel scanning of different intervals, further reducing single-path RT. Vector paths are not supported. |

The usage instructions and examples are as follows:

### Enable parallelism

Hybrid search parallelism is disabled by default. Before using it, you must enable the parameter at the tenant level:

```sql
ALTER SYSTEM SET _enable_hybrid_search_parallel_execution = true;
```

Effect after enabling:

* Automatic multi-way parallelism: If a query contains ≥ 2 recall paths (for example, one `query` full-text path + one or more `knn` paths), multi-way parallelism is automatically enabled without requiring additional configuration in the `dsl_string`.
* Parallelism within the `query` path:
    * If `query_dop` (the parameter under the `query.search_options` object in the `dsl_string` string) is not specified, the system automatically selects the query parallelism based on the CPU load.
    * If the `query_dop` parameter is specified and `query_dop > 1`, the data is split according to the specified value, overriding the adaptive parallelism.
    * If `query_dop = 1` is explicitly specified, intra-path parallelism is disabled, but multi-way parallelism remains unaffected.
* If the parallel execution conditions are not met, or if the parallel execution switch is disabled, the execution path automatically degenerates into serial execution.

### Multiplexing (automatically enabled)

The following example combines full-text and vector search on `doc_table`. After enabling the parallelism switch, the `query` path and the `knn` path are executed in parallel:

```sql
SET @q = '{
  "query": {
    "match": {"content": "oceanbase mysql"}
  },
  "knn": [
    {"field": "vector", "k": 10, "query_vector": "[1,2,3]"}
  ],
  "rank": {"weighted_sum": {"normalizer": "minmax"}},
  "size": 10
}';

SELECT c1, __score
FROM HYBRID_SEARCH(TABLE doc_table, @q);
```

### Parallelism within the `query` path (automatic/manual)

After parallel execution is enabled, the degree of parallelism within the `query` path can be controlled in two ways: automatic and manual:

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Adaptive parallelism is supported starting from V4.6.2.1.</p>
</main>

#### Adaptive DOP (Auto DOP)

When `query_dop` is not specified, the system automatically selects the query parallelism based on the CPU load. You can use the same query as in the multiplexing example from the previous section. You can observe the parallelism decision for this query using [DBMS_XPROFILE.DISPLAY_PROFILE](../700.reference/600.pl-reference/1000.pl-system-package-mysql/20750.dbms-xprofile-mysql/200.display-profile-of-mysql-mode.md).

#### Explicitly specify `query_dop`

In the `dsl_string` string, under the `query.search_options` object, you can specify the intra-path parallelism using `query_dop`.

| **Field** | **Type** | **Default value** | **Value range** | **Note** |
| ------ | ------ | -------- | ---------- | ------ |
| `query_dop` | int | Automatically selected if not specified | `[1, 128]` | If not specified, the adaptive degree of parallelism (Auto DOP) is used. If explicitly specified, `1` indicates that no intra-path parallelism is performed, and `2` to `128` requests the corresponding degree of parallelism. If the value is out of range, an error is reported during the `dsl_string` parsing phase. |

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><code>query_dop</code> takes effect only when the parallelism switch is enabled or when forced parallelism is specified using a hint. If the tenant-level switch is disabled, or if forced serialization is specified using a hint, the <code>query_dop</code> in the <code>dsl_string</code> string is ignored and no error is reported.</p>
</main>

Set `query_dop = 4` on the `query` path and combine it with the `knn` path (where both multi-path parallelism and intra-path parallelism take effect simultaneously). Example:

```sql
-- query_dop = 4: The full-text recall path is split into four segments for parallel scanning based on the data range.
SET @q = '{
  "query": {
    "search_options": {"query_dop": 4},
    "match": {"content": "oceanbase mysql"}
  },
  "knn": [
    {"field": "vector", "k": 5, "query_vector": "[1,2,3]"}
  ],
  "rank": {"rrf": {"rank_constant": 60}},
  "size": 10
}';

SELECT c1, __score
FROM HYBRID_SEARCH(TABLE doc_table, @q);
```

For more information about the `query_dop` parameter, see the Query options section in the [HYBRID_SEARCH](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/8100.select-of-mysql-mode/500.hybrid-search-of-mysql-mode.md).

### Query-level switch

You can temporarily override tenant-level configurations for a single query using hints to facilitate canary testing:

| **Hint** | **Values** | **Note** |
| ------ | ------ | ------ |
| `OPT_PARAM('enable_hybrid_search_parallel_execution', 'TRUE'/'FALSE')` | `'TRUE'` / `'FALSE'` | Single query-level switch with a higher priority than the tenant-level configuration item `enable_hybrid_search_parallel_execution`. |

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>The parameters in the hint do not require an underscore prefix; you can use <code>enable_hybrid_search_parallel_execution</code> directly.</p>
</main>

Comparison example of forced serialization and forced parallelism (the `dsl_string` string is the same, only the hint differs):

```sql
-- Force parallelism (the hint overrides the system setting)
SELECT /*+ OPT_PARAM('enable_hybrid_search_parallel_execution', 'TRUE') */
       c1, __score
FROM HYBRID_SEARCH(TABLE doc_table, @q);

-- Force serialization (the hint overrides the system setting even when it is enabled)
SELECT /*+ OPT_PARAM('enable_hybrid_search_parallel_execution', 'FALSE') */
       c1, __score
FROM HYBRID_SEARCH(TABLE doc_table, @q);
```

For more information about hints, see [Other hints under global hints](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/600.annotation-of-mysql-mode/400.hint-of-mysql-mode/200.hint-list-of-mysql-mode/100.global-hint-of-mysql-mode/300.other-global-hints-of-mysql-mode.md) at the end of this topic.

### Parallelism switches and conditions

There are two switches for hybrid search parallelism, with the following priority (from high to low):

1. Query-level hint: The `OPT_PARAM` hint has the highest priority and will override system parameter settings.
2. Tenant parameter: `_enable_hybrid_search_parallel_execution` (effective when no hint is specified).

A final value of `TRUE` for the switch only indicates that parallelism is allowed. Whether multi-path parallelism or intra-path parallelism on the `query` path is actually used is still determined by the execution plan according to the [strategy described above](#Optimize%20performance%20through%20intra-partition%20parallelism).

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Hints can override system configurations. Therefore, simply setting the tenant parameter <code>_enable_hybrid_search_parallel_execution</code> to <code>FALSE</code> does not guarantee that all parallel queries are disabled. If any SQL explicitly uses hints to force parallelism, these hints must be removed to fully revert to serialization.</p>
</main>

For answers to other parallelism-related questions, see [FAQ on AI scenarios](300.vector-search/800.vector-search-faq.md) in the references at the end of this topic.

## View execution plans

You can use `EXPLAIN` to view the subquery nodes, hybrid fusion methods, and index usage in a hybrid search plan:

```sql
EXPLAIN SELECT c1 FROM HYBRID_SEARCH(table doc_table, '{"query": { "bool": {
      "must" : [{"match" : {"content": "oceanbase mysql"}}],
      "filter": [
        {"range": {"c1": {"gte" : 3}}},
        {"range": {"c1": {"lte" : 10}}}
      ]
    }},
    "knn":
    {
      "field": "vector",
      "k": 10,
      "query_vector": "[1, 2, 3]"
    }}');
```
