# Create a DML trigger

This topic describes how to create a trigger.

## Prerequisites

The user creating the trigger must have the following privileges:

* Privileges on the table associated with the trigger, including `SELECT`, `INSERT`, `UPDATE`, and `DELETE`.

* Privileges on the statements to be executed when the trigger is activated.

## Syntax

You can use the `CREATE` statement to create a trigger.

The SQL syntax for creating a trigger is as follows:

```sql
CREATE
    TRIGGER trigger_name
    trigger_time trigger_event
    ON tbl_name FOR EACH ROW
    [trigger_order]
    trigger_body;

trigger_time: { BEFORE | AFTER }

trigger_event: { INSERT | UPDATE | DELETE }

trigger_order: { FOLLOWS | PRECEDES } other_trigger_name
```

The syntax is described as follows:

* The trigger name `trigger_name` must be unique.

* `tbl_name`: the name of the table on which to create the trigger.

* `BEFORE | AFTER`: the timing of the trigger action. This specifies whether the trigger activates before or after each row is inserted into the table.

* `INSERT | UPDATE | DELETE`: the triggering event, which is the type of operation that activates the trigger.

* `FOR EACH ROW`: defines the body of the trigger. This statement is executed each time the trigger is activated, once for each row affected by the triggering event.

* `FOLLOWS | PRECEDES`: defines the firing sequence of triggers. In the current version of OceanSeek, you can define multiple triggers on the same table with the same triggering event and action time. By default, triggers with the same triggering event and action time are activated in the order they are created. To influence the firing sequence, you can use `FOLLOWS` and `PRECEDES`. Specifying `FOLLOWS` means the new trigger is activated after existing triggers; specifying `PRECEDES` means the new trigger is activated before existing triggers.

OceanSeek also defines `NEW.columnName` and `OLD.columnName`:

* In an `INSERT` trigger, `NEW.columnName` represents the new data that is about to be (in a `BEFORE` trigger) or has been (in an `AFTER` trigger) inserted.

  Here, `columnName` is the name of a column in the corresponding table.
  
* In an `UPDATE` trigger, `OLD.columnName` represents the original data that is about to be or has been modified, and `NEW.columnName` represents the new data that is about to be or has been modified.

* In a `DELETE` trigger, `OLD.columnName` represents the original data that is about to be or has been deleted.

* `OLD.columnName` is read-only, while `NEW.columnName` can be assigned a value using `SET` within the trigger.

Additionally, if the trigger to be defined contains multiple execution statements, you can use the `BEGIN ... END` statement to enclose the entire code block, indicating its start and end.

The syntax for the `BEGIN ... END` statement is as follows:

```sql
BEGIN
[statement_list]
END
```

Here, `statement_list` represents a list of one or more statements, and each statement in the list must end with a semicolon (;). In SQL statements, a semicolon (;) is an identifier that marks the end of a statement. When a semicolon is encountered, it indicates that the current block of statements has ended, and the system proceeds to execute the next block. This can lead to errors during execution if the interpreter cannot find an `END` that matches the `BEGIN`. To avoid such errors, you can use the `DELIMITER` command to modify the statement terminator.

An example of the `DELIMITER` command is shown below:

```sql
DELIMITER new_delimiter
```

Here, `new_delimiter` can be set to one or more symbols of different lengths. The default is the semicolon (;), but you can change it to other symbols, such as `#`.

After adding the `DELIMITER` command, statements that follow it will no longer cause an error when they use a semicolon, until the specified terminator (`#`) is encountered, at which point the statement is considered finished.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>If you use the <code>DELIMITER</code> command to change the delimiter, make sure that you reset the delimiter to the semicolon (;) after the statements are executed.</p>
</main>

## Examples

* Create a trigger named `test_trg` and associate it with the table `test` to activate INSERT operations. The trigger acts as an accumulator, summing the values inserted into columns of the table.

  ```sql
  obclient>CREATE TABLE test (user_id INT, user_num DECIMAL(10,2));
  Query OK, 0 rows affected

  obclient> CREATE TRIGGER test_trg BEFORE INSERT ON test
        FOR EACH ROW SET @sum = @sum + NEW.user_num;
  Query OK, 0 rows affected
  ```

* Create a trigger with multiple statements.

  ```sql
  obclient>CREATE TABLE test (user_id INT, user_num DECIMAL(10,2));
  Query OK, 0 rows affected

  obclient>DELIMITER #

  obclient>CREATE TRIGGER test_trg BEFORE UPDATE ON test
                FOR EACH ROW
                BEGIN
                IF NEW.user_num < 1 THEN
                SET NEW.user_num  = 1;
                ELSEIF NEW.user_num > 45 THEN
                SET NEW.user_num= 45;
              END IF;
              END;#
  Query OK, 0 rows affected

  obclient>DELIMITER ;
  ```

## Limitations on triggers

Triggers have the following limitations:

* Triggers can only be created on permanent tables; temporary tables do not support triggers.

* Triggers cannot use `CALL` statements to invoke stored procedures that return data to the client or use dynamic SQL. However, stored procedures or functions are allowed to return data to the trigger through parameters of the `OUT` or `INOUT` type.

* Triggers cannot contain segments that start or end transactions, such as `START TRANSACTION`, `COMMIT`, or `ROLLBACK`. However, rolling back to a savepoint is allowed because this does not terminate the transaction.

* Foreign keys do not activate triggers.

* Triggers do not allow return values; therefore, they cannot contain return statements. If you need to immediately stop a trigger, you must use the `LEAVE` statement.
