# Partition pruning

The partition pruning feature helps avoid accessing irrelevant partitions, significantly improving SQL execution efficiency. This topic describes the principles and applications of partition pruning.

When users access a partitioned table, they often only need to access a subset of the partitions. The optimization process by which the optimizer avoids accessing irrelevant partitions is called partition pruning. Partition pruning is an important optimization mechanism provided by partitioned tables, which can greatly improve SQL execution efficiency. You can leverage the feature of partition pruning by including partition location conditions in your queries to avoid accessing irrelevant data and optimize query performance.

Partition pruning itself is a complex process. The optimizer needs to extract relevant partition information based on the partitioning information of the user table and the conditions specified in the SQL. Since the conditions in SQL are often complex, the complexity of the extraction logic also increases. This process is performed by the Query Range sub-module in OceanSeek.

When users access a partitioned table, since all data where col1 is 1 resides in partition p1, we only need to access that partition, and there is no need to access partitions 0, 2, 3, or 4. As shown below:

```shell
obclient> CREATE TABLE tbl1(col1 INT, col2 INT) PARTITION BY HASH(col1) PARTITIONS 5;
```

```shell
obclient> SELECT * FROM tbl1 WHERE col1 = 1;
```

You can use `EXPLAIN` to view the execution plan and see the result of partition pruning:

```shell
obclient> EXPLAIN SELECT * FROM tbl1 WHERE col1 = 1;
```

The query result is as follows:


## Basic principles of partition pruning for primary partitions

### HASH and LIST partitions

Partition pruning works by evaluating the conditions in the `WHERE` clause to determine the value of the partitioning key, and then determining which partitions need to be accessed based on the result. If the partition condition is an expression that appears as a whole in an equality condition, partition pruning can also be performed.

The following example shows partition pruning when the partition condition is the expression `c1 + c2`, and this expression appears as a whole in an equality condition:

```shell
obclient> CREATE TABLE t1_h (c1 INT, c2 INT) PARTITION BY HASH(c1 + c2) PARTITIONS 5;
```

```shell
obclient> EXPLAIN SELECT * FROM t1_h WHERE c1 + c2 = 1;
```

The query result is as follows:

```shell
+------------------------------------------------------------------------------------+
| Query Plan                                                                         |
+------------------------------------------------------------------------------------+
| ===============================================                                    |

| Outputs & filters:                                                                 |

```

### RANGE partitions

You can determine the partitions that need to be accessed by finding the intersection between the range of the partitioning key in the `WHERE` clause and the partitioning ranges defined in the table.

For RANGE partitions:

* When the partition condition is a column, partition pruning is supported regardless of whether the query condition is an equality or inequality condition.

* When the partition condition is an expression and the query condition is an equality condition, partition pruning is supported.

For example, if the partitioning condition is the expression `c1` and the query condition is a non-equality condition `c1 < 150 and c1 > 100`, partition pruning can be performed. Example:

```shell
obclient> CREATE TABLE t1_r (c1 INT, c2 INT) PARTITION BY RANGE(c1)
    (PARTITION p0 VALUES LESS THAN(100),
     PARTITION p1 VALUES LESS THAN(200)
    );
```

```shell
obclient> EXPLAIN SELECT * FROM t1_r WHERE c1 < 150 and c1 > 110;
```

```shell
        , PARTITION M202007 VALUES LESS THAN(to_days('2020/08/01'))
        , PARTITION M202008 VALUES LESS THAN(to_days('2020/09/01'))
        , PARTITION M202009 VALUES LESS THAN(to_days('2020/10/01'))
        , PARTITION M202010 VALUES LESS THAN(to_days('2020/11/01'))
        , PARTITION M202011 VALUES LESS THAN(to_days('2020/12/01'))
        , PARTITION M202012 VALUES LESS THAN(to_days('2021/01/01'))
```

## Basic principles of subpartition pruning

For subpartitions, first determine the partitions to access based on the primary partitioning key, and then determine the subpartitions to access based on the subpartitioning key. Finally, determine all the physical subpartitions to access based on the product of the partitions and subpartitions.

In the following example, after calculation, the primary partition pruning result is p0, and the subpartition pruning result is sp0. Therefore, the physical partitions to access are p0sp0.

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p>In this example, the identifier of the physical partition to access is <code>p0sp0</code>, which is not the name of the subpartition. For a template-based subpartitioned table, the naming convention for subpartitions is <code>($part_name)s($subpart_name)</code>, for example, <code>p0ssp0</code>.</p>
</main>

```shell
obclient> CREATE TABLE tbl2_rr(col1 INT,col2 INT)
    PARTITION BY RANGE(col1)
    SUBPARTITION BY RANGE(col2)
    SUBPARTITION TEMPLATE
        (SUBPARTITION sp0 VALUES LESS THAN(1000),
         SUBPARTITION sp1 VALUES LESS THAN(2000)
        ) 
       (PARTITION p0 VALUES LESS THAN(100),
        PARTITION p1 VALUES LESS THAN(200)
       );
```

```shell
obclient> EXPLAIN SELECT * FROM tbl2_rr WHERE (col1 = 1 or col1 = 2) and (col2 > 101 and col2 < 150);
```

The query result is as follows:

```shell
+-----------------------------------------------------------------------------------------------------------------------------------------------------+
| Query Plan                                                                                                                                          |
```

In some scenarios, partition pruning may result in a certain degree of amplification, but the optimizer ensures that the pruned result is a superset of the data to be accessed, with no data loss occurring.
