# Delete expired data from OBKV-Table

OBKV-Table supports deletion of expired data. You can reduce storage space usage by defining, configuring, and triggering expiration policies. OBKV-Table also filters out expired data so that it is invisible to queries. This topic describes how to delete expired data by using commands or periodic tasks.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>The Time-To-Live (TTL) deletion feature is limited to the KV scenario in OceanBase AI Database and is disabled for SQL scenarios. Otherwise, it may cause unexpected accidental data deletion.</p>
</main>

## Usage instructions

The basic process for using the TTL feature is as follows:

1. Enable the TTL feature: Set `enable_kv_ttl = true` to enable TTL tasks for the tenant.
2. Define a TTL table: Specify the TTL attribute when you create a table, or add the TTL attribute to an existing table. You can modify or remove the TTL attribute.
3. Trigger deletion tasks: Trigger the deletion of expired data by using manual commands or periodic tasks. You can pause, resume, or cancel ongoing tasks.
4. View task status: Monitor task execution by using system views.

The following sections describe these steps in detail.

### Step 1: Enable the TTL feature

To enable the TTL feature, set the tenant-level parameter `enable_kv_ttl` to `true`.

```sql
ALTER SYSTEM SET enable_kv_ttl = true; -- Tenant-level parameter. The default value is false.
```

### Step 2: Define a TTL table

The TTL attribute of a table is defined in the `COLUMN_NAME + INTERVAL NUM TTL_UNIT` format, where:

* `COLUMN_NAME`: A column defined in the table, of the `TIMESTAMP` or `DATETIME` type.
* `+ INTERVAL`: A fixed keyword part.
* `NUM`: The integer that represents the expiration time.
* `TTL_UNIT`: Any of the units `SECOND`, `MINUTE`, `HOUR`, `DAY`, `MONTH`, and `YEAR`.

To create a TTL relational table named `t1` and set each row of data to expire after 12 hours, use the following statement:

```sql
CREATE TABLE t1 (
  a INT PRIMARY KEY, 
  b TIMESTAMP DEFAULT current_timestamp ON UPDATE current_timestamp)
TTL (b + INTERVAL 12 HOUR);
```

To change the TTL attribute of an existing table named `t1` to 1 day, use the following statement:

```sql
ALTER TABLE t1 TTL (b + INTERVAL 1 DAY);
```
  
To remove the TTL attribute from a table named `t1`, use the following statement:

```sql
ALTER TABLE t1 REMOVE TTL;
```

### Step 3: Trigger tasks

There are two ways to trigger TTL deletion tasks:

* Trigger by using management commands: Log in to the sys tenant to trigger TTL tasks for all tenants. In addition to triggering tasks, the sys tenant also supports pausing, resuming, and canceling ongoing TTL tasks.
* Trigger by using periodic tasks: Log in to the user tenant in which you want to perform the TTL task and set the daily trigger time for TTL tasks in that tenant.

TTL commands take effect only when executed in a user tenant or the sys tenant. When executed in a user tenant, they can manage only the TTL tasks of that tenant. When executed in the sys tenant, they can manage the TTL tasks of all tenants.

:::tab
tab Trigger by using a control command

Log in to the sys tenant and run the following command to trigger the TTL task for all tenants.

```sql
ALTER SYSTEM TRIGGER TTL;
```

To pause a running TTL task, run the following command:

```sql
ALTER SYSTEM SUSPEND TTL; 
```

To resume a paused TTL task, run the following command:

```sql
ALTER SYSTEM RESUME TTL; 
```

To cancel a running TTL task, run the following command:

```sql
ALTER SYSTEM CANCEL TTL; 
```

tab Trigger by using a periodic task

Log in to the tenant in which you want to perform the TTL task and run the following command to set the daily trigger time for TTL tasks in that tenant.

```sql
-- The default value is "", which indicates that periodic TTL tasks are not triggered.
ALTER SYSTEM SET kv_ttl_duty_duration = '[22:00:00, 24:00:00]';
```
:::

#### Task status description

TTL tasks are classified into tenant-level tasks and tablet-level tasks. Each type has different statuses, all of which can be queried in the `DBA_OB_KV_TTL_TASKS`, `CDB_OB_KV_TTL_TASKS`, `DBA_OB_KV_TTL_TASK_HISTORY`, and `CDB_OB_KV_TTL_TASK_HISTORY` views.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>For a tenant-level task, the <code>TABLE_NAME</code> is <code>NULL</code>, and both <code>TABLET_ID</code> and <code>TABLE_ID</code> are <code>-1</code>.</p>
</main>

Tablet-level task status:

| Task status | Description |
| --------- | ------ |
| PREPARED | The task is being prepared. The deletion of expired data has not started. |
| RUNNING | The task is running. The system is deleting expired data in this partition. |
| PENDING | The task is paused. It can be resumed by using commands. |
| CANCELED | The task is canceled. Execution cannot be resumed. |
| FINISHED | The task is finished. The record is moved to the historical table. |
| INVALID | The status is invalid. |

Tenant-level task status:

| Task status | Description |
| --------- | ------ |
| RS_TRIGGERING | The tenant-level TTL task is in progress. |
| RS_SUSPENDING | The tenant-level TTL task has been paused. |
| RS_CANCELING | The tenant-level TTL task has been canceled. |
| RS_MOVING | All TTL task records are being moved to the historical table. |
| INVALID | The status is invalid. |

### Set the historical task cleanup period (optional)

To avoid unnecessary storage space waste caused by the accumulation of historical TTL task records, you can set the retention period of these records by using the `kv_ttl_history_recycle_interval` parameter. The default value is 7 days.

For example, to automatically clean up historical TTL task records older than 30 days, use the following command:

```sql
ALTER SYSTEM SET kv_ttl_history_recycle_interval = '30d';
```

## Performance optimization

### Set parallelism

You can set the number of worker threads for TTL tasks by using the tenant-level parameter `ttl_thread_score`. The default value is 2.

For example, to change the number of worker threads for TTL tasks to 10:

```sql
ALTER SYSTEM SET ttl_thread_score = 10;
```

### Index scan

TTL supports index scans to improve the efficiency of expired data cleanup. By default, a TTL task must perform a primary key scan on the entire table and read each row of data to determine whether it has expired, which incurs high I/O overhead. If you create a local index on the expiration column and specify this index for the TTL task, the task scans only the index to determine whether data has expired, thereby reducing invalid data reads and significantly improving cleanup speed.

When you create a table, you can enable index scans by specifying an index name for the `TTLScanIndex` sub-parameter of `KV_ATTRIBUTES`. The syntax is as follows:

```sql
-- In practice, $index_name must be replaced with the index name.
CREATE TABLE table_name (
  ...
) TTL (ttl_column + INTERVAL ...) 
KV_ATTRIBUTES = '{"TTLScanIndex": "$index_name"}';
```

The following examples illustrate different scenarios:

:::tab
tab Local index containing the expired column

Example 1 demonstrates how a TTL task uses a local index containing the expired column to improve the efficiency of expired data cleanup:

```sql
CREATE TABLE test_ttl_with_index (
    a INT PRIMARY KEY, 
    b TIMESTAMP DEFAULT current_timestamp ON UPDATE current_timestamp,
    c VARCHAR(128),
    INDEX idx(b) LOCAL
) TTL (b + INTERVAL 12 HOUR) 
KV_ATTRIBUTES = '{"TTLScanIndex": "idx"}';
```

Description:

* The table uses column `b` as the TTL column, with an expiration time of 12 hours.
* The `TTLScanIndex` clause specifies to use index `idx` for scanning.
* Index `idx`, built on the TTL column `b`, can efficiently locate expired data.

tab Redundant local index storing the expired column

When you use the heap-organized table model of OBKV-Table, a unique index is usually created as the primary key. You can redundantly store the expiration column in this unique index, and the TTL task can use this index to scan expired data. Example 2 shows how to create a heap-organized table, redundantly store the expiration column in the unique index, and use that index to scan expired data:

```sql
CREATE TABLE test_ttl_storing_index (
    pagerowkey VARCHAR(1024) NOT NULL,
    request LONGTEXT DEFAULT NULL,
    rawpage LONGBLOB NOT NULL,
    pagecode VARCHAR(1024) NOT NULL,
    timestamp BIGINT(20) NOT NULL,
    _expire_ts TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    -- Redundantly store _expire_ts on the unique index u_idx_pagerowkey.
    UNIQUE INDEX u_idx_pagerowkey (pagerowkey) STORING (_expire_ts)
) ORGANIZATION = HEAP DEFAULT CHARSET = utf8mb4 
TTL (_expire_ts + INTERVAL 1 DAY) 
-- Scan expired data by using the unique index u_idx_pagerowkey.
KV_ATTRIBUTES = '{"TTLScanIndex": "u_idx_pagerowkey"}';
```

Description:

* With `STORING (_expire_ts)`, the TTL column `_expire_ts` is redundantly stored in the unique index `u_idx_pagerowkey`, which avoids querying the base table during the TTL task.

tab Local index created after table creation

Example 3 shows how to create a table first and then add index `idx3` by using `ALTER TABLE` and enable index scanning:

```sql
-- Create a table (index scanning is not used initially).
CREATE TABLE test_ttl_with_index_6 (
    a INT PRIMARY KEY, 
    b TIMESTAMP DEFAULT current_timestamp ON UPDATE current_timestamp,
    c VARCHAR(128),
    INDEX idx(b) LOCAL,
    INDEX idx2(c) LOCAL
) TTL (b + INTERVAL 12 HOUR);

-- Add an index and enable index scanning
ALTER TABLE test_ttl_with_index_6 ADD INDEX idx3(b, c);
ALTER TABLE test_ttl_with_index_6 SET KV_ATTRIBUTES = '{"TTLScanIndex": "idx3"}';
```

Description:

* Add index `idx3` using `ALTER TABLE` and enable index scanning.
* Specify to use index `idx3` for scanning expired data via `KV_ATTRIBUTES`.

:::

### TTL task throttling

TTL tasks continuously consume CPU and log write bandwidth during deletion. When tenant specifications are limited or the write load from the business front end is high, excessive TTL task throughput can affect the latency of front-end requests. To balance backend cleanup efficiency with online business stability, OBKV-Table provides TTL deletion throughput throttling.

By using the tenant-level parameter `kv_ttl_delete_max_ops`, you can limit the maximum total number of deletion operations per second for TTL tasks in a tenant. This parameter controls the upper limit of the deletion rate but does not guarantee a fixed rate. The actual throughput fluctuates with the system load, resource availability, and task distribution.

When throttling is disabled, TTL deletion tasks use available resources as much as possible. After throttling is enabled:

* The throttling value applies to the combined deletion throughput of all concurrent TTL subtasks in the current tenant.
* The maximum throughput a single subtask can obtain is related to its concurrency level [ttl_thread_score](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8100.ttl_thread_score.md) and is dynamically allocated among multiple concurrent tasks. For example, when `kv_ttl_delete_max_ops=1000` and `ttl_thread_score=2`, it means the TTL task has a concurrency of 2, with at most two TTL tasks running simultaneously. The maximum combined deletion throughput for all TTL tasks does not exceed 1000, and the average maximum deletion throughput per TTL task does not exceed 1000/2 = 500.
* In most scenarios, this can reduce the impact of TTL tasks on CPU and log write bandwidth, but it will correspondingly prolong the execution duration of TTL tasks.

We recommend that you enable or tighten throttling in the following scenarios:

* The tenant's resource specification is small, and the volume of data in the TTL table is large.
* During business peak hours, there is a high density of write/update requests from the front end, and latency jitter is sensitive.
* You need to prioritize front-end request latency while also considering backend cleanup efficiency.

You can evaluate the throttling effect and tune it gradually by checking the changes in the deletion count and task duration in [DBA_OB_KV_TTL_TASK_HISTORY](../../../700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/9300.o-dba_ob_kv_ttl_task_history-of-mysql-mode.md).

## Considerations

### Filter change logs

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This feature is supported in OceanBase AI Database V4.6.3 and later, and requires liboblog V4.6.3 or later.</p>
</main>

TTL tasks generate a large number of change logs (CLOGs) when deleting expired data. By default, CDC (liboblog) captures and consumes these change logs before synchronizing them to downstream components. In scenarios with a large volume of expired data, the massive amount of logs generated by TTL deletion imposes additional processing pressure and resource consumption on the CDC link.

To reduce the resource burden on the CDC link, you can enable TTL change log filtering on the CDC side (`filter_ttl_delete_log`). After this feature is enabled, change logs generated by TTL tasks are filtered by CDC and are no longer output downstream. By default, filtering is disabled, which means that TTL change logs are consumed by CDC as usual. Enabling filtering affects only the change logs of TTL tasks and does not change the execution logic of the TTL tasks.

### Visibility of expired data

If you operate on a record that has already expired by using the OBKV-Table API, the behavior is the same as if the record did not exist. For example, if an expired record with primary key `k1` exists in a relational table, inserting another record with primary key `k1` succeeds instead of reporting a primary key conflict.

| --- | --- | --- | --- | --- |

| insert | Y | 0 <br> OB_SUCCESS | 1 |  |
| delete | N | 0 <br> OB_SUCCESS | 1 |  |
| delete | Y | 0 <br> OB_SUCCESS | 0 |  |
| update | N | 0 <br> OB_SUCCESS | 1 |  |
| update | Y | 0 <br> OB_SUCCESS | 0 |  |

  <h4>Note</h4>
  <p>The SQL interface does not filter out expired data. Expired data remains visible until it is deleted by the TTL task.</p>
</main>

### Task execution mechanism

The TTL task is a low-priority background task, and immediate deletion of expired data is not guaranteed. To avoid a significant impact on system performance, the task automatically pauses under the following circumstances:

* Memory pressure: When the MemStore memory `MEMSTORE_USED` exceeds the threshold `FREEZE_TRIGGER`, the task pauses until the memory drops below the threshold. You can view memory usage by using the `GV$OB_MEMSTORE` view.
* Physical restore: For tenants undergoing physical restore, the TTL task pauses until the tenant completes the restore.

### Storage space release

Because OceanBase AI Database uses an LSM-tree architecture, a delete operation is essentially an append write (writing a delete marker). Therefore, after a TTL task deletes expired data, the actual storage space is not immediately released and may even temporarily increase. The final release of storage space depends on the major compaction process.

To ensure that storage space is released promptly, we recommend that you use TTL tasks together with major freeze:

1. Set the execution time window for the TTL task (`kv_ttl_duty_duration`).
2. Set the execution time of major freeze (`major_freeze_duty_time`) after the TTL task window.

In this way, major compaction is automatically triggered after the TTL task completes, which releases the storage space.

## Examples

### Complete TTL process

1. Enable the TTL feature

    ```sql
    ALTER SYSTEM SET enable_kv_ttl = true;
    ```

2. Create a TTL relational table and set each record to expire 10 seconds after the value of column `c`.

    ```sql
    CREATE TABLE ttl_table(a VARCHAR(1024) PRIMARY KEY,
      b VARCHAR(1024),
      c TIMESTAMP)
      TTL(c + INTERVAL 10 SECOND) PARTITION BY KEY(a) PARTITIONS 3;
    ```

3. Insert data. You can use OBKV-Table or SQL. To insert data by using OBKV-Table, see [Connect to a cluster by using the OBKV-Table Java client](../200.use-of-the-obkv-table-client/100.introduction-to-the-obkv-table-client-and-instructions-of-use.md).

    ```sql
    INSERT INTO ttl_table VALUES("k1", "hello obkv", now());
    INSERT INTO ttl_table VALUES("k2", "hello obkv", now());
    INSERT INTO ttl_table VALUES("k3", "hello obkv", now());
    ```

    ALTER SYSTEM TRIGGER TTL; -- Starting from 0:00, the system attempts to trigger the TTL task once.

### Set a rate limit for TTL tasks

1. Create a TTL relational table and set each record to expire 10 seconds after the value of column `c`.

    ```sql
    CREATE TABLE ttl_table(a VARCHAR(1024) PRIMARY KEY,
      b VARCHAR(1024),
      c TIMESTAMP)
      TTL(c + INTERVAL 10 SECOND) PARTITION BY KEY(a) PARTITIONS 3;
    ```

2. Insert data.

    ```sql
    INSERT INTO ttl_table VALUES("k1", "hello obkv", now());
    INSERT INTO ttl_table VALUES("k2", "hello obkv", now());
    INSERT INTO ttl_table VALUES("k3", "hello obkv", now());
    ```

3. Set a rate limit for the TTL task.

    ```sql
    ALTER SYSTEM SET kv_ttl_delete_max_ops = 1000;
    ```

4. Use a view to summarize and calculate the average throughput of TTL tasks deleting expired data over a period of time.

    ```sql
    SELECT
      TABLE_NAME,
      sum(TTL_DEL_CNT) + sum(MAX_VERSION_DEL_CNT) as total_ttl_del_cnt,
      min(START_TIME) as START_TIME,
      max(END_TIME) as END_TIME,
      CASE
        WHEN TIMESTAMPDIFF(MICROSECOND, min(START_TIME), max(END_TIME)) > 0
        THEN (sum(TTL_DEL_CNT) + sum(MAX_VERSION_DEL_CNT)) * 1000000.0 / TIMESTAMPDIFF(MICROSECOND, min(START_TIME), max(END_TIME))
        ELSE -1
      END as avg_ops
    FROM oceanbase.DBA_OB_KV_TTL_TASK_HISTORY
    WHERE STATUS = 'FINISHED'
      AND START_TIME >= '2026-03-19 15:49:00'  -- Replace with your start time.
      AND END_TIME <= '2026-03-19 16:10:00'    -- Replace with your end time.
    GROUP BY TABLE_NAME;  -- Group and count by table name.
    ```

5. View throttling information in logs.

    You can query TTL task throttling information from the observer logs. A TTL task prints throttling information every 30 seconds during execution.

    ```shell
    obclient> grep "TTL TASK DELETE RATE" -rn observer.log*
    ```
