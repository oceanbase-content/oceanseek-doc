# partition_index_dive_limit

## Overview

`partition_index_dive_limit` specifies the maximum number of partitions that the optimizer uses for row estimation at the storage layer.

## Privilege requirements

* Query variables

  * Global level

    The `sys` tenant and all user tenants can use the `SHOW VARIABLES` statement or the `information_schema.GLOBAL_VARIABLES` view to view the values of global system variables.

  * Session level

    Both the `sys` tenant and all user tenants can use the `SHOW VARIABLES` statement or the `information_schema.SESSION_VARIABLES` view to view the values of session system variables.

* Modify variables

  * Global effective

    * The `sys` tenant can directly modify the values of global system variables.

    * The user tenant must have the `SUPER` or `ALTER SYSTEM` privilege to modify the value of a global system variable.

  * Session takes effect

    The `sys` tenant and all user tenants can directly modify the values of session system variables for their own tenants.

## Usage instructions

Modify this variable to control the maximum number of partitions allowed during row estimation for storage layer optimization:

* When the number of partitions is less than this variable, all partitions are always selected for storage-layer row estimation.

* When the number of partitions is greater than or equal to this variable, randomly select `partition_index_dive_limit` partitions for row estimation at the storage layer and scale the estimation results proportionally.

* When the variable is `0`, all partitions are always selected for storage-layer row estimation.

* When both `range_index_dive_limit` and `partition_index_dive_limit` are negative, the storage-layer row estimation strategy reverts to the old version's behavior. It performs storage-layer row estimation only within the first 10 ranges of a single partition and does not sample beyond that.

* To disable row cardinality estimation at the storage layer, you can use the system variable `enable_storage_cardinality_estimation`.

The differences from MySQL are as follows:

* MySQL controls the number of equal-range indexes only through the system variable `eq_range_index_dive_limit` and does not limit the number of partitions. OceanBase AI Database uses this variable to limit the number of partitions for row estimation at the storage layer.

## Configuration example

1. Create partitioned table `t1` and insert data into it.

   ```shell
   obclient [test]> CREATE TABLE t1(c1 int, c2 int, index i1(c2)) PARTITION BY RANGE(c1) (PARTITION p0 VALUES LESS THAN(10), PARTITION p1 VALUES LESS THAN(20), PARTITION p2 VALUES LESS THAN(30));
   Query OK, 0 rows affected (0.457 sec)

   obclient [test]> INSERT INTO t1 SELECT 1,1 FROM table(generator(10));
   Query OK, 10 rows affected (0.130 sec)
   Records: 10  Duplicates: 0  Warnings: 0

   obclient [test]> INSERT INTO t1 SELECT 11,11 FROM table(generator(20));
   Query OK, 20 rows affected (0.008 sec)
   Records: 20  Duplicates: 0  Warnings: 0

   obclient [test]> INSERT INTO t1 SELECT 21,21 FROM table(generator(30));
   Query OK, 30 rows affected (0.009 sec)
   Records: 30  Duplicates: 0  Warnings: 0
   ```

2. View the execution plan. By default, storage-layer row estimation is used for all partitions that are not the first 10.

   ```shell
   obclient [test]> EXPLAIN SELECT c1 FROM t1 WHERE c2 IN (1,11,21);
   ```
