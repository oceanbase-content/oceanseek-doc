# Paginated query

## Optimize pagination scenarios

For scenarios where the query result set in the database is too large, it is recommended to use pagination queries.

### Paginate by unique key

Example: You can paginate by unique key when performing a pagination query.

```sql
obclient> select * from tb where c1 = 'xxx' and c2 = 'xxx' and id > 'xxx' limit 100;
```

Retain the last ID of every 100 rows as the condition value for the next 100 rows (create a composite index on c1, c2, and id).

  <main id="notice" type='notice'>
    <h4>Note</h4>
    <ol>
    <li>Applicable when data distribution is relatively even. If querying 100 rows per page costs scanning tens of thousands or hundreds of thousands of rows, performance will not meet expectations.</li>
    <li>Applicable for scenarios where pagination is performed solely based on id to fetch the entire table without other conditions, such as <code>select * from tb where id > '' limit 100;</code>.</li>
    </ol>
  </main>

### Paginate using delayed joins or subqueries

OceanBase Database does not skip the specified number of rows (offset) but fetches rows starting from offset + N and then returns the first N rows, discarding the remaining rows. Therefore, efficiency degrades significantly when the offset is very large. When encountering such scenarios in your application, consider controlling the total number of pages returned or rewriting SQL statements for page counts exceeding a specific threshold.

* Control the total number of pages returned.

  When implementing pagination logic in code, if the count is 0, return directly to avoid executing the subsequent pagination statement.

  Counterexample: In the "Service Market" application, a transaction could exceed 1,000 pages when paginated. When a user clicked the last page, the database would almost become paralyzed.

* Rewrite SQL for page counts exceeding a specific threshold.

  Example: First, quickly locate the range of IDs that need to be fetched, then perform the join:

  ```sql
  obclient> select a.name from a,(select id from a where id LIMIT 100000,20) b where a.id=b.id;
  ```

## Preserve order in pagination

Paginated order preservation ensures the stability of query pagination results. Specifically, it maintains a consistent order by first sorting the query results and then paginating them.

### Switch for Preserving Order in Paging

OceanBase AI Database provides two methods to control whether a query uses the order-preserving pagination feature: the hidden parameter `_preserve_order_forPagination` and the query hint `PRESERVE_ORDER_FOR_PAGINATION`.

For the above two control methods, OceanBase AI Database prefers to use hints. For example, if a tenant has the hidden parameter set to enabled and the query uses `/*+OPT_PARAM('PRESERVE_ORDER_FOR_PAGINATION', 'FALSE')*/`, the query will not enable the preserve-order feature for pagination.

#### Hide the parameter to control the pagination order-preserving feature

The `_preserve_order_for_pagination` hidden parameter is set at the tenant level and controls whether to enable or disable order preservation for pagination queries. The default behavior is disabled. When this parameter is enabled, the optimizer will actively add an `ORDER BY` clause to pagination queries to ensure that the data is output in order.

| Attribute | Description |
| ---------- | ---------- |
| Parameter type | Boolean |
| Default Value | False indicates that the pagination-preserving order feature is disabled by default. |
| Value range | False or True.<ul><li>True: Indicates that the page ordering feature is enabled.</li><li>False: Indicates that the page ordering feature is disabled.</li></ul> |
| Effective Mode | Effective Immediately |
| Level | Tenant-level |

**Example:**

To enable the ordered paging feature at the tenant level, use the following command:

```sql
ALTER SYSTEM SET _preserve_order_for_pagination = true;
```

#### Query hint to control the order-preserving pagination feature

To provide more fine-grained control, OceanBase AI Database also supports the query-level hint `PRESERVE_ORDER_FOR_PAGINATION`.

**Example:**

If you need to enable the ordered paging feature for a specific query.

```sql
SELECT /*+OPT_PARAM('PRESERVE_ORDER_FOR_PAGINATION', 'TRUE')*/ * FROM test_tbl1
LIMIT 10;
```

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This hint cannot be used to control whether the pagination-preserving order feature is enabled for a specific query block. It can only be used to control whether this feature is enabled for the entire query.</p>
</main>

### Paginated order preservation feature

After the order-preserving pagination feature is enabled, OceanBase AI Database will rewrite the query by adding an `ORDER BY` clause to ensure order preservation during pagination.

For example,

```sql
SELECT t1.c1, t1.c2 FROM t1, t2 WHERE t1.c1 = t2.c1 LIMIT 10,10;
```

For the query above, OceanBase AI Database first sorts the query results and then paginates the sorted results. The rewritten query is as follows:

```sql
SELECT t1.c1, t1.c2 FROM t1, t2 WHERE t1.c1 = t2.c1
ORDER BY t1.c1, t2.c2 LIMIT 10,10;
```

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>After enabling the Preserve Order feature for pagination, some queries may experience performance degradation due to the additional sorting computation introduced, which can reduce query execution efficiency.</p>
</main>

### Considerations on enabling the order-preserving pagination feature

After enabling the Preserve Order feature for pagination, the query output may differ from before because a sorting field has been added.

For other scenarios, the expected order of results may change. For example:

```sql
SELECT t2.c1, t2.c2
FROM (SELECT * from t1 ORDER BY t1.c1, t1.c2) V
  LEFT JOIN t2 ON V.c1 = t2.c1
LIMIT 10,10;
```

The user might expect this query to sort the results by table t1 before paginating them. However, no SQL semantics guarantee that the data must be sorted according to the results of table t1 before pagination. OceanBase AI Database adds the sorting fields t2.c1 and t2.c2 in the outermost layer. The execution result is sorted by the output fields (i.e., the fields of table t2) before pagination. The equivalent query is as follows:

```sql
SELECT t2.c1, t2.c2
FROM t1
  LEFT JOIN t2 ON t1.c1 = t2.c1
ORDER BY t2.c1, t2.c2
LIMIT 10,10;
```
