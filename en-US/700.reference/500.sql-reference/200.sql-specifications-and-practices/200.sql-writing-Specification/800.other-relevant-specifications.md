# Other related specifications

This topic describes other relevant specifications of OceanSeek.

## Guidelines for derivatives

After exporting with DataX, the data needs to be split into multiple small files, and then each file should be imported into the database individually. Keep each small file within 1 GB.

## Others

* The use of `force index`, `ignore index`, `straight_join`, and `SQL_no_cache` is prohibited in production environments.

* Compound statements such as `BEGIN...END`, `LOOP...END LOOP`, `REPEAT...UNTIL...END REPEAT`, and `WHILE...DO...END WHILE` are prohibited.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>Complex logic should be processed within the application to avoid writing complex SQL.</p>
  </main>

* Page search is strictly prohibited from being left-fuzzy or full-fuzzy.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>When using LIKE queries in SQL, always use the leftmost prefix match.</p>
  </main>

* A partitioned table must have a partitioning key. Scanning all tablets without a partitioning key is prohibited.

* Joining more than three tables is not recommended.

* In queries with multiple table joins, the driver table should be selected from those with a smaller result set.

* It is not recommended to write SQL statements with multiple levels of nested subqueries. Instead, it is recommended to rewrite them in the form of sequential table joins.

* Multi-table join operations are prohibited in `INSERT`, `UPDATE`, `DELETE`, and `REPLACE` statements.

* Use covered indexes for query operations to avoid table access.

* Reduce the use of custom functions, custom types, and stored procedures.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>Stored procedures are not conducive to troubleshooting, have poor portability, and from a performance perspective, their SQL typically involves multiple tables or complex judgments. Such statements consume significant resources and take a long time to execute, leading to degraded system concurrency. Furthermore, arithmetic operations within stored procedures can also cause severe performance issues.</p>
  </main>

* Reduce the use of non-logical condition queries such as `!= <> not`.

* Reduce the use of aggregate functions.

* We recommend that you avoid `IN` operations. Subqueries with `IN` should be rewritten as `JOIN` statements whenever possible. If `IN` operations are unavoidable, the number of constants in the `IN list` should be less than 100.

* We recommend that you use the `WHERE` or `LIMIT` clause in your statement. Otherwise, the entire table will be scanned.

* Controls the size of intermediate result sets.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>For queries with <code>distinct</code>, <code>order by</code>, and <code>group by</code> clauses, the intermediate result set is limited to within 10,000 rows. Sorting and grouping for large result sets exceeding 10,000 rows must be implemented on the application side.</p>
  </main>

* It is recommended that the number of `hash` partitions be a power of 2. Otherwise, data distribution among partitions may become uneven.

* We recommend that you do not use the full-text search feature.

* We recommend that you do not use the `EVENT` feature.

* Using or operating the OceanSeek database and test database is prohibited in the program. Creating a database named test or starting with test is also prohibited.

* Using user-defined variables is prohibited in OceanSeek.

* Avoid performing real-time statistical or summarization calculations on data in the database. These operations can be completed after data export using other tools or in an offline backup database.

* Avoid using `HAVING`.

  The `HAVING` clause filters data after the `GROUP BY` operation, whereas the `WHERE` clause filters data during the processing. Therefore, the `WHERE` clause can eliminate a significant amount of sorting and I/O time.
