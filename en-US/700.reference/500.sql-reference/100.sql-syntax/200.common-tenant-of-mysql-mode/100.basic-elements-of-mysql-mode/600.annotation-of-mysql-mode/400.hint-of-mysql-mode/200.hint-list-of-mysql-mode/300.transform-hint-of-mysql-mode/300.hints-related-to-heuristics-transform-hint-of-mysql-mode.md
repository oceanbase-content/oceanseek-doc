# Transform Hints of the Heuristics Type

In SQL queries, hints related to heuristics aim to quickly find a feasible solution, although it may not necessarily be the optimal one. Especially in complex queries, the database optimizer attempts to apply various rules and transformation strategies to find the most effective execution plan.

| Hint type | Description |
| ----------------------------------- | ------------------------- |
| `AGGR_FIRST_UNNEST ` | When a query contains aggregate subqueries (such as functions like AVG, SUM, or MAX), the `AGGR_FIRST_UNNEST` hint enables aggregate-first subquery optimization for aggregate subqueries, improving query rewrite. Its reverse operation is `NO_AGGR_FIRST_UNNEST`. |
| `NO_AGGR_FIRST_UNNEST` | Aggregate-first subquery optimization for aggregate subqueries is prohibited. Its reverse operation is `AGGR_FIRST_UNNEST`. |
| `COUNT_TO_EXISTS` | When enabled, the `COUNT` Subquery converted to `EXISTS` Subqueries are used for query rewriting. Its reverse operation is `NO_COUNT_TO_EXISTS`. |
| `NO_COUNT_TO_EXISTS` | Disable the setting to `COUNT` Subquery transformed into `EXISTS` Subqueries are used for query rewriting. Its reverse operation is `COUNT_TO_EXISTS`. |
| `ELIMINATE_JOIN` | Identify and remove unnecessary join operations from query execution plans. Its reverse operation is `NO_ELIMINATE_JOIN`. |
| `NO_ELIMINATE_JOIN` | Does not eliminate join operations from the query execution plan. Its inverse operation is `ELIMINATE_JOIN`. |
| `FAST_MINMAX` | Enables query rewriting for MIN or MAX optimization. Its reverse operation is `NO_FAST_MINMAX`. |
| `NO_FAST_MINMAX` | Disables query rewriting for MIN or MAX optimization. Its reverse operation is `FAST_MINMAX`. |
| `INLINE` | Indicates to the optimizer to expand the common table expression (CTE) and embed its query content directly into the main query. Its reverse operation is `MATERIALIZE`. |
| `MATERIALIZE` | Controls whether to extract a CTE or not to expand a CTE. Its reverse operation is `INLINE`. |
| `JOIN_FIRST_UNNEST` | When processing subqueries in aggregate functions, the query is rewritten by attempting to use join operations first. Its reverse operation is `NO_JOIN_FIRST_UNNEST`. |
| `NO_JOIN_FIRST_UNNEST` | Applying the join-first rewrite strategy is prohibited in aggregate subqueries. Its reverse operation is `JOIN_FIRST_UNNEST`. |
| `LEFT_TO_ANTI` | Enables the optimizer to attempt converting outer joins (OUTER JOIN) into anti joins (ANTI JOIN). Its reverse operation is `NO_LEFT_TO_ANTI`. |
| `NO_LEFT_TO_ANTI` | Disables the optimizer from attempting to convert outer joins (OUTER JOIN) into anti joins (ANTI JOIN). Its reverse operation is `LEFT_TO_ANTI`. |
| `OUTER_TO_INNER` | Enables the optimizer to rewrite outer joins (OUTER JOIN) into inner joins (INNER JOIN) whenever possible. Its reverse operation is `NO_OUTER_TO_INNER`. |
| `NO_OUTER_TO_INNER` | Disables the optimizer from rewriting outer joins (OUTER JOIN) into inner joins (INNER JOIN). Its reverse operation is `OUTER_TO_INNER`. |
| `PRED_DEDUCE` | Enables the optimizer to generate new predicates from existing ones and optimize query execution through derivation and pushdown. This kind of rewriting is typically effective for nested queries or join queries. Its reverse operation is `NO_PRED_DEDUCE`. |
| `NO_PRED_DEDUCE` | Disables the hint that prompts the optimizer to generate new predicates from existing ones. Its reverse operation is `PRED_DEDUCE`. |
| `PROJECT_PRUNE` | Informs the optimizer to prune unused projected columns in internal query blocks. This is particularly useful when the query involves multi-table joins and multi-level nested queries. Its reverse operation is `NO_PROJECT_PRUNE`. |
| `NO_PROJECT_PRUNE` | Prohibits the optimizer from pruning unused projected columns within internal query blocks. Its reverse operation is `PROJECT_PRUNE`. |
| `PULLUP_EXPR` | Enable expression pull-up rewriting. Its inverse operation is `NO_PULLUP_EXPR`. |
| `NO_PULLUP_EXPR` | Disables expression pull-up rewriting. Its reverse operation is `PULLUP_EXPR`. |
| `PUSH_LIMIT` | Enable pushdown rewrite for limits. Its reverse operation is `NO_PUSH_LIMIT`. |
| `NO_PUSH_LIMIT` | Disables limit pushdown optimization. Its reverse operation is `PUSH_LIMIT`. |
| `REPLACE_CONST` | Enables constant propagation optimization. Its reverse operation is `NO_REPLACE_CONST`. |
| `NO_REPLACE_CONST` | Disables constant propagation optimization. Its reverse operation is `REPLACE_CONST`. |
| `SIMPLIFY_DISTINCT` | Enables a series of DISTINCT-related query rewrite. Its reverse operation is `NO_SIMPLIFY_DISTINCT`. |
| `NO_SIMPLIFY_DISTINCT` | Prohibits a series of DISTINCT-related query rewrites. Its reverse operation is `SIMPLIFY_DISTINCT`. |
| `SIMPLIFY_EXPR` | Enables expression conversion for query rewriting. Its inverse operation is `NO_SIMPLIFY_EXPR`. |
| `NO_SIMPLIFY_EXPR` | Expression conversion-related query rewrite is prohibited. Its reverse operation is `SIMPLIFY_EXPR`. |
| `SIMPLIFY_GROUP_BY` | Enables query rewrite for Group By operations. Its reverse operation is `NO_SIMPLIFY_GROUP_BY`. |
| `NO_SIMPLIFY_GROUP_BY` | Group-by related query rewrite is prohibited. Its reverse operation is `SIMPLIFY_GROUP_BY`. |
| `SIMPLIFY_LIMIT` | Enables query rewrite for LIMIT operations. Its reverse operation is `NO_SIMPLIFY_LIMIT`. |
| `NO_SIMPLIFY_LIMIT` | Prohibit the rewrite of limit-related queries. Its reverse operation is `SIMPLIFY_LIMIT`. |
| `SIMPLIFY_ORDER_BY` | Enable query rewrite for Order By. Its reverse operation is `NO_SIMPLIFY_ORDER_BY`. |
| `NO_SIMPLIFY_ORDER_BY` | Order by-related query rewrite is prohibited. Its reverse operation is `SIMPLIFY_ORDER_BY`. |
| `SIMPLIFY_SET` | Enables query rewriting related to set queries. Its reverse operation is `NO_SIMPLIFY_SET`. |
| `NO_SIMPLIFY_SET` | Prohibit query rewriting related to set queries. Its inverse operation is `SIMPLIFY_SET`. |
| `SIMPLIFY_SUBQUERY` | Enables query rewrite for subqueries. Its reverse operation is `NO_SIMPLIFY_SUBQUERY`. |
| `NO_SIMPLIFY_SUBQUERY` | Subquery-based query rewrite is prohibited. Its reverse operation is `SIMPLIFY_SUBQUERY`. |
| `SIMPLIFY_WINFUNC` | Enables query rewrite for window functions. Its reverse operation is `NO_SIMPLIFY_WINFUNC`. |
| `NO_SIMPLIFY_WINFUNC` | Window function-related query rewrite is prohibited. Its reverse operation is `SIMPLIFY_WINFUNC`. |
| `UNNEST` | Enable subquery improvement for rewriting. Its reverse operation is `NO_UNNEST`. |
| `NO_UNNEST` | Disables subquery improvement for query rewriting. Its reverse operation is `UNNEST`. |

## `AGGR_FIRST_UNNEST` Hint

The `AGGR_FIRST_UNNEST` hint instructs the optimizer to prioritize independent aggregate evaluations over merging subqueries that evaluate aggregate functions into the main query when processing such subqueries. Its counterpart is the `NO_AGGR_FIRST_UNNEST` hint.

It should be noted that using the `AGGR_FIRST_UNNEST` or `NO_AGGR_FIRST_UNNEST` hint directly is not recommended, as they directly affect the query rewrite behavior for subquery elevation. Typically, if you need more fundamental control over the elevation behavior of subqueries, it is better to use the `UNNEST` or `NO_UNNEST` hint.

### Syntax

```sql
/*+ AGGR_FIRST_UNNEST [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the particular query block that should follow the hint.

### Examples

In the query example below, the `AGGR_FIRST_UNNEST` hint is used to enable aggregation for aggregate subqueries, prioritizing subquery elevation in query rewriting.

```sql
-- The hint prompts the optimizer to prioritize optimization of the AVG aggregate function in subqueries during query parsing.
SELECT * FROM t1
WHERE t1.c1 > (SELECT /*+ AGGR_FIRST_UNNEST */ AVG(d1)
               FROM t2
               WHERE t1.c2 = t2.d2);
```

## `NO_AGGR_FIRST_UNNEST` Hint

The `NO_AGGR_FIRST_UNNEST` hint prohibits the optimizer from prioritizing independent aggregate evaluations when processing subqueries that evaluate aggregate functions. Its counterpart is the `AGGR_FIRST_UNNEST` hint.

It should be noted that using the `AGGR_FIRST_UNNEST` or `NO_AGGR_FIRST_UNNEST` hint directly is not recommended, as they directly affect the query rewrite behavior for subquery elevation. Typically, if you need more fundamental control over the elevation behavior of subqueries, it is better to use the `UNNEST` or `NO_UNNEST` hint.

### Syntax

```sql
/*+ NO_AGGR_FIRST_UNNEST [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the particular query block that should follow the hint.

### Examples

In the query example below, the `NO_AGGR_FIRST_UNNEST` hint is used. This query will maintain its original aggregate subquery form and will not undergo query rewriting that prioritizes aggregation.

```sql
SELECT * FROM t1
WHERE t1.c1 > (SELECT /*+ NO_AGGR_FIRST_UNNEST */ AVG(d1)
               FROM t2
               WHERE t1.c2 = t2.d2);
```

## `COUNT_TO_EXISTS` Hint

The `COUNT_TO_EXISTS` hint enables the query rewrite that converts a `COUNT` subquery into an `EXISTS` subquery. Its counterpart is the `NO_COUNT_TO_EXISTS` hint.

### Syntax

```sql
/*+ COUNT_TO_EXISTS [ ( [ @ qb_name ] [ qb_name_list ] ) ] */
```

#### Parameters

- `qb_name_list`: Specifies to rewrite specific query block subqueries. If this parameter is omitted, the hint specifies to attempt rewriting all subqueries.

### Examples

In the query example below, the `COUNT_TO_EXISTS` hint is used to enable query rewrite for the `COUNT` subquery.

```sql
-- The `COUNT_TO_EXISTS` hint instructs the optimizer to convert an embedded `COUNT` subquery into a more efficient `EXISTS` form.
SELECT /*+ COUNT_TO_EXISTS */ * FROM t1
WHERE (SELECT COUNT(*) FROM t2 WHERE t2.c1 = t1.c2) > 0;
```

## `NO_COUNT_TO_EXISTS` Hint

The `COUNT_TO_EXISTS` hint disables query rewriting that converts `COUNT` subqueries into `EXISTS` subqueries. Its reverse operation is the `COUNT_TO_EXISTS` hint.

### Syntax

```sql
/*+ NO_COUNT_TO_EXISTS [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.
- `qb_name_list`: Specifies to disable rewriting for specific query block subqueries. If this parameter is omitted, the hint attempts to disable rewriting for all subqueries.

### Examples

In the query example below, the `NO_COUNT_TO_EXISTS` hint is used to prevent query rewriting for the `COUNT` subquery.

```sql
-- The `NO_COUNT_TO_EXISTS` hint keeps the original COUNT subquery unchanged and prevents conversion.
SELECT /*+ NO_COUNT_TO_EXISTS */ * FROM t1
WHERE (SELECT COUNT(*) FROM t2 WHERE t2.c1 = t1.c2) > 0;
```

## `ELIMINATE_JOIN` Hint

The `ELIMINATE_JOIN` hint controls query rewrite for join elimination. Its reverse operation is the `NO_ELIMINATE_JOIN` hint.

### Syntax

```sql
/*+ ELIMINATE_JOIN [ ( [ @ qb_name ] [ table_list ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.
- `table_list`: Optional. You can specify this parameter to eliminate joins for specific connected tables. If this parameter is omitted, the hint attempts to eliminate joins for all connected tables.

### Examples

In the query examples below, the `ELIMINATE_JOIN` hint is used to enable join elimination query rewrite.

```sql
--  Use the `ELIMINATE_JOIN` hint to find and eliminate the self-join in t1
CREATE TABLE t1(c1 INT PRIMARY KEY, c2 INT, c3 INT);
SELECT /*+ ELIMINATE_JOIN */ *
FROM t1 a, t1 b
WHERE a.c1 = b.c1;
```

## `NO_ELIMINATE_JOIN` Hint

The `NO_ELIMINATE_JOIN` hint disables query rewrite for join elimination and retains all specified joins. Its counterpart is the `ELIMINATE_JOIN` hint.

### Syntax

```sql
/*+ NO_ELIMINATE_JOIN [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.
- `table_list`: Optional. You can specify to disable connection elimination for specific connected tables. If this parameter is omitted, the hint specifies to attempt disabling connection elimination for all connected tables.

### Examples

In the query example below, `NO_ELIMINATE_JOIN` is used to prohibit query rewrite that eliminates joins.

```sql
-- Use the `NO_ELIMINATE_JOIN` hint to ensure join operations are retained.
SELECT /*+ NO_ELIMINATE_JOIN */ *
FROM t1 a, t1 b
WHERE a.c1 = b.c1;
```

## `FAST_MINMAX` Hint

The `FAST_MINMAX` hint enables query rewriting for queries using the `MIN` or `MAX` aggregate function. It instructs the database query optimizer to rewrite the query to retrieve the minimum and maximum values more efficiently. Its counterpart is the `NO_FAST_MINMAX` hint.


#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.

```sql
CREATE TABLE t1(c1 int primary key, c2 int, c3 int);
-- Use the `FAST_MINMAX` hint to execute the calculation of MAX(c1) in the fastest way.
SELECT /*+ FAST_MINMAX */ MAX(c1) FROM t1;
```

## `NO_FAST_MINMAX` Hint

The `NO_FAST_MINMAX` hint disables query rewrite for queries using the `MIN` or `MAX` aggregate function. Its counterpart is the `FAST_MINMAX` hint.

### Syntax

```sql
/*+ NO_FAST_MINMAX [ ( [ @ qb_name ] ) ] */
```

#### Parameters

```sql
CREATE TABLE t1(c1 int primary key, c2 int, c3 int);
-- The `FAST_MINMAX` hint is used to prevent the optimizer from accelerating the MAX(c1) operation.

```

## `INLINE` Hint

The `INLINE` hint is used to specify the expansion of a common table expression (CTE), integrating the CTE directly into the main query. Its reverse operation is the `MATERIALIZE` hint.

### Syntax

```sql
/*+ INLINE [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.

### Examples

For the following query, use the INLINE hint to specify the expansion of the CTE defined by `with cte`.

```sql
-- Use the `INLINE` hint to directly use the content of a subquery defined in a WITH CTE within the main query.
WITH cte AS (
  SELECT /*+INLINE*/ t1.*
  FROM t1
  JOIN t2 ON t1.c1 = t2.c1
)
SELECT * FROM cte A, cte B;
```

## `MATERIALIZE` Hint

The `MATERIALIZE` hint controls whether to extract a CTE or not to expand a CTE. Its reverse operation is the `INLINE` hint.

### Syntax

```sql
/*+ MATERIALIZE [ ( [ @ qb_name ] [ qb_name_list ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.
- `qb_name_list`: Optional. Disables CTE extraction for specific Query Blocks. When the parameter is missing, no CTE extraction is performed. It is recommended to use the `MATERIALIZE` hint only within a CTE defined by `with cte`.

### Examples

For the following query, use the `MATERIALIZE` hint to specify that the CTE defined by `with cte` should not be expanded, or to actively extract the CTE for the query blocks in the query.

```sql
-- Example 1: Materialize a single CTE
WITH cte AS (
  SELECT /*+MATERIALIZE*/ * FROM t1
)
SELECT * FROM cte;

-- Example 2: Materialize multiple query blocks
SELECT /*+MATERIALIZE(("SEL$2", "SEL$3"))*/ v1.*
FROM   (SELECT t1.* FROM t1 JOIN t2 ON t1.c1 = t2.c1) v1,
       (SELECT t1.* FROM t1 JOIN t2 ON t1.c1 = t2.c1) v2,
       (SELECT t1.* FROM t1 JOIN t2 ON t1.c1 = t2.c1) v3,
       (SELECT t1.* FROM t1 JOIN t2 ON t1.c1 = t2.c1) v4;
```

## `JOIN_FIRST_UNNEST` Hint

The `JOIN_FIRST_UNNEST` hint enables query rewrite optimization for aggregate subqueries, prioritizing join operations to optimize subqueries containing aggregate functions. Its reverse operation is the `NO_JOIN_FIRST_UNNEST` hint.

Note that it is not recommended to directly use the `JOIN_FIRST_UNNEST`/`NO_JOIN_FIRST_UNNEST` hints to intervene in subquery optimization. For such optimizations, it is recommended to use the `UNNEST`/`NO_UNNEST` hints.

### Syntax

```sql
/*+ JOIN_FIRST_UNNEST [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.

### Examples

In the query example below, the `JOIN_FIRST_UNNEST` hint is used to enable join-based subquery evaluation, prioritizing subquery evaluation for query rewrite.

```sql
-- When using the `JOIN_FIRST_UNNEST` hint to handle subqueries containing aggregate functions (such as AVG), the join operation in the execution plan is executed first.
SELECT * FROM t1
WHERE t1.c1 > (
  SELECT /*+ JOIN_FIRST_UNNEST */ AVG(d1)
  FROM t2
  WHERE t1.c2 = t2.d2
);
```

## `NO_JOIN_FIRST_UNNEST` Hint

The `NO_JOIN_FIRST_UNNEST` hint is used to prohibit the query optimizer from preferentially joining aggregate subqueries during query rewrite. When this hint is used, the query optimizer will not consider strategies that prioritize joining subqueries. Its reverse operation is the `JOIN_FIRST_UNNEST` hint.

It is important to note that it is not recommended to directly use the `JOIN_FIRST_UNNEST` or `NO_JOIN_FIRST_UNNEST` hint to intervene in subquery join promotion. Instead, it is recommended to use the `UNNEST` or `NO_UNNEST` hint for such purposes.

### Syntax

```sql
/*+ NO_JOIN_FIRST_UNNEST [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.

### Examples

In the query example below, the `NO_JOIN_FIRST_UNNEST` hint is used to prevent the query optimizer from preferentially joining aggregate subqueries during query rewrite.

```sql
-- The `NO_JOIN_FIRST_UNNEST` hint prevents the query optimizer from considering joining the subquery to the outer query.
SELECT * FROM t1
WHERE t1.c1 > (
  SELECT /*+ NO_JOIN_FIRST_UNNEST */ AVG(d1)
  FROM t2
  WHERE t1.c2 = t2.d2
);
```

## `LEFT_TO_ANTI` Hint

The `LEFT_TO_ANTI` hint enables the query optimizer to rewrite `OUTER JOIN` statements as `ANTI JOIN` statements. Its reverse operation is the `NO_LEFT_TO_ANTI` hint.

### Syntax

```sql
/*+ LEFT_TO_ANTI [ ( [ @ qb_name ] [ table_list ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.
- `table_list`: Optional. You can specify the right tables of specific `LEFT JOIN` operations for query rewrite. If this parameter is omitted, the hint specifies to attempt rewriting for all `OUTER JOIN` operations.

### Examples

In the query example below, the `LEFT_TO_ANTI` hint is used to enable the query optimizer to rewrite `OUTER JOIN` statements as `ANTI JOIN` statements.

```sql
CREATE TABLE t1(c1 int primary key, c2 int, c3 int);
CREATE TABLE t2(c1 int primary key, c2 int, c3 int);

SELECT /*+ LEFT_TO_ANTI(t2) */ * FROM t1 LEFT JOIN t2 ON t1.c2 = t2.c2 WHERE t2.c1 IS NULL;
```

## `NO_LEFT_TO_ANTI` Hint

The `NO_LEFT_TO_ANTI` hint disables the query optimizer from rewriting `OUTER JOIN` statements as `ANTI JOIN` statements. Its reverse operation is the `LEFT_TO_ANTI` hint.

### Syntax

```sql
/*+ NO_LEFT_TO_ANTI [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which this hint applies.

### Examples

In the query example below, `NO_LEFT_TO_ANTI` is used to prohibit the query rewrite that converts an `OUTER JOIN` into an `ANTI JOIN`.

```sql
CREATE TABLE t1(c1 int primary key, c2 int, c3 int);
CREATE TABLE t2(c1 int primary key, c2 int, c3 int);

SELECT /*+ NO_LEFT_TO_ANTI */ * FROM t1
LEFT JOIN t2 ON t1.c2 = t2.c2
WHERE t2.c1 IS NULL;
```

## `OUTER_TO_INNER` Hint

The `OUTER_TO_INNER` hint controls the query rewrite of outer joins to inner joins, converting `LEFT OUTER JOIN` or `RIGHT OUTER JOIN` into a more efficient `INNER JOIN`. Its reverse operation is the `NO_OUTER_TO_INNER` hint.

### Syntax

```sql
/*+ OUTER_TO_INNER [ ( [ @ qb_name ] ) ] */
```

#### Parameter description

- `@qb_name`: Optional. Specifies the query block to which this hint applies.

### Examples

In the query example below, `OUTER_TO_INNER` is used to enable rewrite of outer join queries into inner join queries.

```sql
-- The filter condition `b.c1 > 0` applies only to table b. It implicitly excludes the possibility of null values in the right table during the outer join, allowing this outer join operation to be considered an inner join.
SELECT /*+ OUTER_TO_INNER */ *
FROM t1 a
LEFT JOIN t1 b ON a.c2 = b.c2
WHERE b.c1 > 0;
```

## `NO_OUTER_TO_INNER` Hint

The `NO_OUTER_TO_INNER` hint disables query rewrite from outer join to inner join, meaning the query optimizer will not convert an outer join into an inner join. Its reverse operation is the `OUTER_TO_INNER` hint.

### Syntax

```sql
/*+ NO_OUTER_TO_INNER [ ( [ @ qb_name ] ) ] */
```

#### Parameter description

- `@qb_name`: Optional. Specifies the query block to which this hint is applied.

### Examples

In the query example below, `NO_OUTER_TO_INNER` is used to prohibit the query rewrite from an outer join to an inner join.

```sql
-- The conditions in the `WHERE` clause may imply an inner join. The `NO_OUTER_TO_INNER` hint ensures that the logic of the outer join is preserved.
SELECT /*+ NO_OUTER_TO_INNER */ *
FROM t1 a
LEFT JOIN t1 b ON a.c2 = b.c2
WHERE b.c1 > 0;
```

## `PRED_DEDUCE` Hint

The `PRED_DEDUCE` hint controls predicate deduction query rewrite, using existing predicates to derive new ones or push down predicates. This kind of rewrite is typically effective for nested queries or join queries. Its reverse operation is the `NO_PRED_DEDUCE` hint.

### Syntax

```sql
/*+ PRED_DEDUCE [ ( [ @ qb_name ] ) ] */
```

#### Parameter description

- `@qb_name`: Optional. Specifies the query block to which this hint applies.

### Examples

In the query example below, `PRED_DEDUCE` is used to enable the outer Query Block to participate in predicate deduction for query rewriting.

```sql
-- Enable Predicate Derivation to Rewrite Outer Queries
select /*+pred_deduce*/ c1
from (
  -- Disable subquery merging to ensure the effectiveness of the NO.Merge hint.
  select /*+no_merge*/ t1.* from t1
)
where c1 = 3;
```

## `NO_PRED_DEDUCE` Hint

The `NO_PRED_DEDUCE` hint disables the optimizer from generating new predicates from existing ones. Its counterpart is the `PRED_DEDUCE` hint.

### Syntax

```sql
/*+ NO_PRED_DEDUCE [ ( [ @ qb_name ] ) ] */
```

#### Parameter description

- `@qb_name`: Optional. Specifies the query block to which this hint applies.

### Examples

In the query example below, `NO_PRED_DEDUCE` is used to prevent the outer Query Block from participating in predicate deduction for query rewrite.

```sql
-- Disable Predicate Derivation to Rewrite Outer Queries
select /*+no_pred_deduce*/ c1
from (
  -- Disable subquery merging to ensure the effectiveness of the NO.Merge hint.
  select /*+no_merge*/ t1.* from t1
)
where c1 = 3;
```

## `PROJECT_PRUNE` Hint

The `PROJECT_PRUNE` hint optimizes the query execution process by effectively reducing the amount of data processed during queries, especially for large datasets and complex queries. It reduces the output of query blocks by pruning unnecessary columns. This query rewrite technique, known as project pruning, helps improve query efficiency, particularly when processing inner query blocks. Its reverse operation is the `NO_Project_PRUNE` hint.

### Syntax

```sql
/*+ PROJECT_PRUNE [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies which specific query block should apply the `PROJECT_PRUNE` hint, providing finer-grained control over query optimization.

### Examples

In the query example below, the `PROJECT_PRUNE` clause is used to invoke the project pruning rewrite mechanism. This enables the optimizer to prune all output columns in the inline view except for column C1.

```sql
select c1 from (select /*+no_merge project_prune*/ t1.* from t1);
```

## `NO_PROJECT_PRUNE` Hint

The `NO_Project_PRUNE` hint disables query rewrite operations for project pruning. Project pruning automatically prunes unused output columns during query optimization. When it is necessary to retain these columns due to specific performance or functional requirements, the `NOoproject_PRUNE` hint is particularly important. Its counterpart is the `PROJECT_PRUNE` hint.

### Syntax

```sql
/*+ NO_PROJECT_PRUNE [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies which query block should avoid application project pruning. When multiple query blocks exist, this provides more precise control.

### Examples

In the query example below, `NO_Project_PRUNE` is used to disable project pruning. This setting ensures that all output columns except for `c1` are retained in the result of the inline view, even if they are not needed.

```sql
select c1 from (select /*+no_merge no_project_prune*/ t1.* from t1);
```

## `PULLUP_EXPR` Hint

The `PULLUP_EXPR` hint enables the optimizer to pull up subquery expressions to the parent query level. Its counterpart is the `NO_PULLUP_expr` hint.

### Syntax

```sql
/*+ PULLUP_EXPR [ ( [ @ qb_name ] ) ] */
```

#### Parameter description

- `@qb_name`: Optional. Specifies the query block to which this hint is applied.

### Examples

In the query example below, `PULLUP_expr` is used to enable expression pull-up rewrite. After expression pull-up query rewrite is triggered, the `SELECT` subquery in the inline view is pulled up to the outer query.

```sql
-- Assume that t1 is the existing table structure.
CREATE TABLE t1(c1 INT PRIMARY KEY, c2 INT, c3 INT);

-- Execute a query with the PULLUP_expr hint
```
