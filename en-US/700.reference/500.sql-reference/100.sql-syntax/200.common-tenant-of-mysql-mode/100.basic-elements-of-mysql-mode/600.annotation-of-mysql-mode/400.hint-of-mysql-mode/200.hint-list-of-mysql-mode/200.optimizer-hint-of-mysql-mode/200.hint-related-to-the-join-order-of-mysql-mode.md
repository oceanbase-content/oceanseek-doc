# Join Order Hint under Optimized Hint Type

In SQL queries, the hints related to the join order include the `ORDERED` hint and the `LEADING` hint.

| Hint type | Description |
| ----------- | ------------------------------------------------- |
| `LEADING` | Joins are performed in the order of tables specified in the hint. When only some tables in the `FROM` clause are specified, the specified tables act as driving tables and are joined with other tables. |
| `ORDERED` | The table join order is determined by the order of the `FROM` clause. |

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>We recommend that you use the <code>LEADING</code> hint to explicitly specify the desired join order. This is because the <code>ORDERED</code> hint can only specify a particular join order, and this order may be affected by query rewrite.</p>
</main>

## `LEADING` Hint

The `LEADING` hint instructs the optimizer to join tables in a specified order, offering greater flexibility than the `ORDERED` hint. The `LEADING` hint allows you to explicitly define any legal expected join order. In contrast, the `ORDERED` hint can only specify a particular join order, and this order is subject to rewrite. It is recommended to use the `LEADING` hint to directly and explicitly specify the desired join order.

### Syntax

```sql
/*+ LEADING ( [ @queryblock ] tablespec [ tablespec ]...  ) */
```

### Usage instructions and considerations

The `LEADING` hint takes effect only when the specified table name exactly matches a table name that appears in the query.

* If the `table_name` specified in the hint does not exist, the `LEADING` hint becomes invalid.

* If a duplicate table is found in the hint, the `LEADING` hint becomes invalid.

* If a table cannot be found during the join by the optimizer, the join order specified for that table and subsequent tables becomes invalid. The order specified for tables preceding it remains valid.

* The `LEADING` hint is invalid if the specified tables cannot be joined in the specified order due to dependencies in the join graph.

* If two or more conflicting `LEADING` hints are specified, the `LEADING` hint becomes invalid.

* If you specify the `ORDERED` hint, it overrides all `LEADING` hints.

### Examples

```SQL
SELECT /*+ LEADING(e j) */ *
FROM employees e, departments d, job_history j
WHERE e.department_id = d.department_id
  AND e.hire_date = j.start_date;
```

## `ORDERED` Hint

The default join order is used in the query. The `ORDERED` hint has a higher priority than the `LEADING` hint. When the `ORDERED` hint is present, the `LEADING` hint becomes invalid.
When the `ORDERED` hint is used, it is not displayed in the OUTLINE DATA; instead, the complete `LEADING` hint is printed.

### Syntax

```sql
/*+ ORDERED */
```

### Examples

Assume we have three tables, `employees`, `departments`, and `job_history`, that need to be joined:

```sql
SELECT /*+ ORDERED */ e.employee_id, d.department_name, j.job_id
FROM employees e, departments d, job_history j
WHERE e.department_id = d.department_id
  AND e.hire_date = j.start_date;
```

In this example, the database will join these three tables in the order of `employees`, `departments`, and `job_history`.
