# Subquery hint under Optimized hint type

| Hint type | Description |
| -------------------------------- | --------------------------------------------------------- |
| PQ_SUBQUERY | Provides fine-grained control over the behavior of subqueries in parallel processing. |
| PUSH_SUBQ | Used to instruct the optimizer to execute subqueries that have not been rewritten as joins as early as possible. |
| NO_PUSH_SUBQ | Yes `PUSH_SUBQ` is the reverse operation of. It is used by the optimizer to place subqueries that have not been rewritten as joins at the end of the execution plan. |

## PQ_SUBQUERY Hint

The `PQ_SUBQUERY` hint provides fine-grained control over the behavior of subqueries in parallel processing, instructing the optimizer how to handle subqueries in a parallel query (PQ) environment, especially when distributed data distribution is involved.

The `PQ_SUBQUERY` hint supports two main control methods: approximate control and precise control.

### Inexact control methods

#### Syntax

```sql
/*+ PQ_SUBQUERY ([ @qb_name ] [table_list] [op_order_no] sub_qb_name_list method_list) */
```

#### Parameter description

- `@qb_name`: Optional. Specifies an alias for the current query block.
- `table_list`: Optional. Specifies the list represented, which is used only in the subplan filter method allocated during connection establishment.
- `op_order_no`: The sequence number of the operation node.
- `sub_qb_name_list`: The list of aliases for the subquery blocks.
- `method_list`: The distributed data distribution method. The specific methods are as follows:
  - `DIST_BASIC_METHOD`: no specific method is specified.
  - `DIST_PARTITION_WISE`: Distribute data by partition, using the `NONE NONE` method.
  - `DIST_PULL_TO_LOCAL`: Pull data to the local device using the `LOCAL LOCAL` method.
  - `DIST_PARTITION_NONE`: Partition processing is performed, but no subsequent method is specified. In this case, `PARTITION NONE` is used.
  - `DIST_NONE_ALL`: Do not partition the data. Broadcast the data to all nodes by using `NONE ALL`.

### Examples

```sql
PQ_SUBQUERY(@SEL$1 0 SEL$1 PARTITION NONE) -- Can be abbreviated as PQ_SUBQUERY(SEL$1)
PQ_SUBQUERY(@SEL$1 1 SEL$2 PARTITION NONE)

CREATE TABLE t1(c1 INT, c2 INT, c3 INT, c4 INT)
    PARTITION BY HASH(c1) PARTITIONS 10;

EXPLAIN
SELECT
  (SELECT t_inner.c1 FROM t1 t_inner WHERE t_inner.c1 = t_outer.c3) AS a
FROM t1 t_outer
ORDER BY c3;
```

### Precise control method

#### Syntax

```sql
/*+ PQ_SUBQUERY ([ @qb_name ] win_group ...) */
```

#### Parameter description

- `win_group`: A tuple that declares the grouping for window functions and their internal behavior (index list).
  - `dist_method`: Specifies the distributed execution method. Valid values are the same as above.
  - `PARTITION_SORT`: Specifies whether to apply the partition sort algorithm when using hash distributed execution (`HASH`) or no distributed execution (`NONE`). The default is not to use it.
  - `PUSHDOWN`: Specifies whether to push down window functions during hash distribution execution.

#### Examples

```sql
PQ_SUBQUERY (@SEL$1 (t_a t_b t_c) 0 SEL$2 PARTITION NONE)
-- Can be omitted as PQ_SUBQUERY ((t_a t_b t_c) SEL$2 PARTITION NONE)

EXPLAIN
SELECT /*+ PQ_SUBQUERY (@SEL$1 (t_a, t_b, t_c) 0 SEL$2 PARTITION NONE) */
  t_a.c1 AS a_c1,
  t_b.c1 AS b_c1,
  t_c.c1 AS c_c1,
  t_d.c1 AS d_c1
FROM t1 t_a
LEFT JOIN t1 t_b ON t_a.c3 = t_b.c4
INNER JOIN t1 t_c ON t_a.c1 = t_c.c1
RIGHT JOIN t1 t_d ON t_a.c3 = t_d.c4
WHERE t_a.c1 = t_d.c3
  AND t_c.c2 + (SELECT c4 FROM t1 WHERE c1 = t_c.c3 AND c2 = t_a.c2 AND c3 = t_b.c1) = t_a.c3;
```

## PUSH_SUBQ Hint

The `PUSH_SUBQ` hint instructs the optimizer to execute subqueries that have not been rewritten as joins as early as possible. Typically, if not rewritten as joins, these subqueries are evaluated after all table join calculations in the execution plan. If a subquery has a low computation cost and can filter out a large amount of data, executing it in advance may improve plan performance. Note that this hint becomes invalid if the subquery is rewritten as a join using the `/+unnest/` operator. Applicable scenarios include:

* Subqueries have low execution overhead but can quickly filter out large amounts of data.
* You should use the results of subqueries as early as possible to narrow down the data range.

**Syntax:**

```sql
/*+ PUSH_SUBQ[(@qb_name)] */
```

Parameter description:

* `@qb_name`: Optional. Specifies an alias for the subquery (for more information, see **QB_NAME parameter** above). This is used to explicitly identify the object affected by the hint. If omitted, the hint applies by default to the subquery where it is located.

**Example:**

In the query, use the `PUSH_SUBQ` hint to instruct the optimizer to execute the subquery as early as possible, thereby filtering data from the `tbl1` table in advance.

```sql
SELECT /*+ PUSH_SUBQ(@"SEL$2") */ *
FROM tbl1, tbl2
WHERE tbl1.col1 = (SELECT MAX(tbl3.col1)
                   FROM tbl3
                   WHERE tbl3.col2 = tbl2.col2);
```

## NO_PUSH_SUBQ Hint

The `NO_PUSH_SUBQ` hint is the reverse operation of `PUSH_SUBQ`, instructing the optimizer to execute subqueries that have not been rewritten as joins last. It is suitable when a subquery has a high cost or cannot significantly reduce the number of rows. Application scenarios include:

* The subquery has a high execution cost, or its result has little impact on the data volume.
* The execution of subqueries should be delayed until other filtering conditions take effect, to reduce the amount of input data for them.

**Syntax:**

```sql
/*+ NO_PUSH_SUBQ[(@qb_name)] */
```

Parameter description:

* `@qb_name`: Optional. Specifies an alias for the subquery.

**Example:**

Use the `NO_PUSH_SUBQ` hint in queries to instruct the optimizer to push subqueries until the last possible execution moment.

```sql
SELECT /*+ NO_PUSH_SUBQ */ *
FROM tbl1, tbl2
WHERE tbl1.col1 = (SELECT MAX(tbl3.col1)
                   FROM tbl3
                   WHERE tbl3.col2 = tbl2.col2);
```
