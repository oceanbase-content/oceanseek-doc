# CREATE INDEX

## Purpose

This statement is used to create an index. An index is a structure created on a table to sort the values of one or more columns in a database table. Its main purpose is to improve query speed and reduce the performance overhead of the database system.

The current version of OceanBase AI Database supports unique indexes and non-unique indexes. When creating an index, you can use `STORING(column_name,...)` to specify redundant columns on the index table. In addition to the columns explicitly specified by users, the index table automatically includes the primary key columns of the primary key table (or the Hidden PK if no primary key table exists). Storing additional columns in the index provides the database optimizer with more options.

## Limitations and considerations

* If all index columns in a table are dropped, the created index becomes invalid.
* Full-text indexes are only supported on columns of the `CHAR`, `VARCHAR`, and `TEXT` types.
* Search indexes are supported on JSON, single-level arrays, and various scalar type columns. For a complete list, see [Data types supported by search indexes](#Data types supported by search indexes).
* Vector indexes must be created on `VECTOR` columns (for dense vector indexes), `SPARSEVECTOR` columns (for sparse vector indexes), or `VARCHAR` columns (for semantic indexes). For more information, see [Data types supported by vector indexes](#Data types supported by vector indexes).
* The current version only supports creating local (`LOCAL`) full-text or search indexes.
* You cannot specify the `UNIQUE` keyword when creating a full-text index.
* To create a full-text index involving multiple columns, ensure these columns have the same character set.
* You can specify the tokenizer only when creating a full-text index using `WITH PARSER {SPACE | NGRAM | BENG | IK | NGRAM2 | analyzer}`.

## Privilege requirements

To execute the `CREATE INDEX` statement to create an index, the current user must have at least the INDEX privilege on the corresponding object. For more information about OceanBase AI database privileges, see [Permission classification](../../../../../600.manage/500.security-and-permissions/300.access-control/200.user-and-permission/200.permission-of-mysql-mode/100.permission-classification-of-mysql.md).

### Syntax of Search Index

When `index_type` is specified as `SEARCH`, you can use the following syntax to create a search index:

```sql
CREATE [ASYNC] SEARCH INDEX index_name ON table_name (
    search_index_column
    [, search_index_column ...]
) [LOCAL];

search_index_column:
    column_name [WITH (search_col_option_list)]

search_col_option_list:
    [INCLUDE_PATHS = ('path1'[, 'path2']...)]
    [| EXCLUDE_PATHS = ('path1'[, 'path2']...)]
    [| INCLUDE_TYPES = (type1[, type2]...)]
    [| NESTED_PATHS = ('path1'[, 'path2']...)]
```

In addition to `CREATE INDEX`, you can also create a search index using the `CREATE TABLE` or `ALTER TABLE` statement.

In both methods, the semantics of `search_index_column` and `WITH` are consistent with those of `CREATE SEARCH INDEX`. For detailed syntax, see [CREATE TABLE](2600.create-table-of-mysql-mode.md) and [ALTER TABLE](1600.alter-table-of-mysql-mode.md).

### Syntax of Vector Index

When `index_type` is specified as `VECTOR`, you can use the following syntax to create a vector index:

```sql
CREATE [/*+ parallel($value) */] VECTOR INDEX index_name
    ON table_name (column_name)
    WITH (vector_index_option [, vector_index_option ...]);
```

For general parameters of `vector_index_option` (such as `distance`, `type`, `lib`, `m`, and `ef_construction`), see vector index documentation such as [HNSW series indexes](../../../../../400.ai-search/300.vector-search/200.vector-index/300.dense-vector-index/200.hnsw-index.md).

When creating a semantic index on a `VARCHAR` column, you can also specify semantic index parameters using the `WITH` clause. For complete descriptions, limitations, and examples, see [Semantic search](../../../../../400.ai-search/400.semantic-search.md).

| **Parameter** | **Description** | **Value range** |

| search_index_column | You can search by specifying one or more index columns. Each column can be specified using the `WITH (...)` Specify the column-level path and type options. |  |

By default, the full path is used for index construction. Two path configurations are supported:<ul><li>A simple deterministic path. For example, <code>$.key</code> and <code>$.a</code>. In this case, indexes are generated only for scalar and array data under <code>$.key</code> and <code>$.a</code>; paths such as <code>$.a.b</code> do not generate indexes.</li><li>A prefix-matching path. If an outer field is itself an array and there are arrays within it (for example, a `comments` array contains a `replies` array), they must be declared together, for example, <code>('$.comments', '$.comments.replies')</code>. For example, even if `EXCLUDE_PATHS` excludes `$.comments.text`, after declaring `NESTED_PATHS = ('$.comments')`, all fields under the `comments` path (including `text`) will still be forced to have an index:

```sql
CREATE SEARCH INDEX idx_nested ON movie_rating (
  j1 WITH (
    EXCLUDE_PATHS = ('$.comments.text'),
    NESTED_PATHS = ('$.comments')
  )
);
```

#### NESTED_PATHS path matching rules

When declaring `NESTED_PATHS`, the system compares the actual structure of each layer in the JSON with the specified paths.

The path notation is consistent with common JSON paths: `$` denotes the starting point of the entire JSON, and member paths are written layer by layer using dots, for example, `$.comments.replies`. The last segment of the path is the name of the last member (in the example above, `replies`).

Basic rules:

* The value at the end of the path must be a JSON array (for example, `[{...}, {...}]`) and cannot be a single object (for example, `{...}`).
* OceanBase Database AI distinguishes between arrays and objects. A level that is not specified as an array path in the declaration will not be matched as an array. Taking `$.comments.replies` as an example:
  * When only this one is specified, the system splits the path into: `comments` (the middle field) → `replies` (the last segment of the path). Only the last segment `replies` meets the array requirement (indicating that you need
  must be written as an array); the preceding `comments` field is required for a single object.
  * Therefore, `{"comments":{"replies":[...]}}` matches, but `{"comments":[{"replies":[...]}]}` does not — here `comments` is already an array, which conflicts with interpreting it as an object.
  * If the `comments` field in the data is already a list of comments (an array), you must declare both `$.comments` and `$.comments.replies`.

Quick reference for the three declarations:

| **Declaration** | **Summary** |
| --- | --- |
| `$.comments` | `comments` must be an array |
| Only `$.comments.replies` | `comments` must be an object, `replies` must be an array |
| `('$.comments', '$.comments.replies')` | Overwriteable `comments` for arrays, and the elements also contain `replies` Common formats such as arrays |

### sort_column_key

* `column_name [(integer)] [ASC] [ID id]`: specifies a column name as the sort key.

  * `column_name`: the name of the column to be sorted.
  * `integer`: Optional. Specifies the maximum length of the sort key.

  * `ASC`: Optional. Specifies ascending order. DESC order is not supported.

  * `ID id`: Optional. The ID of the key used for sorting.

  For example, to create an index named `index3` on the table named `t3` and specify that the index sorts in ascending order on column `c1`.

  ```sql
  CREATE INDEX index3 ON t3 (c1 ASC);
  ```

* `(index_expr) [ASC] [ID id]`: Specifies an index expression as the sort key. The index expression can be defined using expressions or functions. It can include the following options:

  * `(index_expr)`: Indicates an index expression, which can be a boolean expression, such as `c1=c1`. Creating a function-based index on a generated column is prohibited in the current version of OceanBase AI Database. For expressions supported by function-based indexes, see [List of system functions supported for function-based indexes](../../../../300.database-object-management/500.manage-indexes-of-mysql-mode/500.function-index-list-of-supported-functions-of-mysql-mode.md).

  * `ASC`: Optional. Specifies ascending order. Descending order (DESC) is not supported.

  * `ID id`: Optional. The ID of the key used for sorting.

  For example, to create an index named `index4` on the table named `t4`, specify `c1+c2` as the index expression, and sort in ascending order.

  ```sql
  CREATE INDEX index4 ON t4 ((c1 + c2) ASC);
  ```

You can specify multiple columns for sorting when creating an index. Separate multiple sort columns with commas (`,`). For example, to create an index named `index5` on the table named `t5` and specify using column `c1` and the expression `c2+c3` as the sort keys for the index.

```sql
CREATE INDEX index5 ON t5 (c1, (c2+c3));
```

### tokenizer_option

* `SPACE`: The default value, which indicates that the text is segmented by spaces. The following attributes can be specified:

  |        Attribute      | Value range |
  |------------------|---------|
  | min_token_size   | [1, 16] |
  | max_token_size   | [10, 84]|

* `NGRAM`: Indicates the word segmentation method based on N-gram (Chinese). The following attributes can be specified:

  |        Attribute      | Value range |
  |------------------|---------|
  | ngram_token_size | [1, 10] |

* `NGRAM2`: Indicates that the text is split into consecutive characters within the range of `min_ngram_size` to `max_ngram_size`. The following attributes can be specified:

  |        Attribute      | Value range |
  |------------------|---------|
  | min_ngram_size   | [1, 16] |
  | max_ngram_size   | [1, 16] |

* `BENG`: The word segmentation method based on Beng. You can specify the following attributes:

  |        Attribute      | Value range |
  |------------------|---------|
  | min_token_size   | [1, 16] |
  | max_token_size   | [10, 84]|

* `IK`: Indicates the word segmentation method based on IK (Chinese). Currently, only the `utf-8` character set is supported. The following attributes can be specified:

  |        Attribute      | Value range |
  |------------------|---------|
  | ik_mode          | <ul><li>`smart`</li><li>`max_word`</li></ul>|

* `analyzer`: specifies the text analyzer (Analyzer). This parameter is used through the `analysis` parameter in `PARSER_PROPERTIES`.

You can use the [TOKENIZE](../400.functions-of-mysql-mode/960.text-processing-functions-of-mysql-mode/200.tokenize-of-mysql-mode.md) function to view the tokenization results of a text using the specified tokenizer and JSON-formatted parameters.

### parser_properties

* `min_token_size`: The minimum token length. Default value: 3. Value range: 1 to 16.

* `max_token_size`: the maximum token length. The default value is 84, and the valid range is 10 to 84.

* `ngram_token_size`: The token length for `NGRAM`. This parameter is valid only when the tokenizer is `NGRAM`. The default value is 2, and the valid range is 1 to 10.

* `ik_mode`: The tokenization mode of the `IK` tokenizer. Valid values:

  * `smart`: The default value. It prioritizes identifying longer words, reducing the number of splits, and ensures each character belongs to only one word. It also attempts to merge numerals with measure words into a single word in the output.
  * `max_word`: Outputs recognizable words as much as possible. Longer words and the shorter words within them are retained. The same character can appear in multiple words.

* `min_ngram_size`: Valid only for the `NGRAM2` tokenizer. Specifies the minimum number of characters for a generated n-gram. Value range: `[1, 16]`.

* `max_ngram_size`: Valid only for the `NGRAM2` tokenizer. Specifies the maximum number of characters for a generated n-gram. The value range is `[1, 16]`. The tokenizer generates consecutive character segments with lengths between the minimum and maximum values.

* `analysis`: Valid only when `WITH PARSER analyzer` is specified. Specifies the JSON definition string for the analyzer. Built-in analyzers can be abbreviated as `{"analyzer": "standard"}` and so on. For a complete list of built-in types and their corresponding languages, see the description of the `analyzer_type` parameter in [TOKENIZE](../400.functions-of-mysql-mode/960.text-processing-functions-of-mysql-mode/200.tokenize-of-mysql-mode.md).

**Example:**

1. Create table `tbl1`.

   ```sql
   CREATE TABLE tbl1 (col1 VARCHAR(200), col2 TEXT);
   ```

2. Create a full-text index on column `col2` of table `tbl1`, specify to use the `IK` tokenizer, and set tokenizer properties using `PARSER_PROPERTIES`.

   ```sql
   CREATE FULLTEXT INDEX fidx_tbl1 ON tbl1(col2) WITH PARSER IK PARSER_PROPERTIES=(ik_mode='max_word');
   ```

3. Create a full-text index on the `body` column of the `articles` table using the built-in `standard` analyzer.

   ```sql
   CREATE FULLTEXT INDEX ft_idx_body ON articles(body)
     WITH PARSER analyzer
     PARSER_PROPERTIES=(analysis='{"analyzer": "standard"}');
   ```

* `GLOBAL`: Indicates that a global index is to be created.

* `LOCAL`: Creates a local index.

* `BLOCK_SIZE integer`: Specifies the size of an index block, that is, the number of bytes in each index block.

* `COMMENT STRING_VALUE`: Adds a comment for the index.

* `STORING (column_name [, column_name...])`: Specifies the columns to store in the index. Separate multiple columns with commas (`,`).

* `WITH_ROWID`: Creates an index that includes a row identifier.

* `WITH PARSER STRING_VALUE`: Specifies the parser required for parsing the index.

* `index_using_algorithm`: Specifies the algorithm used by the index. You can specify USING BTREE or USING HASH. However, you cannot use USING HASH to create a multi-valued index.

* `visibility_option`: Specifies the visibility of the index.

* `DATA_TABLE_ID data_table_id`: the ID of the data table to which the index belongs.

* `INDEX_TABLE_ID index_table_id`: the ID of the index table.

* `VIRTUAL_COLUMN_ID virtual_column_id`: Specifies the ID of the virtual column.

* `MAX_USED_PART_ID used_part_id`: The maximum partition ID of the specified index.

### index_column_group_option

* `WITH COLUMN GROUP(all columns, each column)`: Specifies to create a redundant index for row-based and columnar storage.
* `WITH COLUMN GROUP(each column)`: Specifies to create a columnstore index.

### storage_cache_policy

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>The storage cache policy (STORAGE_CACHE_POLICY) can be specified only when creating an index in shared storage mode.</p>
</main>

You can configure hot and cold storage policies for index tables:

* For local indexes, you can specify the table-level `STORAGE_CACHE_POLICY`. If the table-level `STORAGE_CACHE_POLICY` is not specified, the default is `none`, which means the configuration of the data table's `STORAGE_CACHE_POLICY` is used. The hot and cold storage policies for local index partitions then follow the partitioning rules of the data table.

* For global indexes, in addition to specifying the table-level `STORAGE_CACHE_POLICY`, if the index table has partitions, you can also specify the partition-level `STORAGE_CACHE_POLICY` for the index table. If the table-level `STORAGE_CACHE_POLICY` is not specified for a global index, the default is `none`.

Different attributes in `storage_cache_policy_option` are defined in Key-Value format. The semantics of each attribute are as follows:

* `GLOBAL = {"hot" | "auto" | "cold" | "none"}`: Specifies the hot, auto, cold, or none storage strategy for index data. Valid values:

  * `hot`: specifies the index as a hot storage. If sufficient cache disk space is available, all data under the index table will be cached to the local cloud disk.
  * `auto`: Indicates that the system automatically identifies hot data in the specified index table.
  * `cold`: Indicates that the data of the specified index table is cold data and will not be cached to the local cache disk. For data already persisted to the cache, cache eviction will be actively triggered. Subsequent accesses to the table data can be stored in the macroblock memory cache and will not be persisted to the macroblock cache.
  * `none`: The default value. This means the index follows the `STORAGE_CACHE_POLICY` value of the primary table.

* `timeline_strategy_list`: The list of timeline strategy parameters, separated by commas. Timeline strategies use time to determine whether partition data is stored in hot or cold storage. The system automatically adjusts the data on local cache disks based on the configured strategy.

  * `BOUNDARY_COLUMN = column_name`: specifies the column that identifies hot data. The column can be of an integer type (`BIGINT` or `INT`, in Unix timestamp format) or a time type (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`). If `BOUNDARY_COLUMN` is of an integer type, the table must be partitioned by RANGE or RANGE COLUMNS. If `BOUNDARY_COLUMN` is of a time type, the table must be partitioned by RANGE COLUMNS.
  * `BOUNDARY_COLUMN_UNIT = {"s" | "us" | "ms"}`: specifies the time unit for the `BOUNDARY_COLUMN` parameter. This parameter is supported only when `BOUNDARY_COLUMN` is an integer. Valid values:
    * When the partitioning column is of type `INT`, the value of `BOUNDARY_COLUMN_UNIT` can only be `s`.
    * When the partitioning column is of the `BIGINT` type, the values for `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

  * `HOT_RETENTION = intnum retention_time_unit`: Specifies the time range for hot data. Valid values: `MINUTE`, `HOUR`, `DAY`, `WEEK`, `MONTH`, and `YEAR`.

  * `MIXED_RETENTION = intnum retention_time_unit`:

    * If `MIXED_RETENTION` is set, data within the time range of `HOT_RETENTION + MIXED_RETENTION` is considered `cold` data.
    * If `MIXED_RETENTION` is not set, the retention type will remain `auto` after reaching `HOT_RETENTION`.
    * If `HOT_RETENTION` is not set, the time range of [0, MIXED_RETENTION] represents `auto` data, and the data after `MIXED_RETENTION` represents `cold` data.

  * `GRANULARITY = "partition"`: Optional. Specifies the granularity for hot and cold data storage, indicating that caching data is handled at the partition level.

## Examples

### Example 1

Use the following SQL statement to create a columnstore index for a table.

1. Use the following SQL statement to create the `test_tbl1` table.

   ```sql
   CREATE TABLE test_tbl1 (col1 INT, col2 VARCHAR(50));
   ```

2. Create a columnstore index named `idx1_test_tbl1` on the `test_tbl1` table, referencing the `col1` column.

   ```sql
   CREATE INDEX idx1_test_tbl1 ON test_tbl1 (col1) WITH COLUMN GROUP(each column);
   ```

### Example 2

In shared storage mode, use the following SQL statements to create a hot/cold storage strategy for an index table.

* When creating the index, specify the data of the index table `idx1_tbl1` as hot data.

  ```sql
  CREATE INDEX idx1_tbl1 ON tbl1 (c1) LOCAL 
    STORAGE_CACHE_POLICY (GLOBAL = "hot");
  ```

* Create the `tbl2` table and configure the data of the index table `idx2` on it as hot data.

  ```sql
  CREATE TABLE tbl2 (col1 INT, col2 INT,
    INDEX idx2 ((col1 + 1)) STORAGE_CACHE_POLICY (GLOBAL = "hot"), UNIQUE KEY ((col1 + col2)));
  ```

* When creating a global index, configure its partition caching strategy and configure a timeline strategy.

  ```sql
  CREATE INDEX idx_global ON tbl1 (c1) GLOBAL
    PARTITION BY RANGE (c1)
    (PARTITION p1 VALUES LESS THAN (100),
     PARTITION p2 VALUES LESS THAN (200),
     PARTITION p3 VALUES LESS THAN MAXVALUE);
  ```

### Example 3

The following example shows how to create a search index.

1. Create the `tbl` table.

    ```sql
    CREATE TABLE tbl (col1 JSON, col2 DECIMAL(10,2), col3 JSON, col4 JSON, col5 JSON, col6 varchar(512));
    ```

2. Create a search index named `search_idx`.

    ```sql
    CREATE SEARCH INDEX search_idx ON tbl(
      -- Replace path with the actual path.
      col1 WITH (INCLUDE_PATHS = ('$.path3', '$.path4')),
      col2 WITH (EXCLUDE_PATHS = ('$.path1', '$.path3')),
      col3 WITH (INCLUDE_TYPES = (JSON_STRING)),
      col4
    );
   ```

### Example 4

Create an asynchronous full-text index (the target table must be a heap table):

```sql
CREATE ASYNC FULLTEXT INDEX idx_content ON doc_async(content);
```

Create an asynchronous search index (the target table must be a heap table):

```sql
CREATE ASYNC SEARCH INDEX idx_search ON t(doc);
```
