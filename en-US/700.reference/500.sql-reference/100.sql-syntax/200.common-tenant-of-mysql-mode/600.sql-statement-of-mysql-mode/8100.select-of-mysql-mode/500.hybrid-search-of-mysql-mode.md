# HYBRID_SEARCH

`HYBRID_SEARCH` is used to describe a full-text search, vector search, and filter conditions in a single `SELECT` statement using JSON strings that comply with the rules of this document, and returns rows sorted according to the fusion strategy.

## Syntax

```sql
SELECT select_expr_list
FROM HYBRID_SEARCH(TABLE table_name, dsl_string) [table_alias];

-- select_expr_list is the SELECT list.
-- In addition to table columns, you can also reference hybrid search pseudo-columns. For details, see the "Pseudo-columns" section below.
```

## Parameters

| **Parameters** | **Note** |
| --- | --- |
| `table_name` | Target table name. Only heap tables are supported. `ORGANIZATION = HEAP`), which can be a partitioned table or a non-partitioned table. |
| `dsl_string` | JSON string, description. `query`, `knn`, `rank`, `rerank`, `aggs`, `collapse`, `sort`, `from`, `size`, `min_score` and so on. |

## Global limitations and notes

This section only lists syntax limitations. For feature limitations, see [Hybrid search](#References). You must understand them in conjunction with the content of this section.

The following are the details:

* The top-level `query` (full-text search) and `knn` (vector search) procedures can have at most three subqueries in total: one for `query`, and one for `knn` if it is an object; otherwise, one for each element of the array. The total number cannot exceed three, and at least one full-text or vector search must be included.
* Column names in queries are case-insensitive.
* For the `query_vector` parameter in vector queries, it is recommended to input vectors as strings.
* The `min_score` parameter is supported only by the SQL interface and not by the PL interface.
* Each `query` and each `knn` is an independent search path, and their `filters` do not affect each other. If a filter condition is needed for a particular search path, you must specify the corresponding `filter` separately on that path. All search results are merged into a single result set, scored and ranked based on a fusion algorithm, and the top `size` results are returned.
* Any query can support `boost`, but it may not necessarily be used in scoring. For specific rules, see the [boost parameters](#Detailed%20description%20of%20boost%20parameters) section below.
* `rerank` must be used together with either `query` or `knn` and cannot appear alone. The execution order is rough ranking first, followed by fine ranking. You cannot use `rerank` alone to replace the fusion capability of `rank`.

Limitations:

* The `rank_feature`, `es_mode`, and `_source` parameters are not supported.
* Direct use of `WHERE` / `ORDER BY` / `LIMIT` at the same level as `HYBRID_SEARCH` is not supported. If further filtering or sorting is required, process the hybrid search result as a subquery. For example:

    ```sql
    -- Not supported: Using WHERE in the same layer as HYBRID_SEARCH
    SELECT id
    FROM HYBRID_SEARCH(TABLE doc_table, '{"knn":{"field":"vector","k":5,"query_vector":"[1,2,3]"}}')
    WHERE id > 3;

    -- Supported: First subquery, then filtering
    SELECT id
    FROM (
      SELECT id
      FROM HYBRID_SEARCH(TABLE doc_table, '{"knn":{"field":"vector","k":5,"query_vector":"[1,2,3]"}}')
    ) t
    WHERE id > 3;
    ```

* Some nested JSON/ARRAY element paths cannot be pushed down. For example, if the `path` of a `json` element is an `array` whose elements are `json`, you cannot specify a path for this `json` element.
* Scalar query conditions, including `term` / `range` / `terms` / `wildcard` / JSON expressions / array expressions, all support `boost`. When placed at the top level in `query`, `bool.must` / `bool.should`, they participate in scoring; when placed in `bool.filter` / `bool.must_not` / `knn.filter`, they only serve as hard filters. For specific rules, see the [boost parameters](#Detailed%20description%20of%20boost%20parameters) section below.
* The `boost` for non-top-level full-text queries, the `boost` for `bool` queries, the column weights, and word weights for full-text queries must be greater than `0`. For other cases, the `boost` must be greater than or equal to `0`.
* Multiple full-text columns in `multi_match` / `query_string` queries must use the same character set and `collation`, and the full-text index must use the same `parser`.
* When `match` / `multi_match` / `query_string` is used for term-level matching, the corresponding full-text columns should use `FTS_INDEX_TYPE = MATCH` (or the default type equivalent to `MATCH` if not specified). `match_phrase` applies only to full-text index columns for which `FTS_INDEX_TYPE = PHRASE_MATCH` has been created.
* `sort` and `rank` cannot be specified simultaneously; `aggs` and `sort` cannot be specified simultaneously; `aggs` and `collapse` cannot be specified simultaneously.
* The query `SELECT count(*)` is supported. In this query, the SELECT list can only contain `count(*)` and cannot be mixed with table columns, `__score`, or aggregate pseudocolumns. For more information about pseudocolumns, see the [Pseudocolumns](#Aggregation%20pseudo-columns) section below. For counting semantics, see the "Counting queries (`count(*)`)" section.

## Syntax of DSL_STRING parameters

`dsl_string` is a string in JSON format. The syntax structure is described in detail in this section. Please understand it in conjunction with the parameters and examples below.

### Syntax

This section describes the meanings and usage rules of BNF (Backus-Naur Form) syntax symbols:

1. Optional parameters

   * `[ ]` in BNF indicates that multiple elements are optional. For example, `param_list = param [, param]*` means `param_list` can contain one or more `param` elements.
   * The `[ ]` in `rank_expression` also indicates that the sub-parameter is optional.
   * `[, "boost" : boost_value]` indicates that this sub-parameter is optional in expressions that support `boost`.

2. Array representation
   * `[ ]` indicates an array in a JSON structure, such as `[condition_list]`.

3. Select relationships
   * `|` indicates an OR relationship. For example, `param = "query" | "knn"` means param can be "query" or "knn".

4. Repeat representation
   * `*` indicates zero or more repetitions. For example, `param_list = param [, param]*` indicates that `param_list` can contain one or more `param` elements.

5. JSON format requirements
   * All JSON column names and string values must be enclosed in double quotes.
   * Numbers do not need to be enclosed in double quotes.

#### Top-level parameter structure

The top-level parameter structure is used to specify the parameters for hybrid search.

```sql
dsl_string = '{param_list}'
    param_list = param [, param]*
    -- At least one of query and knn must be selected; they can be used together for hybrid search.
    param = "query"     : {query_expression} -- The value is a JSON object that contains the query expression and, optionally, search_options.
          | "knn"       : {knn_expression}
          | "rank"      : {rank_expression}
          | "rerank"    : {rerank_params}
          | "aggs"      : {aggs_expression}
          | "collapse"  : {collapse_expression}
          | "sort"      : [sort_item_list]
          | "from"      : number
          | "size"      : number
          | "min_score" : number -- Supported only by the SQL interface.
```

##### Query expression syntax

In blended search, both the full-text and scalar conditions are specified in the `query` clause. The value of `query` is a JSON object: the innermost element must be a `query_expression` of the following types: `bool`, `match`, or `term`. To configure options such as recall parallelism, you can add an optional `search_options` field to the same JSON object. For details, see [Query options structure](#Query options structure).

```sql
query_expression = bool_query | scalar_term | fulltext_term | nested_query

bool_query = "bool" : {bool_condition_list}
    bool_condition_list = bool_condition [, bool_condition]*
    bool_condition = "must"    : [condition_list]
                  | "should"   : [condition_list]
                  | "must_not" : [condition_list]
                  | "filter"   : [condition_list]
                  | "minimum_should_match" : msm_value -- bool-level minimum_should_match, supported starting from V4.6.2.1
                  | "boost"    : boost_value
    condition_list = query_expression [, query_expression]*
```

The values for `must`, `should`, `must_not`, and `filter` under `bool` are all arrays of query expressions. Each element in the array is a complete `query_expression` (which can further nest `bool`, `nested`, or be followed by `match` / `term`, etc.). The following example shows only the inner fragment of the `query` object:

:::collapse
```shell
{
  "bool": {
    "must": [
      {
        "match": {
          "content": "oceanbase"
        }
      }
    ],
    "filter": [
      {
        "term": {
          "status": 1
        }
      }
    ]
  }
}
```
:::

###### Scalar query structure

Used to define scalar query expressions within a single entry, including `range_query`, `term_query`, `terms_query`, and `wildcard_query`, representing range queries, exact matches, multiple-value matches, and wildcard matches respectively.

```sql
scalar_term = range_query | term_query | terms_query | wildcard_query

range_query = "range" : {"field_name" : {range_condition_list}}
    range_condition_list = range_condition [, range_condition]*
    range_condition = "gte" : number
                    | "gt"  : number
                    | "lte" : number
                    | "lt"  : number
                    | "boost" : boost_value

term_query = "term" : {term_condition_list}
    term_condition_list = term_condition [, term_condition]*
    term_condition = "field_name" : scalar_value
                   | "field_name" : term_value_object
    term_value_object = "value" : scalar_value
                      [, "boost" : boost_value]

terms_query = "terms" : {terms_condition_list [, "boost" : boost_value]}
    terms_condition_list = terms_condition [, terms_condition]*
    terms_condition = "field_name" : [scalar_value_list]
    scalar_value_list = scalar_value [, scalar_value]*

wildcard_query = "wildcard" : {wildcard_condition_list}
    wildcard_condition_list = wildcard_condition [, wildcard_condition]*
    wildcard_condition = "field_name" : wildcard_pattern
                       | "field_name" : {wildcard_value_object}
    wildcard_pattern = "string_value" | number | boolean
    wildcard_value_object = wildcard_value_body [, "boost" : boost_value]
    wildcard_value_body = "value" : wildcard_pattern
                       | "wildcard" : wildcard_pattern
```

In addition to scalar columns, `term` and `terms` also support single-level array columns and array paths within JSON documents. The details are as follows:

| **Query** | **Column type** | **Description** |
| --- | --- | --- |
| `term` | scalar | Equal match |
| `term` | One-dimensional array | Determine whether an array contains a scalar |
| `term` | Array in JSON | Determine whether an array contains a scalar |
| `terms` | scalar | Field value is in the parameter list. |
| `terms` | One-dimensional array | Determine whether the parameter array has an intersection with the array column |
| `terms` | Array in JSON | Determine whether the parameter array and the JSON array have an intersection |

The limitations are as follows:

* Currently, `term` and `terms` only support single-level arrays.

###### Full-text query structure

Used to define full-text query expressions within individual entries, including `match_query`, `match_phrase_query`, `query_string`, and `multi_match`, representing term-level matching, phrase-level matching, full-text search, and multi-column term-level matching.

```sql
fulltext_term = match_query | match_phrase_query | query_string | multi_match

match_query = "match" : {"field_name" : match_body}
    match_body = "string_value" | {match_condition}
    match_condition = "query" : "string_value" [, "operator" : ("OR" | "AND")] [, "minimum_should_match" : msm_value] [, "boost" : boost_value]
    -- The `minimum_should_match` parameter takes effect only when the `operator` is set to `OR` (which is the default when not specified). When `operator` is set to `AND`, all terms must match for a match to be considered valid, which conflicts with the semantics of `minimum_should_match`. Therefore, these two parameters cannot be used simultaneously.

match_phrase_query = "match_phrase" : {"field_name" : phrase_body}
    phrase_body = "string_value" | {phrase_condition}
    phrase_condition = "query" : "string_value" [, "slop" : number] [, "boost" : boost_value]

query_string = "query_string" : {query_string_condition}
    query_string_condition = "fields" : [field_weight_list]
                           | "query"  : "string_value" -- Can contain the metapositional operator ^. For details, see "Weight operator" below.
                           | "boost"  : boost_value
                           | "type"   : ("best_fields" | "most_fields")
                           | "default_operator" : ("AND" | "OR")
                           | "minimum_should_match" : msm_value
    -- The minimum_should_match condition takes effect only when the default_operator is set to OR.

multi_match = "multi_match" : {multi_match_condition}
    multi_match_condition = "fields" : [field_weight_list]
                         | "query"  : "string_value" -- Does not support the ^ metacharacter in query strings.
                         | "boost"  : boost_value
                         | "type"   : ("best_fields" | "most_fields")
                         | "operator" : ("AND" | "OR")
                         | "minimum_should_match" : msm_value
    -- The `minimum_should_match` clause takes effect only when the operator is OR (including the default OR).
    field_weight_list = field_weight [, field_weight]*
    field_weight = "field_name[^number]"

msm_value = number | "string_value" -- String type is supported starting from V4.6.2.1
```

```sql
search_options = "search_options" : {search_options_body}
    search_options_body = "query_dop" : number
```

##### Vector and sorting structures

It is used to specify vector search parameters, including the search vector field, similarity, filter conditions, and weights. It supports both single-channel and multi-channel vector retrieval.

```sql
knn_expression = "knn" : {knn_condition_list} | [multi_knn_condition_list]
    knn_condition_list = knn_condition [, knn_condition]*
    knn_condition = "field"           : "field_name"
                 | "k"               : number
                 | "query_vector"    : [vector_values]
                 | "num_candidates"  : number
                 | "search_options"  : {search_option_list}
                 | "filter"          : [condition_list]
                 | "similarity"      : number
                 | "boost"           : boost_value
    search_option_list = search_option [, search_option]*
    search_option = "ef_search"    : number
                 | "refine_k"      : number
                 | "filter_mode"   : ("pre" | "pre-knn" | "pre-brute" | "post" | "post-index-merge")
    multi_knn_condition_list = {knn_condition} [, {knn_condition}]*
    vector_values = float [, float]*

rank_expression = "rank" : {rank_strategy}
    rank_strategy = "rrf" : {rrf_params}
                  | "weighted_sum" : {weighted_sum_params}
    rrf_params = "rank_window_size" : number [, "rank_constant" : number]
    weighted_sum_params = "rank_window_size" : number [, "normalizer" : ("minmax" | "none")]

rerank_params = "model" : "string_value"
              | "field" : "field_name"
              | "query" : "string_value"
              | "rank_window_size" : number
              | "type" : "string_value"

aggs_expression = "aggs" : {aggregation_bucket}
    aggregation_bucket = "agg_name" : {aggregation_body}
    aggregation_body = "terms" : {terms_condition_list}
                     | "cardinality" : {cardinality_condition_list}
    terms_condition_list = terms_condition [, terms_condition]*
    terms_condition = "field" : "field_name"
                    | "size" : number
                    | "min_doc_count" : number
                    | "order" : {"_count" : ("asc" | "desc")}
                    | "order" : {"_key" : ("asc" | "desc")}
    cardinality_condition_list = "field" : "field_name"

collapse_expression = "collapse" : {collapse_condition_list}
    collapse_condition_list = "field" : "field_name"

sort_item_list = sort_item [, sort_item]*
    sort_item = "field_name"
              | "__score"
              | {"field_name" : {sort_condition_list}}
    sort_condition_list = sort_condition [, sort_condition]*
    sort_condition = "order" : ("asc" | "desc")
                   | "missing" : ("_first" | "_last" | number)
```

During single-vector search, `knn` is a single object. During multi-vector search, `knn` is an array of objects, where each element is a set of `knn_condition`. The following example shows the `knn` section for multi-vector search:

:::collapse
```shell
{
  "knn": [
    {
      "field": "vector_a",
      "k": 3,
      "query_vector": "[1,0,0]"
    },
    {
      "field": "vector_b",
      "k": 3,
      "query_vector": "[0,1,0]"
    }
  ]
}
```
:::

#### Description of Weight Operators

The weight operator `^` is used to specify the weight at the **column level** or **token level** in a **full-text query** statement. The syntax is `column name^weight` or `keyword^weight`, for example, `"title^2.0"`. Supported parameters:

* Column-level weights are supported only for `multi_match` and `query_string`.
* Only `query_string` supports per-token weights.

The token-level weight operator specifies the weight of the keyword to its left (up to the space). Keywords without a weight operator have a default weight of 1.0. A keyword associated with a weight operator or a sequence of consecutive keywords without weight operators forms a group.

```shell
{
  "query": {
    "query_string": {
      "fields": ["title^2.0", "content"],
      "query": "Honeydew pitaya, jelly orange^1.5, autumn moon pear^1.2, blueberry, mangosteen"
    }
  }
}
```

As shown in the preceding example, when querying the term `"Red Heart Pitaya Jellied Orange^1.5 Autumn Moon Pear^1.2 Blueberry Mangosteen"`, it is divided into four groups: Red Heart and Pitaya with a default weight of 1.0; Jellied Orange and Orange with a specified weight of 1.5; Autumn Moon Pear and Pear with a specified weight of 1.2; and Blueberry and Mangosteen with a default weight of 1.0.

Weight operators can be used together with the `boost` parameter. For specific examples, see the [boost parameters](#Detailed%20description%20of%20boost%20parameters) section below.

#### Detailed description of boost parameters

The `boost` parameter specifies the weight of a query condition in the final relevance calculation. When a scalar condition is met, it scores 1 point, which is then multiplied by the cascaded `boost` values. If not specified, the default is `1`. Cascading refers to the way the `boost` parameters are calculated by multiplying nested levels when contributing to the score, for example, `bool.boost × subquery boost`.

1. Expressions that support `boost`

    * `bool` queries.
    * Full-text queries (such as `match`, `match_phrase`, `query_string`, and `multi_match`).
    * Vector queries (single/multi-way `knn`).
    * Scalar query: `term` / `range` / `terms` / `wildcard`.
    * JSON/ARRAY scalar expressions.
    * `nested` queries.

2. Whether to participate in scoring

    | **Query position** | **Included in `__score`** |
    | --- | --- |
    | Top-level `query` clause | Yes |
    | `bool.must` and `bool.should` | Yes. They are included only if their outer expression participates in scoring, for example, in `bool.filter.bool.must`, the inner `must` does not contribute to the score. |
    | `bool.filter` and `bool.must_not` | No |
    | `knn.filter` | No |
    | bool nested inside `filter` or `must_not` | No (this `bool` and its subqueries do not score points) |

3. Value constraints

    * The column weights and term weights for `boost` queries that are not top-level full-text queries, `boost` queries that are not top-level full-text queries, and full-text queries must be greater than `0`.
    * For other cases, the `boost` requirement is greater than or equal to `0`.

4. Syntax examples

    a. Scalar `range` with `boost`:

    ```shell
    {
      "range": {
        "c1": {
          "gt": 1,
          "boost": 2.1
        }
      }
    }
    ```

    b. Scalar `term` with `boost`:

    ```shell
    -- Abbreviation. The default boost is 1.
    {
      "term": {
        "c1": 1
      }
    }
    ```

    ```shell
    -- Object format
    {
      "term": {
        "c1": {
          "value": 1,
          "boost": 2.35
        }
      }
    }
    ```

    c. Scalar `terms` with `boost`:

    ```shell
    {
      "terms": {
        "c1": [1, 3, 5],
        "boost": 3.14
      }
    }
    ```

    d. `wildcard` with `boost`:

    ```shell
    -- Short form. The default boost is 1.
    {
      "wildcard": {
        "content": "*ocea*"
      }
    }
    ```

    ```shell
    -- Object format
    {
      "wildcard": {
        "content": {
          "value": "*ocea*",
          "boost": 1.8
        }
      }
    }
    ```

    e. JSON/single-level array expressions with `boost`:

    ```shell
    {
      "json_contains": {
        "meta_json": {
          "candidate": "\"mysql\"",

        }
      }
    ```

    ```shell
    {
      "array_contains": {

        }
      }
    }
    ```

    ```shell
    {
      "bool": {
    ```

    ```shell
        "boost": 1.5,

          {"range": {"c1": {"gt": 1, "boost": 2.1}}}
        ]
      }
    }
    ```

    `knn` itself contributes to scoring; scalar conditions within `knn.filter` do not contribute to scoring.

#### minimum_should_match

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Starting from V4.6.2.1, in addition to supporting the integer type for <code>minimum_should_match</code>, <code>match</code>, <code>multi_match</code>, and <code>query_string</code> also support string types (including percentages and combinations), and support <code>bool</code> level <code>minimum_should_match</code>.</p>
</main>

`minimum_should_match` (MSM for short) indicates the minimum number of matches. That is, it specifies the minimum number of alternative cells that must be matched for a document to be considered a match.

##### Typical scenarios

There are generally two major scenarios for MSM:

* Full-text search `OR` scenarios: This scenario occurs when the `operator` in `match` or `multi_match` is `OR` or not set (the default is `OR`), or when the `default_operator` in `query_string` is `OR` or not set. The MSM can be written in the `match`, `multi_match`, or `query_string` clause, with a default value of `1`. When `operator` or `default_operator` is `AND`, all optional units must match, which conflicts with the semantics of MSM; therefore, they cannot be used simultaneously. MSM takes effect only in the aforementioned `OR` scenarios.
* Scenario where `bool` clauses are optional: This scenario occurs when a `bool` clause contains one or more `should` clauses. Each element in the `should` array is an optional subquery. An MSM is written within this `bool` object (parallel to the `should` clauses) to specify the minimum number of `should` clauses that must be true for a match to be considered valid. The default value of MSM varies under different conditions:
  * If there is only a `should` clause and no `must` or `filter` clauses, the default value is `1`.
  * When a `must` or `filter` clause is present, the default value is `0`.
  * If there are no `should` clauses and only `must` or `filter` clauses, no error is reported, but the clause has no practical effect.

To calculate the MSM, you must first determine N, which is the total number of selectable units. Regardless of whether the MSM is a positive integer, negative integer, or percentage, it is converted relative to N to obtain the actual minimum hit count. The N values corresponding to each query clause type are as follows:

| **Types of query clauses** | **N Value** |
| --- | --- |
| `match` / `multi_match` | Number of Tokens after Query Tokenization |
| `query_string` | The number of groups after splitting by the token-level weight `^` in `query` (see [Description of weight operators](#Description%20of%20Weight%20Operators) above for the rules; this is not the number of tokens after tokenization). |
| `bool` | Within the object `should` Number of clauses |

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The units counted by MSM are collectively referred to as <b>alternatives</b> in the following text. Among them, <code>match</code> and <code>multi_match</code> are tokens, <code>query_string</code> is a group after segmentation by <code>^</code>, and <code>bool</code> is the <code>should</code> clause.</p>
</main>

##### Single-value matching logic

The value of N can be an integer or a string. If the string can be parsed as an integer, it behaves the same as an integer; otherwise, it is parsed as a string. Unless specified otherwise in this section, the example assumes `N = 10`.

###### Positive Integer

Represents the minimum number of selectable units that must be met (the final calculated result in this section is set as `m`). The value range is `[0, N]`, and `m=min(MSM, N)`.

| **MSM Value** | **Calculation (N=10)** | **Note** |
| --- | --- | --- |
| `2` or `"2"` | m = min(2, 10) = 2 | At least 2 hits |
| `0` | m = min(0, 10) = 0 | Special handling based on query type:<ul><li><code>match</code>, <code>multi_match</code>, and <code>query_string</code> are effectively treated as <code>1</code>.</li><li>For <code>bool</code>, manually setting it to <code>0</code> is invalid when it contains only <code>should</code> (the system enforces it as <code>1</code>).</li><li>For <code>bool</code>, <code>0</code> takes effect when it contains both <code>must</code> and/or <code>filter</code>, indicating that a document only needs to pass <code>must</code>/<code>filter</code> to be included in the result set.</li></ul> |
| `12`(≥ N) | m = min(12, 10) = 10 | Equivalent to all hits (`operator = AND`) |

```shell
"minimum_should_match": 2
```

###### Negative Integer

It indicates the maximum number of optional units that are allowed to be unmatched (denoted as `m` in the final calculation of this section). The value of `m` is calculated by subtracting `|MSM|` from `N`, using the formula `m = N - |MSM|`.

| **MSM Value** | **Computing** | **Note** |
| --- | --- | --- |
| `-2`(N=10) | m = 10 - \| −2 \| = 8 | At least 8 hits |
| `-4`(N=3) | m = 3 - \| −4 \| = −1 | -1 rounded to 0 (see [Positive integers](#Positive%20Integer) for logic), and the system automatically treats it as 1 available unit. |

```shell
"minimum_should_match": -2
```

###### Positive Percentage

It indicates the minimum percentage of selectable cells that must be hit. The value is rounded down to the nearest integer based on the percentage of N, calculated by the formula `m = floor(N × MSM / 100)`.

| **MSM Value** | **Calculation (N=10)** | **Note** |
| --- | --- | --- |
| `"75%"`(less than 100%) | m = floor(10 × 75 / 100) = 7 | At least 7 hits |
| `"100%"`(100%) | m = floor(10 × 100 / 100) = 10 | All Hits |
| `"150%"`(Greater than 100%) | m = floor(10 × 150 / 100) = 15. When m exceeds N, the system automatically truncates it to N, that is, m = 10. | Equivalent to all hits, no error will be reported |

```shell
"minimum_should_match": "75%"
```

###### Negative percentage

It indicates the allowable proportion of missing optional units, rounded down to the nearest integer as a percentage of N (for example, `trunc(-1.5) = -1`). In the calculation formula of this section, `MSM` represents the signed value in the percentage (for example, `MSM = −25` in `"-25%"`), and the formula is `m = N + trunc(N × MSM / 100)`.

| **MSM Value** | **Calculation (N=10)** | **Note** |
| --- | --- | --- |
| `"-25%"`(The value is greater than −100%, that is, the absolute value is less than 100%.) | m = 10 + trunc(10 × (−25) / 100) = 10 + trunc(−2.5) = 10 + (−2) = 8 | At least 8 hits |
| `≤ −100%`(For example, `"-150%"`) | m = 10 + trunc(10 × (−150) / 100) = 10 + (−15) = −5 | If the median value is ≤ 0, the system automatically treats it as one available unit without returning an error. |

```shell
"minimum_should_match": "-25%"
```

##### Combined operation logic

MSM can also be written as a string with operators, in the format `condition_threshold < MSM_value`. For example, `"3<90%"` means that when the total number of selectable units N is greater than the condition threshold 3, MSM is calculated as `90%`. For scenarios where N is less than or equal to 3, it is fixed at `100%` (all hits). Multiple segments are separated by spaces. The system checks from left to right. Condition threshold intervals are **open on the left and closed on the right** (the leftmost is a closed interval), as shown in the examples below.

:::tab
tab Single-line example

| **MSM Value** | **Calculation (N=10)** | **Note** |
| --- | --- | --- |
| `"3<90%"` | When N = 10, it falls within the interval (3, +∞). According to the rule that `90%` Calculation | m = 10 × 0.9 = 9 |
| `"15<90%"` | N = 10 falls in the `[0, 15]`, press `100%` Calculation | m = 10 |

tab Multi-line example

```shell
"minimum_should_match": "2<60%, 5<70%, 9<80%"
```

When you explicitly specify three percentage segments for a string, the system automatically adds an implicit default segment (treating N as 100% when it does not exceed the first threshold). The complete interval is as follows (left-open, right-closed; the leftmost is a closed interval):

* The number of selectable units is in the range of [0, 2], with an application threshold of 100%.
* Number of selectable cells is in the range of (2, 5], with an application threshold of 60%.
* When the number of selectable units is in the range (5, 9], use the application's 70% threshold.
* Number of selectable units is in the range (9, +∞), with an application threshold of 80%.

Therefore, for different values of N, the calculation results are as follows:

| **N Value** | **Scanning Process** | **Result** |
| --- | --- | --- |
| N ≤ 2 | If the number of available units in the first segment is greater than or equal to 2, the service stops directly. | m = N × 100 / 100 = N |
| 2 < N ≤ 5 (for example, N = 5) | 5 is in the interval (2, 5]. Calculated by `60%`: m = 5 × 60 / 100 = 3. The next available unit-count range is (5, 9]. Since 5 is not in this range, the process stops. | m = 3 |
| 5 < N ≤ 9 (for example, N = 9) | 9 in the interval (5, 9], by `70%` Calculation: m = trunc(9 × 70 / 100) = 6. The next available unit range is (9, +∞). Since 9 is not within this range, the process stops. | m = 6 |
| N > 9 (for example, N = 10) | 10 in the interval (9, +∞), by `80%` Calculation: m = 10 × 80 / 100 = 8 | m = 8 |
:::

##### Nesting and Hierarchical Structure

Based on the preceding rules, it is important to understand that `minimum_should_match` applies only to the query level where it is defined. Constraints at each level are independent of one another and are evaluated separately at each level during nested queries, without overriding each other.

| **Placement** | **Constraint objects (N)** |
| --- | --- |
| `match` / `multi_match` internal | Number of tokens after word segmentation in this query |
| `query_string` internal | Number of groups after boosting segmentation (see [Weight operator description](#Weight operator description) for rules) |
| `bool` and `should` Same Level | `should` Number of clauses |

For example, if the outer `bool` condition sets MSM to 2 (at least 2 of the 3 `should` conditions must be met), and within one of the `should` conditions, `match` is set to MSM = 2 (at least 2 of the 3 terms in this `match` must be matched), then both layers of conditions must be met simultaneously. See the "Minimum match number example" section for an illustration.

#### Nested queries

This section provides additional information on path naming in nested queries, the differences between nested queries and DDL statements, and the semantics of `must_not`.

The following table describes the differences between path naming and DDL.

| **Context** | **Format** | **Example** |
| --- | --- | --- |
| DDL `NESTED_PATHS` | `$.path`, excluding column name | `$.comments` |
| dsl_string `nested.path` | `column name/path`, excluding `$` | `j1.comments` |
| Field path of inner query in dsl_string | `column name.full path` | `j1.comments.author` |

Nested queries can appear in the top-level `query` or in any clause of a `bool`. Multiple conditions in an inner `bool` must match the same array element; for multi-layer nested queries, further `nested` clauses are required to query deeper fields. For details on the DDL-side path matching rules (how arrays and objects correspond to declared paths), see the "NESTED_PATHS Path Matching" section in [CREATE INDEX](../2200.create-index-of-mysql-mode.md).

The negation domain is determined by the relative position of `must_not` relative to `nested`:

```shell
Parent document (a row in a table / the entire JSON)
  └── comments[]          ← child elements affected by nested
        ├── {author: alice}
        └── {author: bob}
```

* Parent domain negation: The outer `bool.must_not` directly wraps `nested`, for example:

```shell
# Indicates that no Alice characters are allowed in the comment.
{
  "bool": {
    "must_not": [{"nested": {"path": "comments", "query": {"bool": {"must": [{"term": {"comments.author": "alice"}}]}}}}]
  }
}
```

The parent document matches if no nested element satisfies the negation condition. In other words, as long as one nested element meets the condition, the document does not match. If the nested array is empty, or the document lacks this path field, it will also match.

* Child domain negation: `must_not` is placed under `nested.query.bool`, for example:

```shell
# There must be at least one comment other than Alice's.
{
  "nested": {
    "path": "comments",
    "query": {"bool": {"must_not": [{"term": {"comments.author": "alice"}}]}}
  }
}
```

The parent document matches if at least one nested element does not satisfy the negated condition. In other words, as long as one nested element does not meet the negation condition (for example, the author is not alice), the document matches. If all nested elements satisfy the negation condition, it does not match. If the nested array is empty, or the document lacks this path field, it will also match.

#### Aggregation pseudo-columns

`HYBRID_SEARCH` provides the following pseudo-columns in the `SELECT` list. Pseudo-columns are only valid in hybrid search syntax and are not part of the general MySQL `SELECT` expression.

| **Pseudo column name** | **Meaning** | **Application scenarios** |
| --- | --- | --- |
| `__score` | Final score after fusing search results from multiple sources | Can be referenced in any mixed-search query for returning rows |
| `agg_name` | Aggregated bucket count (the name must be consistent with the custom bucket key in `aggs`) | Available only when a same-named `aggs` variable is declared in `dsl_string` |

For aggregation over `terms`, the pseudo-column `agg_name` returns the number of documents corresponding to that group key (equivalent to `COUNT(*)`). For aggregation over `cardinality`, the pseudo-column `agg_name` returns the deduplication count of that field (equivalent to `COUNT(DISTINCT field)`). You can also write `COUNT(DISTINCT field)` in `SELECT`, but `field` must match `cardinality.field`.

#### Count queries (`count(*)`)

`SELECT count(*)` is used to count the total number of documents in the union of search results from all paths. Single-path searches return the number of hits for that path index, while multi-path searches count the union of row keys after deduplication. Counting is done at the index layer, without scoring or accessing the primary table.

`size`, `from`, `sort`, `aggs`, and `collapse` do not affect the count result; `min_score` does. When both `rank` and `min_score > 0` are specified, only documents within the fusion window and with a score meeting the threshold are included in the count.

The following example sets `"size": 1`, but `count(*)` still returns the actual total number of full-text hits, not 1:

```sql
SELECT count(*)
FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "query": {
      "match": {"content": "oceanbase"}
    },
    "size": 1
  }'
);
```

### Nested query example

The DDL and test data for the sample table `search_idx_nested` are as follows (subsequent nested query examples are based on this table; multi-level nesting examples rely on the `$.comments.replies` declaration):

:::collapse
```sql
CREATE TABLE search_idx_nested (
  k INT,
  j1 JSON,
  SEARCH INDEX idx_nested (
    j1 WITH (
      NESTED_PATHS = ('$.comments', '$.comments.replies')
    )
  )
) ORGANIZATION = HEAP;

INSERT INTO search_idx_nested VALUES
-- k=1: Alice scores 4 points, Bob scores 5 points (with different comments); no reply from Bob to Alice
(1, '{"title":"doc1","comments":[{"author":"alice","rating":4,"replies":[]},{"author":"bob","rating":5,"replies":[{"author":"bob","text":"good"}]}]}'),
-- k=2: Alice scores 5 points on the same comment, and Bob is among the replies.
(2, '{"title":"doc2","comments":[{"author":"alice","rating":5,"replies":[{"author":"bob","text":"good"},{"author":"carol","text":"well"}]},{"author":"bob","rating":4,"replies":[]}]}'),
-- k=3: No Alice
(3, '{"title":"doc3","comments":[{"author":"bob","rating":4},{"author":"carol","rating":3}]}'),
-- k=4: All comments are from alice
(4, '{"title":"doc4","comments":[{"author":"alice","rating":5}]}'),
-- k=5: comments is empty
(5, '{"title":"doc5","comments":[]}');
```
:::

Find the same comment where the author is `alice` and the rating is greater than or equal to `5`:

```sql
SELECT k, j1 FROM HYBRID_SEARCH(
  TABLE search_idx_nested,
  '{
    "query": {
      "nested": {
        "path": "j1.comments",
        "query": {
          "bool": {
            "must": [
              {"term": {"j1.comments.author": "alice"}},
              {"range": {"j1.comments.rating": {"gte": 5}}}
            ]
          }
        }
      }
    }
  }'
);
```

The expected results are `k=2` and `k=4`. In `k=1`, alice and a rating of `5` are not in the same comment, so it does not match.

### Multi-level nested query example

If multiple nested paths are declared when creating an index (for example, `NESTED_PATHS = ('$.comments', '$.comments.replies')`), you must continue to nest `nested` clauses when querying deeper fields. For example, find the comment where `author=alice` and there exists a comment with `author=bob` in its replies:

```sql
SELECT k, j1 FROM HYBRID_SEARCH(
  TABLE search_idx_nested,
  '{
    "query": {
      "nested": {
        "path": "j1.comments",
        "query": {
          "bool": {
            "must": [
              {"term": {"j1.comments.author": "alice"}},
              {
                -- Continue Nested Clauses
                "nested": {
                  "path": "j1.comments.replies",
                  "query": {
                    "term": {"j1.comments.replies.author": "bob"}
                  }
                }
              }
            ]
          }
        }
      }
    }
  }'
);
```

The outer and inner conditions must apply to the same comment. The expected result is only `k=2`.
