# CREATE MATERIALIZED VIEW

## Purpose

This statement is used to create a materialized view.

A materialized view is a special type of database object that stores a copy of query results and is periodically refreshed (or can be refreshed manually) to maintain the data in its latest state. Materialized views can contain aggregations, joins, and subqueries, and can be indexed and partitioned to further improve performance.

## Privilege requirements

Creating a materialized view requires the `CREATE TABLE` privilege. For more information about OceanBase AI Database privileges, see [Permission classification](../../../../../600.manage/500.security-and-permissions/300.access-control/200.user-and-permission/200.permission-of-mysql-mode/100.permission-classification-of-mysql.md).

## Syntax

```sql
CREATE MATERIALIZED VIEW view_name [([column_list] [PRIMARY KEY(column_list)])]
    [table_option_list]
    [partition_option]
    [mv_column_group_option]
    [refresh_clause]
    [query_rewrite_clause]
    [on_query_computation_clause]
    AS view_select_stmt;

column_list:
    column_name [, column_name ...]

refresh_clause:
    REFRESH [refresh_option [PARALLEL n] [nested_refresh_option]] [mv_refresh_on_clause]
    | NEVER REFRESH

refresh_option:
    COMPLETE
    | FAST
    | FORCE

nested_refresh_option:
    INDIVIDUAL
    | INCONSISTENT
    | CONSISTENT

mv_refresh_on_clause:
    [ON DEMAND] [[START WITH expr] [NEXT expr]]

query_rewrite_clause:
    DISABLE QUERY REWRITE
    | ENABLE QUERY REWRITE

on_query_computation_clause:
    DISABLE ON QUERY COMPUTATION
    | ENABLE ON QUERY COMPUTATION

mv_column_group_option:
    WITH COLUMN GROUP(all columns)
    | WITH COLUMN GROUP(each column)
    | WITH COLUMN GROUP(all columns, each column)
```

### mv_column_group_option

* `WITH COLUMN GROUP(all columns)`: Specifies to create a row-store format materialized view.
* `WITH COLUMN GROUP(each column)`: Specifies to create a column-store format materialized view.
* `WITH COLUMN GROUP(all columns, each column)`: Specifies to create a hybrid row-column store format materialized view.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>You can use the <code>SHOW CREATE TABLE view_name;</code> or <code>SHOW CREATE VIEW view_name;</code> command to view the definition of a materialized view and determine its storage format.</p>
</main>

### refresh_clause

* `REFRESH [refresh_option [PARALLEL n] [nested_refresh_option]] [mv_refresh_on_clause]`: Specifies the refresh method and parallelism for the materialized view.

  * `refresh_option`: Specifies the refresh method for the materialized view. Optional. If no refresh method is specified, the default is `FORCE`.

    * `COMPLETE`: Indicates a complete refresh, which recalculates the data for the entire materialized view to ensure the data in the view is fully consistent with the source table.
    * `FAST`: Indicates an incremental refresh, which only refreshes the data related to changes in the source table, avoiding a full recalculation of the entire view.

      <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p><ul><li>The <code>REFRESH FAST</code> method uses the record information in the materialized view's log to determine what needs to be refreshed incrementally. Therefore, when using incremental refresh for a materialized view, you must create the materialized view log (mlog) for the base table before creating the materialized view.</li><li>All columns used in the incremental refresh of a materialized view must be included in the mlog.</li></ul>For information about creating a materialized view log, see <a href="../../../../300.database-object-management/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/200.materialized-views-log-of-mysql-mode.md">Materialized view logs</a>.</p>
      </main>

    * `FORCE`: The default value. It specifies to perform a hybrid refresh. In other words, the system first attempts an incremental refresh. If the incremental refresh fails, it then performs a full refresh.
    * `nested_refresh_option`: Specifies the refresh strategy for nested materialized views. This option is optional. If not specified, the default is `INDIVIDUAL`. Valid values:

      * `INDIVIDUAL`: The default value, indicating an independent refresh.
      * `INCONSISTENT`: Indicates a cascading non-consistent flush.
      * `CONSISTENT`: indicates a cascading consistent refresh.

      <main id="notice" type='explain'>
        <h4>Note</h4>
        <p>For non-nested materialized views, cascading refresh is not supported. Specifying any refresh strategy is meaningless as they all default to independent refresh. The three specified refresh strategies only take effect for background tasks. When manually scheduling a refresh using the PL package (<a href="../../../../600.pl-reference/1000.pl-system-package-mysql/9950.dbms-mview-mysql/300.refresh-mysql.md">DBMS_MVIEW.REFRESH</a>), the refresh is executed according to the specified PL parameters.</p>
      </main>

    * `PARALLEL n`: Specifies the refresh parallelism, which is the degree of parallelism used when refreshing the materialized view. `n` must be an integer greater than or equal to 0. When `n` is 0, the system variable `mview_refresh_dop` is used to determine the refresh parallelism.

* `NEVER REFRESH`: specifies that the materialized view does not need to be refreshed. This means the materialized view is refreshed only when it is created and cannot be refreshed again after creation.

### mv_refresh_on_clause

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Aside from defining a refresh plan using the <code>mv_refresh_on_clause</code> clause, you can also manually refresh a materialized view by calling the <code>dbms_mviews.refresh</code> stored procedure.</p>
</main>

* `ON DEMAND`: Optional. Specifies to refresh the materialized view on demand.
* `[[START WITH expr] [NEXT expr]]`: Optional. Defines the refresh interval.

  * `[START WITH expr]`: Optional. The time expression at which the refresh plan starts.
  * `[NEXT expr]`: Optional. The expression that specifies the time for the next refresh.

    <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p><ul><li>If the <code>NEXT</code> clause is used, the time expression for refreshing the plan must be set to a future point in time; otherwise, an error will occur.</li><li>To periodically and automatically schedule refresh tasks for a materialized view, define <code>NEXT</code> to set the scheduling cycle.</li></ul></p>
    </main>

It is recommended to use `sysdate()` to represent the current time in the local timezone. An example time expression is as follows:

```sql
START WITH sysdate() NEXT sysdate() + INTERVAL 1 DAY
```

The preceding clause means that the materialized view will be refreshed every day starting from the current time (`sysdate()`).

### query_rewrite_clause

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This feature requires that the materialized view contains only the <code>SELECT JOIN</code> and <code>WHERE</code> clauses, that is, it must be an SPJ query. Materialized views that do not meet this condition will not cause an error but will not be used for query rewrite.</p>
</main>

* `DISABLE QUERY REWRITE`: The default value. Specifies that automatic query rewrite is not enabled for the current materialized view.
* `ENABLE QUERY REWRITE`: Specifies to enable automatic query rewrite for the current materialized view.

For more information about materialized view query rewrite, see [Query rewrite using materialized views](../../../../300.database-object-management/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/500.materialized-views-rewrite-of-mysql-mode.md).

### on_query_computation_clause

* `DISABLE ON QUERY COMPUTATION`: The default value, which specifies to create a normal materialized view.
* `ENABLE ON QUERY COMPUTATION`: Specifies to create a real-time materialized view.

  <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p><ul><li>Materialized views that use the <code>MIN</code>/<code>MAX</code> function do not support real-time materialization.</li><li>Aggregate materialized views with outer joins do not support real-time materialization.</li><li>Materialized views with set queries do not support real-time materialization.</li><li>Nested materialized views cannot be created as real-time materialized views.</li></ul></p>
  </main>

For more information about real-time materialized views, see the **Create a real-time materialized view** section in [Create a materialized view](../../../../300.database-object-management/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/300.create-materialized-views-of-mysql-mode.md).

## Examples

1. Create the table `test_tbl1`.

   ```sql
   CREATE TABLE test_tbl1 (col1 INT PRIMARY KEY, col2 VARCHAR(20), col3 INT, col4 INT);
   ```

2. Create a materialized view named `mv_test_tbl1`. Partition the materialized view by hash on the `col1` column into `8` partitions. Use the complete refresh method to refresh the materialized view, starting from the current date and refreshing every `1` day. Use the records in the `test_tbl1` table that satisfy the condition `col3 >= 30` as the base table for queries, and use the query results as the data for the materialized view.

   ```sql
   CREATE MATERIALIZED VIEW mv_test_tbl1
     PARTITION BY HASH(col1) PARTITIONS 8
     REFRESH COMPLETE START WITH sysdate() NEXT sysdate() + INTERVAL 1 DAY
     AS SELECT col1, col2, col3
       FROM test_tbl1
       WHERE col3 >= 30;
   ```

3. Create a materialized view named `mv2_test_tbl1` and specify its primary key.

   ```sql
   CREATE MATERIALIZED VIEW mv2_test_tbl1(c1, c2, c3, PRIMARY KEY(c1))
         AS SELECT col1, col2, col3
           FROM test_tbl1;
   ```

4. Create a materialized view `mv3_test_tbl1` in columnar format.

   ```sql
   CREATE MATERIALIZED VIEW mv3_test_tbl1
     WITH COLUMN GROUP(each column)
     AS SELECT col1, col2, col3
       FROM test_tbl1;
   ```

5. View the definition of the materialized view `mv3_test_tbl1`.

   ```sql
   SHOW CREATE VIEW mv3_test_tbl1;
   ```
