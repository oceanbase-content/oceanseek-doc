# ALTER TABLE

## Purpose

This statement is used to modify the structure of an existing table, such as altering the table and its attributes, adding columns, modifying columns and their attributes, and dropping columns.

## Syntax

```sql
alter_table_stmt:
    ALTER TABLE table_name alter_table_action_list;

alter_table_action_list:
    alter_table_action [, alter_table_action ...]

alter_table_action:
      ADD [COLUMN] column_definition
          [ opt_position_column ]
    | ADD [COLUMN] (column_definition_list)
    | ADD [CONSTRAINT [constraint_name]] UNIQUE {INDEX | KEY}
          [index_name] index_desc
    | ADD [CONSTRAINT [constraint_name]] FOREIGN KEY
          [index_name] index_desc
          REFERENCES reference_definition
          [match_action][opt_reference_option_list]
    | ADD PRIMARY KEY (column_name)
    | ADD CONSTRAINT [constraint_name] CHECK (expression)[[NOT] ENFORCED]
    | ADD PARTITION (range_partition_list)
    | ADD {INDEX | KEY} [index_name] [index_type] (key_part,...) [index_option_list][index_column_group_option]
    | ADD [ASYNC] FULLTEXT [INDEX | KEY] [index_name](column_name, [column_name ...]) [WITH PARSER tokenizer_option] [PARSER_PROPERTIES[=](parser_properties_list)] [FTS_INDEX_TYPE [=] {MATCH | PHRASE_MATCH}] [LOCAL]
    | ADD [ASYNC] SEARCH INDEX [index_name] (search_index_column [, search_index_column ...])
    | ADD COLUMN GROUP([all columns, ]each column) [DELAYED]
    | ALTER [COLUMN] column_name {
          SET DEFAULT const_value
        | DROP DEFAULT
      }
    | ALTER {CHECK | CONSTRAINT} symbol [NOT] ENFORCED
    | ALTER INDEX index_name [VISIBLE | INVISIBLE] [STORAGE_CACHE_POLICY = {"hot"|"auto"|"none"}]
    | ALTER INDEX index_name
          [VISIBLE | INVISIBLE]
    | CHANGE [COLUMN] column_name column_definition
    | DROP [COLUMN] column_name [, DROP COLUMN column_name ...]
    | DROP {PARTITION | SUBPARTITION} partition_name_list
    | DROP TABLEGROUP
    | DROP FOREIGN KEY fk_name
    | DROP PRIMARY KEY [, ADD PRIMARY KEY (column)]
    | DROP CHECK constraint_name
    | DROP COLUMN GROUP([all columns, ]each column)
    | DROP CLUSTERING KEY
    | MODIFY [COLUMN] column_definition
    | RENAME COLUMN old_col_name [TO|AS] new_col_name
    | RENAME [TO|AS] table_name
    | RENAME {INDEX | KEY} old_index_name [TO|AS] new_index_name
    | [SET] table_option_list
    | TRUNCATE {PARTITION | SUBPARTITION} partition_name_list
    | EXCHANGE PARTITION partition_name WITH TABLE origin_table_name WITHOUT VALIDATION
    | REORGANIZE PARTITION partition_name INTO (split_range_partition_list)
    | PARTITION BY {RANGE [COLUMNS]([column_name_list]) [SIZE('size_value')] [range_partition_list]
                   | partition_option}
    | MODIFY PARTITION partition_name ADD SUBPARTITION (add_subpartition_option)
    | ALTER {PARTITION | SUBPARTITION} partition_name STORAGE_CACHE_POLICY = {"hot" | "auto" | "none"}
    | FORCE
    | REMOVE TTL
    | {ENABLE | DISABLE} ROW LEVEL SECURITY
    | {FORCE | NO FORCE} ROW LEVEL SECURITY

column_definition_list:
    column_definition [, column_definition ...]

column_definition:
    column_name data_type
    [DEFAULT const_value] [AUTO_INCREMENT]
    [NULL | NOT NULL] [[PRIMARY] KEY] [UNIQUE [KEY]] [COMMENT string_value] [SKIP_INDEX(skip_index_option_list)] [ opt_position_column ]

skip_index_option_list:
    skip_index_option [,skip_index_option ...]

skip_index_option:
    MIN_MAX
    | SUM

opt_position_column:
    FIRST | BEFORE | AFTER column_name

   (column_desc_list) [index_type] [index_option_list]

    [| INCLUDE_TYPES = (type1[, type2]...)]
    [| NESTED_PATHS = ('path1'[, 'path2']...)]

index_type:
    USING BTREE

index_option_list:
    index_option [ index_option ...]

index_option:
     [GLOBAL | LOCAL]
    | block_size
    | compression
    | STORING(column_name_list)
    | COMMENT string_value
    | STORAGE_CACHE_POLICY (storage_cache_policy_option)

    SPACE
    | NGRAM
    | BENG
    | IK
    | NGRAM2
    | analyzer

parser_properties_list:

      TABLEGROUP = tablegroup_name
    | block_size
    | lob_inrow_threshold [=] num
    | compression
    | AUTO_INCREMENT [=] INT_VALUE
    | COMMENT string_value
    | parallel_clause
    | TABLE_MODE [=] 'table_mode_value'
    | AUTO_INCREMENT_CACHE_SIZE [=] INT_VALUE
    | READ {ONLY | WRITE}
    | DUPLICATE_SCOPE= 'none | cluster'
    | enable_macro_block_bloom_filter [=] {True | False}
    | DYNAMIC_PARTITION_POLICY [=] (dynamic_partition_policy_list)
    | SEMISTRUCT_ENCODING_TYPE [=] 'encoding' # Replaced by SEMISTRUCT_PROPERTIES.
    | SEMISTRUCT_PROPERTIES [=] (encoding_type=encoding|none[,freq_threshold=INT_VALUE])
    | STORAGE_CACHE_POLICY (storage_cache_policy_option)
    | CLUSTER BY (column_name_list)
    | HMS_CATALOG_NAME [=] string_value
    | COLUMN_NAME_CASE_SENSITIVE [=] {True | False}
    | DELTA_FORMAT [=] 'flat | encoding'
    | SKIP_INDEX_LEVEL [=] {1 | 0}
    | TTL col_name + INTERVAL interval_num ttl_unit BY COMPACTION
    | ASYNC_INDEX_PARAMS [=] 'async_index_params_string'

parallel_clause:
    {NOPARALLEL | PARALLEL integer}

table_mode_value:
    NORMAL
    | QUEUING
    | MODERATE
    | SUPER
    | EXTREME

dynamic_partition_policy_list:
    dynamic_partition_policy_option [, dynamic_partition_policy_option ...]

dynamic_partition_policy_option:
    ENABLE = {true | false}
    | PRECREATE_TIME = {'-1' | '0' | 'n {hour | day | week | month | year}'}
    | EXPIRE_TIME = {'-1' | '0' | 'n {hour | day | week | month | year}'}

partition_option:
      PARTITION BY HASH(expression)
      [subpartition_option] PARTITIONS partition_count
    | PARTITION BY KEY([column_name_list])
      [subpartition_option] PARTITIONS partition_count

    | SUBPARTITION BY KEY(column_name_list)
      SUBPARTITIONS subpartition_count
    | SUBPARTITION BY RANGE {(expression) | COLUMNS (column_name_list)}
      (range_subpartition_list)

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "cold" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit
    | MIXED_RETENTION = intnum retention_time_unit
    | GRANULARITY = "partition"

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE

split_range_partition_list:
    PARTITION split_partition_name VALUES LESS THAN (value)
    [, PARTITION split_partition_name VALUES LESS THAN (value) ...]
     , PARTITION split_partition_name VALUES LESS THAN (source_value)

range_partition_list:
    range_partition [, range_partition ...]

range_partition:
    PARTITION partition_name
    VALUES LESS THAN {(expression_list) | MAXVALUE}
    [STORAGE_CACHE_POLICY = {"hot" | "auto" | "cold" | "none"}]

range_subpartition_list:
    range_subpartition [, range_subpartition ...]

range_subpartition:
    SUBPARTITION subpartition_name
    VALUES LESS THAN {(expression_list) | MAXVALUE}
    [STORAGE_CACHE_POLICY = {"hot" | "auto" | "cold" | "none"}]

expression_list:
    expression [, expression ...]

column_name_list:
    column_name [, column_name ...]

partition_name_list:
    partition_name [, partition_name ...]

partition_count | subpartition_count:
    INT_VALUE

add_subpartition_option:
    {SUBPARTITION subpartition_name VALUES LESS THAN range_partition_expr
        [, SUBPARTITION subpartition_name VALUES LESS THAN range_partition_expr] ...}
    | {SUBPARTITION subpartition_name VALUES IN list_partition_expr
        [, SUBPARTITION subpartition_name VALUES IN list_partition_expr] ...}
```

### table_mode_value

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>In the <code>TABLE_MODE</code> modes listed below, all modes except for <code>NORMAL</code> mode represent <code>QUEUING</code> tables. This type of <code>QUEUING</code> table is the most basic table type, and the several modes listed later (except for NORMAL mode) represent more aggressive major compaction strategies.</p>
</main>

* `NORMAL`: The default value, indicating normal. In this mode, the probability of triggering a major compaction after a minor compaction is extremely low.
* `QUEUING`: In this mode, the probability of triggering a major compaction after a minor compaction is low.
* `MODERATE`: Moderate. In this mode, the probability of triggering a major compaction after a minor compaction is moderate.
* `SUPER`: Super. In this mode, a major compaction is more likely to be triggered after a minor compaction.
* `EXTREME`: Extreme. In this mode, the probability of triggering a major compaction after a minor compaction is higher.

For more information about major compactions, see [Adaptive compaction](../../../../200.system-management/500.manage-data-storage/200.merge-management/320.adaptive-compaction.md).

### tokenizer_option

* `SPACE`: The default value. Indicates that the text is segmented by spaces. The following attributes can be specified:

  |        Attribute      | Value range |
  |------------------|---------|
  | min_token_size   | [1, 16] |
  | max_token_size   | [10, 84]|

* `NGRAM`: Indicates the word segmentation method based on N-gram (Chinese). The following attributes can be specified:

  |        Attribute      | Value range |
  |------------------|---------|
  | ngram_token_size | [1, 10] |

* `NGRAM2`: Indicates that the text is split into consecutive characters within the range of `min_ngram_size` to `max_ngram_size`. The following attributes can be specified:

  |        Attribute      | Value range |
  |------------------|---------|
  | min_ngram_size   | [1, 16] |
  | max_ngram_size   | [1, 16] |

* `BENG`: word segmentation based on Beng (Basic English). The following attributes can be specified:

  |        Attribute      | Value range |
  |------------------|---------|
  | min_token_size   | [1, 16] |

  |        Attribute      | Value range |
  |------------------|---------|
  | ik_mode          | <ul><li>`smart`</li><li>`max_word`</li></ul>|

* `analyzer`: the text analyzer (Analyzer). It is used through the `analysis` parameter in `PARSER_PROPERTIES`.

You can use the [TOKENIZE](../400.functions-of-mysql-mode/960.text-processing-functions-of-mysql-mode/200.tokenize-of-mysql-mode.md) function to view the tokenization results of a text string using the specified tokenizer and JSON-formatted parameters.

### parser_properties

* `min_token_size`: The minimum token length. The default value is 3, and the valid range is 1 to 16.

* `max_token_size`: the maximum token length. The default value is 84, and the valid range is 10 to 84.

* `ngram_token_size`: The token length for `NGRAM`. This parameter is valid only for the `NGRAM` tokenizer. The default value is 2, and the valid range is 1 to 10.

* `ik_mode`: the stemming mode of the `IK` stemmer. Valid values:

  * `smart`: The default value. This mode prioritizes identifying longer words, reducing the number of splits and ensuring each character belongs to only one word. It also attempts to merge numerals with measure words into a single word in the output.
  * `max_word`: Outputs recognizable words as much as possible. Longer words and the shorter words within them are retained. The same character can appear in multiple words.

* `min_ngram_size`: Only valid for the `NGRAM2` tokenizer. Specifies the minimum number of characters for a generated n-gram. Value range: `[1, 16]`.

* `max_ngram_size`: Only valid for the `NGRAM2` tokenizer. Specifies the maximum number of characters for a generated n-gram. The value range is `[1, 16]`. The tokenizer generates consecutive character segments with lengths between the minimum and maximum values.

* `analysis`: Valid only when `WITH PARSER analyzer` is specified. Specifies the JSON definition string for the analyzer. Built-in analyzers can be abbreviated as `{"analyzer": "standard"}` and so on. For a complete list of built-in types and their corresponding languages, see the `analyzer_type` parameter description in [TOKENIZE](../400.functions-of-mysql-mode/960.text-processing-functions-of-mysql-mode/200.tokenize-of-mysql-mode.md).

**Example:**

1. Create table `tbl1`.

   ```sql
   CREATE TABLE tbl1 (col1 VARCHAR(200), col2 TEXT);
   ```

2. Add a full-text index named `fidx` to table `tbl1`.

   ```sql
   ALTER TABLE tbl1 ADD FULLTEXT INDEX fidx(col2) WITH PARSER ik PARSER_PROPERTIES=(ik_mode='max_word');
   ```

3. Add a full-text index using the built-in `english` analyzer to the `articles` table.

   ```sql
   ALTER TABLE articles ADD FULLTEXT INDEX ft_idx_body(body)
     WITH PARSER analyzer
     PARSER_PROPERTIES=(analysis='{"analyzer": "english"}');
   ```

### dynamic_partition_policy_option

* `ENABLE = {true | false}`: Specifies whether to enable dynamic partition management. Valid values:

  * `true`: The default value. It specifies to enable dynamic partition management.
  * `false`: Indicates that dynamic partition management is disabled.

* `PRECREATE_TIME = {'-1' | '0' | 'n {hour | day | week | month | year}'}`: Specifies the precreation time. When you schedule a dynamic partition management task, partitions are precreated so that **max_partition_upper_bound > now() + precreate_time**. Valid values:

  * `-1`: The default value, which indicates not to pre-create partitions.
  * `0`: Indicates that only the current partition is to be pre-created.
  * `n {hour | day | week | month | year}`: Indicates to pre-create partitions for the specified time span. For example, `3 hour` means to pre-create partitions for the next 3 hours.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p><ul><li>If multiple partitions need to be pre-created, the interval between partition boundaries is <code>TIME_UNIT</code>.</li><li>The boundary of the first pre-created partition is the existing maximum partition boundary rounded up by <code>TIME_UNIT</code>.</li></ul></p>
  </main>

* `EXPIRE_TIME = {'-1' | '0' | 'n {hour | day | week | month | year}'}`: Optional. Specifies the partition expiration time. When dynamic partition management is scheduled, all partitions whose **upper_bound < now() - expire_time** are deleted. This parameter can be modified. Valid values:

  * `-1`: The default value, indicating that the partition never expires.
  * `0`: Indicates that all partitions except the current one have expired.
  * `n {hour | day | week | month | year}`: the partition expiration time. For example, `1 day` indicates the partition expires in 1 day.

For more information about modifying a dynamically partitioned table, see [Modify a dynamic partitioned table](../../../../300.database-object-management/300.manage-partitions-of-mysql-mode/260.dynamic-partition-of-mysql-mode/400.modify-dynamic-partition-table-of-mysql-mode.md).

**Example:**

```sql
ALTER TABLE tbl2 SET DYNAMIC_PARTITION_POLICY(
    ENABLE = true,
    PRECREATE_TIME = '1 day',
    EXPIRE_TIME = '-1'
);
```

### storage_cache_policy

Different attributes in `storage_cache_policy_option` are defined in Key-Value format. The semantics of each attribute are as follows:

* `GLOBAL = {"hot" | "auto" | "cold" | "none"}`: Specifies the hot, auto, cold, or none storage strategy for all table data. Valid values:

  * `hot`: Indicates that all data in the specified table is hot data. If sufficient cache disk space is available, all data under the table will be cached to the local cloud disk.
  * `auto`: Indicates that the system automatically identifies the hot data for the specified table.
  * `cold`: Indicates that the data of the specified table is cold data and will not be cached to the local cache disk. For data that has already been persisted to the cache, cache eviction will be actively triggered. Subsequent accesses to the table data can be stored in the macroblock memory cache and will not be persisted to the macroblock cache.
  * `none`: Indicates that the index's policy follows the value of the primary table's `STORAGE_CACHE_POLICY`.

    <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>The <code>none</code> attribute can only be used for indexes.</p>
    </main>

* `timeline_strategy_list`: The list of timeline strategy parameters, separated by commas. Timeline strategies use time to determine whether partition data is stored in hot or cold storage. The system automatically adjusts the data on local cache disks based on the configured strategies.

    <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>Timeline: Hot data is cached based on the partitioning range defined by RANGE partitioning. When certain time conditions are met, the data in that partition is identified as hot data. When using the timeline strategy, note the following considerations:<ul><li>Only supported for RANGE-partitioned tables (RANGE partitioning can be at the primary or secondary level), because time is required to determine whether a partition has expired. However, it cannot be a dual RANGE partition, as it would be impossible to determine which RANGE partition's time to use.</li><li>When using the timeline strategy, the partition expression can only contain column names; expression conversion is not supported. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code>.</li><li><code>BOUNDARY_COLUMN</code> must be the partitioning key. If the partitioning key consists of multiple columns, <code>BOUNDARY_COLUMN</code> must be the first column, used to determine whether the partition has expired.</li></ul></p>
  </main>

* `BOUNDARY_COLUMN = column_name`: Identifies the column for hot data detection. Supports integer types (`BIGINT` or `INT`, in Unix timestamp format) and time types (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).
  * If the `BOUNDARY_COLUMN` type is integer, the table's partitioning method supports RANGE and RANGE COLUMNS partitioning types.
  * If `BOUNDARY_COLUMN` is of a time type, the table can only use the RANGE COLUMNS partitioning method.

* `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: Specifies the time unit for the `BOUNDARY_COLUMN` parameter. This parameter is supported only when `BOUNDARY_COLUMN` is an integer. When an integer value is used as a timestamp, a timestamp unit must be specified; otherwise, it may lead to incorrect time parsing. Valid values:

  * When the partitioning column is of type `INT`, the value of `BOUNDARY_COLUMN_UNIT` can only be `s`.
  * When the partitioning column is of the `BIGINT` type, the value of `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

      <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p>If the format is not a Unix timestamp, the time represented by the <code>INT</code> type cannot be correctly identified.</p>
      </main>

* `HOT_RETENTION = intnum retention_time_unit`: Specifies the time range for hot data.
  * `intnum`: an integer.
  * `retention_time_unit`: the time unit. Valid values:
    * `YEAR`: the year.
    * `MONTH`: the month.
    * `WEEK`: week.
    * `DAY`: day.
    * `HOUR`: the hour.
    * `MINUTE`: the number of minutes.

  <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p>You must set at least one of the parameters <code>HOT_RETENTION</code> and <code>MIXED_RETENTION</code> in the timeline syntax.</p>
  </main>

* `MIXED_RETENTION = intnum retention_time_unit`:

  * If `MIXED_RETENTION` is set, data within the time range of `HOT_RETENTION + MIXED_RETENTION` is considered `cold` data.
  * If `MIXED_RETENTION` is not set, the data remains `auto` after reaching `HOT_RETENTION`.
  * If `HOT_RETENTION` is not set, the time range of [0, MIXED_RETENTION] represents `auto` data, and the data after `MIXED_RETENTION` represents `cold` data.

* `GRANULARITY = "partition"` : Optional. Specifies the operation granularity for hot and cold data storage, indicating that caching data is handled at the partition level.

### partition_storage_cache_policy

`STORAGE_CACHE_POLICY = {"hot" | "auto" | "cold" | "none"}`: Specifies the hot, warm, or cold storage policy for partition data. Valid values:

* `hot`: specifies the partition as a hot storage. If there is sufficient cache disk space, all data in the partition will be cached to the local cloud disk.
* `auto`: Indicates that the system automatically identifies hot data in the specified partition.
* `cold`: Indicates that the data in the specified partition is cold data and will not be cached to the local cache disk. The system will proactively trigger cache eviction for data already persisted to the cache. Subsequent table data accesses can be stored in macroblock memory cache without being persisted to the macroblock cache.
* `none`: The default value. This means the partition's policy follows the value of the primary table's `STORAGE_CACHE_POLICY` field.

### Specify the table-level hot and cold storage strategy for an index when adding it to an existing table

The syntax is as follows:

```sql
ALTER TABLE table_name ADD INDEX index_name(column_name)
    STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

#### Related parameters

You can configure hot and cold storage policies for indexed tables:

* For local indexes, you can specify the table-level `STORAGE_CACHE_POLICY`. If the table-level `STORAGE_CACHE_POLICY` is not specified, the default is `none`, which means the configuration of the data table's `STORAGE_CACHE_POLICY` is used. The hot and cold storage policies for local index partitions then follow the partitioning rules of the data table.

* For global indexes, in addition to specifying the table-level `STORAGE_CACHE_POLICY`, you can also specify a partition-level `STORAGE_CACHE_POLICY` for the index table if it has partitions. If the table-level `STORAGE_CACHE_POLICY` is not specified for a global index, the default is `none`.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>If the table-level <code>STORAGE_CACHE_POLICY</code> is not specified for a global index, and the primary table uses the Global strategy, the index follows the primary table's <code>STORAGE_CACHE_POLICY</code> by default. If the primary table uses the timeline strategy, the index defaults to the <code>hot</code> strategy.</p>
  </main>

When setting the table-level `STORAGE_CACHE_POLICY`, different options within the `storage_cache_policy_option` parameter are defined in Key-Value format. The semantics of each option are as follows:

* `GLOBAL = {"hot" | "auto" | "cold" | "none"}`: Specifies the hot, auto, cold, or none storage strategy for index data. Valid values:

  * `hot`: specifies the index as a hot storage. If there is sufficient cache disk space, all data under the index table will be cached to the local cache disk.
  * `auto`: Indicates that the system automatically identifies hot data in the specified index table.
  * `cold`: Indicates that the data of the specified index table is cold data and will not be cached to the local cache disk. For data already persisted to the cache, cache eviction will be actively triggered. Subsequent accesses to the table data can be stored in the macroblock memory cache and will not be persisted to the macroblock cache.
  * `none`: The default value. This means the index follows the `STORAGE_CACHE_POLICY` value of the primary table.

* `timeline_strategy_list`: The list of timeline strategy parameters, separated by commas. Timeline strategies use time to determine whether partition data is stored in hot or cold storage. The system automatically adjusts the data on local cache disks based on the configured strategies.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>Timeline: Hot data is cached based on the partitioning range defined by RANGE partitioning. When certain time conditions are met, the data in that partition is identified as hot data. When using the timeline strategy, note the following considerations:<ul><li>Only supported for RANGE-partitioned tables (RANGE partitioning can be at the primary or secondary level), because time is required to determine whether a partition has expired. However, it cannot be a dual RANGE partition, as it would be impossible to determine which RANGE partition's time to use.</li><li>When using the timeline strategy, the partition expression can only contain column names; expression conversion is not supported. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code>.</li><li><code>BOUNDARY_COLUMN</code> must be the partitioning key. If the partitioning key consists of multiple columns, <code>BOUNDARY_COLUMN</code> must be the first column, used to determine whether the partition has expired.</li></ul></p>
  </main>

  * `BOUNDARY_COLUMN = column_name`: specifies the column for identifying hot data. The column name can be of an integer type (`BIGINT` or `INT`, in the format of a Unix timestamp) or a time type (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).

    * If `BOUNDARY_COLUMN` is of the integer type, the table supports RANGE and RANGE COLUMNS partitioning.
    * If the `BOUNDARY_COLUMN` type is a time type, the table can only use the RANGE COLUMNS partitioning method.

  * `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: Specifies the time unit for the `BOUNDARY_COLUMN` parameter. This parameter is supported only when `BOUNDARY_COLUMN` is an integer. When an integer value is used as a timestamp, a timestamp unit must be specified; otherwise, it may lead to incorrect time parsing. Valid values are as follows:

    * When the partitioning column is of type `INT`, the value of `BOUNDARY_COLUMN_UNIT` can only be `s`.
    * When the partitioning column is of the `BIGINT` type, the value of `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

  * `HOT_RETENTION = intnum retention_time_unit`: Specifies the time range for hot data.

    * `intnum`: an integer.
    * `retention_time_unit`: the time unit. Valid values:

      * `YEAR`: the year.
      * `MONTH`: the month.
      * `WEEK`: week.
      * `DAY`: day.
      * `HOUR`: the hour.
      * `MINUTE`: the number of minutes.

#### Examples

* Specify the table-level `STORAGE_CACHE_POLICY` for the index during creation:

  1. Create table `tbl3`.

      ```sql
      CREATE TABLE tbl3 (col1 INT, col2 INT, col3 INT);
      ```

  2. Create index `idx1_tbl3` and specify the data in the index table as hot data.

      ```sql
      CREATE INDEX idx1_tbl3 ON tbl3 (col1) LOCAL 
          STORAGE_CACHE_POLICY (GLOBAL = "hot");
      ```

* Create an index when creating a table and specify the index table's data as hot data.

    ```sql
    CREATE TABLE tbl4 (col1 INT, col2 INT,
        INDEX idx2 ((col1 + 1)) STORAGE_CACHE_POLICY (GLOBAL = "hot"), UNIQUE KEY ((col1 + col2)));
    ```

* When adding an index to an existing table, specify the data in the index table as hot data.

    ```sql
    ALTER TABLE tbl4 ADD INDEX idx3(col1, col2) GLOBAL 
        STORAGE_CACHE_POLICY (GLOBAL = "hot");
    ```

OceanBase AI Database does not support modification or will not automatically cascade modifications in the following scenarios:

* If a renamed column is referenced by a generated list expression, the column name cannot be modified; otherwise, an error will occur during execution.

  ```shell
  obclient> CREATE TABLE tbl12(a INT, b INT AS (a + 1), c INT, d INT, CONSTRAINT d_check CHECK(d > 0)) PARTITION BY HASH(c + 1) PARTITIONS 2;

  obclient> ALTER TABLE tbl12 RENAME COLUMN a TO e;
  ERROR 3108 (HY000): Column 'a' has a generated column dependency
  ```

* If a renamed column is referenced by a partitioning expression, the column name cannot be modified, otherwise an error will occur during execution.

  ```shell
  obclient> ALTER TABLE tbl12 RENAME COLUMN c TO e;
  ERROR 3855 (HY000): Column 'c' has a partitioning function dependency and cannot be dropped or renamed.
  ```

* If a renamed column is referenced by a `CHECK` constraint, the column name cannot be modified, otherwise an error will occur during execution.

  ```shell
  obclient> ALTER TABLE tbl12 RENAME COLUMN d TO e;
  ERROR 3959 (HY000): Check constraint 'd_check' uses column 'd', hence column cannot be dropped or renamed.
  ```

* If a renamed column is referenced by a functional index, the column name cannot be modified; otherwise, an error will occur during execution.

  ```shell
  DROP TABLE IF EXISTS tbl12;
  obclient> CREATE TABLE tbl12(i INT, INDEX ((i+1)));
  Query OK, 0 rows affected

  obclient> ALTER TABLE tbl12 RENAME COLUMN i TO j;
  ERROR 3837 (HY000): Column 'i' has a functional index dependency and cannot be dropped or renamed.
  ```

* If a renamed column is referenced by a view, the `RENAME COLUMN` statement executes successfully, but querying the view will report an error. You must manually modify the view definition.

  ```shell
  obclient> CREATE TABLE tbl13(a INT);
  Query OK, 0 rows affected

  obclient> CREATE VIEW v1 AS SELECT a + 1 FROM tbl13;
  Query OK, 0 rows affected

  obclient> SELECT * FROM v1;
  Empty set

  obclient> ALTER TABLE tbl13 RENAME COLUMN a TO b;
  Query OK, 0 rows affected

  obclient> SELECT * FROM v1;
  ERROR 1356 (42S22): View 'test.v1' references invalid table(s) or column(s) or function(s) or definer/invoker of view lack rights to use them
  ```

* A renamed column is referenced by a stored procedure. The `RENAME COLUMN` statement executes successfully, but the `CALL` procedure reports an error, requiring manual modification by the user.

  ```shell
  obclient> CREATE TABLE tbl14(a INT);
  Query OK, 0 rows affected

  obclient> CREATE PROCEDURE proc() SELECT a + 1 FROM tbl14;
  Query OK, 0 rows affected

  obclient> CALL proc();
  Empty set

  obclient> ALTER TABLE tbl14 RENAME COLUMN a TO b;
  Query OK, 0 rows affected

  obclient> CALL proc();
  ERROR 1054 (42S22): Unknown column 'a' in 'field list'
  ```

### Modify the columnar storage attributes of a table

1. Use the following SQL statement to create table `tbl1`.

   ```sql
   CREATE TABLE tbl1 (col1 INT PRIMARY KEY, col2 VARCHAR(50));
   ```

2. Change the `tbl1` table to a hybrid row-column storage table, and then drop the hybrid row-column storage attribute.

   ```sql
   ALTER TABLE tbl1 ADD COLUMN GROUP(all columns, each column);
   ```

   ```sql
   ALTER TABLE tbl1 DROP COLUMN GROUP(all columns, each column);
   ```

3. Change table `tbl1` to a columnar storage table, and then drop the columnar storage attribute.

   ```sql
   ALTER TABLE tbl1 ADD COLUMN GROUP(each column);
   ```

   ```sql
   ALTER TABLE tbl1 DROP COLUMN GROUP(each column);
   ```

### Modify the skip index attribute of a column

Use the following SQL statement to create a table named `test_skidx`.

```sql
CREATE TABLE test_skidx(
  col1 INT SKIP_INDEX(MIN_MAX, SUM),
  col2 FLOAT SKIP_INDEX(MIN_MAX),
  col3 VARCHAR(1024) SKIP_INDEX(MIN_MAX),
  col4 CHAR(10)
  );
```

* Modify the skip index attribute of column `col2` in table `test_skidx` to `SUM` Skip Index.

  ```sql
  ALTER TABLE test_skidx MODIFY COLUMN col2 FLOAT SKIP_INDEX(SUM);
  ```

* Add a column with a skip index attribute after table creation. Add a `MIN_MAX` skip index type for column `col4` in table `test_skidx`.

  ```sql
  ALTER TABLE test_skidx MODIFY COLUMN col4 CHAR(10) SKIP_INDEX(MIN_MAX);
  ```

* Remove a column with a skip index attribute after table creation. Remove the skip index attribute for column `col1` in table `test_skidx`.

  ```sql
  ALTER TABLE test_skidx MODIFY COLUMN col1 INT SKIP_INDEX();
  ```

  or

  ```sql
  ALTER TABLE test_skidx MODIFY COLUMN col1 INT;
  ```

### Modify table-level STORAGE_CACHE_POLICY

* Change the hot cache for table `tbl1` to be automatically identified by the system.

  ```sql
  ALTER TABLE tbl1 SET STORAGE_CACHE_POLICY (GLOBAL = "auto");
  ```

* Modify table `tbl2` to identify partition data within 2 months from the current time as hot data based on the value of `col3`.

  ```sql
  ALTER TABLE tbl2 SET STORAGE_CACHE_POLICY (BOUNDARY_COLUMN = col3, HOT_RETENTION = 2 MONTH); 
  ```

### Modify the partition-level STORAGE_CACHE_POLICY

* Add partition p2 to table `tbl3`. The system automatically identifies the hot data that needs to be cached to the local disk in partition p2.

  ```sql
  ALTER TABLE tbl3 ADD PARTITION (PARTITION p2 VALUES LESS THAN(300) STORAGE_CACHE_POLICY = "auto");
  ```

* Modify the data in the existing partition p1 of table `tbl3` to hot data.

  ```sql
  ALTER TABLE tbl3 ALTER PARTITION p1 STORAGE_CACHE_POLICY = 'hot';
  ```

* The data that needs to be cached to the local disk in subpartition sp3 of table `tbl4` is automatically identified by the system.

  ```sql
  ALTER TABLE tbl4 ALTER SUBPARTITON sp3 STORAGE_CACHE_POLICY = 'auto';
  ```

### Modify or delete a table's TTL policy

* Modify the table's TTL policy. For example, change the data expiration time to 1 hour.

  ```shell
  obclient(root@mysql001)[infotest]> ALTER TABLE ttl_tbl1 SET TTL ORA_ROWSCN + INTERVAL 1 HOUR BY COMPACTION;
  ```

* The TTL strategy for deleting tables.

  ```shell
  obclient(root@mysql001)[infotest]> ALTER TABLE ttl_tbl1 SET REMOVE TTL;
  ```

* Enable row-level privileges on tables and enforce policy restrictions on table owners as well.

  ```sql
  ALTER TABLE hr.employees ENABLE ROW LEVEL SECURITY;
  ALTER TABLE hr.employees FORCE ROW LEVEL SECURITY;
  ```

* Removed mandatory row-level privileges and disabled them.

  ```sql
  ALTER TABLE hr.employees NO FORCE ROW LEVEL SECURITY;
  ALTER TABLE hr.employees DISABLE ROW LEVEL SECURITY;
  ```

### Add or modify an async index

Example of adding an asynchronous full-text index (the target table must be a heap table):

```sql
ALTER TABLE doc_async ADD ASYNC FULLTEXT INDEX idx_content(content);
```

Example of adding an asynchronous search index (the target table must be a heap table):

```sql
ALTER TABLE t ADD ASYNC SEARCH INDEX idx_search(doc);
```

The following example shows how to modify the table-level configuration of an async index:

```sql
ALTER TABLE doc_async SET ASYNC_INDEX_PARAMS = 'ASYNC_REFRESH_INTERVAL=10';
```

Modify multiple configurations at the same time:

```sql
ALTER TABLE doc_async SET ASYNC_INDEX_PARAMS = 'ASYNC_REFRESH_INTERVAL=10, DELETE_PURGE_THRESHOLD=30, MERGE_SEGMENT_THRESHOLD=8';
```

Skip abnormal rows during incremental refresh:

```sql
ALTER TABLE doc_async SET ASYNC_INDEX_PARAMS = 'REFRESH_ON_ERROR=SKIP';
```
