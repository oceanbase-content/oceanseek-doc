# DELETE BACKUP POLICY

The `ADD DELETE BACKUP POLICY` statement and the `DROP DELETE BACKUP POLICY` statement are used to set and drop a cleanup policy, respectively.

To enable automatic cleanup for users, you can use the `ADD DELETE BACKUP POLICY` statement to set a cleanup policy for a tenant. A tenant with a cleanup policy will trigger an automatic cleanup task every hour.

During the execution of a cleanup task, if you only want to cancel the ongoing cleanup task, you can execute the `CANCELE DELETE BACKUP` statement. For more information about the `CANCELE DELETE BACKUP` statement, see [CANCEL DELETE BACKUP](900.cancel-delete-backup.md). If you want to prevent the cleanup task from being scheduled for execution in the future, you must first execute the `DROP DELETE BACKUP POLICY` statement to remove the automatic cleanup policy, and then execute the `CANCELE DELETE BACKUP` statement to cancel the ongoing cleanup task.

## Limitations and considerations

* When using the `ADD DELETE BACKUP POLICY` statement to set a cleanup policy, only tenant-level automatic cleanup policies are supported; cluster-level cleanup policies are not supported.

* Each command can set or remove only one cleanup strategy for a tenant.

* When you use the `DROP DELETE BACKUP POLICY` statement to drop a tenant's cleanup policy, if all cleanup policies for the tenant are dropped, the automatic cleanup feature for that tenant is effectively disabled.

* Dropping a cleanup policy using the `DROP DELETE BACKUP POLICY` statement does not affect ongoing cleanup tasks. It only means that the system will no longer generate cleanup tasks for the dropped policy during the next automatic cleanup scheduling.

## Privilege requirements

This statement must be executed by the `root` user of the `sys` tenant (`root@sys`) or the administrator user of a user tenant (`root` user).

## Syntax

```sql
ALTER SYSTEM delete_backup_action [ TENANT [=] tenant_name ];

delete_backup_action:
      ADD DELETE BACKUP POLICY [=] policy_name [RECOVERY_WINDOW [=] recovery_window]
    | DROP DELETE BACKUP POLICY [=] policy_name
```

## Parameters

| Parameter | Description |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- |
| POLICY | Specifies the cleanup policy name. Valid values: <ul><li>`default`: Indicates that the automatic cleanup scope is limited to the backups specified by the current tenant's `DATA_BACKUP_DEST` and `LOG_ARCHIVE_DEST` parameters. </li> <li>`log_only`: Indicates that the automatic cleanup scope is limited to the logs in the archive path specified by the current tenant's `LOG_ARCHIVE_DEST` parameter. This applies to scenarios where no data backup is performed and only log archiving is enabled. Furthermore, when the cleanup policy is set to `log_only`, the value of the current `DATA_BACKUP_DEST` parameter must be empty, indicating that no data backup destination has been configured. Accordingly, if the cleanup policy is set to `log_only`, the `DATA_BACKUP_DEST` parameter cannot be set. </li></ul> |
| RECOVERY_WINDOW | Optional. Controls the time window within which backup data can be restored. If this parameter is not explicitly specified, the default time window is 0 days, meaning the backup set will not expire and the system will not perform cleanup. For more information about this parameter, see [Introduction to backup cleanup parameters](../../../../../600.manage/600.backup-and-recovery/500.clear-backup-data/500.parameters-of-cleaning-up-backup.md). |
| tenant_name | Optional. The name of the tenant. This parameter is required only when the statement is executed by the system tenant. |

## Examples

* System tenant

  * The system tenant sets the cleanup strategy for the `mysql_tenant` tenant to `default`, with a recoverable time window of 7 days for backup data.

    ```shell
    obclient [oceanbase]> ALTER SYSTEM ADD DELETE BACKUP POLICY = 'default' RECOVERY_WINDOW ='7d' TENANT = mysql_tenant;
    ```

    After successful configuration, you can use the following statement to view the cleanup strategy set for the tenant.

    ```sql
    obclient [oceanbase]> SELECT * FROM oceanbase.CDB_OB_BACKUP_DELETE_POLICY WHERE TENANT_ID=1002;
    ```

    The query result is as follows:

    ```shell
    +-----------+-------------+-----------------+
    | TENANT_ID | POLICY_NAME | RECOVERY_WINDOW |
    +-----------+-------------+-----------------+
    |      1002 | default     | 7d              |
    +-----------+-------------+-----------------+
    1 row in set
    ```

  * The system tenant's cleanup policy `default` for deleting the `mysql_tenant` tenant.

    ```shell
    obclient [oceanbase]> ALTER SYSTEM DROP DELETE BACKUP POLICY 'default' TENANT mysql_tenant;
    ```

* User tenant

  * The tenant `mysql_tenant` has its cleanup policy set to `default`, and the time window for restoring backed-up data is 7 days.

    ```shell
    obclient [SYS]> ALTER SYSTEM ADD DELETE BACKUP POLICY 'default' RECOVERY_WINDOW '7d';
    ```

    After the cleanup policy is successfully set, you can use the following statement to view the cleanup policies set for the current tenant.

    ```sql
    obclient [SYS]> SELECT * FROM SYS.DBA_OB_BACKUP_DELETE_POLICY;
    ```

    The query result is as follows:

    ```shell
    +-------------+-----------------+
    | POLICY_NAME | RECOVERY_WINDOW |
    +-------------+-----------------+
    | default     | 7d              |
    +-------------+-----------------+
    1 row in set
    ```

  * The cleanup policy for the tenant `mysql_tenant` when it is deleted.

    ```shell
    obclient [SYS]> ALTER SYSTEM DROP DELETE BACKUP POLICY 'default';
    ```
