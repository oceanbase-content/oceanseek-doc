# Modify a table-level hot/cold storage policy

This topic describes how to modify the hot/cold storage policy (`STORAGE_CACHE_POLICY`) at the table level by using SQL statements:

* Modify the hot/cold storage policy for a regular table.
* Modify the hot/cold storage policy for an index table.

## Modify a hot/cold storage policy for a regular table

After a table is created, you can use the `ALTER TABLE` statement to modify its hot/cold storage policy (`STORAGE_CACHE_POLICY`). The syntax is as follows:

```sql
ALTER TABLE table_name SET STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "cold"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit
    | MIXED_RETENTION = intnum retention_time_unit
    | GRANULARITY = "partition"

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

### Related parameters

The attributes in `storage_cache_policy_option` are defined in Key-Value format. The semantics of each attribute are as follows:

* `GLOBAL = {"hot" | "auto" | "cold"}`: Specifies the hot/cold storage policy for all data in the table. Valid values:

  * `hot`: Indicates that all data in the specified table is hot data. If sufficient cache disk space is available, all data under the table will be cached to the local cache disk.
  * `auto`: Indicates that the system automatically identifies the hot data for the specified table.
  * `cold`: Indicates that the data in the specified table is cold data and will not be cached to the local cache disk. For data already persisted to the cache, cache eviction is actively triggered. Subsequent accesses to the table data can be stored in the macroblock memory cache and will not be persisted to the macroblock cache.

* `timeline_strategy_list`: Indicates the list of timeline strategy parameters, separated by commas. The timeline strategy determines whether partition data is hot or cold based on time, and the system automatically adjusts the data on the local cache disk according to the configured strategy.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>Timeline: Hot data caching is performed based on the partition range defined by the RANGE partitioning. When certain time conditions are met, the data in that partition is identified as hot data. When using the timeline strategy, note the following considerations:<ul><li>Only supported for RANGE-partitioned tables (RANGE partitioning can be at the primary or secondary level), because time is needed to determine if it has expired. However, it cannot be a dual RANGE partition, as it would be unclear which RANGE partition time to use.</li><li>When using the timeline strategy, the partition expression can only contain column names; expression conversion is not supported. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code>.</li><li><code>BOUNDARY_COLUMN</code> must be the partitioning key. If the partitioning key consists of multiple columns, <code>BOUNDARY_COLUMN</code> must be the first column, used to determine whether the partition has expired.</li></ul></p>
  </main>

  * `BOUNDARY_COLUMN = column_name`: Specifies the column for identifying hot data. Supports integer types (`BIGINT` or `INT`, in Unix timestamp format) and time types (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).

    * If `BOUNDARY_COLUMN` is of an integer type, the table's partitioning method supports RANGE or RANGE COLUMNS partitioning.
    * If `BOUNDARY_COLUMN` is of a time type, the table's partitioning method can only use RANGE COLUMNS partitioning.

  * `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: Specifies the time unit for the `BOUNDARY_COLUMN` parameter. This parameter is only supported when `BOUNDARY_COLUMN` is an integer. When an integer value is used as a timestamp, a timestamp unit must be provided; otherwise, it may lead to incorrect time parsing. Valid values:

    * When the partitioning column is of type `INT`, the value for `BOUNDARY_COLUMN_UNIT` can only be `s`.
    * When the partitioning column is of type `BIGINT`, the value for `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

      <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p>If the format is not a Unix timestamp, the time represented by <code>INT</code> type will not be correctly identified.</p>
      </main>

  * `HOT_RETENTION = intnum retention_time_unit`: Configures the time range for hot data.

    * `intnum`: Represents an integer.
    * `retention_time_unit`: Represents a time unit. Valid values:

      * `YEAR`: Represents years.
      * `MONTH`: Represents months.
      * `WEEK`: Represents weeks.
      * `DAY`: Represents days.
      * `HOUR`: Represents hours.
      * `MINUTE`: Represents minutes.

  * `MIXED_RETENTION = intnum retention_time_unit`:

    * If `MIXED_RETENTION` is set, data within the time range of `HOT_RETENTION + MIXED_RETENTION` is classified as `cold` data.
    * If `MIXED_RETENTION` is not set, data remains `auto` data after reaching `HOT_RETENTION`.
    * If `HOT_RETENTION` is not set, the time range [0, MIXED_RETENTION] is classified as `auto` data, and data after `MIXED_RETENTION` is classified as `cold` data.

  * `GRANULARITY = "partition"`: Optional. Specifies the operation granularity for classifying data as hot or cold, indicating that the caching strategy is processed at the partition level.

### Examples

* Modify table `tbl1` so that the system automatically identifies hot data.

    ```shell
    obclient> ALTER TABLE tbl1 SET STORAGE_CACHE_POLICY (GLOBAL = "auto");
    ```

* Modify table `tbl2_date` so that hot data identified by `col3` becomes cold data directly after being considered hot for 2 months.

    ```shell
    obclient> ALTER TABLE tbl2_date SET STORAGE_CACHE_POLICY (
        BOUNDARY_COLUMN = col3,
        HOT_RETENTION = 2 MONTH,
        MIXED_RETENTION = 0 HOUR);
    ```

* Modify the timeline strategy for table `tbl2_int` so that hot data becomes `AUTO` after 3 years.

    ```shell
    obclient> ALTER TABLE tbl2_int STORAGE_CACHE_POLICY (
        BOUNDARY_COLUMN = col3,
        BOUNDARY_COLUMN_UNIT = 'ms',
        HOT_RETENTION = 3 YEAR);
    ```

## Modify a hot/cold storage policy for an index table

You can use the `ALTER TABLE` statement to modify the hot/cold storage policy (`STORAGE_CACHE_POLICY`) of an existing index. The syntax is as follows:

```sql
ALTER TABLE table_name ALTER INDEX index_name STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "cold" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    | BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit
    | MIXED_RETENTION = intnum retention_time_unit
    | GRANULARITY = "partition"

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

### Related parameters

* `GLOBAL = {"hot" | "auto" | "cold" | "none"}`: Specifies the hot/cold storage policy for index data. Valid values:

  * `hot`: Specifies the index for hot storage. If sufficient cache disk space is available, all data under the index table will be cached to the local cache disk.
  * `auto`: Indicates that the system automatically identifies hot data for the index table.
  * `cold`: Indicates that the index table data is cold data, which will not be cached to the local cache disk. For data already persisted to the cache, cache eviction is actively triggered. Subsequent accesses to the index data can be stored in the macroblock memory cache and will not be persisted to the macroblock cache.
  * `none`: The default value, indicating that the index's policy follows the primary table's `STORAGE_CACHE_POLICY` value.

* `timeline_strategy_list`: Indicates the list of timeline strategy parameters, separated by commas. The timeline strategy determines whether partition data is hot or cold based on time, and the system automatically adjusts the data on the local cache disk according to the configured strategy.

However, it cannot be a dual RANGE partition, as it would be unclear which RANGE partition time to use.</li><li>When using the timeline strategy, the partition expression can only contain column names; expression conversion is not supported.   * `BOUNDARY_COLUMN = column_name`: Specifies the column for identifying hot data. Supports integer types (`BIGINT` or `INT`, in Unix timestamp format) and time types (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).

    * If `BOUNDARY_COLUMN` is of an integer type, the table's partitioning method supports RANGE/RANGE COLUMNS partitioning.
    * If `BOUNDARY_COLUMN` is of a time type, the table's partitioning method can only use RANGE COLUMNS partitioning.

  * `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: Specifies the time unit for the `BOUNDARY_COLUMN` parameter. This parameter is only supported when `BOUNDARY_COLUMN` is an integer. When an integer value is used as a timestamp, a timestamp unit must be provided; otherwise, it may lead to incorrect time parsing. Valid values:

    * When the partitioning column is of type `INT`, the value for `BOUNDARY_COLUMN_UNIT` can only be `s`.
    * When the partitioning column is of type `BIGINT`, the value for `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

  * `HOT_RETENTION = intnum retention_time_unit`: Configures the time range for hot data.

    * `intnum`: Represents an integer.
    * `retention_time_unit`: Represents a time unit. Valid values:

      * `YEAR`: Represents a year.
      * `MONTH`: Represents a month.
      * `WEEK`: Represents a week.
      * `DAY`: Represents a day.
      * `HOUR`: Represents an hour.
      * `MINUTE`: Represents a minute.

  * `MIXED_RETENTION = intnum retention_time_unit`:

    * If `MIXED_RETENTION` is set, data beyond the time range of `HOT_RETENTION + MIXED_RETENTION` is considered `cold` data.
    * If `MIXED_RETENTION` is not set, data becomes `auto` data after reaching `HOT_RETENTION`.
    * If `HOT_RETENTION` is not set, the time range [0, MIXED_RETENTION] is `auto` data, and data after `MIXED_RETENTION` is `cold` data.

  * `GRANULARITY = "partition"`: Optional. Specifies the operation granularity for hot/cold data storage, indicating that the caching strategy processes data at the partition level.

### Examples

Modify index `idx2` so that the system automatically identifies its hot data.

```sql
ALTER TABLE test_tbl2 ALTER INDEX idx2
    STORAGE_CACHE_POLICY (GLOBAL = "auto");
```
