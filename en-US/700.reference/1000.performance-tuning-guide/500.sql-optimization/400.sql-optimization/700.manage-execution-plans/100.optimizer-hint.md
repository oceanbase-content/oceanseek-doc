# Optimizer hint

The hint mechanism allows the optimizer to generate a specified execution plan.

Generally, the optimizer selects the best execution plan for a user query without the need for hints. However, in certain scenarios, the optimizer's generated execution plan may not meet the user's requirements. In such cases, you can use hints to specify the desired execution plan.

## Hint syntax

From a syntax perspective, a hint is a special SQL comment. The difference is that after the left delimiter of the comment (the "/\*" symbol), a "+" is added. Since it is a comment, if the server cannot recognize the hint in the SQL statement, the optimizer will ignore the hint and use the default plan generation logic. Additionally, hints only affect the logical structure of the plan generated by the optimizer and do not affect the semantics of the SQL statement.

```sql
{ DELETE | INSERT | SELECT | UPDATE | REPLACE } /*+ [hint_text][,hint_text]... */
```

    <h4>Notice</h4>
    <p>If you use the MySQL C client to execute SQL statements with hints, you must log in using the <code>-c</code> option. Otherwise, the MySQL client will remove the hints as comments from the user's SQL statements, preventing the system from receiving the user's hints.</p>
  </main>

## QB_NAME parameter

In DML statements, each `query_block` has a `QB_NAME` (Query Block Name), which can be specified by the user or automatically generated by the system. If the user does not specify `QB_NAME` using hints, the system generates it in the order of `SEL$1`, `SEL$2`, `UPD$1`, and `DEL$1` from left to right (which is also the resolution order of the resolver).

`QB_NAME` can be used to precisely locate a table or to specify the behavior of any query block at a certain point. The `QB_NAME` in `TBL_NAME` is used to locate a table, and the first `QB_NAME` in a hint is used to specify which `query_block` the hint applies to.

As shown in the following example, according to the default rules, the `t1_c1` path is selected for the `t1` table in `SEL$1`, and the primary table access is selected for the `t2` table in `SEL$2`.

Query OK, 0 rows affected

obclient> CREATE TABLE t2(c1 INT, c2 INT, KEY t2_c1(c1));
Query OK, 0 rows affected

The SQL in the preceding example can also be written in the following ways:

```sql
SELECT /*+INDEX(t1 PRIMARY) INDEX(@SEL$2 t2@SEL$2 t2_c1)*/ * FROM t1 , (SELECT * FROM t2 WHERE c2 = 1 LIMIT 5) WHERE t1.c1 = 1;
```

or:

```sql
SELECT /*+INDEX(t1 PRIMARY)*/ * FROM t1 , (SELECT /*+INDEX(t2 t2_c1)*/ * FROM t2 WHERE c2 = 1 LIMIT 5) WHERE t1.c1 = 1;
```

or:

```sql
SELECT /*+INDEX(@SEL$1 t1 PRIMARY) INDEX(@SEL$2 t2 t2_c1)*/ * FROM t1 , (SELECT * FROM t2 WHERE c2 = 1 LIMIT 5) WHERE t1.c1 = 1;
```

## Hint usage rules

The general usage rules for hints are as follows:

* If a hint does not specify a query block, it applies to the current query block.

  **Example 1:** The `t2` table is in Query Block 2, and it cannot be rewritten to Query Block 1. Therefore, the hint does not take effect.

## Common hints and syntax

Compared with other databases, the optimizer of OceanBase AI Database is dynamic programming and has considered all possible optimal paths. Hints mainly specify the behavior of the optimizer and execute SQL queries based on the hints.

### INDEX Hint

The syntax of the `INDEX` hint is as follows.

* The MySQL syntax for the `INDEX` hint is as follows:

```sql
table_name [[AS] alias] [index_hint_list]

index_hint_list:
index_hint [, index_hint] ...

index_hint:
USE {INDEX|KEY}
  [FOR {JOIN|ORDER BY|GROUP BY}] ([index_list])
  | IGNORE {INDEX|KEY}
  [FOR {JOIN|ORDER BY|GROUP BY}] (index_list)
  | FORCE {INDEX|KEY}
  [FOR {JOIN|ORDER BY|GROUP BY}] (index_list)

index_list:
index_name [, index_name] ...
```

OceanBase AI Database in MySQL-compatible mode supports specifying multiple `INDEX` hints. However, for the `USE` and `FORCE` methods, only the first `INDEX` is used to generate the path, even if the SQL statement does not include a `filter` for that `INDEX` and a full scan with subsequent table access occurs. This is because OceanBase AI Database currently assumes that the writer of the hint knows better than the program which path is preferable. The `IGNORE` method ignores all specified indexes. If the `INDEX` specified for this method does not exist or is in the `invalid` state, the hint is ineffective. For the `IGNORE` method, if all indexes, including those of the primary table, are ignored, the hint is ineffective.

In SQL statements, if a table name has an alias, written as `table_name [AS] alias`, the alias must be specified for the `INDEX` hint to take effect. Here is an example:

### FULL Hint

The `FULL` hint specifies a full table scan for the specified table. The syntax is as follows:

```sql
/*+ FULL(table_name)*/
```

The `FULL` hint specifies a full table scan for the specified table, which is equivalent to the `INDEX` hint `/*+ INDEX(table_name PRIMARY)*/`.

### ORDERED Hint

The `ORDERED` hint specifies the join order based on the order of tables after the `FROM` keyword. The syntax is as follows:

```sql
/*+ ORDERED */
```

If the SQL statement is rewritten after you specify this hint, the join order follows the From Items of the rewritten `stmt`, because the `sub_query` is placed at the corresponding position in the From Items during rewriting.

### LEADING Hint

The `LEADING` hint specifies the join order of tables. The syntax is as follows:

```sql
/*+ LEADING(table_name_list)*/
```

### USE_MERGE Hint

The `USE_MERGE` hint specifies that the specified table is used as the right table when the Merge Join algorithm is used. The syntax is as follows:

```sql
/*+ USE_MERGE(table_name_list) */
```

  <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p>In OceanBase AI Database, Merge Join requires an equality condition in the <code>join-condition</code>. Therefore, if two tables without an equality condition are joined, the <code>use_merge</code> hint is ineffective.</p>
  </main>

Currently, there is no definitive conclusion on whether A Merge Join B is equivalent to B Merge Join A. According to the cost model, Merge Join distinguishes between the left and right tables when calculating the cost, which increases the flexibility of the hint. Therefore, Merge Join distinguishes between the left and right tables, and the `use_merge` hint takes effect only when the table is used as the right table.

### USE_NL Hint

The basic structure of hints related to joins is as follows:
`join_hint_name ( @ qb_name table_name_list)`
The basic semantics are that when the right table matches the table_name_list, a plan is generated based on the hint semantics. Generally, the `LEADING` hint is used to specify the join order, making the tables in the table_name_list the right tables. Otherwise, the hint becomes ineffective as the join order changes.

The table_name_list can be in the following forms:

* Single table use_nl ( t1 ): Use Nested Loop Join when t1 is the right table.
* Multiple single tables use_nl ( t1 t2 ... ): Use Nested Loop Join when t1 or t2 is the right table.
* Multiple tables use_nl ( (t1 t2) ): Use Nested Loop Join when t1 join t2 is the right table, ignoring the join order and method of t1 and t2.
* Multiple groups of tables use_nl ( t1 (t2 t3)  (t4 t5 t6) ... ): Use Nested Loop Join when t1 / t2 join t3 / t4 join t5 join t6 is the right table.

The `USE_NL` hint specifies that the specified table is used as the right table when the Nested Loop Join algorithm is used. The syntax is as follows:

```sql
/*+ USE_NL(table_name_list) */
```

### PUSH_SUBQ Hint

The `PUSH_SUBQ` hint instructs the optimizer to execute subqueries that have not been rewritten as joins as early as possible. Typically, these subqueries are executed after all table joins in the execution plan. If a subquery has a low computational cost and can filter a large amount of data, executing it early may improve plan performance. Note that this hint is invalid if the subquery has been rewritten as a join (`/+unnest/`). The hint is applicable to the following scenarios:

* The subquery has a low execution cost but can quickly filter out a large amount of data.
* The result of the subquery needs to be used as early as possible to narrow down the data range.

**Syntax:**

```sql
/*+ PUSH_SUBQ[(@qb_name)] */
```

**Parameters:**

* `@qb_name`: Optional. Specifies an alias for the subquery (for more information, see the **QB_NAME parameter** section above). This helps clarify the target of the hint. If omitted, the hint applies to the subquery where it is placed.

**Examples:**

Use the `PUSH_SUBQ` hint in a query to instruct the optimizer to execute the subquery early to filter data in the `tbl1` table.

```sql
SELECT /*+ PUSH_SUBQ(@"SEL$2") */ *
FROM tbl1, tbl2
WHERE tbl1.col1 = (SELECT MAX(tbl3.col1)
                   FROM tbl3
                   WHERE tbl3.col2 = tbl2.col2);
```

### NO_PUSH_SUBQ Hint

The `NO_PUSH_SUBQ` hint is the opposite of `PUSH_SUBQ`. It instructs the optimizer to execute subqueries that have not been rewritten as joins at the end. It is applicable when the subquery has a high cost or cannot significantly reduce the number of rows. The hint is applicable to the following scenarios:

* The subquery has a high execution cost, or its result has a minimal impact on the data volume.
* The subquery needs to be executed after other filtering conditions take effect to reduce the input data volume.

**Syntax:**

```sql
/*+ NO_PUSH_SUBQ[(@qb_name)] */
```

**Parameters:**

* `@qb_name`: An optional parameter that specifies the alias of the subquery.

**Examples:**

Use the `NO_PUSH_SUBQ` hint in a query to instruct the optimizer to execute the subquery at the end.

```sql
SELECT /*+ NO_PUSH_SUBQ */ *
FROM tbl1, tbl2
WHERE tbl1.col1 = (SELECT MAX(tbl3.col1)
                   FROM tbl3
                   WHERE tbl3.col2 = tbl2.col2);
```

### OPT_PARAM Hint

The `OPT_PARAM` hint specifies optimizer-related configurations or system variables at the query level.

**Syntax:**

```sql
/*+ OPT_PARAM(parameter_name [,] parameter_value) */
```

**Parameters:**

* `parameter_name`: The name of the configuration item or system variable.
* `parameter_value`: The value of the variable.

The `OPT_PARAM` hint applies to the following parameters:

* `rowsets_enabled`: Specifies whether to enable vectorization. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Enclose the value in single quotation marks ('').
* `rowsets_max_rows`: Sets the number of rows to be returned in batches (`batch_size`). Data type: `INT`. Value range: `[0, 65535]`. Do not enclose the value in single quotation marks ('').
* `enable_newsort`: Specifies whether to enable the newsort optimization in queries. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Enclose the value in single quotation marks ('').
* `use_part_sort_mgb`: Specifies whether to enable part sort merge group by in queries. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Enclose the value in single quotation marks ('').
* `enable_in_range_optimization`: Specifies whether to enable the in optimization in queries. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Enclose the value in single quotation marks ('').
* `xsolapi_generate_with_clause`: Specifies whether to enable CTE extraction rewrite in queries. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Enclose the value in single quotation marks ('').

### INDEX_MERGE Hint

The `INDEX_MERGE` hint controls whether an index merge plan is used for the specified table. If the specified index cannot generate an index merge plan, the hint is ignored. If no index is specified, the system tries to generate an index merge plan as much as possible.

You can use the `INDEX_MERGE` hint to generate an index merge plan even when the `_enable_index_merge` configuration item is set to `False`.

**Syntax:**

```sql
/*+ INDEX_MERGE([@query_block_name] tbl_name [index_name [,index_name]...]) */
```

**Parameters:**

* `@query_block_name`: Optional. Specifies the name of the query block to which the hint applies. If omitted, the hint applies to the main query block of the current query.
* `tbl_name`: Specifies the table name.
* `index_name`: Optional. Specifies the index name. You can specify multiple index names.

  * When the specified table is not followed by the `index_name` parameter, the specified table uses an index merge plan.
  * When the specified table is followed by the `index_name` parameter, the specified index is used to generate an index merge plan for the table.

**Examples:**

* Specify index names in the `INDEX_MERGE` hint.

    ```shell
    obclient> SELECT /*+ INDEX_MERGE(t1 idx_c2 idx_c3) */ * FROM t1
        WHERE c2 = 1
        AND c3 = 1
        AND c4 = 1;
    ```

* Do not specify an index name in the `INDEX_MERGE` hint.

    ```shell
    obclient> SELECT /*+ INDEX_MERGE(t1)*/ * FROM t1
        WHERE c2 = 1
        AND c3 = 1
        AND c4 = 1;
    ```

### NO_INDEX_MERGE Hint

The `NO_INDEX_MERGE` hint controls whether an index merge plan is generated by using the specified index for the specified table. If no index is specified, the table is not allowed to generate an index merge plan.

If the `NO_INDEX_MERGE` hint conflicts with the `INDEX_MERGE` hint, both hints are ignored.

**Syntax:**

```sql
/*+ NO_INDEX_MERGE([@query_block_name] tbl_name [index_name [,index_name]...]) */
```

**Parameters:**

* `@query_block_name`: Optional. Specifies the name of the query block to which the hint applies. If omitted, the hint applies to the main query block of the current query.
* `tbl_name`: Specifies the table name.
* `index_name`: Optional. Specifies the index name. You can specify multiple index names.

  * When the specified table is not followed by the `index_name` parameter, an index merge plan is not used.
  * When the specified table is followed by the `index_name` parameter, the specified index is not used to generate an index merge plan.

**Examples:**

```shell
obclient> SELECT /*+ NO_INDEX_MERGE(t1)*/ * FROM t1
    WHERE c2 = 1
    AND c3 = 1
    AND c4 = 1;
```

### CACHE Hint

The `CACHE` hint manually enables the cache for the specified table and its indexes. The cache is always enabled during queries on this table.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>If no hint is specified, the cache is controlled using an adaptive strategy.</p>
</main>

**Syntax:**

```sql
/*+ CACHE ([@qb_name] table_name) */
```

**Parameters:**

* `@qb_name`: Optional. Specifies the name of the query block to which the hint applies. If omitted, the hint applies to the main query block of the current query.
* `table_name`: Specifies the table name.

**Examples:**

* Manually enable the cache for `tbl1`.

    ```shell
    obclient> SELECT /*+ CACHE(tbl1) */ * FROM tbl1;
    ```

* Manually enable the cache for `tbl1`, and `tbl2` remains in the automatically enabled default state.

    ```shell
    obclient> SELECT /*+ CACHE(tbl1) */ * FROM tbl1, tbl2
        WHERE tbl1.col1 = tbl2.col1;
    ```

### NOCACHE Hint

The `NOCACHE` hint manually disables the cache for the specified table and its indexes. The cache is always disabled during queries on this table.

**Syntax:**

```sql
/*+ NOCACHE ([@qb_name] table_name) */
```

**Parameters:**

* `@qb_name`: Optional. Specifies the name of the query block to which the hint applies. If omitted, the hint applies to the main query block of the current query.
* `table_name`: Specifies the table name.

**Examples:**

Manually disable the cache for `tbl1`.

```shell
obclient> SELECT /*+ NOCACHE(tbl1) */ * FROM tbl1;
```

When multiple `CACHE` or `NOCACHE` hints are specified, they are merged. If a `CACHE` hint conflicts with a `NOCACHE` hint, that is, they specify the same table, `CACHE` takes precedence, which means the cache is enabled for the table.

**Examples:**

The `CACHE` hint takes effect, manually enabling the cache for `tbl1`.

```shell
obclient> SELECT /*+ CACHE(tbl1) NOCACHE(tbl1) */ * FROM tbl1;
```
