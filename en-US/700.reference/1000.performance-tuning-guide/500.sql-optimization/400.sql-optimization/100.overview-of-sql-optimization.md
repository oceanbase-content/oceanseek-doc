# Overview of SQL tuning

SQL tuning refers to the process of adjusting SQL execution strategies to maximize resource utilization by comprehensively analyzing factors such as SQL execution plans, execution monitoring information, system configuration, and system load.

SQL tuning can generally be divided into single-statement tuning and system-level SQL tuning.

## Single-statement tuning

Single-statement tuning focuses on the execution of the SQL statement being tuned. Common tuning objectives include reducing the execution time and runtime resource consumption. Common tuning techniques include modifying the access path, adjusting the execution order, and rewriting the query logic.

Performance tuning for a single SQL statement's execution plan can be further divided into two scenarios: single-table access and multi-table access.

| **Scenario** | **Focus areas of SQL tuning** |
| -------- | ---------------------------- |
| Single-table access | <ul><li> Whether the index scan feature is enabled for the access path: Index scanning reduces the amount of data to be read.</li>   <li> Whether a proper index is created: Index sorting reduces time-consuming operations such as sorting and aggregation.</li>   <li> Whether partition pruning conditions are set properly: Appropriate partitioning conditions reduce unnecessary partition access.</li>   <li> Whether the degree of parallelism (DOP) is improved: When a large number of partitions need to be accessed, a higher DOP improves the performance of a single SQL query at the cost of higher resource consumption.</li></ul> |
| Multi-table access | Apart from the SQL tuning items of single-table access, you need to pay attention to multi-table joins: <ul><li> Join order</li>   <li> Join algorithms</li>   <li> Data redistribution in cross-zone or parallel joins</li>   <li> Query rewriting</li> </ul> |

## System-level SQL tuning

The purpose of system-level SQL tuning is to improve the overall system throughput or utilization. This process often requires analyzing the execution plans of multiple SQL statements and comprehensively assessing the current system's workload characteristics. It primarily focuses on global tuning points such as hotspot row contention and buffer cache hit rates.

Throughput performance tuning aims to maximize the database system's request processing capacity under given resources (CPU, I/O, network, etc.). Key considerations include the following aspects:

| **Method** | **Description** |
| ------------------- | ----------------------------- |
| Optimize slow SQL queries | Find a specific slow SQL query and optimize its performance. For more information, see [Find the TOP N queries with the longest execution time within a certain period](300.monitor-sql-execution-performance/400.sql-performance-analysis-example/1000.query-the-top-n-requests-with-the-most-execution-time.md). |
| Balance the traffic of SQL queries | For more information, see [Check whether SQL queries are balanced across servers in a cluster](300.monitor-sql-execution-performance/400.sql-performance-analysis-example/600.check-whether-the-sql-request-traffic-is-balanced.md). The main factors that may affect the balance are as follows: <ul><li> Settings of the `ob_read_consistency` parameter</li>   <li> Settings of the primary zone</li>   <li> Settings of the proxy or Java client routing strategy</li>   <li> Partitioning for frequently executed queries</li> |
| Balance the resources for RPCs of subplans | For more information, see [Check whether the RPC execution count of a distributed subplan is balanced across servers in a cluster](300.monitor-sql-execution-performance/400.sql-performance-analysis-example/1200.check-whether-the-number-of-distributed-rpc-executions-is-balanced.md). The main factors that may affect the balance are as follows: <ul><li> Settings of the internal routing strategy of an OBServer node</li>   <li> Partitioning for frequently executed queries</li> |
