# Parallel DML

Parallel DML uses a parallel execution mechanism to improve the efficiency of inserting, updating, and deleting operations on tables and indexes in large databases. For decision support system (DSS) databases, parallel DML provides query and update capabilities, complementing parallel query functionality. For OLTP databases, parallel DML operations can accelerate the execution of batch processing jobs.

## Enable and disable parallel DML

OceanBase AI Database supports explicitly enabling parallel DML in SQL statements or sessions.

### Enable and disable parallel DML in SQL statements

To enable parallel DML in an SQL statement, insert the following hint into the statement:

```sql
/*+ ENABLE_PARALLEL_DML PARALLEL(3) */
```

Generally, the `ENABLE_PARALLEL_DML` hint must be used together with the `PARALLEL` hint to enable parallel DML. However, if the table-level degree of parallelism (DOP) is specified on the schema of the target table, you only need to specify the `ENABLE_PARALLEL_DML` hint.

The following example uses both the `ENABLE_PARALLEL_DML` and `PARALLEL(n)` hints to set the DOP (`n`) to `2`, meeting the requirement of `n > 1`.

```sql
CREATE TABLE t1 (c1 INT PRIMARY KEY, c2 INT) NOPARALLEL;
CREATE TABLE t2 (c1 INT PRIMARY KEY, c2 INT) PARALLEL 11 PARTITION BY HASH(c1) PARTITIONS 3;
CREATE TABLE t3 (c1 INT PRIMARY KEY, c2 INT) PARALLEL 10 PARTITION BY HASH(c1) PARTITIONS 4;
```

To disable parallel DML, insert the following hint into the statement:

```sql
/*+ DISABLE_PARALLEL_DML */
```

Even if parallel DML is enabled in a session, you can still use the `DISABLE_PARALLEL_DML` hint to disable parallel DML in a specified SQL statement.

### Enable and disable parallel DML in a session

By default, even if a `PARALLEL` hint is specified in an SQL statement, parallel DML is not enabled. You need to enable parallel DML in the session as well.

The syntax to enable parallel DML in a session is:

```sql
SET _FORCE_PARALLEL_DML_DOP = n;
```

where `n` is greater than 1.

To disable parallel DML, execute the following SQL statement:

```sql
SET _FORCE_PARALLEL_DML_DOP = 1;
```

When parallel DML is disabled, parallel DML is not executed even if the `PARALLEL` hint is used in SQL statements.

When parallel DML is enabled in a session, parallel execution is enabled for all DML statements in the session. If you use the `ENABLE_PARALLEL_DML` hint to enable parallel DML for an SQL statement, parallel execution is enabled only for the specified statement. However, if no table with parallel attributes exists, or the usage limitations on parallel operations are violated, parallel DML does not take effect even if it is enabled.

### Support for partition-wise parallel DML

Here is an example of the partition-wise parallel DML feature.

1. Create the test table `branch_sp_tbl_src`.

    ```sql
    CREATE TABLE branch_sp_tbl_src(id INT PRIMARY KEY, v INT) PARTITION BY KEY(id) PARTITIONS 4;
    ```

2. Create the test table `branch_sp_tbl_dest`.

    ```sql
    CREATE TABLE branch_sp_tbl_dest LIKE branch_sp_tbl_src;
    ```

3. View the execution plan.

    Execute the following SQL statement to show the execution plan of an INSERT operation.

    ```sql
    obclient [test]> EXPLAIN BASIC INSERT /*+enable_parallel_dml parallel(100) query_timeout(1000000000)*/ INTO branch_sp_tbl_dest SELECT id, v FROM branch_sp_tbl_src ON DUPLICATE KEY UPDATE v = v + 1;
    ```

    The return result is as follows:

    ```shell
    +-------------------------------------------------------------------------------------------------------------------------------------+
    | Query Plan                                                                                                                          |
    +-------------------------------------------------------------------------------------------------------------------------------------+
    | ================================================                                                                                    |
    | |ID|OPERATOR                 |NAME             |                                                                                    |

    | |4 |      └─SUBPLAN SCAN     |ANONYMOUS_VIEW1  |                                                                                    |
    ```

    The operators in the query plan are analyzed as follows:

    * Operator 0: a parallel execution coordinator for managing parallel execution processes.
    * Operator 1: distributes data among different execution nodes.
    * Operator 2: traverses partitions for the query. `partition wise` indicates that the query intelligently processes data across partitions.
    * Operator 3: an `INSERT` or `UPDATE` operation. If the key to be inserted does not exist in the destination table, the database performs an `INSERT` operation. Otherwise, the database performs an `UPDATE` operation.
    * Operators 4 and 5: perform a full scan on the `branch_sp_tbl_src` table. This table is the data source from which data is selected for the `INSERT` operation.

## Usage instructions

OceanBase AI Database supports parallel execution for the following SQL statements:

* `INSERT INTO SELECT`
* `UPDATE`
* `DELETE`

Parallel execution is supported if the table has any of the following types of indexes:

* Local indexes
* Single-partition global indexes
* Multi-partition global indexes

### Supported scenarios for parallel DML

| **Scenario** | **INSERT** | **UPDATE** | **DELETE** | **MERGE INTO** |
| ------ | -------- | -------- | -------- | ------------ |
| The table has foreign keys, triggers, PL/UDFs, or unique indexes.  <main id="notice" type='explain'><h4>Note</h4><p>Whether a trigger is fired cannot be determined: if a trigger is unrelated to the DML operation, it will not be fired, and parallel DML will proceed. For example, operations such as <code>INSERT</code> and <code>DELETE</code> on a table with an <code>UPDATE</code> trigger will use parallel DML, but executing the <code>UPDATE</code> operation itself cannot use parallel DML.</p></main> | Not supported | Not supported | Not supported | Not supported |
| Multi-table DML | `INSERT ALL` syntax is not supported for parallel DML. | Parallel `UPDATE` on joined tables is supported. | Same as `UPDATE` | Syntax not supported |
| Auto-increment column | Parallel DML is supported in some scenarios. For details, see the examples below. | Supported | Supported | Supported (seq) |
| ArrayBinding batch optimization | Not supported | Not supported | Not supported | Not supported |
| Use USER_VARIABLE | Not supported | Not supported | Not supported | Not supported |
| IGNORE | Not supported | Not supported | Not supported | Syntax not supported |
| DBLink | Not supported | Not supported | Not supported | Not supported |
| Others | The following statements do not support parallel DML:<ul><li>`INSERT ... VALUES ...`</li><li>`INSERT INTO ON DUPLICATE KEY UPDATE`</li><li>`REPLACE`</li></ul> | Columns that contain `ON UPDATE CURRENT_TIMESTAMP` are not supported. | | |

When writing to a table with auto-increment columns using `INSERT`, parallel DML is not supported if the auto-increment column is the primary key or partitioning key, and that column is specified.

**Example:**

1. Create table `tbl1`, where column `col1` is an auto-increment column and is specified as the primary key.

    ```sql
    CREATE TABLE tbl1(col1 INT AUTO_INCREMENT PRIMARY KEY, col2 INT, col3 INT);
    ```

2. Create table `tbl2`, where column `col1` is an auto-increment column.

    ```sql
    CREATE TABLE tbl1(col1 INT AUTO_INCREMENT, col2 INT, col3 INT);
    ```

3. Create table `tbl3`.

    ```sql
    CREATE TABLE tbl3(col1 INT, col2 INT, col3 INT);
    ```

4. When writing data via `INSERT`, since the auto-increment column `col1` is the primary key, parallel DML is not supported.

    ```sql
    INSERT /*+enable_parallel_dml parallel(3)*/ INTO tbl1 SELECT * FROM tbl3;
    ```

5. When writing data via `INSERT`, since column `col1` is not specified, parallel DML is supported.

    ```sql
    INSERT /*+enable_parallel_dml parallel(3)*/ INTO tbl1(col2, col3) SELECT col2, col3 FROM tbl3;
    ```

6. When writing data via `INSERT`, since column `col1` is only an auto-increment column, parallel DML is supported.

    ```sql
    INSERT /*+enable_parallel_dml parallel(3)*/ INTO tbl2 SELECT * FROM tbl3;
    ```

### Parallel DML with correlated updates

Correlated updates refer to using multi-table join operations in an `UPDATE` statement to update a target table based on data from related tables. With the parallel DML feature, you can significantly improve the performance of large-scale data update operations.

**Example:**

The following steps demonstrate how to implement correlated updates using parallel DML.

1. Create two test tables `customers` and `orders`.

    ```sql
    CREATE TABLE customers (
        id INT PRIMARY KEY,
        name VARCHAR(50),
        customer_level VARCHAR(10)
    );
    ```

    ```sql
    CREATE TABLE orders (
        order_id INT PRIMARY KEY,
        customer_id INT,
        discount DECIMAL(3, 2),
        amount DECIMAL(10, 2)
    );
    ```

2. Insert test data.

   * Insert customer data into the `customers` table:

       ```sql
       INSERT INTO customers (id, name, customer_level) VALUES
       (1, 'Alice', 'VIP'),
       (2, 'Bob', 'NORMAL'),
       (3, 'Charlie', 'OTHER');
       ```

   * Insert order data into the `orders` table:

       ```sql
       INSERT INTO orders (order_id, customer_id, discount, amount) VALUES
       (101, 1, NULL, 1000.00),
       (102, 2, NULL, 2000.00),
       (103, 3, NULL, 1500.00),
       (104, 1, NULL, 3000.00),
       (105, 2, NULL, 2500.00);
       ```

3. Perform parallel DML with correlated updates.

    Use `EXPLAIN` to view the execution plan for the parallel DML correlated update: specify the degree of parallelism as 4 using the `PARALLEL` hint, and update the `discount` column in the `orders` table based on the customer level (`customer_level`) in the `customers` table.

    ```sql
    EXPLAIN UPDATE /*+ PARALLEL(4) */
        orders o JOIN customers c ON o.customer_id = c.id
    SET o.discount = CASE
        WHEN c.customer_level = 'VIP' THEN 0.9
        WHEN c.customer_level = 'NORMAL' THEN 0.95
        ELSE 1.0
        END;
    ```

    The return result is as follows:
