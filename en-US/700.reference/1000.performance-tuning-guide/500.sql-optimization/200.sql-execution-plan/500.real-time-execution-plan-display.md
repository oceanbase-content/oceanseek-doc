# Real-time execution plan display

Real-time execution plan display can show the logical and physical execution plans of an SQL statement.

In OceanSeek, the `DBMS_XPLAN` system package is used to query logical execution plans. The `(G)V$OB_PLAN_CACHE_PLAN_EXPLAIN` view is used to query the physical execution plan of a specific SQL statement in the plan cache. The `GV$SQL_PLAN_MONITOR` view provides information related to tenant-level execution plans.

## Query logical execution plans

When a user executes a large SQL statement, if the current connection takes too long to complete, the user needs to understand the query execution status, such as the execution plan and process. In this case, since the current session is occupied by the large SQL statement, the user needs to open a new connection. Use the `SHOW PROCESSLIST` command to find the session where the large SQL statement resides, and then use the `session_id` and the `[DISPLAY_ACTIVE_SESSION_PLAN](../../../600.pl-reference/1000.pl-system-package-mysql/20700.dbms-xplan-mysql/200.display-active-session-plan-of-mysql-mode.md)` function from the `DBMS_XPLAN` system package to display the execution details of the large SQL statement.

This topic uses a specific example to demonstrate how to use the `DBMS_XPLAN` system package to query logical execution plans.

1. Connect to the database and execute the slow SQL statement.

   ```shell
   obclient> SELECT COUNT(*) FROM TABLE(GENERATOR(100000)) A, TABLE(GENERATOR(10000))B;   
   +------------+
   | COUNT(*)   |
   +------------+
   | 1000000000 |
   +------------+
   1 row in set
   ```

2. Connect to another session and use the `SHOW PROCESSLIST` command to query the Session ID of the SQL statement being executed.

   ```shell
   obclient> SHOW PROCESSLIST;
   ```

Additionally, the `GV$OB_SQL_PLAN` (or `V$OB_SQL_PLAN`) view is used to query execution plans executed by using the `EXPLAIN PLAN` tool. However, it is recommended that you use the `DBMS_XPLAN` system package to view execution plans.

The query definition for the `GV$OB_SQL_PLAN` view is as follows:

```sql
VIEW_DEFINITION='SELECT * FROM oceanbase.GV$OB_SQL_PLAN WHERE TENANT_ID = effective_tenant_id()'
```

The query definition for the `V$OB_SQL_PLAN` view is as follows:

```sql
VIEW_DEFINITION='SELECT * FROM oceanbase.V$OB_SQL_PLAN WHERE SVR_IP=host_ip() AND SVR_PORT=rpc_port()'
```

## Query physical execution plans

Using the `EXPLAIN` command can display the execution plan generated by the current optimizer. However, changes in statistics or user session variable settings may cause the actual plan corresponding to this SQL statement in the plan cache to differ from the result of `EXPLAIN`. To determine the actual execution plan used by this SQL statement in the system, you need to further analyze the physical execution plans in the plan cache.

Each server's plan cache in OceanSeek is independent. You can directly access the `V$OB_PLAN_CACHE_PLAN_STAT` view to query the plan cache on your own server and provide the `tenant_id` and the SQL string to query (fuzzy match can be used) to find the `plan_id` corresponding to that SQL in the plan cache. Then, further access the `V$OB_PLAN_CACHE_PLAN_EXPLAIN` view to display the physical execution plan of that SQL in the plan cache.

The query definition for the `V$OB_PLAN_CACHE_PLAN_EXPLAIN` view is as follows:

```sql
VIEW_DEFINITION='SELECT * FROM oceanbase.V$OB_PLAN_CACHE_PLAN_EXPLAIN WHERE TENANT_ID = tenant_id() AND PLAN_ID = plan_id()'
```

## Real-time SQL Plan Monitor

OceanSeek supports the real-time SQL Plan Monitor feature, which tracks detailed performance metrics for each execution operator, such as first-row return time, output row count, hash conflict rate, and disk flush count. You can query the tenant-level view `GV$SQL_PLAN_MONITOR` to obtain execution plan-related information, including the number of rows output by an operator, the start and end times of an operator, and the execution status of an operator by each execution thread.

### Enable the SQL Plan Monitor feature

Set the parameter [`enable_perf_event`](../../../800.configuration-items-and-system-variables/100.system-configuration-items/300.cluster-level-configuration-items/7600.enable_perf_event.md) to true to enable SQL Plan Monitor.

After SQL Plan Monitor is enabled, the following SQL statements will be recorded:

* Queries explicitly specified with the `/*+ MONITOR */` hint.
* Queries that execute parallel data modification (PDML) statements.
* The first execution operator in a query whose execution time exceeds 3 seconds.

### Obtain execution plan-related information

The `OTHERSTAT_?_ID` and `OTHERSTAT_?_VALUE` fields in the `GV$SQL_PLAN_MONITOR` view are used to record operator-specific performance data. Currently, there are 10 such fields. The actual name of the data recorded in each field is represented by an ID. To understand the specific meaning of the ID, you need to query the `V$SQL_MONITOR_STATNAME` view.
