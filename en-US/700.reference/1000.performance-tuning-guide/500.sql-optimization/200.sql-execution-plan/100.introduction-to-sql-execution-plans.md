# Introduction to SQL execution plans

An execution plan describes the process by which an SQL query is executed in a database. You can use the `EXPLAIN` command to view the logical execution plan generated by the optimizer for a specified SQL statement.

To analyze the performance of an SQL statement, you typically need to first examine its execution plan to identify any issues with each step of the execution. Therefore, understanding execution plans is a prerequisite for SQL optimization, and knowing the operators in an execution plan is key to understanding the `EXPLAIN` command.

## EXPLAIN command format

OceanSeek supports three modes for the execution plan command: `EXPLAIN BASIC`, `EXPLAIN`, and `EXPLAIN EXTENDED`. These modes present execution plans at different levels of detail:

* The `EXPLAIN BASIC` command displays the most basic plan information.

* The `EXPLAIN EXTENDED` command displays the most detailed plan information and is usually used when troubleshooting.

* The `EXPLAIN` command displays information that helps users understand how the entire plan is executed.

The `EXPLAIN` command format is as follows:

```sql
EXPLAIN [INTO table_name ] [SET statement_id = string] [explain_type] [PRETTY | PRETTY_COLOR] dml_statement;

explain_type:
    BASIC
  | OUTLINE
  | EXTENDED
  | EXTENDED_NOADDR
  | PARTITIONS
  | FORMAT = {TRADITIONAL| JSON}

dml_statement:
    SELECT statement
  | DELETE statement
  | INSERT statement
  | UPDATE statement
  | REPLACE statement
```

The `EXPLAIN` command applies to `SELECT`, `DELETE`, `INSERT`, `REPLACE`, and `UPDATE` statements. It displays information about the execution plan provided by the optimizer, including how the statement is processed, how tables are joined, and in what order they are joined.

Generally, you can use the `EXPLAIN EXTENDED` command to display the range segments scanned by tables. Use the `EXPLAIN OUTLINE` command to display outline information.

The `FORMAT` option allows you to select the output format. `TRADITIONAL` means the output is displayed in a table format, which is also the default setting. `JSON` means the information is displayed in `JSON` format.

You can also use `EXPLAIN PARTITIONS` to check queries involving partitioned tables. If checking a non-partitioned table, no error will be returned, but the value in the `PARTITIONS` column will always be `NULL`.

Specifically, you can use the `INTO table_name` SQL statement to save the `EXPLAIN` plan information into a specified table. By default, it queries the `PLAN_TABLE` table. Use the `SET statement_id` statement to mark the current query with a string for easy later retrieval of its plan information. An empty string is used as the marker by default. For more details, see [EXPLAIN](../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/5300.explain-of-mysql-mode.md).

For complex execution plans, you can use the `PRETTY` or `PRETTY_COLOR` option to connect parent and child nodes in the plan tree with lines or colored lines, making the execution plan easier to read. Example:

```sql
obclient> CREATE TABLE p1table(c1 INT ,c2 INT) PARTITION BY HASH(c1) PARTITIONS 2;
Query OK, 0 rows affected

obclient> EXPLAIN EXTENDED PRETTY_COLOR SELECT  * FROM p1table p1 JOIN p2table p2 ON p1.c1=p2.c2;
```

## Execution plan shapes and operator information

In a database system, execution plans are typically represented internally as trees, but different databases choose different ways to present them to users.

The following examples show how the execution plans for TPC-DS Q3 are presented in PostgreSQL, Oracle Database, and OceanSeek, respectively.

```sql
obclient> SELECT /*TPC-DS Q3*/ *
     FROM (SELECT dt.d_year,
                  item.i_brand_id    brand_id,
                  item.i_brand       brand,
                  Sum(ss_net_profit) sum_agg
           FROM   date_dim dt,
                  store_sales,
                  item
           WHERE  dt.d_date_sk = store_sales.ss_sold_date_sk
                  AND store_sales.ss_item_sk = item.i_item_sk
                  AND item.i_manufact_id = 914
                  AND dt.d_moy = 11
           GROUP  BY dt.d_year,
                     item.i_brand,
                     item.i_brand_id
           ORDER  BY dt.d_year,
                     sum_agg DESC,
                     brand_id)
     WHERE ROWNUM <= 100;
```

* The execution plan in PostgreSQL is as follows:

  ```sql

           Sort  (cost=13986.86..13986.93 rows=27 width=65)
           Sort Key: dt.d_year, (sum(store_sales.ss_net_profit)), item.i_brand_id
                HashAggregate  (cost=13985.95..13986.22 rows=27 width=65)
                       Merge Join  (cost=13884.21..13983.91 rows=204 width=65)
                       Merge Cond: (dt.d_date_sk = store_sales.ss_sold_date_sk)
                             Index Scan using date_dim_pkey on date_dim dt  (cost=0.00..3494.62 rows=6080 width=8)
                             Filter: (d_moy = 11)
                             Sort  (cost=12170.87..12177.27 rows=2560 width=65)
                             Sort Key: store_sales.ss_sold_date_sk
                                   Nested Loop  (cost=6.02..12025.94 rows=2560 width=65)
                                         Seq Scan on item  (cost=0.00..1455.00 rows=16 width=59)
                                         Filter: (i_manufact_id = 914)
                                         Bitmap Heap Scan on store_sales  (cost=6.02..658.94 rows=174 width=14)
                                         Recheck Cond: (ss_item_sk = item.i_item_sk)
  ```

You may notice from the examples above that a plan in OceanSeek is similar to that in Oracle Database.

The following table describes the columns of an execution plan in OceanSeek.

| **Column** | **Description** |
| ------------- | ---------------------------- |
| `ID` | The sequence number of the execution tree obtained by preorder traversal, starting from 0. |
| `OPERATOR` | The name of the operator. |
| `NAME` | The name of the table or index corresponding to a table operation. |
| `EST. ROWS` | The estimated number of output rows of the operator. |
| `COST` | The execution cost of the operator, in microseconds. |

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>In a table operation, the <code>NAME</code> field displays the name (alias) of the table involved in the operation. If an index is used for access, the name of the index is also displayed in parentheses after the name. For example, <code>t1(t1_c2)</code> indicates that the <code>t1_c2</code> index is used. If the scan order is reverse, the <code>REVERSE</code> keyword is used to indicate this, for example, <code>t1(t1_c2,REVERSE)</code>.</p>
  </main>

The first part of the output of the `EXPLAIN` command in OceanSeek is a tree structure representation of the execution plan. The hierarchy of each operation in the tree is indicated by its indentation in `operator`. Operations with deeper hierarchies are executed first. For operations at the same level, execution follows the standard order of specific operators.

The following figure shows the plan display tree for the TPC-DS Q3 example above:

![p181620](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer/V4.0.0/sql-execution-plan-1.png)

The second part of the output of the `EXPLAIN` command in OceanSeek provides detailed information about each operator, including the output expression, filter conditions, partition information, and unique information for each operator (such as the sort keys, join keys, pushdown conditions, etc.). Example:

```sql
Outputs & filters:
-------------------------------------
  0 - output([t1.c1], [t1.c2], [t2.c1], [t2.c2]), filter(nil), sort_keys([t1.c1, ASC], [t1.c2, ASC]), prefix_pos(1)
  1 - output([t1.c1], [t1.c2], [t2.c1], [t2.c2]), filter(nil),
      equal_conds([t1.c1 = t2.c2]), other_conds(nil)
  2 - output([t2.c1], [t2.c2]), filter(nil), sort_keys([t2.c2, ASC])
  3 - output([t2.c2], [t2.c1]), filter(nil),
      access([t2.c2], [t2.c1]), partitions(p0)
  4 - output([t1.c1], [t1.c2]), filter(nil),
      access([t1.c1], [t1.c2]), partitions(p0)
```
