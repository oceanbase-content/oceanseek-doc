# Analyze an ASH report

After an ASH report is generated, view its content to determine the possible causes of the instantaneous performance issues.

## ASH report content

The ASH report records statistical data about the ASH report in the ASH Report section. This includes information such as the system version, operating system environment, information sampling time period, analysis time period, ASH and WR data sources, number of samples, number of events, and average number of active sessions. Based on this data, it generates information for 18 modules, including Top Active Tenants, Top Node Load, Top Groups, Top Foreground DB Time, Top Background DB Time, Top Sessions, Top IO Bandwidth, Top Blocking Sessions, Top Latches, Top DB Objects, Activity Over Time, Top Execution Phase, Top IO Events, Top SQL Statement Types, Top SQL with Top Events, Top SQL with Top Operator, Top PL/SQL Procedures, and Complete List of SQL Text.

These modules primarily display the performance data collected by the OBServer from two aspects: resource overhead and execution path overhead. Therefore, when analyzing specific performance issues, you can examine the relevant modules to determine whether the root cause is a resource bottleneck or inefficient execution.

### ASH report

This section displays information about the sampling time, analysis time, and general statistics in the Active Session History (ASH) report.

* Cluster Name: The name of the cluster, which is the name of the database cluster.
* Observer Version: The version information of OceanBase AI Database, including the version number and detailed build version.
* Operation System Info: The operating system information, including the kernel version and architecture.
* User Input Begin Time: The time when sampling started, indicating the point in time when session activity recording began.
* User Input End Time: The time when sampling ended, indicating the point in time when session activity recording stopped.
* Analysis Begin Time: The time when analysis started, indicating the starting point in time for analyzing the sampled data.
* Analysis End Time: The time when analysis ended, indicating the ending point in time for analyzing the sampled data.
* Ash Data Source: The ASH data source. If ASH is not used, this column will be absent.
* Wr Data Source: The WR data source. If WR is not used, this column will be absent.
* Elapsed Time: The total number of seconds of all sampling times.
* Ash Num of Sample: The number of ASH samples, indicating the number of recorded session activities.
* Wr Num of Sample: The number of WR samples, indicating the number of performance snapshots generated within the analysis time range.
* Average Active Sessions: The average number of active sessions, indicating the average number of active sessions during the sampling period.

The statistics provide information about the activities, number of sessions, and system activity during the sampling period.

### Top Active Tenants

This section breaks down resource consumption into foreground user requests and background tasks, allowing you to view the overall resource usage within a tenant.

* Tenant Name: The name of the tenant, identifying the information of a specific tenant.
* Session Type: The type of session. Possible values include BACKGROUND and FOREGROUND, representing background processes and foreground processes, respectively.
* Total Samples: The total number of records, indicating the total number of samples within the ASH report analysis time period.
* Wait Event Count: The number of wait events, indicating the number of samples where the session is waiting for an event.
* On CPU Samples: The number of samples on the CPU, indicating the number of samples where the session is executing on the CPU.
* Avg Active Sessions: The average number of active sessions, indicating the average number of database sessions that were active at any given time during the sampling period (either on the CPU or waiting for an event).
* % Activity: The percentage of activity, indicating the percentage of activity (CPU + wait) for a given tenant within the specified time period.
* Equivalent Client Load: The number of active connections between clients and the database during the ASH report analysis time period.

This information provides details about tenant activity, revealing different aspects of database performance and how tenants use resources.

In the Top Active Tenants module, performance issues may originate from within the database or in the interaction chain between the database and business applications. First, you need to identify the metrics Equivalent Client Load and Avg Active Sessions where the performance issue occurs. These two metrics are used to assess the impact of the database and links on performance. A larger ratio (Avg Active Sessions/Equivalent Client Load) indicates a greater impact of internal database overhead on performance; a smaller ratio indicates a greater impact of network links or the client.

For example, if the report shows a ratio of 88%, it indicates that the performance issue is mainly caused by database load. After confirming that there is a problem with the database load, you should further analyze the resource overhead within the database. In the Top Active Tenants module, foreground user requests consume 69.65% of database resources, while background tasks account for about 30%. Therefore, the performance bottleneck primarily occurs in the execution chain of user requests. Additionally, the wait events for foreground tasks consume a total of 1140 seconds of database time, while CPU execution consumes 72860 seconds. This indicates that the business model does not experience significant waiting due to resource limitations such as disk I/O or network bandwidth; the main overhead is concentrated on CPU execution. Since the business runs normally at the current version, it can be inferred that the cluster's CPU resources are sufficient. The slowdown in performance may be related to a decrease in execution efficiency at some stage of the SQL execution chain after the upgrade.

### Top IO Bandwidth

This section lists the throughput of the top I/O operations from the perspectives of SQL and background tasks.

* % Object ID: The I/O percentage of the leader shard.

### Top Execution Phase

This section displays the activities with a high proportion in the execution phase, categorized by session type, covering multiple aspects such as SQL execution, PL/SQL processing, and storage read/write.

* Session Type: The session type. Possible values include BACKGROUND and FOREGROUND, representing background and foreground processes respectively.

* Phase of Execution: The name of the execution phase, for example, IN_SQL_EXECUTION (SQL execution), IN_COMMITTING (commit process), IN_PLSQL_EXECUTION (PL/SQL execution), etc.

* Active Samples: The number of occurrences or records in each execution phase.

* % Activity: The percentage of activity for the event, representing the percentage of activity (CPU + wait) of a given tenant within a specified time period.

* SQL ID: The SQL ID with high load among the waiting events.

* % SQL ID/Module: The percentage of SQL IDs or modules with high load among the waiting events, used to prioritize optimization of high-impact queries.

Since performance issues with the base path typically affect all requests in the database, the Top Execution Phase provides a direct summary of the performance impact on the base path.

For example, from the content of the Top Execution Phase module, we can obtain the following information:

1. IN_SQL_EXECUTION accounts for 69.65% of the overhead. This part represents the total cost when SQL enters execution after obtaining the plan. Among the several execution phases defined in OceanBase AI Database, IN_SQL_EXECUTION includes IN_STORAGE_WRITE, IN_STORAGE_READ, and IN_RPC_ENCODE. This metric shows that the main cost of SQL lies in the execution (EXECUTION) phase, rather than the parsing (PARSER) or plan cache (PLAN CACHE) phase.

2. IN_STORAGE_WRITE is a sub-phase within the IN_SQL_EXECUTION phase, and this part of the cost accounts for 68.19%, indicating that the main performance cost occurs during data writes to the memtable.

3. IN_deadLOCK_ROW_REGISTER is a sub-phase of IN_STORAGE_WRITE, and this part of the cost accounts for 65.10%, indicating that most of the cost in this scenario occurs at this stage.

The above three metrics typically do not exceed 30% in import-type task benchmarks because, in import-type tasks, background tasks such as the entire system's memtable minor compaction, clog synchronization, and persistence to disk consume some CPU resources, while stages like SQL parsing and expression evaluation also consume CPU resources. In this task, however, the IN_STORAGE_WRITE phase accounts for nearly 70%, far exceeding the benchmark reference value, indicating that the performance issue in this business scenario primarily occurs at this stage.
Additionally, the IN_DEADLOCK_ROW_REGISTER phase is mainly responsible for registering the row lock information held in the written data with the Deadlock Manager, facilitating background tasks to detect whether active transactions are deadlocked. Typically, this operation only updates and maintains a hashmap value, which is a very fast operation. In benchmarks, the cost for this phase usually does not exceed 3%. Clearly, in this system, this part of the cost is much higher than the empirical benchmark value.

Based on the analysis above, we can almost certainly determine that the performance issue lies in the IN_DEADLOCK_ROW_REGISTER phase. This is a general path for memtable writes. Performance issues that occur on this general path may affect either a specific SQL statement or the performance of all SQL statements accessing this path. So, in this problem, how do we determine the scope of affected SQL statements?

In addition to listing the proportionate costs of each phase predefined by OceanBase AI Database, the Top Execution Phase section also displays the SQL statement with the highest cost for each phase and its specific proportion. From the report data, we know that the SQL statement with the highest cost in the IN_DEADLOCK_ROW_REGISTER phase is D5B2150EA75EB405C25592A65708DD21. According to the text information displayed in the report, this SQL statement is an INSERT statement:

```shell
INSERT INTO TRADE_BASE_000_LOAD_42
SELECT TRADE_NO, TRADE_NO
FROM TRADE_BASE_000_LOAD PARTITION(p42)
WHERE ROWNUM <= 50000000;
```

The cost of this SQL statement in the IN_DEADLOCK_ROW_REGISTER phase is 0.67%, which is significantly different from the total cost of the entire phase, indicating that the total cost of the IN_DEADLOCK_ROW_REGISTER phase is not concentrated on a single SQL statement but is distributed across many SQL statements.

* Sampled Executions: The number of sampled executions for this type of SQL (multiple executions may be independently counted due to different parameters).

* Top Event: The name of the primary I/O wait event.

* % Event: The proportion of total database activity for this event. A high percentage may indicate that this event is the main bottleneck in system performance.

* Top Operator/ExecPhase: The operation that takes the longest time in the current SQL execution plan.

* % Operator/ExecPhase: The percentage of the total SQL execution time occupied by this operation/phase, used to locate execution plan bottlenecks.

* SQL Text: The text of the SQL query.

This information identifies specific events that cause the highest proportion of activity during SQL statement execution, directly pointing to the core of the performance bottleneck. * PLSQL Entry Subprogram: Displays the top-level PL/SQL entry subprogram of the application, which can be a procedure, function, trigger, or package initialization.
