# Load balancing

Load balancing is an important aspect of performance tuning, which includes two aspects: load balancing within the cluster and load balancing of business traffic. Good load balancing can fully utilize the software and hardware environment and achieve the best performance. During stress testing, you need to pay attention to the resource usage of each OBServer node in the cluster, such as CPU, I/O, and load. This topic briefly describes cluster deployment and resource distribution.

## Cluster deployment

For a cluster deployment, information about locations, latency, and bandwidth is needed.

### Location

Location information is crucial, and some critical information such as the IDC and deployment method affects SQL routing and forwarding, the transaction model, and performance. It includes the following aspects:

* Deployment method: same-city three IDCs, two regions with three data centers, three regions with five data centers, or other deployment methods.

* Location of OBProxy and other middleware: whether they are deployed on the client side or co-located with OBServer nodes. Different deployment modes have different performance impacts.

* Locations of application servers and other middleware.

You can use the following SQL query to view the IDC of each zone in the cluster and the city where the IDC is located:

```shell
obclient [oceanbase]> SELECT * FROM oceanbase.DBA_OB_ZONES;
```

The query result is as follows:

```shell
+-------+----------------------------+----------------------------+--------+------+----------------+-----------+
| ZONE  | CREATE_TIME                | MODIFY_TIME                | STATUS | IDC  | REGION         | TYPE      |
```

### Latency

You can assess the response time (RT) of an SQL statement based on the latency information. The specific latency information of the cluster is as follows:

* Latency between IDCs;

* Latency between zones;

* Latency from OBProxy to OBServer nodes;

* Latency from clients to OBProxy.

### Bandwidth

You need to confirm the bandwidth of the following components:

* Bandwidth of the NIC of the machine where OBProxy is installed.

* Bandwidth of the NIC of the application server.

* NIC bandwidth and disk I/O bandwidth of OBServer nodes.

You can obtain this information by using commands such as ping, tsar, ethtool xxx, and ifconfig. The following example uses the FFF deployment with three IDCs in the same city and three replicas.

## Other

Any component that processes requests from the application server to the OBServer node is a key focus area. A bottleneck at any point can significantly impact performance. Pay attention to the following aspects:

* Physical resources: whether the resources of each component in the intermediate link are reaching bottlenecks, such as the JVM memory, the CPU usage of the application server and OBProxy, and soft interrupts.

* Request routing: whether OBProxy can correctly route SQL requests and whether there are any routing errors.

* Connection pool: the numbers of long and short connections and the SocketTimeout configuration.

* Traffic balancing: whether there is a severe imbalance in the number of SQL statements received and processed by each OBServer node.
