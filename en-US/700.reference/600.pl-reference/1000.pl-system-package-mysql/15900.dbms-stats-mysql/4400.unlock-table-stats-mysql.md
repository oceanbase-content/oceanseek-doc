# UNLOCK_TABLE_STATS

The `UNLOCK_TABLE_STATS` procedure is used to unlock table-level statistics.

## Syntax

```sql
DBMS_STATS.UNLOCK_TABLE_STATS (
  ownname    VARCHAR2,
  tabname    VARCHAR2,
  stattype   VARCHAR2 DEFAULT 'ALL');
```

## Parameters

| Parameter | Explanation |
| ---------- | ----------------------- |
| ownname | Username. If the username is set to `NULL`, the current login username will be used by default. |
| tabname | Table name. |
| stattype | The type of lock. Generally, there are the following three types: <ul><li>`'ALL'` </li>  <li> `'DATA'`   </li>  <li> `'CACHE'` </li>  </ul> |

## Usage instructions

* To call this procedure, you must be the owner of the table. For objects owned by `SYS`, you must be the table owner or have the `SYSDBA` privilege to call this procedure.

* When the statistics of a table are locked, all statistics that depend on it are locked, including table-level statistics, column-level statistics, histogram statistics, and all index-dependent statistics.

* If the statistics of an object are locked, executing the `SET_*, DELETE_*, IMPORT_*, or GATHER_*` procedure to modify the statistics of a single table, index, or column will cause an error.

* Neither the `UNLOCK_SCHEMA_STATS` nor the `UNLOCK_TABLE_STATS` procedure can unlock statistics for the corresponding partition. When you call the `LOCK_TABLE_STATS` procedure, it sets a lock at the table level. In this case, you cannot collect statistics on dependent objects such as partitions and indexes. Furthermore, if table statistics are locked, their dependencies are also locked, so there is no need to explicitly call the `LOCK_PARTITION_STATS` stored procedure to lock partition statistics.

## Examples

Unlock the table-level statistics for table `t1` under user `test`.

```sql
obclient> CALL DBMS_STATS.UNLOCK_TABLE_STATS('test', 't1');
Query OK, 0 rows affected
```
