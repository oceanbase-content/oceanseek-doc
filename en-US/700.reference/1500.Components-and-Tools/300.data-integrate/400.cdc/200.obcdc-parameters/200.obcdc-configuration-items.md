### Synchronization granularity

obcdc supports data synchronization in multiple dimensions. A single obcdc instance can synchronize the data of one cluster, one or more tenants, several databases, and several tables.

| Synchronization granularity | Single obcdc instance | Multiple obcdc instances |
|----------|-------------------------|-----------------|
| Cluster | Supported (a single obcdc instance cannot synchronize data of multiple clusters) | Supported |
| Tenant | Supported | Supported |
| Database | Not supported | Not supported |
| Table | Not supported | Not supported (see the multi-instance parameters below) |

If the traffic of a tenant is heavy, it is difficult for a single obcdc instance to synchronize the data of the entire cluster in real time. In this case, you can use multiple obcdc instances to synchronize the same cluster to share the load, with each instance synchronizing the data of a different tenant.

## Monitoring-related parameters

### Throttling

To prevent out-of-memory (OOM) issues caused by data accumulation in the memory in abnormal cases, obcdc provides throttling capabilities. Throttling is triggered based on the internal state of obcdc. During throttling, obcdc stops pulling new data and resumes when its status recovers. The following table describes the throttling parameters. You can modify them to adjust the throttling level as needed.

| Parameter | Description | Default value | Real-time modification supported | Remarks |
|---------------------------------------------|----------------------------|--------|--------|---------------------------------------------------------------|
| memory_limit | The memory limit for triggering throttling. | `20G` | Yes | This is one of the throttling reference parameters. obcdc tries to keep the memory usage around the value of `memory_limit`, but this does not mean that obcdc uses at most `memory_limit` memory. The minimum value is 2 GB. |
| memory_usage_warn_threshold | The memory usage ratio that triggers log pulling throttling, relative to `memory_limit`. | 85 | Yes | None |
| system_memory_avail_percentage_lower_bound | The lower limit of available system memory, in percentage. | 10 | Yes | The value range is \[10, 80]. |
| part_trans_task_active_count_upper_bound | The maximum number of active partition transactions. | 200000 | Yes | This parameter specifies the number of active partition transaction structs in memory (allocated and not recycled). |
| storager_task_count_upper_bound | The throttling threshold of the number of tasks for the storager module to persist. | 1000 | Yes | The minimum value is 1. |
| storager_mem_percentage | The multiple of the throttling memory occupied by the persistence module. | 1 | Yes | The value `0` specifies automatic adjustment. |
| part_trans_task_reusable_count_upper_bound | The maximum number of partition transactions to reuse. | 10240 | Yes | This parameter specifies the sum of tasks to be output to the user queue, to be output by users, to be returned by users, and pending garbage collection (GC). |
| ready_to_seq_task_upper_bound | The maximum number of tasks to be sequenced. | 2000 | Yes | This parameter specifies the maximum number of tasks to be sequenced, including tasks pending parsing, tasks pending formatting, and tasks pending persistence. |
| pause_fetcher | Specifies whether to forcibly stop pulling logs. | 0 | Yes | The value `0` specifies to forcibly stop pulling logs regardless of the result of the throttling logic. |
| direct_load_inc_thread_num | The number of threads for reading and parsing incremental direct load logs. | 0 | Yes | This is an automatic configuration parameter for memory throttling. Its value can be automatically adjusted based on the `memory_limit` parameter of obcdc, or you can manually modify the configuration for dynamic adjustment.<main id="notice" type='notice'><h4>Notice</h4><p>If you enable the incremental direct load feature and use obcdc for data synchronization, adjust this parameter with caution. Otherwise, memory throttling may be affected and the memory limit may be exceeded.</p></main> |
| direct_load_inc_queue_backlog_lowest_tolerance | The task backlog threshold that triggers throttling. | 0 | Yes | This is an automatic configuration parameter for memory throttling. Its value can be automatically adjusted based on the `memory_limit` parameter of obcdc, or you can manually modify the configuration for dynamic adjustment.<main id="notice" type='notice'><h4>Notice</h4><p>If you enable the incremental direct load feature and use obcdc for data synchronization, adjust this parameter with caution. Otherwise, memory throttling may be affected and the memory limit may be exceeded.</p></main> |

The reference throttling conditions are as follows:

1. Condition 1: The number of active partitions exceeds the threshold specified by `part_trans_task_active_count_upper_bound`. \|\| The memory held by obcdc exceeds the threshold specified by `memory_limit`. \|\| The available memory of the system is lower than the threshold specified by `system_memory_avail_percentage_lower_bound`.
2. Condition 2: The number of partition transaction structs to be reused exceeds the threshold specified by `part_trans_task_reusable_count_upper_bound`. \|\| The number of tasks to be sequenced exceeds the threshold specified by `ready_to_seq_task_upper_bound`.
3. Condition 3 (since OceanBase Database V3.x): The number of tasks to be persisted exceeds the threshold specified by `storager_task_count_upper_bound`. \&\& The memory held by obcdc exceeds the throttling triggering memory (`memory_limit`) multiplied by the ratio of the memory occupied by the persistence module to the throttling memory (`storager_mem_percentage`).

The formula for triggering throttling is: ((Condition 1 \&\& Condition 2) \|\| Condition 3) \|\| (`pause_fetcher` != 0).

The `direct_load_inc_thread_num` and `direct_load_inc_queue_backlog_lowest_tolerance` parameters are automatically adjusted as follows:

| memory_limit | 2G | 4G | 8G | 16G | 32G | 128G |
| ---------------------------------------------- | ---- | ---- | ----- | ----- | ----- | ------ |
| direct_load_inc_thread_num | 1 | 1 | 1 | 2 | 3 | 5 |
| direct_load_inc_queue_backlog_lowest_tolerance | 4096 | 8192 | 16384 | 32768 | 65536 | 131072 |

When the memory is sufficient, you can appropriately increase the value of `direct_load_inc_thread_num` to speed up the reading and parsing of incremental direct load logs, and appropriately increase the task backlog threshold that triggers throttling (`direct_load_inc_queue_backlog_lowest_tolerance`). When the memory is insufficient, you can appropriately decrease the values of `direct_load_inc_thread_num` and `direct_load_inc_queue_backlog_lowest_tolerance`, or keep their default values.

### Filter data based on cluster_id

obcdc allows you to filter data based on the `cluster_id` blocklist. Although OceanBase Database specifies a valid `cluster_id` range, you can specify `cluster_id` values when writing data to prevent unwanted data from being synchronized. For more information about how to configure the `cluster_id` values written to the source, see [ob_org_cluster_id](../../../../800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/800.ob_org_cluster_id-session.md).

* Data whose `cluster_id` is outside the valid range specified by OceanBase Database and OceanBase Migration Service (OMS) is not synchronized. The valid range is \[1, 4294901759] U \[4294901760, 4294967295].
* Data whose `cluster_id` is in the `cluster_id_black_list` is not synchronized.
* Each `cluster_id` in the `cluster_id_black_list` must range from `cluster_id_value_min` to `cluster_id_value_max`.

| Parameter | Description | Default value | Real-time modification supported | Remarks |
|----------------------------|----------------------|------------|--------|------------------------------------------------------------------------------|
| cluster_id_black_list | The blocklist of cluster IDs for synchronization. | `\|` | No | Separate multiple cluster IDs with vertical bars (`\|`). Each cluster ID must range from `cluster_id_value_min` to `cluster_id_value_max`. |
| cluster_id_black_value_min | The lower limit of cluster IDs in the synchronization blocklist. | 2147473648 | No | None |
| cluster_id_black_value_max | The upper limit of cluster IDs in the synchronization blocklist. | 2147483647 | No | None |

### Server-level blocklists

obcdc sends SQL and RPC requests to OBServer nodes. OceanBase AI Database provides parameters that allow you to block all requests sent to specific servers.

In addition, because obcdc pulls logs at the partition level, it has a built-in partition-level log-pulling blocklist. Servers that time out or report errors when partition logs are pulled are added to this blocklist. Servers are automatically added to and removed from the blocklist.

| Parameter | Description | Default value | Real-time modification supported | Remarks |
|----------------------|-------------------------------|-----|--------|-----------------------------------------------------------------------------------------------------------|
| server_blacklist | A blocklist of OBServer nodes that are blocked from receiving RPC requests from obcdc. | `\|` | Yes | The information about each OBServer node must be in the format of `svr_ip:rpc_port`. Separate the information about multiple OBServer nodes with vertical bars (`\|`). Logs are not pulled from the OBServer nodes in the blocklist. If an OBServer node cannot provide log services normally, for example, due to network partitioning or high latency, you can manually add the node to the blocklist. |
| sql_server_blacklist | A blocklist of OBServer nodes that are blocked from receiving SQL requests from obcdc. | `\|` | Yes | The information about each OBServer node must be in the format of `svr_ip:rpc_port`. Separate the information about multiple OBServer nodes with vertical bars (`\|`). |
