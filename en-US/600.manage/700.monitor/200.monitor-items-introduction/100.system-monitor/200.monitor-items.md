# SYSSTAT metrics

SYSSTAT metrics are one of the common diagnostic monitoring information items. They collect key performance values of system running, such as the number of SQL statement executions, execution time, and I/O count. These metrics cover all core components of OceanSeek, including clusters, tenants, and hosts.

## Source of metrics

The data of metrics is stored in the [[G]V$SYSSTAT](../../../../700.reference/700.system-views/300.system-view-of-sys-tenant/300.performance-view-of-sys-tenant/5700.gv-sysstat-of-sys-tenant.md) view. The key fields are described as follows:

| **Field name** | **Description** |
| ------------ | ----------------------------------------------------------- |
| CON_ID | Tenant ID |
| SVR_IP | Node IP |
| STAT_ID | Metric ID |
| NAME | Metric name |
| CLASS | Metric category |
| VALUE | Metric value |
| VALUE_TYPE | Value type of the metric: <ul><li>ADD: cumulative</li><li>SET: update</li></ul> |

## Query metrics

Take the `[G]V$SYSSTAT` view as an example to query all metrics in the SQL category.

```shell
obclient> SELECT STAT_ID, CLASS, NAME FROM V$STATNAME;
```

Take the `GV$SYSSTAT` view as an example to query all metrics in the SQL category:

```shell
obclient> SELECT CLASS,STAT_ID,NAME,VALUE_TYPE FROM GV$SYSSTAT WHERE CLASS=8;
```

Many metrics are related to internal implementations and may change or be deleted. The actual situation prevails.

## Metric categories

OceanSeek supports more than 600 metrics in 15 categories, covering key execution information such as the network, request queue, transaction, SQL, cache, storage, resource, and log. The categories are as follows:

### Network

You can query network-related metrics using the following example:

```shell
obclient> select distinct class,stat_id,name,VALUE_TYPE from gv$sysstat where class=1 and stat_id in (10000,10001,10002,10003,10004,10005,10006);
```

The result is as follows:

```shell
+-------+---------+----------------------+------------+
| class | stat_id | name                 | VALUE_TYPE |

|     1 |   10001 | rpc packet in bytes  | ADD_VALUE  |
|     1 |   10002 | rpc packet out       | ADD_VALUE  |
|     1 |   10003 | rpc packet out bytes | ADD_VALUE  |
|     1 |   10004 | rpc deliver fail     | ADD_VALUE  |

7 rows in set (0.06 sec)
```

Common network monitoring items:

| Metric ID | Metric name | Description |
| --------- | ---------- | ---- |

| 10001 | rpc packet in bytes | The cumulative number of bytes of RPC packets received by the tenant, in bytes. This value is calculated by adding the byte size of each RPC request received by the tenant or each response packet received after sending an RPC. |
| 10002 | rpc packet out | The cumulative number of RPC packets sent by the tenant. The count increments by 1 each time a tenant sends an RPC request or responds to an RPC request received. |
| 10003 | rpc packet out bytes | The cumulative number of bytes in RPC packets sent by the tenant, in bytes. This is the sum of the byte count of an RPC request sent by the tenant and the byte count of the response packet sent after receiving an RPC request. |
| 10004 | rpc deliver fail | The total number of failures in forwarding RPC requests to the tenant's work queue. This count increments by 1 whenever an RPC request fails to be forwarded to the tenant queue during IO forwarding. |
| 10005 | rpc net delay | The cumulative network transmission delay of RPC requests received by a tenant, in microseconds. | 10006 | rpc net frame delay | The cumulative network framework processing time received by a tenant for RPC requests, in microseconds. | 10007 | mysql packet in | The cumulative number of SQL request packets received by the tenant. This value is incremented by 1 each time a network thread decodes a complete SQL request packet. |
| 10008 | mysql packet in bytes | The cumulative size of SQL request packets received by the tenant, in bytes. The size of the original data packets received by the network thread, obtained according to protocol rules. |
| 10009 | mysql packet out | The cumulative number of response packets for an SQL request. When a network thread returns a packet, the counter increments by 1 for each encoded complete packet. |
| 10010 | mysql packet out bytes | The cumulative value of the bytes returned in SQL requests for a tenant, in bytes. The encoding size is accumulated during the encoding of the response set. |
| 10011 | mysql deliver fail | The cumulative number of times that tenant SQL login requests failed to be placed into the login queue and other requests failed to be placed into the worker thread queue. | 10012 | rpc compress original packet cnt | The cumulative number of RPC requests sent by the tenant that specify compression. This count increments by 1 whenever an RPC request is sent with the `compressor_type` parameter set. |
| 10013 | rpc compress compressed packet cnt | The cumulative number of compressed RPC requests sent by the tenant. When an RPC is sent, if the `compressor_type` parameter is set and the compression succeeds (the compressed byte count is less than the original byte count), the counter increments by 1. |
| 10014 | rpc compress original size | The RPC request sent by the tenant specifies the original byte size of the request to be compressed, in bytes. | 10015 | rpc compress compressed size | The cumulative size of compressed RPC requests sent by the tenant, in bytes. When an RPC is sent, if the `compressor_type` parameter is set and the compression succeeds, the compressed size is accumulated in the `RPC_COMPRESS_COMPRESSED_SIZE` metric. |
| 10016 | rpc stream compress original packet cnt | Deprecated. Reserved only for code. The unit is times. |
| 10017 | rpc stream compress compressed packet cnt | Deprecated. Reserved only for code. The unit is times. |
| 10018 | rpc stream compress original size | Deprecated. Reserved only for code. Unit: bytes. |
| 10019 | rpc stream compress compressed size | Deprecated. Reserved only for code. Unit: bytes. |

Common request queue monitoring items:

### Cache

You can query KVCache-related metrics using the following example.

```shell
obclient> select distinct class,stat_id,name,VALUE_TYPE from gv$sysstat where class=16 and stat_id in (50000, 50001, 50004, 50005, 50008, 50009, 50010, 50011, 50037, 50038,120001,120008,120009);
```

The `GV$SYSSTAT` view describes the hit rate of KVCache. To further explore the actual memory usage of each module in KVCache, you can query the `GV$OB_KVCACHE` view. For example:

```shell
obclient> select DBA_OB_TENANTS.tenant_id,tenant_name, svr_ip,svr_port, cache_name, cache_size

```

## Other

In addition to the `GV$SYSSTAT` view, there are other rich views that describe metrics from various perspectives.

For example, `GV$OB_PROCESSLIST` describes the current sessions of the system, including their active status and the SQL statements being executed. It also includes important fields such as `SID`, `SQL_ID`, `TRANS_ID`, and `TRACE_ID`, making it a powerful tool for end-to-end tracing.

* Query active sessions based on the `GV$OB_PROCESSLIST` view:

    ```shell
    obclient> select TENANT,SVR_IP,SVR_PORT,USER,HOST,COMMAND,STATE,INFO,SQL_ID,TRACE_ID 
    from GV$OB_PROCESSLIST 
    where STATE='ACTIVE' or null limit 10;
    ```

    The result is as follows:

    ```shell
    +--------+------------+----------+-----------+-------------------+---------+--------+------+----------------------------------+-----------------------------------+
    | TENANT | SVR_IP     | SVR_PORT | USER      | HOST              | COMMAND | STATE  | INFO | SQL_ID                           | TRACE_ID                          |
    +--------+------------+----------+-----------+-------------------+---------+--------+------+----------------------------------+-----------------------------------+
    | sys    |xx.xx.xx.xx |     2882 | DBA_query | xx.xx.xx.xx:51588 | Query   | ACTIVE | ...  | D18F6AE855AD0D7478162DD8EF48C781 | YB4206008451-0005F55893CEA363-0-0 |
    +--------+------------+----------+-----------+-------------------+---------+--------+------+----------------------------------+-----------------------------------+
    1 row in set (0.04 sec)
    ```

* Query the number of active sessions at the unit level based on the `GV$OB_PROCESSLIST` view:

    ```shell
    obclient>
    select 
    tenant_id, tenant_name,  svr_ip,
    case 
        when cnt is null then 0 
        else cnt end 
    as cnt
    from (
        select DBA_OB_TENANTS.tenant_name, DBA_OB_TENANTS.tenant_id, svr_ip, cnt 
        from DBA_OB_TENANTS 
        left join (
            select count(`state`='ACTIVE' OR NULL) as cnt, tenant as tenant_name, svr_ip
            from GV$OB_PROCESSLIST
            group by tenant,svr_ip ) t1 
        on DBA_OB_TENANTS.tenant_name = t1.tenant_name 
    where DBA_OB_TENANTS.tenant_type!='META'
    ) t2;
    ```
