# High availability at the database layer

OceanSeek is deployed on cost-effective commodity servers. Based on the Paxos protocol, each data copy is written to more than half of the replicas of LogService on three or more servers. Therefore, no data is lost when a minority of replicas are unavailable (one replica can be unavailable in a three-replica cluster), ensuring a recovery point objective (RPO) of 0. If the leader replica fails, a new leader is automatically elected from the remaining follower replicas to continue to provide services within a short time without manual intervention, ensuring a recovery time objective (RTO) of less than 8s. This design achieves a balance between strong consistency and high availability. Users can also adopt flexible deployment modes, such as single-IDC or three-IDC-in-the-same-city deployment, to achieve lossless disaster recovery at all levels.

## Root Service

In OceanSeek, Root Service is responsible for managing cluster nodes. Each OBServer reports its process status to Root Service every 2 seconds through heartbeat packets. Root Service monitors these heartbeat packets to obtain the working status of the OBServer processes.

The configuration items related to the OBServer heartbeat status are as follows:

* `lease_time`
  
  The cluster-level configuration item `lease_time` specifies the heartbeat lease duration. The default value is 10 seconds. For more information about this configuration item, see [lease_time](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/300.cluster-level-configuration-items/11400.lease_time.md).

  If Root Service does not receive a heartbeat packet from an OBServer within the period specified by `lease_time`, Root Service considers the observer process temporarily disconnected and marks its heartbeat status as `lease_expired`.

* `server_permanent_offline_time`
  
  The cluster-level configuration item `server_permanent_offline_time` specifies the time threshold for heartbeat loss of a node. A node is considered permanently offline after its heartbeat is lost for the specified period, and the data replicas on the permanently offline node must be automatically replenished. The default value is 3600 seconds. For more information about this configuration item, see [server_permanent_offline_time](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/300.cluster-level-configuration-items/20300.server_permanent_offline_time.md).

  If Root Service does not receive a heartbeat packet from an OBServer within the period specified by `server_permanent_offline_time`, Root Service considers the observer process disconnected and marks its heartbeat status as `permanent_offline`.

<main id="notice" type='explain'>
      <h4>Note</h4>
      <p>You can query the values of the preceding cluster-level configuration items by using the <code>SHOW PARAMETERS</code> statement. For example: <code>SHOW PARAMETERS LIKE 'server_permanent_offline_time';</code>.</p>
</main>

Based on the heartbeat packets, Root Service can obtain the following working statuses of an OBServer:

* The OBServer properly sends heartbeat packets, and the disk status in the heartbeat packets is normal. In this case, Root Service considers that the OBServer is working properly.

* The OBServer properly sends heartbeat packets, but the disk status in the heartbeat packets is abnormal. In this case, Root Service considers that the observer process still exists, but the disk of the OBServer is faulty. In addition, Root Service switches all leaders on this OBServer to another OBServer.

* No heartbeat packet is received from the OBServer within the period specified by `lease_time`, and the heartbeat status of the OBServer is marked as `lease_expired`. In this case, Root Service sets the status of the OBServer to `INACTIVE` and does not take other measures.

* No heartbeat packet is received from the OBServer within the period specified by `server_permanent_offline_time`, and the heartbeat status of the OBServer is marked as `permanent_offline`. In this case, Root Service removes the data replicas on this OBServer from the Paxos member group, and adds the removed data replicas to another active OBServer to ensure that the Paxos member group of data replicas is complete.

## Isolate a node

ODP can detect abnormal states of OBServer nodes, such as the stopped state (`ACTIVE` but with a `stop_time` field greater than 0) or the `INACTIVE` state, thereby avoiding routing application traffic to such abnormal nodes.

If a node is unstable, it may occasionally provide service but exhibit various abnormalities such as slow responses. If a client connects to this node, it will experience instability. OceanSeek provides the `STOP SERVER` command for isolating a node. After isolation, the node no longer provides external services, and ODP does not route requests to it, allowing for safe diagnostic, replacement, or maintenance actions. This makes it a powerful tool for operations and emergency response. The Stop Server operation checks whether all remaining replicas form a majority and whether log synchronization is complete. If these conditions are not met, the operation returns failure; if they are met, the system returns success after all leaders on the failed node have been switched over. Successful completion of Stop Server ensures that any maintenance action can be performed, including killing the observer process. For more information about the `STOP SERVER` command, see [Isolate a node](../../100.cluster-management/100.compute-service-management/300.common-cluster-operations/600.isolation-a-node.md).

Node isolation is applicable in single-IDC failure scenarios:

* Non-disconnection failures (such as machine instability caused by NIC packet loss) strongly rely on node isolation; otherwise, repeated leader switchover will affect the application.

* Disconnection failures (such as direct server downtime) do not strongly rely on node isolation. Instead, the system marks the node status as `INACTIVE` in the `oceanbase.DBA_OB_SERVERS` view to isolate application traffic.

When a node is isolated or a leader fails, an election is triggered. The election service's priority mechanism takes into account user-specified primary zones and the abnormal status of machines, ensuring a better replica is selected as the new leader.

## Disaster recovery operations

OceanSeek adopts a storage-and-compute separation architecture. It provides data durability through high-availability LogService, ensuring zero data loss (RPO = 0), and guarantees data high availability through multi-replica compute nodes. Different replica counts correspond to different disaster recovery operations: two-replica deployment supports manual leader switchover, while single-replica deployment supports disaster recovery within or across availability zones (AZs). For more information about replica deployment scenarios, see [Disaster recovery deployment solutions](400.disaster-recovery-deployment-plan.md).

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The cross-AZ disaster recovery feature for single replicas is supported starting from V4.6.2.1.</p>
</main>

### Disaster recovery operations in a two-replica scenario

For a compute node deployment with two replicas, in addition to isolating nodes, you can also perform an active leader switchover to switch the primary/secondary roles of log stream replicas.

The procedure for performing an active leader switchover is as follows:

1. Log in to the `sys` tenant of the cluster as the `root` user.

   Here is an example. Use the actual environment settings when you connect to the database.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

   For more information about how to connect to a database, see [Overview of connection methods](../../../200.connect/100.connection-methods-overview.md).

2. Query the zones, servers, and log stream replicas of tenants.

   ```shell
   obcllient [(none)]> SELECT a.TENANT_ID,a.LS_ID,a.SVR_IP,a.SVR_PORT,a.ZONE,a.role,b.TENANT_NAME,b.TENANT_TYPE FROM oceanbase.CDB_OB_LS_LOCATIONS a, oceanbase.DBA_OB_TENANTS b WHERE a.TENANT_ID=b.TENANT_ID;
   ```

   The query result is as follows:

   ```shell
   +-----------+-------+----------------+----------+-------+----------+-------------+-------------+
   | TENANT_ID | LS_ID | SVR_IP         | SVR_PORT | ZONE  | role     | TENANT_NAME | TENANT_TYPE |
   +-----------+-------+----------------+----------+-------+----------+-------------+-------------+
   |         1 |     1 | xx.xx.xx.237   |     2882 | zone1 | LEADER   | sys         | SYS         |
   |         1 |     1 | xx.xx.xx.238   |     2882 | zone2 | FOLLOWER | sys         | SYS         |
   |      1001 |     1 | xx.xx.xx.237   |     2882 | zone1 | LEADER   | META$1002   | META        |

   |      1002 |     1 | xx.xx.xx.237   |     2882 | zone1 | LEADER   | mysql001    | USER        |
   |      1002 |     1 | xx.xx.xx.238   |     2882 | zone2 | FOLLOWER | mysql001    | USER        |
   |      1002 |  1001 | xx.xx.xx.237   |     2882 | zone1 | LEADER   | mysql001    | USER        |
   |      1002 |  1001 | xx.xx.xx.238   |     2882 | zone2 | FOLLOWER | mysql001    | USER        |
   +-----------+-------+----------------+----------+-------+----------+-------------+-------------+
   8 rows in set
   ```

   For more information about the `CDB_OB_LS_LOCATIONS` view, see [CDB_OB_LS_LOCATIONS](../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/9700.o-cdb_ob_ls_locations-of-sys-tenant.md).

3. Perform a leader switchover.

   ```sql
   ALTER SYSTEM SWITCH REPLICA role LS [=] ls_id SERVER [=] 'ip:port' TENANT = tenant_name;
   ```

   The parameters are described as follows:

   * `role`: the role of the replica. Valid values are `LEADER` and `FOLLOWER`.

   * `ls_id`: the ID of the log stream replica to be modified.

   * `ip:port`: the IP address and RPC port of the server where the log stream replica to be modified resides.

   * `tenant_name`: the tenant to which the log stream replica to be modified belongs.

   Here is an example:

   ```shell
   obclient [(none)]> ALTER SYSTEM SWITCH REPLICA LEADER LS = 1001 SERVER = 'xx.xx.xx.238:2882' TENANT = mysql001;
   ```

4. After the operation is completed, query the view again to check whether the replica role is modified.

   ```shell
   obclient [(none)]> SELECT * FROM oceanbase.CDB_OB_LS_LOCATIONS WHERE TENANT_ID = 1002;
   ```

   The query result is as follows:


### Disaster recovery operations in single-replica scenarios

In a single-replica deployment, after a compute node fails, you need to restart the failed log stream replica on another available node. The disaster recovery operations for different failure scenarios are as follows:

| Failure scenario | Disaster recovery operation | Applicable to | Recovery location | Trigger method | Operation granularity |
| --- | --- | --- | --- | --- | --- |
| Some compute nodes are unavailable, but there are available nodes in the availability zone (AZ), or other nodes can be added. | `REPLACE LS` | User tenant | Within the AZ | Manual execution, one by one | Log stream |
| Some compute nodes are unavailable, and there are no available nodes in the AZ and no other nodes can be added. | `ALTER TENANT` (change the locality) | User tenant | Cross-AZ | Manual execution + automatic disaster recovery task initiated by RS | Tenant |
| All compute nodes in the entire AZ are unavailable. | `REPLACE TENANT` (restore the sys tenant) + change the locality (restore user tenants one by one) | System tenant and user tenant | Cross-AZ | Manual execution + automatic disaster recovery task initiated by RS | Tenant |

#### Scenario 1: Some compute nodes are unavailable, but there are available nodes within the availability zone (AZ), or additional nodes can be added.

When you replace a log stream within an availability zone (AZ), the system does not automatically trigger a Replace task. You need to query the cluster to identify the log streams on the failed server (you can query by `SVR_IP` and `SVR_PORT` in the `CDB_OB_LS_LOCATIONS` view), and then execute the `REPLACE LS` command for these log streams one by one to rebuild the failed log streams.

The syntax for the `REPLACE LS` command is as follows:

```sql
ALTER SYSTEM REPLACE LS [=] <ls_id>
  SERVER [=] '<ip>:<rpc_port>'
  [TENANT [=] '<tenant_name>'];
```

The relevant parameters are described as follows:

* `LS`: the log stream ID, which must be an integer, such as `1` or `1001`. It cannot be specified as a string.

* `SERVER`: the RPC address of the target node, which must be in the `ip:rpc_port` format. If you specify only the IP address but not the port, a parameter error is returned.

* `TENANT`: (Optional) the tenant to which the log stream belongs. When you use the `sys` tenant to operate on a Meta tenant, the format is `META$<user_tenant_id>`, for example, `META$1002`. If this parameter is omitted, the tenant of the current session is used.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <ul><li>The clause order is fixed: you must write <code>LS</code> first, then <code>SERVER</code>, and finally the optional <code>TENANT</code>. Reversing the order will result in a syntax error.</li><li>Incomplete forms such as writing only <code>REPLACE SERVER</code> or <code>REPLACE TENANT</code> are not supported.</li></ul>
</main>

Using the user tenant `mysql_tenant` (tenant ID 1002) as an example, the procedure is as follows:

1. Add or enable a new node within the availability zone (AZ), and execute `ALTER SYSTEM ADD SERVER` to join the new node to the cluster:

   ```sql
   ALTER SYSTEM ADD SERVER 'ip:port' ZONE 'zone1';
   ```

2. Migrate the units of this tenant to the new node. The `REPLACE LS` command can only be executed if the new node has units of this tenant:

   ```sql
   ALTER SYSTEM MIGRATE UNIT unit_id DESTINATION 'ip:port';
   ```

   Here, `unit_id` is the ID of the unit to be migrated, and `ip:port` is the IP and RPC port of the new node.

3. Execute the following `REPLACE LS` commands in sequence:

   <main id="notice" type='notice'>
     <h4>Notice</h4>
     <p>Before executing the <code>REPLACE LS</code> command, the following conditions must be met. Failure to meet any one will result in an error:</p>
     <ul><li>The target node is alive, allows migration in, is not permanently offline, and already has a unit of this tenant.</li><li>All machines in the log stream member list are unavailable (<code>INACTIVE</code>). As long as one machine is still alive, the command will be rejected.</li><li>The target node does not already have a replica of this log stream, and no other disaster recovery tasks are currently running on this log stream.</li></ul>
     <p><code>REPLACE LS</code> is recommended to be executed in the sys tenant; when executed in a user tenant, it can only operate on that tenant.</p>
   </main>

   1. First, restore the Meta tenant log stream:

      ```sql
      ALTER SYSTEM REPLACE LS = 1001 SERVER = 'ip:port' TENANT = 'META$1002';
      ALTER SYSTEM REPLACE LS = 1 SERVER = 'ip:port' TENANT = 'META$1002';
      ```

   2. Restore the user tenant's log stream:

      ```sql
      ALTER SYSTEM REPLACE LS = 1 SERVER = 'ip:port' TENANT = 'mysql_tenant';
      ```

   If there are other user log streams, proceed to restore them one by one.

   A successful command return only indicates that the task has been accepted by the system. It does not mean that the log stream has been restored. Wait until the task is completed before you execute the next command.

4. To determine whether a task is successfully executed, all of the following conditions must be met:

   * The `REPLACE REPLICA` task for that tenant and `ls_id` no longer exists in the `CDB_OB_LS_REPLICA_TASKS` view:

     ```sql
     SELECT * FROM oceanbase.CDB_OB_LS_REPLICA_TASKS WHERE TENANT_ID = 1002 AND LS_ID = 1 AND TASK_TYPE = 'REPLACE REPLICA';
     ```

   * The corresponding historical record in the `CDB_OB_LS_REPLICA_TASK_HISTORY` view has a `TASK_STATUS` of `COMPLETED` and an `EXECUTE_RESULT` of `OB_SUCCESS`:

     ```sql
     SELECT TASK_STATUS, EXECUTE_RESULT, TASK_TYPE, GMT_CREATE FROM oceanbase.CDB_OB_LS_REPLICA_TASK_HISTORY WHERE TENANT_ID = 1002 AND LS_ID = 1 AND TASK_TYPE = 'REPLACE REPLICA' ORDER BY GMT_CREATE DESC;
     ```

   When querying within a user tenant, you can use the `DBA_OB_LS_REPLICA_TASKS` and `DBA_OB_LS_REPLICA_TASK_HISTORY` views (which contain only data for the current tenant).

   If the `TASK_STATUS` in the historical record is not `COMPLETED` or the `EXECUTE_RESULT` is not `OB_SUCCESS`, the task failed. Decide whether to retry based on the error message.

   After a task succeeds, you can also verify business availability in the following ways:

   * Confirm that the leader of that log stream is located at the target node:

     ```sql
     SELECT TENANT_ID, LS_ID, ROLE, SVR_IP, SVR_PORT FROM oceanbase.CDB_OB_LS_LOCATIONS WHERE TENANT_ID = 1002 AND LS_ID = 1 AND ROLE = 'LEADER';
     ```

   * Perform simple read and write operations on that tenant (such as creating tables, inserting data, and querying) to confirm normal business operation.

5. After all log streams for that tenant are restored, confirm that unit migration is complete (`DBA_OB_UNITS` view: fields `MIGRATE_FROM_SVR_IP` and `MIGRATE_FROM_SVR_PORT` are cleared), and delete the failed server according to operational specifications.

#### Scenario 2: Some compute nodes are unavailable, and there are no available nodes or additional nodes can be added within the zone (AZ)

Before restoration, add sufficient compute nodes to the new zone (AZ) to host the restored log stream replicas. Also, confirm that all compute nodes for that tenant in the failed zone (AZ) are in the `INACTIVE` state (queryable via the `DBA_OB_SERVERS` view). For each user tenant in the cluster, perform the following operations in sequence:

1. Lock the tenant.

   ```sql
   ALTER TENANT mysql_tenant LOCK;
   ```

2. Expand the tenant resource pool's `ZONE_LIST`. A tenant with single-replica deployment has only one resource pool. By adding zones from the new zone (AZ) to the resource pool's `ZONE_LIST`, resources are provided for the restored log stream replicas.

   ```sql
   ALTER RESOURCE POOL mysql_tenant_pool ZONE_LIST = ('zone1', 'zone2');
   ```

3. Directly change the tenant's locality from the failed zone (AZ) to the new zone (AZ). After the locality change, RS automatically initiates a single-replica disaster recovery task, starting the tenant's log stream replica in the new zone (AZ).

   ```sql
   ALTER TENANT mysql_tenant LOCALITY = 'F@zone2';
   ```

4. Determine whether the disaster recovery task is complete. You can determine this by using any of the following methods:

   * The `JOB_STATUS` column in the `DBA_OB_TENANT_JOBS` view for the corresponding task is `SUCCESS`.

     ```sql
     SELECT * FROM oceanbase.DBA_OB_TENANT_JOBS WHERE TENANT_ID = 1002;
     ```

   * The `PREVIOUS_LOCALITY` column for the tenant in the `DBA_OB_TENANTS` view is `NULL`.

     ```sql
     SELECT TENANT_ID, TENANT_NAME, LOCALITY, PREVIOUS_LOCALITY FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_ID = 1002;
     ```

   <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>If there are unfinished resource specification change tasks for the tenant before the single-replica disaster recovery task is initiated, the <code>JOB_STATUS</code> in <code>DBA_OB_TENANT_JOBS</code> is marked as <code>SUCCESS</code> only after the previous task is completed. In this case, you can determine the result based on whether <code>PREVIOUS_LOCALITY</code> in the <code>DBA_OB_TENANTS</code> view is <code>NULL</code>.</p>
   </main>

5. Modify the tenant's `PRIMARY_ZONE` to change the primary availability zone (AZ) from the failed AZ to the new AZ.

   ```sql
   ALTER TENANT mysql_tenant PRIMARY_ZONE='zone2';
   ```

6. After the disaster recovery task is complete, narrow the tenant's resource pool by retaining only the zones in the new AZ and removing the zones from the failed AZ.

   ```sql
   ALTER RESOURCE POOL mysql_tenant_pool ZONE_LIST = ('zone2');
   ```

7. Unlock the tenant and restore business access.

   ```sql
   ALTER TENANT mysql_tenant UNLOCK;
   ```

#### Scenario 3: All compute nodes in an availability zone (AZ) are unavailable

Before recovery, add sufficient compute nodes to the new AZ to host the restored log stream replicas. Then perform the recovery in the following order:

1. Execute `REPLACE TENANT` on an idle server in the new AZ to restore the `sys` tenant.

   ```sql
   ALTER SYSTEM REPLACE TENANT = 'sys'
     REGION = 'region_name' ZONE = 'zone2' SERVER = 'ip:port'
     LOGSERVICE_ACCESS_POINT 'ip:port'
     SHARED_STORAGE_INFO 'shared_storage_info';
   ```

   This statement starts the log streams of the `sys` tenant on an idle server in the new AZ.

2. After the `sys` tenant is restored, modify its locality.

   ```sql
   ALTER TENANT sys LOCALITY = 'F@zone2';
   ```

   <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>If the operation <code>ALTER TENANT sys LOCALITY = 'F@zone2';</code> fails, you can restart RS and try the command again.</p>
   </main>

3. For each user tenant in the cluster, perform steps 1 through 7 from scenario 2 to restore that tenant's log stream replicas from the failed AZ to the new AZ.
