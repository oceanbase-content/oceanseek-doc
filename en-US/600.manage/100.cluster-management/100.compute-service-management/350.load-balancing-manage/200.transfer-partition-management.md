# Transfer a partition

When automatic load balancing cannot meet your requirements for aggregating or splitting specific partitions, you can manually initiate a partition transfer operation.

## Limitations and considerations

* The user performing the partition transfer operation must have the `ALTER SYSTEM` privilege. For more information about privileges, see [User and permission overview](../../../500.security-and-permissions/300.access-control/200.user-and-permission/100.user-and-permission-overview.md).

* The partition transfer operation is supported only for primary tenants, and partitions can be transferred only within a user tenant.

* If the transfer feature for a tenant is disabled (that is, the value of the `enable_transfer` parameter is `false`), an error will be returned when executing the `TRANSFER PARTITION` statement for that tenant. For `TRANSFER PARTITION` statements that have already been successfully executed, the corresponding partition transfer tasks may be canceled.

* The partition transfer operation is not supported for system tables.

* The partition transfer operation is not supported for user tables in the sys tenant.

* Transferring a regular table to a broadcast log stream or a replicated table to a regular log stream is not supported.

* Non-independent partitions cannot be transferred. For example, partitions in a local index table or a LOB table cannot be transferred.

* For the same partition, another partition transfer operation cannot be initiated before the current one is completed.

* If a balance job is being executed in the current cluster, a manually triggered partition transfer task will not be scheduled immediately. To schedule the partition transfer task as soon as possible, you can cancel the existing balance job. For more information about how to cancel a balance job, see [Cancel a balance job](400.cancel-balance-job-task.md).

## Prerequisites

* Before you transfer a partition, you must enable the transfer feature. The transfer feature is controlled by the tenant-level parameter `enable_transfer`. The default value is `true`, indicating that the feature is enabled. For more information about the `enable_transfer` parameter, see [enable_transfer](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3000.enable_transfer.md).

* Since the partition transfer strategy may conflict with the automatic rebalancing strategy, to ensure that partition positions remain unchanged, you are advised to disable the automatic rebalancing strategy before you transfer a partition. That is, set the `enable_rebalance` parameter of the corresponding tenant to `false`. For more information about the `enable_rebalance` parameter, see [enable_rebalance](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2800.enable_rebalance.md).

  The partition transfer operation itself is not controlled by the `enable_rebalance` parameter. However, when both `enable_rebalance` and `enable_transfer` are set to `true`, it is possible that after a user migrates a partition to its corresponding log stream, the system's automatic rebalancing strategy moves the same partition to another log stream.

## Transfer partitions in the sys tenant

1. Log in to the `sys` tenant of the cluster as the `root` user.

   The following example shows how to connect to the database. Modify the parameters according to your actual environment.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

2. Query the `DBA_OB_TENANTS` view for the `TENANT_ID` of the target tenant.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_NAME = 'mysql001';
   ```

   The query result is as follows:

   ```shell
   +-----------+
   | TENANT_ID |
   +-----------+
   |      1006 |
   +-----------+
   1 row in set
   ```

3. Confirm the partition information.

   You can query the `CDB_OB_TABLE_LOCATIONS` view for the `TABLE_ID`, `OBJECT_ID`, and `LS_ID` of a specified partition in a table.

   * Get the `TABLE_ID`, `OBJECT_ID`, and `LS_ID` of a specified partition in a non-partitioned table

      Assume that there is a non-partitioned table named `T1` in the `mysql001` tenant. The following example shows how to query it:

      ```shell
      obclient(root@sys)[oceanbase]> SELECT TABLE_ID AS TABLE_ID, OBJECT_ID, TABLET_ID, LS_ID FROM oceanbase.CDB_OB_TABLE_LOCATIONS WHERE TENANT_ID = 1006 AND DATABASE_NAME = 'SYS' AND TABLE_NAME= 'T1' LIMIT 1;
      ```

      The query result is as follows:

      ```shell
      +----------+-----------+-----------+-------+
      | TABLE_ID | OBJECT_ID | TABLET_ID | LS_ID |
      +----------+-----------+-----------+-------+
      |   500002 |    500002 |    200001 |  1001 |
      +----------+-----------+-----------+-------+
      1 row in set
      ```

   * Get the `TABLE_ID`, `OBJECT_ID`, and `LS_ID` of a specified partition in a partitioned table

      For a partitioned table, you only need to specify the name of the partition.

      Assume that there is a partitioned table named `TBL1_LOG_R` in the `mysql001` tenant.

      ```shell
      obclient(root@mysql001)[oceanbase]> CREATE TABLE tbl1_log_r(log_id INT,log_date DATE NOT NULL DEFAULT SYSDATE)
       PARTITION BY RANGE(log_date) 
        (PARTITION M202001 VALUES LESS THAN(TO_DATE('2020/02/01','YYYY/MM/DD'))
         , PARTITION M202002 VALUES LESS THAN(TO_DATE('2020/03/01','YYYY/MM/DD'))
         , PARTITION M202003 VALUES LESS THAN(TO_DATE('2020/04/01','YYYY/MM/DD'))
         , PARTITION M202004 VALUES LESS THAN(TO_DATE('2020/05/01','YYYY/MM/DD'))
         , PARTITION M202005 VALUES LESS THAN(TO_DATE('2020/06/01','YYYY/MM/DD'))
         , PARTITION M202006 VALUES LESS THAN(TO_DATE('2020/07/01','YYYY/MM/DD'))
         , PARTITION M202007 VALUES LESS THAN(TO_DATE('2020/08/01','YYYY/MM/DD'))
         , PARTITION M202008 VALUES LESS THAN(TO_DATE('2020/09/01','YYYY/MM/DD'))
         , PARTITION M202009 VALUES LESS THAN(TO_DATE('2020/10/01','YYYY/MM/DD'))
         , PARTITION M202010 VALUES LESS THAN(TO_DATE('2020/11/01','YYYY/MM/DD'))
         , PARTITION M202011 VALUES LESS THAN(TO_DATE('2020/12/01','YYYY/MM/DD'))
         , PARTITION M202012 VALUES LESS THAN(TO_DATE('2021/01/01','YYYY/MM/DD'))
         , PARTITION MMAX VALUES LESS THAN (MAXVALUE)
         );
      ```

      The following example shows how to query the partition `M202005` in this table:

      ```shell
      obclient(root@sys)[oceanbase]> SELECT TABLE_ID AS TABLE_ID, OBJECT_ID, TABLET_ID, LS_ID FROM oceanbase.CDB_OB_TABLE_LOCATIONS WHERE TENANT_ID = 1006 AND DATABASE_NAME = 'SYS' AND TABLE_NAME= 'TBL1_LOG_R' AND PARTITION_NAME = 'M202005' LIMIT 1;
      ```

      The query result is as follows:

      ```shell
      +----------+-----------+-----------+-------+
      | TABLE_ID | OBJECT_ID | TABLET_ID | LS_ID |
      +----------+-----------+-----------+-------+
      |   500003 |    500009 |    200006 |  1002 |
      +----------+-----------+-----------+-------+
      1 row in set
      ```

   * Get the `TABLE_ID`, `OBJECT_ID`, and `LS_ID` of a subpartition in a subpartitioned table

      For a subpartitioned table, you need to specify both the name of the partition and the name of the subpartition.

      Assume that a subpartitioned table named `T2_F_RL` exists in the `mysql001` tenant.

      ```shell
      obclient(root@mysql001)[oceanbase]> CREATE TABLE t2_f_rl(col1 INT,col2 VARCHAR(50))
       PARTITION BY RANGE(col1)
       SUBPARTITION BY LIST(col2)
       (PARTITION p0 VALUES LESS THAN(100)
         (SUBPARTITION sp0 VALUES('01'),
          SUBPARTITION sp1 VALUES('02')
          ),
        PARTITION p1 VALUES LESS THAN(200)
         (SUBPARTITION sp2 VALUES('01'),
          SUBPARTITION sp3 VALUES('02'),
          SUBPARTITION sp4 VALUES('03')
         )
        );
      ```

      The following example shows how to query information related to the subpartition `SP2` in this subpartitioned table:

      ```shell
      obclient(root@sys)[oceanbase]> SELECT TABLE_ID AS TABLE_ID, OBJECT_ID, TABLET_ID, LS_ID FROM oceanbase.CDB_OB_TABLE_LOCATIONS WHERE TENANT_ID = 1006 AND DATABASE_NAME = 'SYS' AND TABLE_NAME= 'T2_F_RL' AND PARTITION_NAME = 'P1' AND SUBPARTITION_NAME = 'SP2' LIMIT 1;
      ```

      The query result is as follows:

      ```shell
      +----------+-----------+-----------+-------+
      | TABLE_ID | OBJECT_ID | TABLET_ID | LS_ID |
      +----------+-----------+-----------+-------+
      |   500018 |    500023 |    200017 |  1003 |
      +----------+-----------+-----------+-------+
      1 row in set
      ```

4. Select the destination log stream for the data transfer.

   1. Query the `CDB_OB_LS` view for the status and information of the tenant's log streams.

      ```shell
      obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.CDB_OB_LS WHERE TENANT_ID = 1006;
      ```

      The query result is as follows:

      ```shell
      +-----------+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+------+-----------+
      | TENANT_ID | LS_ID | STATUS | PRIMARY_ZONE | UNIT_GROUP_ID | LS_GROUP_ID | CREATE_SCN          | DROP_SCN | SYNC_SCN            | READABLE_SCN        | FLAG | UNIT_LIST |
      +-----------+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+------+-----------+
      |      1006 |     1 | NORMAL | zone1        |             0 |           0 |                NULL |     NULL | 1701244663685197789 | 1701244663685197789 |      |           |
      |      1006 |  1001 | NORMAL | zone1        |             0 |        1001 | 1701239786827662637 |     NULL | 1701244663685197789 | 1701244663685197789 |      | 1001      |
      |      1006 |  1002 | NORMAL | zone1        |             0 |        1002 | 1701239786831568305 |     NULL | 1701244664066906860 | 1701244664066906859 |      | 1002      |
      |      1006 |  1003 | NORMAL | zone1        |             0 |        1003 | 1701239786834300282 |     NULL | 1701244664175263949 | 1701244664175263948 |      | 1003      |
      +-----------+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+------+-----------+
      4 rows in set
      ```

   2. Query the `CDB_OB_TABLET_TO_LS` view for the distribution information of tablets on the log streams.

      ```shell
      obclient(root@sys)[oceanbase]> SELECT LS_ID, COUNT(*) AS C FROM oceanbase.CDB_OB_TABLET_TO_LS WHERE TENANT_ID = 1006 GROUP BY LS_ID;
      ```

      The query result is as follows:

      ```shell
      +-------+------+
      | LS_ID | C    |
      +-------+------+
      |     1 |  578 |
      |  1001 |    7 |
      |  1002 |    5 |
      |  1003 |    7 |
      +-------+------+
      4 rows in set
      ```

      Based on the information presented above, select an appropriate log stream as the destination for the data transfer.

5. Execute the following command to perform the partition transfer operation.

   ```shell
   ALTER SYSTEM TRANSFER PARTITION TABLE_ID [=] table_id, OBJECT_ID [=] object_id TO LS ls_id TENANT = 'tenant_name';
   ```

   where:

   * `table_id`: the ID of the table.

   * `object_id`: the unique identifier of the partition.

   * `ls_id`: the ID of the log stream at the destination of the data transfer.

   * `tenant_name`: the tenant to which the partition to be transferred belongs.

   Taking tenant `mysql001` as an example, the following example shows how to migrate the `M202005` partition from the current log stream `1002` to log stream `1003` for the table `TBL1_LOG_R`.

   ```shell
   obclient(root@sys)[oceanbase]> ALTER SYSTEM TRANSFER PARTITION TABLE_ID = 500003, OBJECT_ID = 500009 TO LS 1003 TENANT = 'mysql001';
   ```

6. After the partition transfer statement is executed successfully, you can view the task status by using the following views.

   1. Query the `CDB_OB_TRANSFER_PARTITION_TASKS` view for the task's `TASK_ID`, `TRANSFER_TASK_ID`, and `BALANCE_JOB_ID`.

      The `CDB_OB_TRANSFER_PARTITION_TASKS` view displays all partition transfer tasks currently in progress for all tenants. A sample query is as follows:

      ```shell
      obclient(root@sys)[oceanbase]> SELECT TASK_ID, BALANCE_JOB_ID, TRANSFER_TASK_ID, STATUS FROM oceanbase.CDB_OB_TRANSFER_PARTITION_TASKS WHERE TENANT_ID = 1006 AND TABLE_ID = 500003 AND OBJECT_ID = 500009;
      ```

      A sample query result is as follows:

      ```shell
      +---------+----------------+------------------+--------+
      | TASK_ID | BALANCE_JOB_ID | TRANSFER_TASK_ID | STATUS |
      +---------+----------------+------------------+--------+
      |       1 |          17304 |                1 | DOING  |
      +---------+----------------+------------------+--------+
      1 row in set
      ```

      You can confirm the task status based on the value of the `STATUS` column in the query results to further check the task execution progress:

      * `WAITING`: The task is waiting and has not started scheduling.
      * `INIT`: The task has built a `BALANCE_JOB`. You can view the execution progress of the associated `BALANCE_JOB` using the `BALANCE_JOB_ID`.
      * `DOING`: The task has started executing the transfer. You can view the associated partition transfer task using the `TRANSFER_TASK_ID`. The `TRANSFER_TASK_ID` changes multiple times, as one partition transfer task involves multiple transfers.

      If the query result of the `CDB_OB_TRANSFER_PARTITION_TASKS` view is empty, you can view the task result through the `CDB_OB_TRANSFER_PARTITION_TASK_HISTORY` view.

   2. Query the `CDB_OB_BALANCE_JOBS` or `CDB_OB_BALANCE_JOB_HISTORY` view with the obtained `BALANCE_JOB_ID` to confirm the execution status of the associated BALANCE_JOB.

      The `CDB_OB_BALANCE_JOBS` view displays all load balancing jobs currently in progress for all tenants. Each tenant has only one load balancing job (BALANCE_JOB) at a time, and each job generates multiple load balancing tasks (TRANSFER_TASK). The `CDB_OB_BALANCE_JOB_HISTORY` view displays the history of all load balancing jobs executed by all tenants. A sample query is as follows:

      ```shell
      obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.CDB_OB_BALANCE_JOBS WHERE JOB_ID = 17304;
      ```

      ```shell
      obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.CDB_OB_BALANCE_JOB_HISTORY WHERE JOB_ID = 17304;
      ```

      Here, `17304` needs to be replaced with the `BALANCE_JOB_ID` obtained from the previous step.

      The `STATUS` column in the query results shows the execution status of the `BALANCE_JOB`:

      * `DOING`: The load balancing job is being executed.
      * `COMPLETED`: The load balancing job was executed successfully.
      * `CANCELING`: The load balancing job is being canceled.
      * `CANCELED`: The load balancing job has been canceled.

   3. Query the `CDB_OB_TRANSFER_TASKS` or `CDB_OB_TRANSFER_TASK_HISTORY` view with the obtained `TRANSFER_TASK_ID` to confirm the execution status of the task's associated TRANSFER_TASK.

      The `CDB_OB_TRANSFER_TASKS` view displays all load balancing tasks currently in progress for all tenants. Multiple load balancing tasks may be running at the same time, and these tasks (TRANSFER_TASK) all belong to the same load balancing job (BALANCE_JOB). The `CDB_OB_TRANSFER_TASK_HISTORY` view displays the history of all load balancing tasks executed by all tenants. A sample query is as follows:

      ```shell
      obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.CDB_OB_TRANSFER_TASKS WHERE TASK_ID = 1;
      ```

      ```shell
      obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.CDB_OB_TRANSFER_TASK_HISTORY WHERE TASK_ID = 1;
      ```

      Here, `1` needs to be replaced with the `TRANSFER_TASK_ID` obtained from the previous step.

      The `STATUS` column in the query results shows the execution status of the `TRANSFER_TASK`:

      * `INIT`: The task is being created.
      * `START`: The transfer has started.
      * `DOING`: The transfer is in progress.
      * `ABORTED`: The transfer task failed and was terminated.
      * `COMPLETED`: The transfer task succeeded.
      * `FAILED`: The transfer task failed.
      * `CANCELED`: The transfer task was canceled.

   4. Query the `CDB_OB_TRANSFER_PARTITION_TASK_HISTORY` view with the obtained `TASK_ID` to confirm the result of the partition transfer task.

      The `CDB_OB_TRANSFER_PARTITION_TASK_HISTORY` view displays the history of all partition transfer tasks performed by a tenant.

      ```shell
      obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.CDB_OB_TRANSFER_PARTITION_TASK_HISTORY WHERE TASK_ID = 1;
      ```

      Replace `1` with the `TASK_ID` obtained in the previous step.

      The `STATUS` column in the query results indicates the result of the partition transfer task:

      * `COMPLETED`: The partition transfer task succeeded.

      * `FAILED`: The partition transfer task failed. You can check the `COMMENT` column for the cause of the failure. Common information in the `COMMENT` column includes:

        * `LS not exist or may be in DROPPING/WAIT_OFFLINE status`: The log stream at the destination of the log stream transfer may not exist, or it may be in the `DROPPING` or `WAIT_OFFLINE` state.
        * `LS status is not NORMAL or is in BLOCK_TABLET_IN state`: The log stream at the destination of the log stream transfer may not be in the `NORMAL` state. For example, it may be in the `CREATING` or `CREATED` state, or the log stream may have been blocked by `BLOCK_TABLET_IN` and cannot be migrated in.
        * `Table has beed dropped`: The table to which the partition to be transferred belongs has been dropped.
        * `Partition has beed dropped`: The partition to be transferred has been dropped.
        * `Partition is already in dest LS`: The partition is already on the destination log stream.
        * `Need retry, partition may be dropped`: During the log stream transfer, the partition has been dropped. The system will check again to determine whether the partition exists when generating the next load balancing task.
        * `Need retry, partition may be dropped or be transferre`: During the log stream transfer, the partition no longer exists. This may be because the partition has been dropped or it is no longer on the source log stream. The system will check whether the partition exists or needs to regenerate a log stream transfer task when generating the next load balancing task.

7. After the log stream transfer task is successfully executed, view the information about the corresponding partition again.

    ```shell
    obclient(root@sys)[oceanbase]> SELECT TABLE_ID AS TABLE_ID, OBJECT_ID, TABLET_ID, LS_ID FROM oceanbase.CDB_OB_TABLE_LOCATIONS WHERE TENANT_ID = 1006 AND DATABASE_NAME = 'SYS' AND TABLE_NAME= 'TBL1_LOG_R' AND PARTITION_NAME = 'M202005' LIMIT 1;
    ```

    The query result is as follows:

    ```shell
    +----------+-----------+-----------+-------+
    | TABLE_ID | OBJECT_ID | TABLET_ID | LS_ID |
    +----------+-----------+-----------+-------+
    |   500003 |    500009 |    200006 |  1003 |
    +----------+-----------+-----------+-------+
    1 row in set
    ```

    According to the result, the `M202005` partition of the `TBL1_LOG_R` table in the `SYS` database has been migrated from the previous log stream `1002` to log stream `1003`. The log stream transfer operation is successful.

## Transfer a partition in a user tenant

This document uses the `mysql_tenant` tenant as an example to provide operational guidance.

1. Connect to the database as the tenant administrator of the user tenant.

   Note that you must specify the corresponding options in the following sample code based on your actual database configurations.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@mysql_tenant#obdemo -p***** -A
   ```

2. Confirm partition information.

   Query the `DBA_OB_TABLE_LOCATIONS` view for the `TABLE_ID`, `OBJECT_ID`, and `LS_ID` of the specified partition.

   * Retrieve `TABLE_ID`, `OBJECT_ID`, and `LS_ID` for a non-partitioned table

      Assume the `mysql_tenant` tenant contains a non-partitioned table named `t1`. The query example is as follows:

      ```shell
      obclient(root@mysql_tenant)[test]> SELECT TABLE_ID AS TABLE_ID, OBJECT_ID, TABLET_ID, LS_ID FROM oceanbase.DBA_OB_TABLE_LOCATIONS WHERE DATABASE_NAME = 'test' AND TABLE_NAME= 't1' LIMIT 1;
      ```

      The query result is as follows:

      ```shell
      +----------+-----------+-----------+-------+
      | TABLE_ID | OBJECT_ID | TABLET_ID | LS_ID |
      +----------+-----------+-----------+-------+
      |   500002 |    500002 |    200001 |  1001 |
      +----------+-----------+-----------+-------+
      1 row in set
      ```

   * Retrieve `TABLE_ID`, `OBJECT_ID`, and `LS_ID` for a partitioned table

      For a partitioned table, you only need to specify the name of the partition. Here is an example:

      Assume the `mysql_tenant` tenant contains a partitioned table named `tbl1_l`.

      ```shell
      obclient(root@mysql_tenant)[test]> CREATE TABLE tbl1_l (col1 BIGINT PRIMARY KEY,col2 VARCHAR(50))
       PARTITION BY LIST(col1) 
        (PARTITION p0 VALUES IN (1, 2, 3),
         PARTITION p1 VALUES IN (5, 6),
         PARTITION p2 VALUES IN (DEFAULT)
        );
      ```

      The following example shows how to query information about partition `p1` in this partitioned table:

      ```shell
      obclient(root@mysql_tenant)[oceanbase]> SELECT TABLE_ID AS TABLE_ID, OBJECT_ID, TABLET_ID, LS_ID FROM oceanbase.DBA_OB_TABLE_LOCATIONS WHERE DATABASE_NAME = 'test' AND TABLE_NAME= 'tbl1_l' AND PARTITION_NAME = 'p1' LIMIT 1;
      ```

      The query result is as follows:

      ```shell
      +----------+-----------+-----------+-------+
      | TABLE_ID | OBJECT_ID | TABLET_ID | LS_ID |
      +----------+-----------+-----------+-------+
      |   500012 |    500014 |    200009 |  1001 |
      +----------+-----------+-----------+-------+
      1 row in set
      ```

   * Retrieve `TABLE_ID`, `OBJECT_ID`, and `LS_ID` for a subpartitioned table

      For a subpartitioned table, you need to specify both the partition name and the subpartition name.

      Assume the `mysql_tenant` tenant contains a subpartitioned table named `t2_f_rclc`.

      ```shell
      obclient(root@mysql_tenant)[test]> CREATE TABLE t2_f_rclc (col1 INT,col2 INT) 
       PARTITION BY RANGE COLUMNS(col1)
       SUBPARTITION BY LIST COLUMNS(col2)
       (PARTITION p0 VALUES LESS THAN(100)
         (SUBPARTITION sp0 VALUES IN(1,3),
          SUBPARTITION sp1 VALUES IN(4,6),
          SUBPARTITION sp2 VALUES IN(7,9)),
        PARTITION p1 VALUES LESS THAN(200)
         (SUBPARTITION sp3 VALUES IN(1,3),
          SUBPARTITION sp4 VALUES IN(4,6),
          SUBPARTITION sp5 VALUES IN(7,9))
       ); 
      ```

      The following example shows how to query information about subpartition `sp3` in this subpartitioned table:

      ```shell
       obclient(root@mysql_tenant)[oceanbase]> SELECT TABLE_ID AS TABLE_ID, OBJECT_ID, TABLET_ID, LS_ID FROM oceanbase.DBA_OB_TABLE_LOCATIONS WHERE DATABASE_NAME = 'test' AND TABLE_NAME= 't2_f_rclc' AND PARTITION_NAME = 'P1' AND SUBPARTITION_NAME = 'sp3' LIMIT 1;
      ```

      The query result is as follows:

      ```shell
      +----------+-----------+-----------+-------+
      | TABLE_ID | OBJECT_ID | TABLET_ID | LS_ID |
      +----------+-----------+-----------+-------+
      |   500003 |    500009 |    200005 |  1002 |
      +----------+-----------+-----------+-------+
      1 row in set
      ```

   ALTER SYSTEM TRANSFER PARTITION TABLE_ID [=] table_id, OBJECT_ID [=] object_id TO LS ls_id;

   ```

5. After the partition transfer command is successfully executed, you can view the task status using the following views.

   1. Query the `DBA_OB_TRANSFER_PARTITION_TASKS` view to obtain the task's `TASK_ID`, `TRANSFER_TASK_ID`, and `BALANCE_JOB_ID`.

      The `DBA_OB_TRANSFER_PARTITION_TASKS` view displays the current partition transfer tasks being processed under the tenant. An example query is as follows:

      ```shell
      obclient(root@mysql_tenant)[oceanbase]> SELECT TASK_ID, BALANCE_JOB_ID, TRANSFER_TASK_ID, STATUS FROM oceanbase.DBA_OB_TRANSFER_PARTITION_TASKS WHERE TABLE_ID = 500012 AND OBJECT_ID = 500014;
      ```

      An example of the query result is as follows:

      ```shell
      +---------+----------------+------------------+--------+
      | TASK_ID | BALANCE_JOB_ID | TRANSFER_TASK_ID | STATUS |
      +---------+----------------+------------------+--------+
      |       1 |          26506 |                1 | DOING  |
      +---------+----------------+------------------+--------+
      1 row in set
      ```

      You can confirm the task status based on the value of `STATUS` in the query result and further check the task execution progress:

      * `WAITING`: The task is waiting and has not started scheduling.
      * `INIT`: The task has built a `BALANCE_JOB`. You can view the execution progress of the associated `BALANCE_JOB` by using the `BALANCE_JOB_ID`.
      * `DOING`: The task has started executing the transfer. You can view the associated partition transfer task by using the `TRANSFER_TASK_ID`. The `TRANSFER_TASK_ID` changes multiple times, as one partition transfer task involves multiple transfers.

      If the query result of the `DBA_OB_TRANSFER_PARTITION_TASKS` view is empty, you can view the task results through the `DBA_OB_TRANSFER_PARTITION_TASK_HISTORY` view.

   2. Query the `DBA_OB_BALANCE_JOBS` or `DBA_OB_BALANCE_JOB_HISTORY` view based on the obtained `BALANCE_JOB_ID` to confirm the execution status of the associated `BALANCE_JOB`.

      The `DBA_OB_BALANCE_JOBS` view displays the load balancing jobs currently being executed for the current tenant. Each tenant has only one load balancing job (BALANCE_JOB) at a time, and each job generates multiple load balancing tasks (TRANSFER_TASK). The `DBA_OB_BALANCE_JOB_HISTORY` view displays the history of load balancing jobs executed for the current tenant. An example query is as follows:

      ```shell
      obclient [oceanbase]> SELECT * FROM oceanbase.DBA_OB_BALANCE_JOBS WHERE JOB_ID = 26506;
      obclient(root@mysql_tenant)[oceanbase]>```

      ```shell
      obclient(root@mysql_tenant)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_BALANCE_JOB_HISTORY WHERE JOB_ID = 26506;
      ```

      Here, `26506` needs to be replaced with the `BALANCE_JOB_ID` obtained from the previous step.

      The `STATUS` column in the query result shows the execution status of the `BALANCE_JOB`:

      * `DOING`: The load balancing job is being executed.
      * `COMPLETED`: The load balancing job was executed successfully.
      * `CANCELING`: The load balancing job is being canceled.
      * `CANCELED`: The load balancing job has been canceled.

   3. Query the `DBA_OB_TRANSFER_TASKS` or `DBA_OB_TRANSFER_TASK_HISTORY` view based on the obtained `TRANSFER_TASK_ID` to confirm the execution status of the associated `TRANSFER_TASK`.

      The `DBA_OB_TRANSFER_TASKS` view displays the load balancing tasks currently being executed for the current tenant. Multiple load balancing tasks may be executing at the same time, and these tasks (TRANSFER_TASK) all belong to the same load balancing job (BALANCE_JOB). The `DBA_OB_TRANSFER_TASK_HISTORY` view displays the history of load balancing tasks executed for the current tenant. An example query is as follows:

      ```shell
      obclient(root@mysql_tenant)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_TRANSFER_TASKS WHERE TASK_ID = 1;
      ```

      ```shell
      obclient(root@mysql_tenant)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_TRANSFER_TASK_HISTORY WHERE TASK_ID = 1;
      ```

      Here, `1` needs to be replaced with the `TRANSFER_TASK_ID` obtained from the previous step.

      The `STATUS` column in the query result shows the execution status of the `TRANSFER_TASK`:

      * `INIT`: The task is being created.
      * `START`: The transfer has started.
      * `DOING`: The transfer is in progress.
      * `ABORTED`: The transfer task failed and the task was terminated.
      * `COMPLETED`: The transfer task was executed successfully.
      * `FAILED`: The transfer task failed.
      * `CANCELED`: The transfer task has been canceled.

   4. Query the `DBA_OB_TRANSFER_PARTITION_TASK_HISTORY` view with the obtained `TASK_ID` to confirm the result of the partition transfer task.

      The `DBA_OB_TRANSFER_PARTITION_TASK_HISTORY` view displays the history of partition transfer tasks executed for the current tenant. A sample query is as follows:

      ```shell
      obclient(root@mysql_tenant)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_TRANSFER_PARTITION_TASK_HISTORY WHERE TASK_ID = 1;
      ```

      Here, `1` should be replaced with the `TASK_ID` obtained in the previous step.

      The `STATUS` column in the query results indicates the outcome of the partition transfer task:

      * `COMPLETED`: The partition transfer task was successfully executed.

      * `FAILED`: The partition transfer task failed. You can check the `COMMENT` column for further details about the failure. Common information in the `COMMENT` column includes:

        * `LS not exist or may be in DROPPING/WAIT_OFFLINE status`: The log stream at the destination of the transfer may not exist, or it may be in the `DROPPING` or `WAIT_OFFLINE` state.
        * `LS status is not NORMAL or is in BLOCK_TABLET_IN state`: The log stream at the destination of the transfer may not be in the `NORMAL` state. For example, it may be in the `CREATING` or `CREATED` state, or the log stream may have been blocked by `BLOCK_TABLET_IN` and cannot be migrated in.
        * `Table has beed dropped`: The table to which the partition to be transferred belongs has been dropped.
        * `Partition has beed dropped`: The partition to be transferred has been dropped.
        * `Partition is already in dest LS`: The partition is already on the destination log stream.
        * `Need retry, partition may be dropped`: During the transfer, the partition was dropped. The system will recheck whether the partition exists when generating the next load balancing task.
        * `Need retry, partition may be dropped or be transferre`: During the transfer, the partition no longer existed. This may be because the partition was dropped or it is no longer on the source log stream. The system will check whether the partition exists or regenerate the transfer task when generating the next load balancing task.

6. After the partition transfer task is executed successfully, view the partition information again.

    ```shell
    obclient(root@mysql_tenant)[oceanbase]> SELECT TABLE_ID AS TABLE_ID, OBJECT_ID, TABLET_ID, LS_ID FROM oceanbase.DBA_OB_TABLE_LOCATIONS WHERE DATABASE_NAME = 'test' AND TABLE_NAME= 'tbl1_l' AND PARTITION_NAME = 'p1' LIMIT 1;
    ```

    The query result is as follows:

    ```shell
    +----------+-----------+-----------+-------+
    | TABLE_ID | OBJECT_ID | TABLET_ID | LS_ID |
    +----------+-----------+-----------+-------+
    |   500012 |    500014 |    200009 |  1003 |
    +----------+-----------+-----------+-------+
    1 row in set
    ```

    According to the results, the `p1` partition of the `tbl1_l` table in the `test` database has been successfully transferred from log stream `1001` to log stream `1003`.
