# Update object storage access credentials

In a shared storage architecture, the observer process uses object storage to persist business data, and LogService uses object storage to persist log data. When you need to update the object storage access credentials (for example, due to periodic rotation of AK/SK or credential leakage), you can use the `ALTER SYSTEM` statement to complete the credential update. This topic describes how to update the observer process's access credentials for object storage.

The AK/SK rotation for LogService is independent of the observer process credential update. For specific operations, see [Rotate LogService access credentials](../../300.logservice-management/300.logservice-operations/800.rotate-access-key.md).

## Prerequisites

Before updating the access credentials for data storage and log storage, you must create new AK/SK on the object storage service and ensure the new credentials have read/write permissions for the target bucket. For permission requirements, see [Object storage overview](../../200.object-storage-management/100.object-storage-overview.md).

## Update data storage access credentials

Data storage access credentials are directly held by the compute node OBServer and point to the object storage bucket where the data storage is located. They are used to read from and write baseline data and minor compaction data. These credentials are initially configured during cluster creation using the `SHARED_STORAGE_INFO` parameter.

If you later need to change the access key for an object storage bucket, you can update it online using the following statement without restarting the cluster: `ALTER SYSTEM CHANGE SHARED_STORAGE_DEST`.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>The <code>ALTER SYSTEM CHANGE SHARED_STORAGE_DEST</code> statement can only be executed by the system tenant (i.e., the <code>sys</code> tenant).</p>
</main>

### Procedure

1. Log in to the `sys` tenant of the cluster as the `root` user.

   Note that you must specify the corresponding options in the following sample code based on your actual database configurations.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

2. Query the `oceanbase.DBA_OB_ZONE_STORAGE` view to view the object storage information configured for the current cluster.

   ```shell
   obclient [(none)]> SELECT * FROM oceanbase.DBA_OB_ZONE_STORAGE;
   ```

3. Update the object storage access credentials:

   ```sql
   ALTER SYSTEM {ALTER|CHANGE|MODIFY} SHARED_STORAGE_DEST
       PATH [=] 'path'
       SET
       ACCESS_INFO [=] 'access_info';
   ```

   The parameters are described as follows:

   * `PATH`: the path of the object storage. For S3-compatible object storage, the format is `s3://<bucket>/<prefix>?host=<endpoint>`. For Azure Blob, the format is `azblob://<container>/<prefix>?host=<endpoint>`. It must be consistent with the object storage path configured for the current cluster.
   * `ACCESS_INFO`: the new access credentials, in the format of `access_id=<new_access_id>&access_key=<new_access_key>`.

   Here is an example:

   ```shell
   obclient [(none)]> ALTER SYSTEM CHANGE SHARED_STORAGE_DEST
       PATH='s3://xxx?host=cn-hangzhou-alipay-b.oss-cdn.aliyun-inc.com'
       SET ACCESS_INFO='access_id=xxx&access_key=xxx';
   ```

4. After the update is successful, query the `oceanbase.DBA_OB_ZONE_STORAGE` view again to confirm the update result. A `STATE` field value of `CHANGING` indicates the rotation is in progress, and a value of `CHANGED` indicates the rotation is complete.

## Update log service access credentials

The log service access credentials are held by the compute node OBServer through the LibPalf client library and point to the object storage bucket used by the log service. The OBServer uses these credentials to perform service discovery (read AccessPoint) and communicate with the log service.

These credentials are configured and managed through the cluster parameter `logservice_access_point`. You can update the credential information by modifying this parameter.

<main id="notice" type='notice'>
<h4>Notice</h4>
<ul>
<li>The <code>logservice_access_point</code> parameter only allows modification of the <code>access_id</code> and <code>access_key</code> fields. Other fields (such as <code>host</code>, <code>s3_region</code>, etc.) cannot be modified; otherwise, the statement execution will report an error.</li>
<li>The <code>logservice_access_point</code> parameter cannot be set using startup parameters (<code>-o</code>). It can only be modified using the <code>ALTER SYSTEM SET</code> statement, or automatically set by the system during cluster initialization (bootstrap).</li>
</ul>
</main>

### Procedure

1. Log in to the `sys` tenant of the cluster as the `root` user.

   Note that you must specify the corresponding options in the following sample code based on your actual database configurations.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

2. Execute the following statement to view the current value of the `logservice_access_point` parameter.

   ```shell
   obclient [(none)]> SHOW PARAMETERS LIKE 'logservice_access_point';
   ```

   <main id="notice" type='notice'>
   <h4>Note</h4>
   <p>The value of this parameter is stored in encrypted form. Therefore, the <code>SHOW PARAMETERS</code> statement displays the encrypted value.</p>
   </main>

3. Execute the following statement to update the access credentials in the `logservice_access_point` parameter (only modify the `access_id` and `access_key` fields, and keep other fields unchanged).

   The statement is as follows:

   ```sql
   ALTER SYSTEM SET logservice_access_point = 's3://<bucket>/<prefix>?host=<endpoint>&logservice_cluster_id=<cluster_id>&s3_region=<region>&max_iops=<iops>&max_bandwidth=<bandwidth>&access_id=<new_access_id>&access_key=<new_access_key>';
   ```

   Here is an example:

   ```shell
   obclient [(none)]> ALTER SYSTEM SET logservice_access_point = 's3://test/logservice?host=http://10.0.0.1:9000&logservice_cluster_id=20260617&s3_region=cn-north-1&max_iops=10000&max_bandwidth=1GB&access_id=<NEW_AK>&access_key=<NEW_SK>';
   ```

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>When modifying this parameter, the system uses the new AK/SK to access the object storage to verify its validity. If the new credentials do not exist or lack permissions, the statement execution will be denied.</p>
   </main>

4. After the update is successful, confirm the result.

   * Re-execute the `SHOW PARAMETERS LIKE 'logservice_access_point';` statement to confirm that the configuration has been updated.

   * Confirm in the observer process log that the log storage credentials have been refreshed.

     ```shell
     grep "rotate_object_store_ak" observer.log | tail -5
     ```

5. (Optional) Clean up old access credentials.

   After the new credentials take full effect, you can delete the old credentials from the object storage service. Before deleting, confirm the following:

   * All OBServer nodes have completed credential updates and the cluster is running normally.
   * You have continuously observed for at least one config reload cycle (about 10 seconds), and success logs for the update appear in the logs of all nodes.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>If you delete the old credentials before the update is complete, OBServer nodes still using the old credentials will be unable to access the object store, which may cause node exceptions or even prevent the cluster from starting (because the <code>observer.config.bin</code> file still contains the old credentials, causing load failure upon restart).</p>
   </main>

### Common errors and troubleshooting

Errors that may occur when you update the `logservice_access_point` parameter and their handling methods are as follows:

| Error message | Cause | Solution |
| --- | --- | --- |
| `logservice_access_point: libpalf env not initialized` | The libpalf environment is not initialized (the observer is starting or the cluster runs in non-shared storage mode). | Retry after the observer is started. |
| `only access_id and access_key can be changed` | A field other than AK or SK is modified (for example, `host`, `path`, or `region`). | Check the new value and make sure that only `access_id` and `access_key` are modified. |
| `new access_id/access_key validation failed` | The new AK/SK cannot access the object storage. | Make sure that the new credentials are created on the object storage service and have read permissions. |
| `logservice_access_point cannot be setted by -o` | An attempt is made to set the parameter by using the startup parameter `-o`. | You can set the parameter only by using the `ALTER SYSTEM SET` statement or during bootstrap. |
