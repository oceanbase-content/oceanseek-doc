# Enable security auditing

A series of filters are used to audit specific events.

## Auditing scope

Filters can be applied based on dimensions such as account, event type, and event attributes. For each filter, you can choose whether to audit the filtered events.

## Limitations and considerations

* An expression must be placed directly and uniquely in an output column (select item) of a `SELECT` statement, and cannot have a parent expression.
* Expressions cannot be used in subqueries.
* After defining a filter, you must assign it to a user for it to take effect.
* A filter can be assigned to multiple users, but each user can have only one filter.
* When a connection is established, the current session determines which auditing filter to use, and this filter remains unchanged throughout the session lifecycle.

## Create a filter

You can create a filter to enable the auditing mode. The filter supports selective filtering of audit event types. Currently, you can choose to record all events, record no events, or record only logins and logouts.

### Syntax

You can execute the [AUDIT_LOG_FILTER_SET_FILTER](../../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/400.functions-of-mysql-mode/970.audit-functions-of-mysql-mode/400.audit-log-filter-set-filter-of-mysql-mode.md) function to create a filter. The syntax is as follows:

```sql
AUDIT_LOG_FILTER_SET_FILTER('filter_name', 'definition_of_filters');
```

**The parameters are described as follows:**

| Parameter | Description |
| ------ | ----- |
| filter_name | The name of the filter. <main id="notice" type='explain'><h4>Note</h4><p><code>AUDIT_LOG_FILTER_SET_FILTER</code> has <code>CREATE OR REPLACE</code> semantics. Executing a DDL statement on an existing object will overwrite it.</p></main> |
| definition_of_filters | The specific configurations of the auditing filter, which is in the JSON string format. The filter design principle of the current version is compatible with that of MySQL, but only audit event types can be filtered. |

Currently, the following filter configurations are supported:

* Record all events.

    ```sql
    {
    "filter": {
        "log": true
    }
    }
    ```

    or

    ```sql
    {
    "filter": {
        "log": true,
        "class": [
        { "name": "connection" },
        { "name": "general" },
        { "name": "table_access" }
        ]
    }
    }
    ```

* Record no events.

    ```sql
    {
    "filter": {
        "log": false
    }
    }
    ```

* Record only logins and logouts.

    ```sql
     {
    "filter": {
        "log": true,
        "class": [
        { "name": "connection" }
        ]
    }
    }
    ```

**Audit events are classified as follows:**

| Event type | Description |
| -------------- | ------ |
| connection | Login and logout. |
| table_access | DML statements. |
| general | CMD statements that fail to be parsed. |

### Example

Create a filter named `log_all` to record all events.

```shell
obclient [test]>SELECT AUDIT_LOG_FILTER_SET_FILTER('log_all', '{ "filter": { "log": true } }');
```

* When a DDL statement is executed successfully, the expression returns `OK`.

    ```shell
    +-------------------------------------------------------------------------+
    | AUDIT_LOG_FILTER_SET_FILTER('log_all', '{ "filter": { "log": true } }') |
    +-------------------------------------------------------------------------+
    | OK                                                                      |
    +-------------------------------------------------------------------------+
    1 row in set
    ```

* When the DDL statement fails, the `SELECT` statement still succeeds, and the output result of the expression is an error message.

    ```shell
    obclient [test]>SELECT AUDIT_LOG_FILTER_SET_FILTER('log_err', '1');
    ```

    The return result is as follows:

    ```shell
    +---------------------------------------------+
    | AUDIT_LOG_FILTER_SET_FILTER('log_err', '1') |
    +---------------------------------------------+
    | ERROR: JSON parsing error.                  |
    +---------------------------------------------+
    1 row in set
    ```

View the definition of an audit filter through the [mysql.audit_log_filter](../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/3170.mysql-audit_log_filter-of-mysql-mode.md) view.

```shell
obclient [test]> select * from mysql.audit_log_filter;
```

The return result is as follows:

```shell
+---------+-------------------------------+
| NAME    | FILTER                        |
+---------+-------------------------------+
| log_all | { "filter": { "log": true } } |
+---------+-------------------------------+
1 row in set (0.003 sec)
```

**The fields are described as follows:**

| **Field** | **Description** |
| -------------- | ------------ |
| NAME | The name of the filter. |
| FILTER | The definition of the filter. |

## Configure filters

After you configure filters for the corresponding users, the background thread can print audit logs.

### Syntax

You can call the [AUDIT_LOG_FILTER_SET_USER](../../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/400.functions-of-mysql-mode/970.audit-functions-of-mysql-mode/500.audit-log-filter-set-user-of-mysql-mode.md) function to set a filter on a user.

```sql
AUDIT_LOG_FILTER_SET_USER('user_name', 'filter_name');
```

**The parameters are described as follows:**

| Parameter | Description |
| ------ | ----- |
| user_name | Specifies the user name. <main id="notice" type='explain'><h4>Note</h4><p>The <code>user@host</code> specified in <code>AUDIT_LOG_FILTER_SET_USER</code> does not need to be an existing user. Wildcards or non-existent users are allowed. When a non-existent user is specified, it can take effect during login auditing. The <code>user_name</code> has the following limitations:<ul><li><code>user</code> only supports wildcarding the entire field, which is <code>%</code>.</li><li>Specifying the <code>host</code> field or partial wildcarding like <code>test_%</code> is not supported. If <code>host</code> or <code>test_%</code> is specified, the filter cannot be created.</li></ul></p></main> |
| filter_name | Specifies the filter name. <main id="notice" type='explain'><h4>Note</h4><p><code>AUDIT_LOG_FILTER_SET_USER</code> has <code>CREATE OR REPLACE</code> semantics. Executing this statement on an existing object will overwrite it. If the specified <code>filter_name</code> does not exist, the DDL will not take effect but no error will be returned either.</p></main> |

### Example

Assign the `log_all` filter to the `user001` user.

```shell
obclient [test]> SELECT AUDIT_LOG_FILTER_SET_USER('user001', 'log_all');
```

* When the DDL statement is executed successfully, the expression returns `OK`.

    ```shell
    +-------------------------------------------------+
    | AUDIT_LOG_FILTER_SET_USER('user001', 'log_all') |
    +-------------------------------------------------+
    | OK                                              |
    +-------------------------------------------------+
    1 row in set
    ```

* When the DDL statement fails, the `SELECT` statement still succeeds, and the output result of the expression is an error message.

    ```shell
    obclient [test]>SELECT AUDIT_LOG_FILTER_SET_USER('log_err', '1');
    ```

    The return result is as follows:

    ```shell
    +--------------------------------------------+
    | AUDIT_LOG_FILTER_SET_USER('log_err', '1')  |
    +--------------------------------------------+
    | ERROR: Invalid character in the user name. |
    +--------------------------------------------+
    1 row in set (0.001 sec)
    ```

View the mapping between auditing filters and users through the [mysql.audit_log_user](../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/3175.mysql.audit_log_user-of-mysql-mode.md) view.

```shell
obclient [test]> select * from mysql.audit_log_user;
```

The return result is as follows:

```shell
+---------+------+------------+
| USER    | HOST | FILTERNAME |
+---------+------+------------+
| user001 | %    | log_all    |
+---------+------+------------+
1 row in set (0.003 sec)
```

**The fields are described as follows:**

| **Field** | **Description** |
| -------------- | ------------ |
| USER | The username. |
| HOST | The hostname. |
| FILTERNAME | The filter name. |

## Enable auditing

Enable the auditing feature for a user tenant by configuring the [audit_log_enable](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/235.audit_log_enable.md) configuration item.

```shell
obclient> ALTER SYSTEM SET audit_log_enable=TRUE;
```
