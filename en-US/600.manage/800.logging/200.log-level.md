# Log levels

OceanSeek logs are divided into seven levels, as shown in the following table. The levels are listed in descending order.

| Log level | Meaning |
| ------------ | -------------------------------------------------------------------------------- |
| ERROR | Critical error. Used to record system failure information that requires troubleshooting; otherwise, the system will be unavailable. |
| WARN | Warning. The system can continue to provide services, but its behavior may not meet expectations, or serious errors may occur that require troubleshooting. |
| INFO | Information. Used to record the current system status. This information is normal. |
| EDIAG | Error Diagnosis. Diagnostic information to help troubleshoot, typically related to bugs in the OceanSeek program. |
| WDIAG | Warning Diagnosis. Diagnostic information to help troubleshoot. For expected errors, OceanSeek can provide fault tolerance. |
| TRACE | SQL statement-level debugging information. The number of logs is related to SQL complexity and not to the volume of data accessed. |
| DEBUG | Debugging information. Used to gain a more detailed understanding of the system's runtime status during debugging, including the current function name, parameters, variables, and return values of function calls. |

<main id="notice" type='notice'>
    <h4>Notice</h4>
    <p>The methods for viewing and setting log levels described in this topic apply only to regular log files (<code>election.log</code>, <code>observer.log</code>, <code>rootservice.log</code>). For WARNING log files (files with the `.wf` suffix), logs at or above the WARN level are always printed.</p>
</main>

You can execute the `SHOW PARAMETERS` statement to view the current log output level. The default log output level is WDIAG.

```shell
obclient> SHOW PARAMETERS LIKE '%syslog_level%';
```

OceanSeek allows you to set log levels to obtain more precise logs. You can set log levels at three levels: system level, session level, and statement level. When logs are printed, the priority in descending order is statement level, session level, and system level. OceanSeek also allows you to set log levels by module.

* System level: Applies to all OBServer nodes in the cluster. It can be configured only in the sys tenant.
* Session level: Applies to the OBServer node where the current tenant resides in the cluster.
  * Variables set at the session level are valid only for the current session and not for other sessions.
  * Variables set at the global level are not effective for the current session. They take effect only after you log out and log in again to establish a new session.
* Statement level: Applies to the OBServer node where the current statement is executed. It takes effect only during the execution of the SQL statement.

The following describes how to set log levels at the system, session, and statement levels.

* Set the log level of a module at the system level.

    You can use either of the following methods:

  * Use the system configuration item `syslog_level` to set the system-level log level. For example, you can set the log level of the SQL module to `debug` and that of the COMMON module to `error`.

      ```shell
        obclient > ALTER SYSTEM SET syslog_level='sql.*:debug, common.*:error';
      ```

  * Use the operating system command `bash kill -41/42 $pid` to set the system-level log level.

     `kill -41` lowers the program log level. For example, if the current program log level is INFO, it is lowered to TRACE after you execute `kill -41`. `kill -42` raises the program log level. For example, if the current program log level is INFO, it is raised to WARN after you execute `kill -42`.

      We recommend that you use the system configuration item `syslog_level` to set the system-level log level. This is because when OceanSeek refreshes its configuration, it imports the `syslog_level` setting from the `config` file (located in the `etc/observer.config.bin` directory under the OceanSeek installation directory), which makes the kill method ineffective.

      <main id="notice" type='notice'>
       <h4>Notice</h4>
       <p>We recommend that you use <code>kill -41/kill -42</code> to adjust the log level only when you cannot log in to the OceanSeek cluster via the SQL client.</p>
      </main>

* Set the log level of a module at the session level.

    Use the system variable `ob_log_level` to set the log level of a module at the session level. For example, you can set the log level of the SQL module to `debug` and that of the COMMON module to `info`.

    ```shell
    obclient > SET @@ob_log_level='sql.*:debug, common.*:info';
    ```

* Set the log level of a module at the statement level.

    You can use hints to set the log level of a module at the statement level. For example, you can set the log level of the SQL module to `debug` and that of the COMMON module to `info`. For more information about hint statements, see [Optimizer hint](../../700.reference/1000.performance-tuning-guide/500.sql-optimization/400.sql-optimization/700.manage-execution-plans/100.optimizer-hint.md).

    ```shell
    obclient > SELECT /*+log_level('sql.*:debug, common.*:info')*/ * FROM t;
    ```

    <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>If you execute an SQL statement with hints using the MySQL C client, you must log in by using the <code>-c</code> option. Otherwise, the MySQL client removes the hints from your SQL statement as comments, preventing the system from receiving the hints.</p>
    </main>
