# Scale tenants by adjusting the unit number

Tenant scaling aims to improve or reduce the service capabilities of the tenant, including the computing and storage capacities. To meet this purpose, you can improve the service capabilities of a single node or add service nodes. This topic describes how to modify the unit number to increase or decrease service nodes to improve or reduce the overall service capabilities of a tenant, thereby implementing tenant scaling.

You can increase or decrease the unit number.

## Background information

In the current version, OceanSeek supports homogeneous and heterogeneous zone modes for tenants:

* In the homogeneous zone mode, all zones of a tenant must have the same number of units. To facilitate unit management, the system introduces the unit group mechanism. Units in different zones can be classified into the same unit group. The units in a single unit group share the same unit group ID. Increasing or decreasing the number of units is to create or delete units based on unit groups.

* In the heterogeneous zone mode, the `UNIT_NUM` values of different zones can be the same or different. However, a tenant can have at most two different `UNIT_NUM` values. Log streams are no longer bound to unit groups. Replicas in different zones are no longer required to be symmetric. For a tenant in the heterogeneous zone mode, you can increase or decrease the number of units of a resource pool in addition to increasing or decreasing the number of units of the tenant. This way, you can scale in or out a resource pool.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>By default, existing tenants or tenants upgraded from earlier versions are in the homogeneous zone mode. To enable the heterogeneous zone mode, you must set the tenant-level parameter <code>zone_deploy_mode</code> to <code>hetero</code>. After you modify this parameter, you cannot change it back to <code>homo</code>.</p>
</main>

## Prerequisites

Before you perform a scale-in or scale-out operation on a tenant, you must perform the following steps:

* Enable load balancing for the tenant.

  The load balancing strategy for a tenant is jointly controlled by the tenant-level parameters `enable_rebalance` and `enable_transfer`.
  
  * You can specify the `enable_rebalance` parameter in the `sys` tenant to control whether to enable load balancing among tenants, and specify this parameter in a user tenant to control whether to enable load balancing for the current tenant. When you scale in or out a tenant, you must enable load balancing for the tenant. The default value is `true`. The setting takes effect immediately without the need to restart the OBServer node.

  * You can specify the `enable_transfer` parameter to control whether to enable the transfer feature for a tenant. The default value is `true`. The setting takes effect immediately without the need to restart the OBServer node. Specifically:
    
    * If the value of `enable_rebalance` is `false`, the system does not perform automatic load balancing regardless of whether the value of `enable_transfer` is `true` or `false`.

    * If the value of `enable_rebalance` is `true` and the value of `enable_transfer` is `true`, the system automatically adjusts partition distribution to achieve load balancing during a tenant scaling operation.

    * If the value of `enable_rebalance` is `true` and the value of `enable_transfer` is `false`, the system cannot initiate transfer operations during tenant scaling, but can implement limited load balancing through log stream migration.

  You can enable load balancing for a tenant in the following ways:

  * Enable load balancing for a specified tenant from the `sys` tenant

    * Enable load balancing and the transfer feature for a specified tenant from the `sys` tenant

       ```sql
       ALTER SYSTEM SET enable_rebalance = true TENANT = 'tenant_name';
       ```

       ```sql
       ALTER SYSTEM SET enable_transfer = true TENANT = 'tenant_name';
       ```

       These statements only set the values of the `enable_rebalance` and `enable_transfer` parameters to `true` for the specified user tenant.

    * Enable intra-tenant load balancing and the transfer feature for all user tenants from the `sys` tenant

       ```sql
       ALTER SYSTEM SET enable_rebalance = true TENANT = all_user;
       ```

       ```sql
       ALTER SYSTEM SET enable_transfer = true TENANT = all_user;
       ```

       or

       ```sql
       ALTER SYSTEM SET enable_rebalance = true TENANT = all;
       ```

       ```sql
       ALTER SYSTEM SET enable_transfer = true TENANT = all;
       ```

       These statements only set the values of the `enable_rebalance` and `enable_transfer` parameters to `true` for all user tenants.

       <main id="notice" type='explain'>
       <h4>Note</h4>
       <p><code>TENANT = all_user</code> and <code>TENANT = all</code> have the same semantics. If you want an operation to take effect on all user tenants, we recommend that you use <code>TENANT = all_user</code>. <code>TENANT = all</code> will be deprecated in the future.</p>
       </main>

  * Enable load balancing for a user tenant from the current tenant

    You can execute the following statements to enable load balancing and the transfer feature for the current tenant:

    ```sql
    ALTER SYSTEM SET enable_rebalance = true;
    ```

    ```sql
    ALTER SYSTEM SET enable_transfer = true;
    ```

  For more information about the `enable_rebalance` and `enable_transfer` parameters, see [enable_rebalance](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2800.enable_rebalance.md) and [enable_transfer](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3000.enable_transfer.md).

* If the tenant is deleted, drop the resource pool of the tenant to release resources. Resources in an idle resource pool are also considered occupied resources.

  For more information about how to drop a resource pool, see [Drop a resource pool](../1500.resource-pool-management/600.delete-resource-pool.md).

* Before you scale in a tenant, we recommend that you perform a minor compaction to release the memory in use by the tenant.

  For more information about how to manually initiate a minor compaction, see [Manually trigger a minor compaction](../../../../700.reference/200.system-management/500.manage-data-storage/100.dump-management/300.trigger-dump-manually.md).

* Plan resources for the tenant to achieve the expected result.

  For more information about resource planning for tenant scaling, see [Resource planning for tenant scaling](150.resources-planning-for-tenant-scale-in-and-out.md).

	
## Considerations

When you scale in or out a tenant by adjusting the unit number, note the following considerations:

* Do not modify the locality of the tenant during scaling in or out.

* Do not expand the `ZONE_LIST` of the resource pool of the tenant during scaling in or out.

* Do not add a new resource pool to the tenant during scaling in or out.

* Do not merge resource pools during scaling in or out.

* Do not migrate a unit in the `DELETING` state during scaling in or out.

## Increase the unit number

### Increase the unit number for all resource pools of a tenant

For a tenant in the homogeneous zone mode or the heterogeneous zone mode, you can use the `ALTER RESOURCE TENANT` statement to increase the unit number for all resource pools of the tenant. The following example describes how to increase the unit number for all resource pools of the `mysql001` tenant.

1. Log in to the `sys` tenant of the cluster as the `root` user.

    ```shell
    obclient -h172.30.xxx.xxx -P2883 -uroot@sys#obdemo -pxxxx -A
    ```

2. Access the database named `oceanbase`.

    ```shell
    obclient(root@sys)[(none)]> use oceanbase;
    ```

3. View the information about the `mysql001` tenant to obtain its `TENANT_ID`.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID, TENANT_NAME, TENANT_TYPE, PRIMARY_ZONE, LOCALITY, TENANT_ROLE, UNIT_NUM, ZONE_UNIT_NUM_LIST FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_NAME = 'mysql001';
   ```

   The query result is as follows:

   ```shell
   +-----------+-------------+-------------+--------------------+---------------------------------------------+-------------+----------+-------------------------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE       | LOCALITY                                    | TENANT_ROLE | UNIT_NUM | ZONE_UNIT_NUM_LIST      |
   +-----------+-------------+-------------+--------------------+---------------------------------------------+-------------+----------+-------------------------+
   |      1006 | mysql001    | USER        | zone1;zone2;zone3  | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 | PRIMARY     |        1 | zone1:1,zone2:1,zone3:1 |
   +-----------+-------------+-------------+--------------------+---------------------------------------------+-------------+----------+-------------------------+
   1 row in set
   ```

   In the query result, the `TENANT_ID` of the tenant is 1006, and the value of `UNIT_NUM` is 1:1:1, indicating that the tenant has one unit in each zone.

4. View the units owned by the `mysql001` tenant.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT UNIT_ID, TENANT_ID, STATUS, RESOURCE_POOL_ID, UNIT_GROUP_ID, ZONE, UNIT_CONFIG_ID FROM oceanbase.DBA_OB_UNITS WHERE TENANT_ID = 1006;
   ```

   The query result is as follows:

   ```shell
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   | UNIT_ID | TENANT_ID | STATUS | RESOURCE_POOL_ID | UNIT_GROUP_ID | ZONE  | UNIT_CONFIG_ID |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   |    1013 |      1006 | ACTIVE |             1002 |          1023 | zone2 |           1001 |
   |    1014 |      1006 | ACTIVE |             1001 |          1023 | zone1 |           1001 |
   |    1015 |      1006 | ACTIVE |             1003 |          1023 | zone3 |           1001 |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   3 rows in set
   ```

   According to the query result, the `mysql001` tenant has one unit in each zone, and these three units correspond to the same `UNIT_GROUP_ID`.

5. Change the value of `UNIT_NUM` to 2 for the `mysql001` tenant.

   ```shell
   obclient(root@sys)[oceanbase]> ALTER RESOURCE TENANT mysql001 UNIT_NUM = 2;
   ```

6. After the command is executed, view the status of the current units.

   ```shell
   obclient> SELECT UNIT_ID, TENANT_ID, STATUS, RESOURCE_POOL_ID, UNIT_GROUP_ID, ZONE, UNIT_CONFIG_ID FROM oceanbase.DBA_OB_UNITS WHERE TENANT_ID = 1006;
   ```

   The query result is as follows:

   ```shell
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   | UNIT_ID | TENANT_ID | STATUS | RESOURCE_POOL_ID | UNIT_GROUP_ID | ZONE  | UNIT_CONFIG_ID |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   |    1013 |      1006 | ACTIVE |             1002 |          1024 | zone2 |           1001 |
   |    1014 |      1006 | ACTIVE |             1001 |          1024 | zone1 |           1001 |
   |    1015 |      1006 | ACTIVE |             1003 |          1024 | zone3 |           1001 |
   |    1025 |      1006 | ADDING |             1001 |          1025 | zone1 |           1001 |
   |    1026 |      1006 | ADDING |             1002 |          1025 | zone2 |           1001 |
   |    1027 |      1006 | ADDING |             1003 |          1025 | zone3 |           1001 |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   6 rows in set
   ```

   You can see that the new units are in the `ADDING` state. After internal balancing is completed, the unit state changes from `ADDING` to `ACTIVE`.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <ul><li>In OceanSeek, <code>UNIT_NUM</code> scaling is an asynchronous process, and the pending units are in the <code>ADDING</code> state.</li>
   <li>Rollback operations are supported during the scaling process (when the pending units are still in the <code>ADDING</code> state). <p>For example, in this scenario, you can execute the <code>ALTER RESOURCE TENANT mysql001 UNIT_NUM = 1;</code> statement to revert <code>UNIT_NUM</code> to its original value. During rollback, the original <code>ADDING</code> units directly transition to the <code>DELETING</code> state. Note that when performing a rollback, you cannot specify a UNIT_GROUP to delete; the system automatically selects <code>ADDING</code> units for deletion.</p></li>
   <li>Before the scaling process ends, only rollback operations are allowed; modifying <code>UNIT_NUM</code> to other values is prohibited.</li></ul>
   </main>

   ```shell

   ```

   The query result is as follows:

   ```shell
   +--------+--------------------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+-----------------------------------------------------------+-------------------+--------------+-------------+
   | JOB_ID | JOB_TYPE                       | JOB_STATUS | RESULT_CODE | PROGRESS | START_TIME                 | MODIFY_TIME                | TENANT_ID | SQL_TEXT                                                  | EXTRA_INFO        | RS_SVR_IP    | RS_SVR_PORT |

   +--------+--------------------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+-----------------------------------------------------------+-------------------+--------------+-------------+
   1 row in set
   ```

   In the query result, find the corresponding job record based on the following fields:

   * `START_TIME`: the time when the job was initiated.
   * `SQL_TEXT`: the SQL statement corresponding to the job.
   * `EXTRA_INFO`: the number of units before and after the change.

   If the value of `JOB_STATUS` in the corresponding change record is `SUCCESS`, the job for increasing the unit number is successfully executed.

   For more information about the fields in the `DBA_OB_TENANT_JOBS` view, see [DBA_OB_TENANT_JOBS](../../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/23000.o-dba_ob_tenant_jobs-of-sys-tenant.md).

8. View the units of the `mysql001` tenant after the modification.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT UNIT_ID, TENANT_ID, STATUS, RESOURCE_POOL_ID, UNIT_GROUP_ID, ZONE, UNIT_CONFIG_ID FROM oceanbase.DBA_OB_UNITS WHERE TENANT_ID = 1006;
   ```

   The query result is as follows:

   ```shell
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   | UNIT_ID | TENANT_ID | STATUS | RESOURCE_POOL_ID | UNIT_GROUP_ID | ZONE  | UNIT_CONFIG_ID |
   +---------+-----------+--------+------------------+---------------+-------+----------------+

   |    1015 |      1006 | ACTIVE |             1003 |          1024 | zone3 |           1001 |
   |    1025 |      1006 | ACTIVE |             1001 |          1025 | zone1 |           1001 |
   |    1026 |      1006 | ACTIVE |             1002 |          1025 | zone2 |           1001 |
   |    1027 |      1006 | ACTIVE |             1003 |          1025 | zone3 |           1001 |

   6 rows in set
   ```

The query result shows that the number of units in each zone is changed from 1 to 2 for the `mysql001` tenant. The tenant has one unit in each zone before the change, and two units in each zone after the change, thereby achieving tenant scaling out.

## Reduce the unit number

### Considerations

Before you reduce the unit number of a tenant, make sure whether GTS exclusive mode is enabled. The tenant-level parameter [enable_gts_standalone](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2550.enable_gts_standalone.md) specifies whether to enable GTS exclusive mode. The default value is `False`, which indicates that the feature is disabled.

If GTS exclusive mode is enabled, note the following considerations:

* After GTS exclusive mode is enabled, the `UNIT_NUM` of each zone of the tenant must be greater than or equal to 2. If you reduce the `UNIT_NUM` of any zone to a value less than 2, an error is returned.

* When you reduce the unit number by deleting a specified unit list or unit group, you cannot delete a unit or unit group exclusive to GTS. Otherwise, an error is returned.

5. Change the value of `UNIT_NUM` to 2 for the `mysql001` tenant.

   * Randomly delete a unit to reduce the unit number

     For a tenant in the homogeneous zone mode or the heterogeneous zone mode, you can execute the following statement to reduce the unit number.

     ```shell
     obclient(root@sys)[oceanbase]> ALTER RESOURCE TENANT mysql001 UNIT_NUM = 2;
     ```

     After this statement is executed:

     * For a tenant in the homogeneous zone mode, such as the `mysql001` tenant in this example, where the `UNIT_NUM` of all resource pools is changed from 3 to 2, the system randomly specifies a unit group with the same `UNIT_GROUP_ID` for deletion.

     * For a tenant in the heterogeneous zone mode, the system randomly selects a unit group for deletion.

   * Delete a specified unit group to reduce the unit number

     For a tenant in the homogeneous zone mode, you can also execute the following statement to reduce the unit number. This statement is not supported for a tenant in the heterogeneous zone mode.

     ```shell
     obclient(root@sys)[oceanbase]> ALTER RESOURCE TENANT mysql001 UNIT_NUM = 2 DELETE UNIT_GROUP =(1018);
     ```

     After this statement is executed, for a scenario where each zone has three units, the system redistributes the data in the specified unit group to other unit groups, and then deletes the unit group.
