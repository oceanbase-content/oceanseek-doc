# Prepare for log archiving

This topic describes the preparations before you archive logs.

## Configure the concurrency of log archiving (optional)

Before you enable the archiving mode, you can configure the concurrency of log archiving to improve the log archiving speed of the tenant.

1. Log in to the database as the `sys` tenant user or the tenant administrator of the user tenant.

2. Run the appropriate statement to set the `log_archive_concurrency` configuration item.

   The `log_archive_concurrency` configuration item of a tenant specifies the total number of worker threads for log archiving. This configuration item takes effect immediately and does not require a restart of the OBServer node. The value range is [0, 100]. The default value is `0`, which indicates that OceanSeek adapts the log archiving concurrency. We recommend that you use the default value.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>For small tenants (with 4 CPU cores or fewer), we recommend that you use the default value and do not modify the value of this configuration item.</p>
   </main>

   The following methods are supported for setting the configuration item:

   * Adjust the log archiving concurrency for a specified tenant as the `sys` tenant user.

     ```sql
     ALTER SYSTEM SET log_archive_concurrency = 10 TENANT = mysql_tenant;
     ```

   * Adjust the log archiving concurrency for all tenants as the `sys` tenant user.

     ```sql
     ALTER SYSTEM SET log_archive_concurrency = 10 TENANT = all_user;
     ```

     or

     ```sql
     ALTER SYSTEM SET log_archive_concurrency = 10 TENANT = all;
     ```

     <main id="notice" type='explain'>
     <h4>Note</h4>
     <p><code>TENANT = all_user</code> has the same meaning as <code>TENANT = all</code>. When you need the setting to take effect for all user tenants, we recommend that you use <code>TENANT = all_user</code>. <code>TENANT = all</code> will be deprecated in the future.</p>
     </main>

   * Adjust the log archiving concurrency for the current tenant as a user tenant.

     ```sql
     ALTER SYSTEM SET log_archive_concurrency = 10;
     ```

   For more information about the `log_archive_concurrency` configuration item, see [log_archive_concurrency](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/4300.log_archive_concurrency.md).

## Configure the archiving destination

Before you start a log archiving task, you must run the `ALTER SYSTEM` command to set the `LOG_ARCHIVE_DEST` parameter. The system tenant does not contain user data and is a tenant used for cluster management. Backup and restore are not supported for the `sys` tenant. Therefore, you do not need to configure an archive destination for this tenant.

Configuring an archiving destination mainly involves setting the `LOCATION`, `BINDING`, and `PIECE_SWITCH_INTERVAL` attributes.

### Considerations

When you configure the archiving destination, make sure that the archiving path for each tenant is an independent empty directory, and that the archiving paths for different tenants are different.

### Procedure

1. Log in to the database as the tenant administrator of the `sys` tenant or a user tenant.

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>The administrator user of a user tenant is the <code>root</code> user.</p>
   </main>

2. Configure the archive destination.

   * Configure an archive destination for a specified tenant as the system tenant.

     ```sql
     ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=archive_path [BINDING=archive_mode] [PIECE_SWITCH_INTERVAL=piece_switch_interval]' TENANT = tenant_name;
     ```

   * Configure the archive destination for the current tenant as a user tenant.
  
     ```sql
     ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=archive_path [BINDING=archive_mode] [PIECE_SWITCH_INTERVAL=piece_switch_interval]';
     ```

   The following table describes the attributes.

   * Configure `LOCATION` (required)

       The `LOCATION` attribute specifies the archiving path. Currently, OceanSeek supports the following archive media: Azure Blob, AWS S3, and S3-compatible object storage such as Alibaba Cloud OSS, Huawei OBS, Google GCS, and Tencent Cloud COS. Some archive media may need to meet certain basic requirements before they can be used. For more information about the requirements for each archive medium, see the **Backup media requirements** section in [Overview of physical backup and restore](../100.overview-of-physical-backup-and-recovery.md).

      :::tab
      tab AWS S3

      You can specify the `delete_mode` parameter to configure the mode for deleting archive files when you use AWS S3 as the archive medium. You can also specify the `checksum_type` parameter to indicate the checksum algorithm for verifying the integrity of archive files. The supported values are `md5` and `crc32`. If you do not explicitly specify the `checksum_type` parameter, the default value is `md5`.

      For more information about the `delete_mode` and `checksum_type` parameters, see [SET LOG_ARCHIVE_DEST](../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/200.alter-system/3800.set-log-archive-dest.md).

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>When an object storage service is used as the archive medium, separate the parameters for the object storage path with the <code>&</code> character. Make sure that the parameter values contain only uppercase and lowercase letters, numbers, <code>/-_$+=</code>, and wildcard characters. If you enter other characters, the setting may fail.</p>
      </main>

      Here are some examples of using S3 as the archive medium:

      * When using S3 as the archive medium, set the archiving path for the tenant `mysql_tenant` in the system tenant, configure the cleanup mode as `delete`, and specify the checksum algorithm as `crc32`.

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=s3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=******&s3_region=******&delete_mode=delete&checksum_type=crc32' TENANT = mysql_tenant;
        ```

      * When using S3 as the archive medium, set the archiving path for the current tenant in a user tenant, configure the cleanup mode as `delete`, and specify the checksum algorithm as `crc32`.

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=s3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=******&s3_region=******&delete_mode=delete&checksum_type=crc32';
        ```

      In the preceding examples, `s3://` indicates that AWS S3 is used as the archive medium. The bucket name is `oceanbase-test-bucket`, and the path in the bucket is `/backup/archive`. The parameters are separated from the path by using `?`, and the parameters are separated by using `&`. `host` specifies the domain name of the Amazon S3 service. `access_id` and `access_key` specify the access keys of the AWS service. `s3_region` is required when S3 is used as the archive medium and specifies the region where the S3 bucket is located. The cleanup mode is `delete`, and the CRC32 algorithm is used to verify the integrity of archive files.

      For more information about the AWS S3 path format, see [Appendix: S3 path format](../1600.appendix-explanation-of-aws-s3-backupdest.md).

      tab Object storage compatible with the S3 protocol

      Most object storage services are compatible with the S3 protocol. Object storage services that are compatible with the S3 protocol and meet the requirements of OceanSeek (the object storage must be compatible with the behaviors of the S3 APIs that implement OceanSeek system calls) can serve as the archive media for OceanSeek. You can access compatible object storage services such as OBS, GCS, and COS through the S3 protocol.

      For object storage services such as OBS, GCS, and COS accessed through the S3 protocol, you can also specify the `checksum_type` parameter to indicate the checksum algorithm for verifying the integrity of archive files. Only `md5` is supported. If you do not explicitly specify the `checksum_type` parameter, the default value is `md5`. For more information about the `checksum_type` parameter, see [SET LOG_ARCHIVE_DEST](../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/200.alter-system/3800.set-log-archive-dest.md).

      <li>Some S3-compatible object storage services may not support the default URL encoding method of the AWS S3 SDK. When you access them through the <code>s3://</code> protocol, if object storage-related error codes such as 9129 or 9026 occur, we recommend that you set the cluster-level configuration item <a href="../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/300.cluster-level-configuration-items/16620.ob_storage_s3_url_encode_type.md">ob_storage_s3_url_encode_type</a> to specify that AWS S3 uses the RFC 3986 standard for URL encoding when sending requests.    * Configure the `BINDING` attribute (optional)

        The `BINDING` attribute specifies the priority mode between archiving and business. The attribute supports the `Optional` and `Mandatory` modes. If you do not configure the attribute, the default value `Optional` takes effect.

        * The `Optional` mode indicates that business takes priority. In this mode, if the archiving speed falls behind the log generation speed, logs may be recycled before they are archived, causing a log stream interruption.

        * The `Mandatory` mode indicates that archiving takes priority. In this mode, if archiving falls behind the data write speed, data write may fail.

        Here is an example of setting the archiving path and the `BINDING` attribute for the `mysql_tenant` tenant in the sys tenant when you use S3 as the archive medium:

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=s3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=****** BINDING=Optional' TENANT = mysql_tenant;
        ```

        Here is an example of setting the archiving path and the `BINDING` attribute for the current tenant when you use S3 as the archive medium:

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=s3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=****** BINDING=Optional';
        ```

   * Configure the `PIECE_SWITCH_INTERVAL` attribute (optional)

        The `PIECE_SWITCH_INTERVAL` attribute specifies the interval for switching `piece`. The value range is `[1d, 7d]`. If you do not configure the attribute, the default value `1d` takes effect.

        Here is an example of setting the archiving path and the `PIECE_SWITCH_INTERVAL` attribute to switch a log `piece` every other day for the `mysql_tenant` tenant in the sys tenant when you use S3 as the archive medium:

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=s3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=******  BINDING=Optional PIECE_SWITCH_INTERVAL=1d' TENANT = mysql_tenant;
        ```

        Here is an example of setting the archiving path and the `PIECE_SWITCH_INTERVAL` attribute to switch a log `piece` every other day for the current tenant when you use S3 as the archive medium:

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=s3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=****** BINDING=Optional PIECE_SWITCH_INTERVAL=1d';
        ```

3. After the configuration is completed, you can query the parameter settings in views.

   The `sys` tenant can query the parameter settings in the `CDB_OB_ARCHIVE_DEST` view, and a user tenant can query the parameter settings in the `DBA_OB_ARCHIVE_DEST` view. For more information about how to query the parameter settings, see [View archive parameters](../300.log-archive/800.view-parameters-of-log-archive.md).

### Considerations and descriptions after the configuration is completed

1. After the `LOG_ARCHIVE_DEST` parameter is successfully configured, the system creates a `format` file in the directory where the specified backup destination is located. The `format` file is used to verify the validity of the backup destination and ensure the integrity of data in the destination. Therefore, note the following considerations when you configure the archiving destination:

    * If the `format` file does not exist, the specified directory must be empty. Otherwise, an error `-9080` is returned, indicating that the file does not exist.

    * If the `format` file already exists, its content must pass the verification for the specified parameter to take effect. Otherwise, an error `-9081` is returned, indicating that the file does not match. The content verification of the `format` file mainly checks whether the cluster, tenant, and backup destination type specified in the file are consistent with those in the current operation.

    * If the `format` file does not exist or its content fails the verification during backup task execution, the task will fail.

2. After the archiving destination is successfully configured, incremental configuration is not supported. For example, assume the archive path `/oceanbase-test-bucket/backup/archive` under S3 has the `BINDING` attribute set to `Mandatory` and the `PIECE_SWITCH_INTERVAL` attribute set to `1d`. If you need to update `PIECE_SWITCH_INTERVAL` to `2d` while retaining the `MANDATORY` configuration for `BINDING`, you still need to specify the values for other attributes in the command. Otherwise, unspecified attributes will use their default values.

    You need to execute the following statements again for the modification.

    * Modify a specified tenant in the sys tenant

      ```sql
      obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST = 'LOCATION=s3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=******  BINDING=Mandatory PIECE_SWITCH_INTERVAL=2d' TENANT = mysql_tenant;
      ```

    * Modify the current tenant in a user tenant

      ```sql
      obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST = 's3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=******  BINDING=Mandatory PIECE_SWITCH_INTERVAL=2d';
      ```

3. After the archiving destination is set successfully, if the user changes the key information of the object storage due to security or other reasons, you need to update the `access_id` and `access_key` information for the configured archiving path. For more information, see [Update object storage key information](../450.change-sk-and-ak-for-the-backup-path-or-logarchive-path.md).

## (Optional) Configure archive lag

OceanSeek uses the tenant-level configuration item `archive_lag_target` to control the latency of log archiving for the tenant. This configuration item supports units of ms, s, m, and h. The default value is 2 minutes, which specifies the maximum interval between two consecutive archive I/O operations and ensures that online logs can be archived in a timely manner, thereby reducing the risk of data loss.

OceanSeek archives logs by log stream. If a log stream has logs written to it and the time since its last archive exceeds the interval specified by the `archive_lag_target` configuration item, the system triggers an archive action for that log stream to archive all unarchived logs in the log stream.

For example, if the configuration item is set to `archive_lag_target='120s'` (2 minutes), each log stream attempts to trigger an archive action every 2 minutes (unless other conditions are met, such as the archive buffer being full), ensuring that the interval between two consecutive archive actions of the log stream is less than 2 minutes. If the `archive_lag_target` configuration item is set to `0`, real-time archiving is achieved.

For more information about the `archive_lag_target` configuration item, see [archive_lag_target](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/200.archive_lag_target.md).

### Prerequisites

Before you modify the value of the `archive_lag_target` configuration item, make sure that the archive destination has been configured. If the archive destination is not configured, the system will return an error message indicating that the archive destination has not been set when you try to modify the value of the `archive_lag_target` configuration item.

### Considerations

* For archive media such as S3 or other object storage services compatible with the S3 protocol, the value of the `archive_lag_target` configuration item cannot be less than `60s`. If you set the value to less than `60s`, the system will return an error.

* We recommend that you set the `archive_lag_target` configuration item to a reasonable value to avoid frequent I/O operations that may affect system performance, especially when object storage is used. A high value may fail to meet the timeliness requirement for data recovery. Therefore, you need to strike a balance between the RPO and the performance of the archive media based on your business needs.

### Procedure

1. Log in to the database as the tenant administrator of the `sys` tenant or a user tenant.

2. Based on your needs, execute the appropriate statement to configure the archive lag.

   Here are some examples:

   * Configure the archive lag for a specified tenant when you are in the `sys` tenant.

     ```shell
     obclient> ALTER SYSTEM SET archive_lag_target = '120s' TENANT = mysql_tenant;
     ```

     <main id="notice" type='notice'>
     <h4>Notice</h4>
     <p>When you configure the <code>archive_lag_target</code> parameter, you cannot use <code>TENANT = all_user</code> to specify all user tenants in the <code>sys</code> tenant.</p>
     </main>

   * Configure the archive lag for the current tenant when you are in a user tenant.

     ```shell
     obclient> ALTER SYSTEM SET archive_lag_target = '120s';
     ```
