# OceanSeek V4.6.3

## V4.6.3

### Version overview

OceanSeek V4.6.3 is a feature-enhanced version for AI search and lakehouse data management. This version upgrades core capabilities in three main areas: vector and full-text search, storage engine, and lakehouse integration. It focuses on improving the performance, recall, and observability of vector and full-text search, enhancing access to hot and cold data, data branching, and Catalog synchronization capabilities, and improving the runtime isolation of Java/Python UDFs and the stability of CDC data synchronization. The specific enhancements are as follows:

* AI engine: Optimized the search performance of asynchronous search indexes and asynchronous full-text indexes to cover continuous incremental write scenarios; HNSW series and IVF series indexes now support L1 (Manhattan distance), enriching the selection of vector distance algorithms; added a single-vector search profile, which allows viewing execution details during filtering, index search, and incremental data processing stages, aiding in query time troubleshooting; supports online modification of HNSW series index parameters. Parameter changes take effect after rebuilding the backend partition, eliminating the need to delete and recreate the index first. In logical table scenarios, further improved the query performance stability, availability, and read/write consistency of IVF indexes after primary/standby switchover.
* Storage engine: Supports pruning the query range by partition hot/cold status using the `PARTITION TIER` clause to reduce unnecessary data access. FORK TABLE/FORK DATABASE is extended to columnstore tables and optimizes fork performance for databases containing a large number of tables. Testing shows that a database with 1,000 tables can complete a single fork within 10 seconds, significantly shortening the preparation time for evaluation and test datasets. Also improved the stability of CDC.
* Computing engine: Catalog synchronization now supports more DDL operations, partitioned tables, and manual synchronization, making the lakehouse integrated data management pipeline smoother; Java/Python UDFs support running in independent child processes, reducing the impact of external language exceptions on the OBServer main process.

### Key features

#### AI engine

* Enhanced performance and stability of asynchronous indexes (Experimental feature)

    Optimized the search performance of asynchronous search indexes and asynchronous full-text indexes, covering scenarios with continuous incremental data writes. Key optimizations include single-token full-text search, search with multiple tokens requiring only a small number of top-ranked results (low TopK), phrase matching (`match_phrase`), and range filtering on fields with many distinct values (high NDV Range). This reduces the overhead of repeated scans and candidate result processing, while improving the stability of incremental writes, major compactions, and fault recovery. Asynchronous indexes still use eventual consistency, making them suitable for businesses that can accept brief data visibility delays. For details, see [Search indexes](../400.ai-search/300.vector-search/210.search-index.md) and [Full-text search](../400.ai-search/500.full-text-search.md).

* Full direct load is supported for tables with search indexes or full-text indexes

    When writing data to indexed tables in batches, you can improve import efficiency through full direct load. Heap tables with synchronous or asynchronous search indexes support full direct load via `INSERT INTO ... SELECT` or `LOAD DATA`, but do not support incremental direct load. Tables with full-text indexes support full direct load via `INSERT INTO ... SELECT` only in `FULL` mode. For specific limitations, see [Search indexes](../400.ai-search/300.vector-search/210.search-index.md) and [Full-text search](../400.ai-search/500.full-text-search.md).

* View the profile of a single vector search

    When a vector search SQL statement takes a long time or experiences occasional significant latency, you can use the `MONITOR` hint to collect execution information. Then, use `DBMS_XPROFILE.DISPLAY_PROFILE()` to view the time consumption and execution details of each internal stage of the vector search in a hierarchical manner, including scalar filtering, vector index search, and incremental data processing, to help identify the main cost. This capability covers all dense and sparse vector indexes currently supported. A single profile reflects only one execution of a specified query and does not provide summary metrics such as average time or P95 over multiple executions, nor historical trends. For details, see [Index monitoring and maintenance](../400.ai-search/300.vector-search/200.vector-index/600.vector-index-monitor-and-maintain.md).

* Online modification of HNSW series index parameters is supported

    You can use `DBMS_VECTOR.ALTER_INDEX_PARAMS` to adjust the build parameters and query parameters of HNSW series indexes online, to adapt to changes in data scale, recall rate, query latency, or resource usage requirements, without first dropping and recreating the index. When build parameters change, the system asynchronously rebuilds the index by partition in the background. Completion of the call does not mean all data segments have applied the new parameters; modifying only query parameters does not trigger a rebuild. You can view the actual index parameters used by each data segment in the `SEGMENT_PARAMS` column of the HNSW Segment Information view. For details, see [ALTER_INDEX_PARAMS](../700.reference/600.pl-reference/1000.pl-system-package-mysql/17850.dbms-vector-mysql/900.alter-index-params-mysql.md).

* Enhanced IVF index capability in logical table scenarios

    In scenarios where multiple logical tables share a physical table, optimized the vector search for filtered IVF series indexes, enabling the query optimizer to more accurately select execution paths based on the data distribution of the current logical table partition, reducing query performance fluctuations. After a primary/standby switchover, the system asynchronously restores the IVF cluster center cache (excluding IVF_PQ), reducing the impact of cache restoration on frontend queries. Simultaneously, improved the incremental write processing for IVF indexes (excluding IVF_PQ), enhancing read/write consistency.

* L1 distance is supported for HNSW and IVF series indexes

    Supports using L1 (Manhattan distance) for vector index search. L1 distance is the sum of the absolute differences in each dimension between two vectors, and can be used as an option besides L2, inner product, and cosine distances based on business needs. Specify `distance=l1` when creating the index, and use `l1_distance()` during search. Only supports FP32 general dense vectors in HNSW and IVF series indexes; quantized indexes or sparse vectors are not supported. For details, see [Vector functions](../400.ai-search/300.vector-search/250.vector-function.md).

#### Storage engine

* Query data by partition hot/cold status

    When the same table stores both hot and cold data, you can use the `SELECT ... PARTITION TIER` clause to specify `HOT`, `COLD`, `NOT_COLD`, or `NOT_HOT` to query only partitions that meet the hot/cold status criteria. For example, online business operations can query only hot data, while archiving and analysis can query only cold data, to control the query scope and reduce unnecessary data access and resource overhead. If this clause is not specified, the query scope is not limited by hot/cold status. For details, see [PARTITION TIER](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/8100.select-of-mysql-mode/600.partition-tier.md).

* Support for `ROWID`

    For tables lacking a suitable primary key, you can first query `ROWID`, then locate the data to be updated or deleted using this row identifier, without modifying the table structure. Supports querying `ROWID`, using table aliases to qualify `ROWID`, and locating rows by `ROWID` in `UPDATE` and `DELETE` operations on a single-target table. `ROWID` is used for row location from query to update or delete and should not be used as a long-term business identifier. For details, see [ROWID pseudo-column](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/50.rowid-pseudo-column.md).

* Reduced metadata memory overhead in large-scale table scenarios

    Optimized the caching method for table structure metadata, loading user table metadata on demand and allowing infrequently accessed table metadata to be evicted from the cache, reducing memory overhead in large-scale table scenarios. Suitable for scenarios with a large number of tables where actual access is concentrated on a subset.

* FORK TABLE/FORK DATABASE supports columnar storage tables

    Data fork capability has been extended to columnar storage tables. Both row-based and columnar storage tables can create derived replicas via FORK TABLE / FORK DATABASE for data evaluation, testing, and analysis. Also optimized the performance of FORK DATABASE when containing a large number of tables, shortening the preparation time for database replicas. For details, see [Overview of Fork](../380.data-branching/100.data-branching-overview.md).

* Support for executing major compactions within a maintenance window

    Supports configuring a maintenance window for tenant-level major compactions, facilitating scheduling major compactions during off-peak business hours and reducing resource contention. No new major compaction tasks are scheduled after the window ends, but ongoing tasks continue to complete. Major compactions not completed in the current round will continue with the original target in subsequent windows, and data that has already reached the target will not be processed repeatedly. Supports both automatic and manual triggering.

#### Computing engine

* Enhanced catalog synchronization capability

    Enhanced Catalog Sync to support synchronizing metadata such as databases and tables from OceanSeek to Hive Metastore (HMS). This facilitates unified metadata management via Unified Catalog by Lakebase, and enables external computing engines to discover and access data within the database. This version supports more DDL operations and partitioned tables, and introduces manual synchronization capability to meet on-demand metadata synchronization requirements. For details, see [Automatic catalog data synchronization](../300.data-pipeline/300.data-sharing/100.auto-synchronize-catalog-data.md) and [Manual catalog data synchronization](../300.data-pipeline/300.data-sharing/200.manual-synchronize-catalog-data.md).

* Support for running Java/Python UDFs in independent child processes

    Supports executing Java or Python UDFs in independent child processes (sandboxes), isolating them from the main OBServer process. This reduces the impact of external language runtime exceptions on database services. Added the `[G]V$OB_SANDBOX_PROCESS` view to view child process status and resource usage.

    The Java UDF sandbox is disabled by default. It must be enabled under the system tenant using the cluster-level parameter `ob_enable_java_udf_sandbox` and used with the corresponding version of the Java SDK. For configuration instructions, see [ob_enable_java_udf_sandbox](../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/300.cluster-level-configuration-items/16655.ob_enable_java_udf_sandbox.md).

* External tables support skipping the UTF-8 file header BOM

    Some tools generate UTF-8 files with a Byte Order Mark (BOM) at the file header. When reading from an external table, the BOM might be interpreted as content for the first column, causing data anomalies. This version supports explicitly setting `byteordermark=check` in the `FORMAT` clause for CSV/text external tables. This detects and skips the BOM in the file header, improving compatibility with such files. If this attribute is not specified or set to `nocheck`, the BOM is not detected.

#### CDC

* Enhanced data synchronization performance and stability

    Optimized the processing efficiency of incremental data extraction and synchronization, reducing synchronization latency in scenarios with high-concurrency writes, cross-IDC extraction, and large transactions. Simultaneously reduced memory usage and CPU overhead of the CDC process, minimized latency fluctuations, and improved the stability of standalone and centralized CDC links.

* Support for filtering change logs generated by TTL deletion

    OBKV supports configuring whether to filter change logs generated by TTL deletion via `filter_ttl_delete_log`, reducing the I/O pressure on LogService from such log synchronization. This feature is disabled by default. Once enabled, TTL-deletion changes are no longer output downstream via CDC, and the corresponding data downstream will not be automatically deleted through this link either, but this does not affect the normal execution of TTL tasks within the database. This feature requires use with liboblog V4.6.3 or later. For details, see [OBKV-Table TTL](../700.reference/960.obkv/100.obkv-table/700.obkv-table-reference/290.obkv-table-ttl.md).
